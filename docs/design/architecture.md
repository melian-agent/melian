# Architecture

### Three layers

```
┌─────────────────────────────────────────────────────────┐
│ Hosts: cli │ skills (claude-code, codex, pi) │ server │ actions │ slack (later)
├─────────────────────────────────────────────────────────┤
│ Pipeline: review orchestration as Pi Durable tasks and conversations
├─────────────────────────────────────────────────────────┤
│ Core: findings, lenses, checks, config, standards, knowledge, decisions, git, provider port
└─────────────────────────────────────────────────────────┘
```

**Core** is harness-free TypeScript. It imports pi-ai types and nothing else from Pi. It holds the finding schema and stable IDs, finding identity and the lifecycle rules, guardrail evaluation, SARIF normalisation of static tool output, lens loading, configuration layering, the standards loader, the git client, and the provider port. The GitHub client lives in `packages/github`, behind that port. The `Decider` port, built in milestone 2, sits beside the provider port, with its adapters in `packages/decisions` as the GitHub client is in `packages/github`, and the knowledge loader arrives in milestone 4. Dismissal, the first command that acts on findings across revisions, was built in milestone 2. All of it is unit-testable without a harness.

**Pipeline** is the only place review flow lives. It is written once against Pi Durable: tasks, child conversations, documents, memos, hooks. It also holds the static tool runners, because running a tool executes repository code and so goes through Pi Durable's `ExecutionEnv`, which core may not import. Every host embeds this layer; none reimplements it.

**Hosts** adapt triggers, storage, credentials, execution environment, and time budget. The CLI is the primary host. The skills for Claude Code, Codex, and Pi invoke the CLI and relay its output; they never run a review with the host agent's own model. The server host receives webhooks and runs a long-lived harness. The Actions host is ephemeral and self-rescheduling.

Why the split: Pi has two extension systems. The coding agent uses `ExtensionAPI` (`pi.on()`, `pi.registerTool()`). Pi Durable uses `defineExtension()`, `defineTask()`, `hook()`. They do not interoperate. Writing orchestration against Pi Durable and keeping the local Pi extension thin avoids maintaining the review flow twice.

### Mapping onto Pi Durable

| Melian | Pi Durable |
|---|---|
| A changeset's review history | One storage per changeset, whose root conversation is that changeset's history. Pi mints conversation IDs, so Melian keeps the map from changeset to storage |
| A new revision, a comment, a command | A `submit()` into that conversation; comments while busy use `whenBusy: "steer"` |
| A pipeline step | A `defineTask()` with phases and checkpoints. A root document indexes the lens task of each revision, base and head, and lens selection, and the adjudication task of each revision and input, so a repeat call for that revision attaches to the task rather than starting another |
| A lens | A child conversation created and owned by the lens task, configured with `configure()` with its own model, instructions, and an explicit tool list, because an owned conversation otherwise inherits its owner's tools. Never a subagent tool the model chooses to call |
| Findings | A `defineDoc()` document, rewindable, committed atomically with the transcript, and owned by the changeset's root conversation so a fork of the root at any revision carries them. It holds immutable sightings keyed by revision, lens, version, and level, and finding ID, plus one lifecycle record per ID; reading a head merges its sightings. A lens's tool writes to the root through the ID it is constructed with, never to its own child conversation |
| Triage decisions, knowledge proposals | `defineDoc()` documents, rewindable, committed atomically with the transcript |
| The review plan | A `defineDoc()` document written at intake and keyed by revision, so a resumed review keeps the routes it started with |
| Verification | A verification task per revision that owns one child conversation per candidate for the LLM executor. Each verdict upserts into the findings document beside the sighting it judges, keyed by that sighting's revision, lens and version, and finding ID, plus the verifier's version |
| Standards and lens bodies | `section()` prompt sections rebuilt from files before every request, so edits take effect immediately and the transcript records what the model saw |
| Idempotent publication | A durable `published` document keyed by revision and finding ID, written in the same commit that records the post, plus a check for Melian's signed marker on the pull request before posting. The signing secret is a root document of the changeset's storage, disposed with it. Not `api.memo()`: memos are task-scoped and discarded when the task ends |
| The walkthrough | A summarise task per pull-request revision that owns one child conversation with one recording tool. Its output is stored with the verdict, keyed by revision, and publish renders it |
| The ledger | Its comment ID in a changeset-level document, a root document of the changeset's storage, not the per-revision `published` document, because one comment spans every revision. A replay edits the comment rather than posting another |
| Webhook delivery deduplication | `requestId` on submission, exactly-once. A `requestId` is scoped to one conversation, so the changeset's storage and conversation are resolved before deduplication |
| Tool restriction and command guardrails | `hook(ToolTask)` with `beforeTool` |
| Storage | The `Storage` interface: one atomic `commit(writes)`, ID minting, a set of reads, and `close()`, with no cross-process locking. The state-branch backend wraps Pi's JSONL storage and relies on one writer per changeset |
| Where tools run | The `ExecutionEnv` interface: a `FileSystem` plus a `Shell` |

Pi Durable is pinned to an exact version and imported by one internal module, because its API is declared experimental. That module re-exports Pi's API, so it quarantines import paths, not churn: a changed signature upstream still reaches its callers. A narrow Melian-owned facade grows in front of it as the pipeline gains callers, and Pi's types stay inside the pipeline package.

### Stage telemetry

Milestone 2, step 31. A 240-line round took 64 minutes, with no way to split mutation, lens and verifier time. [The token telemetry decision](../decisions/2026-10-18-token-telemetry-incomplete-requests.md), milestone 2 step 32, retains the timing authority and extends usage to every model call whose response becomes durable.

Read lens, verifier-candidate and walkthrough timings from durable transcripts. An assistant answer ends at its request timestamp plus response duration; an absent duration falls back to the timestamp with a note. Deterministic triage, each check, adjudication and publication memoise their first start and copy it with an end into a separate document-family member for that task in their terminal commit. Pi Durable 1.1.0 supplies a faulted task's end. No shared timing document or timing counters are stored. Pi retires literal task-scoped documents at settlement, so these per-task records use conversation families keyed by task ID. A check-source map preserves the producing task across reruns. Publication selects by revision, including after dismissal.

Adjudication task version 3 preserves inputs from versions 1 and 2 and marks their checkpoints as predating stage timing. Version 2 added changed files for hunk merging. Version 1 has no files and keeps snippet merging. Both upgrade paths report timing unavailable.

Replay preserves the first timestamps. Settled model runs retain their transcript end across a crash. Older deterministic tasks with no start say timing unavailable. Quick and escalated runs remain separate. Spend comes from Pi's durable usage records, per model and token kind, with optional reasoning and one-hour cache counters. Conversation ledgers include failover, retries and compaction. The LLM triage adapter forwards each returned assistant's usage through the core ports, before validation. Its task commits usage with the decision or failure in a separate task-keyed document-family member. Before each triage provider request, it durably increments a task-keyed attempt count. The result commit stores started minus the number of measured responses as unmeasured. Any lost receipt marks the stage and run total `usage incomplete: N request(s) not measured`, with usageIncomplete in JSON. That counter extension changed no existing document version. Reasoning capture below raises the model-usage family to version 3. Run totals sum selected stages once, including reused work; absent usage remains unavailable and partial totals name the missing stages. Nothing estimates provider requests lost before durable settlement. Pi Durable 1.1.0 exposes no durable resend count through GenerationTask, CompactionTask or UsageDoc. Lens, verifier and walkthrough totals cover settled responses; undetectable pre-settlement losses remain a documented limit. Telemetry changes no verdict, task attachment key or publication fingerprint. Timing storage grows with stages. Usage receipts grow with returned requests.

`melian review --json` adds telemetry beside the verdict fields. One standard-error line names the three slowest ended stages, marking reused work and including timeouts, followed by total tokens and cost. JSON carries the same per-model total and missing-usage stage IDs. Live lens, verifier and triage evals read the same record before closing storage, and print each golden's spend beside its score. A failed triage measurement prints every attempted pass’s spend and saves available records to the requested output file before propagating the failure. Its version-2 measurement JSON marks completion explicitly; comparison refuses an incomplete baseline. Older measurement files remain readable as complete. [The incomplete-baseline decision](../decisions/2026-10-18-triage-incomplete-baselines.md) records the contract. `melian telemetry <range|#pr> [--json]` reads storage through the detached API used by comparison exports. It opens no harness or scheduler, writes nothing and asks no model. Terminal text escapes control characters. Parallel intervals are never added as elapsed review time.

[Reasoning capture](../decisions/2026-10-18-reasoning-telemetry.md) records each returned request's requested level, sent reasoning settings from pi-ai's payload callback, and any provider-reported level. The host-supplied model port observes generation, compaction and failover; triage forwards capture through its usage observer. Model-usage document version 3 keeps these receipts beside usage and permits an unrecognised capture status. Versions 1 and 2 migrate unchanged. Pi's ledger still supplies conversation totals. Text, review JSON, detached telemetry and live golden spend show the settings. Omitted settings say provider default; an unavailable callback is labelled derived, not observed. A reasoning-shaped field outside the captured paths marks the request unrecognised, even beside known settings. Unknown names and values are not retained. Message, tool and schema contents remain opaque data. [The unknown-field contract](../decisions/2026-10-18-unrecognised-reasoning-capture.md) defines the status. Bedrock adaptive requests retain both thinking and the nested output_config effort. Offline tests build one non-off request through every installed chat adapter with a reasoning-capable catalogue model. Bedrock stops at its payload callback because its AWS SDK ignores fetch; the other adapters reach a fetch that returns no response. This chooses no reasoning level. For managed-effort Anthropic models, such as Sonnet and Opus 5.5, pi-ai sends `output_config.effort: high` in the opening body and sets the requested level in a mid-conversation system message. The provider-reported level is the authority there; an observed opening effort of high is not the level used. Receipts commit before Pi settles the response, so a crash can retain a capture whose usage Pi has not yet included in its totals.

[Review spans](../decisions/2026-10-24-review-spans.md) time the work between tasks. The host opens a recorder at its process's start, from `performance.timeOrigin`; the CLI's steps (startup, resolution, lens, standards and configuration loading, secrets, models, triage set-up, storage, resumption, the caller query) and `reviewChangeset`'s own (standards trust, replaced-run aborts, bands, routes, lens preparation, caller coverage, verification and adjudication preparation, reading the verdict) join it. One step is open at a time and ends before each task wait. Nested work, such as credential unlocks, design baselines, enclosing functions and the Enola graph and query, records its open step as parent. The host stores one `melian.prepare` family member per revision in the root conversation just before the verdict prints; the next review of the revision replaces it. Text and JSON list the spans in time order after the stages and name each gap over a second that no span or stage covers as `untimed`. Model stages also report `modelMs`, the summed response durations of their answers. Spans inside `static.enola`'s own task are deferred.

pi-telemetry is deferred until Pi Durable passes a telemetry context. Callback-scoped spans cannot represent a stage that survives the process; Pi currently emits none.
