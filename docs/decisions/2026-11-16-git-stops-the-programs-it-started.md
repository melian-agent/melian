# Core's git stops the programs git started

Amends: [The git record store refuses a stray file by where it sits](2026-11-14-git-record-store-refuses-by-location.md), the row "Child processes"
Amends: [The git record store refuses a stray file by where it sits](2026-11-14-git-record-store-refuses-by-location.md), the row "Time"

Status: for [issue #480](https://github.com/melian-agent/melian/issues/480), whose brief asks for the stop by recorded pid and its tests. The coordinator answered on 2026-11-16, in a message to the builder, that the code choosing which pids to signal moves into core unchanged, with pipeline re-exporting it, and set four conditions: the move is a move, the table is read before any signal, an unreadable table stops git alone and says so, and each exclusion has a test on a fake `kill`. That is a choice of approach, not a ruling.

## Problem

Core's `git` stopped git alone, at a call's deadline or when git flooded standard error. Git starts other programs to reach a remote: a remote helper, ssh, a credential helper. When git was stopped, such a program kept running. Example: `melian doctor` fetches `melian/state` over ssh, the key needs a passphrase, and ssh waits at its prompt. The deadline passes, git is stopped, and ssh is still waiting after doctor has exited.

A process group would end the whole tree in one call, and AGENTS.md forbids it: a group of 1 is `kill(-1)`, which ends every process the user owns.

## Choice

When core's `git` stops git, it reads the process table once, while git still runs, and records git and every process below it, each with its start time. Then it stops each recorded process by its pid, SIGTERM and then SIGKILL a second later, through `terminateRecorded`, which reads the table again before each signal and leaves alone a pid whose start time has changed. It also stops git through its own handle. It never signals this process or any of its ancestors, and never a root or a pid of 0, 1 or below. The read comes first because a process whose parent has ended is re-parented, and no longer reads as below git.

The table is read at the stop, not on a timer. A transport still waiting at the deadline is still below git when the deadline fires. A scan on a timer would also record a helper that detaches on purpose, such as git's credential-cache daemon, and kill it. A program that left git's tree before the stop is therefore not stopped. Nor is one that git starts while the stop reads the table, and the call does not report it: the window is one `ps` read, about 20 ms, at the moment of the stop, from when `ps` takes its snapshot until git gets its SIGTERM. The reads before each signal check only the pids already recorded, so they cannot add a newcomer, and once git is killed the newcomer is re-parented and reads as below nothing. Such a program keeps running after the call returns, as it did before this decision. The maintainer ruled on 2026-11-16, in the coordinator's session, that the stop keeps this window, as [the pull request records](https://github.com/melian-agent/melian/pull/498#issuecomment-6907010396); a mechanism that freezes git's tree before the read would be an issue of its own.

The same stop runs when git writes more standard error than `stderrLimit`, and when its standard output reaches a call's `maxBytes`, since all three are Melian stopping git before it ends. A cut result waits for the stop, as a timed-out one does, and carries `childrenLeft` when the stop could not find or end the tree.

When the table cannot be read, with no `ps` or under a sandbox that refuses it, `git` stops git alone, as before. A timed-out result then carries `childrenLeft`, and the `gitOutputTooLarge` error ends by saying the programs git started were not stopped. No pid is guessed. The same holds when a later read fails, after the first one recorded the tree: the stop then signals nothing more, so the deadline's result and the overflow error wait for the stop, about a second and never past its budget, below, and report it. The same holds when the table no longer shows git, or shows it as a zombie: git has exited, so any program it started has been re-parented and no longer reads as below it. A git that exits while a program it started holds its output open reaches its deadline this way, and `stopTree` then signals nothing and says so. The record store does not yet repeat this in its own `unreachable` message.

A stop reads the table only while git has not been reaped. Node reaps git and sets `child.exitCode` or `child.signalCode` in one callback, before any other code runs, so until then git's pid is git's, live or a zombie, and no other process can hold it. After it, the pid can pass to another process, and a stop that read it as git's would signal that process and everything below it. So `git` checks the two fields at the moment of the stop, and calls `stopTree` in the same turn; `stopTree` reads the table and records the tree before it awaits anything. Once git has exited, nothing below it is signalled, even if the table still lists processes under its old pid, and the result and the overflow error say the programs git started may still run. The cost: a program git started that still holds git's output after git exits is no longer stopped, and the call says so. Such a program was already re-parented and could not be found below git, so nothing that worked before is lost. Codex's review found the reuse on 2026-11-16, the third instance of a stop acting on git's pid without knowing git was still there, and the coordinator chose this rule that day, as a choice of approach, not a ruling.

A stop closes this end of both of git's output pipes, not standard error alone. A program the stop could not find, such as one re-parented after git exited, can hold either pipe, and an open pipe keeps this process alive after the call has settled with `childrenLeft`, so the CLI could not exit. Nothing reads output after a stop: the result is cut, timed out or rejected.

The table is read synchronously, so the check, the read and the record stay in one turn, and a `ps` that stalled would stall the event loop, and the call's deadline with it. `ProcessTable` gives `ps` five seconds, and ends a `ps` past them through Node's own handle with SIGKILL, since a stalled `ps` may ignore SIGTERM. That signals only the `ps` the same call started, never a pid read from the table. A read that runs out is a failed read: the stop signals nothing below git and says the programs git started may still run. The path and the limit are constructor arguments with defaults, and only tests pass them; no configuration, environment variable or head reaches them. One limit remains: a `ps` in an uninterruptible wait ignores SIGKILL too, and would still block the event loop until it returns. main's read was as synchronous, with no limit at all. Codex's review found both gaps on 2026-11-16, and the coordinator chose these fixes that day, as a choice of approach, not a ruling.

A stop has one budget: ten seconds, on a monotonic clock, from when it begins. `terminateRecorded` reads the table again before each signal and while it waits out its second of grace, about 2N+23 reads for N recorded processes that outlast SIGTERM, and each read may take its whole five seconds. With no budget, one stop over a slow table could take minutes, and the call would wait for all of it. So `git` hands `stopTree` its table wrapped so that every read past the budget throws, and a throwing read already ends the stop and reports `childrenLeft`. A call therefore settles at most the budget plus one read limit, about fifteen seconds, after its deadline or output bound. The budget was three seconds at first, and CI's macOS runner showed that too tight: a normal stop of git and its transport took 2.5 to 3.8 seconds there, since each read of its table is slow and a stop reads it again before every signal and while it waits, so a three-second budget gave up part way through SIGTERM and left the transport running. Ten seconds leaves about three times the slowest stop measured. The coordinator chose it on 2026-11-16, as a choice of approach, not a ruling. A stop has a cost even when nothing outlives git: a local command cut at `maxBytes`, such as `cat-file`, pays for the stop's reads of the table and its first wait. The review of record measured 33.5 to 34.9 ms for such a call in a cloud container, against 3.4 to 3.7 ms on `main`, and each read blocks the event loop while it runs. Git gives no sign of which commands started a program, so every stopped call reads the table.

The budget is checked when a read starts. Matching the records against a read runs synchronously, for each record against every row, and again for each record as the stop signals, so a tree far larger than any git starts could hold the stop past its budget. A stop also counts a process as ended once it has sent SIGKILL: a process in an uninterruptible wait ignores that signal, survives the stop, and the result carries no `childrenLeft`. [Issue #507](https://github.com/melian-agent/melian/issues/507) is to read the table after SIGKILL, here and in the mutation supervisor. Both stand by [the maintainer's ruling of 2026-11-16](https://github.com/melian-agent/melian/pull/498#issuecomment-6910822936), given in the coordinator's session.

So a call's deadline bounds when its last git command starts, not when the call returns. A stopped git can settle up to about fifteen seconds after the deadline: the budget plus one read limit. A state-git write gives its push three quarters of the time it has left, and keeps the rest to check whether a stopped push landed. A slow stop near the deadline can use that rest, and the write then throws that its push may have landed and should be repeated, even when it did land. This amends the record store's Time row, by the same ruling. The cost is a named limit: once the budget runs out, a process already sent SIGTERM may get no SIGKILL, and the result says the programs git started may still run. `terminateRecorded`, and every other line the mutation supervisor shares, stay as they were. This closes one class, a stop whose time nothing bounded, which two of Codex's reviews found in turn on 2026-11-16: the unbounded read of a `ps` that stalls, and the repeated reads of one that is slow. The coordinator chose the budget that day, as a choice of approach, not a ruling.

A recorded process that `ps` shows as a zombie is neither signalled nor waited for. A zombie has exited, and it keeps its pid until it is reaped, so no other process can hold that pid meanwhile. A cloud container's pid 1 can leave an orphan unreaped for good, and each such zombie cost the stop its whole second of grace, which the deadline's result now waits for. Only a state `ps` reports as a zombie counts, and a row with no state counts as live, as before. `ProcessTable` and the mutation supervisor's own read both ask `ps` for `stat=` after `lstart=`, so the state is the word after the start's five fields, and an unknown state cannot shift the start. Those five fields are an assumption about `ps`: ctime's form, which the C locale promises. In a locale whose date has another number of words, every row would misread, and the stop would signal nothing and say nothing. So both reads run `ps` with `LC_ALL=C` in its own environment, never this process's, and the forced locale is what holds the assumption. `ps` also prints a start in the caller's time zone: one pid read `Mon Nov 16 01:27:48 2026` in UTC, `Sun Nov 15 20:27:48 2026` in New York and `Mon Nov 16 12:27:48 2026` in Sydney. Within one stopped git call the zone is constant, but the mutation check compares a start that one process recorded with a read made by another. So both reads also pass `TZ=UTC`. A record stored before this change by a process in another zone now reads as a different process and is not signalled, which fails toward leaving a process running, never toward signalling the wrong one. The supervisor's check that its controller is alive still counts a zombie controller as alive: it decides when a mutation run's tree ends, not which pids are signalled, so changing it is a change to the mutation check's lifecycle and is left out. The coordinator chose this on 2026-11-16, as a choice of approach, not a ruling; it closes [issue #333](https://github.com/melian-agent/melian/issues/333).

`ps` gives a start time to the second, so a recorded process can exit within its start's second and leave its pid to another that a later read cannot tell apart from it. `ProcessTable` therefore also asks `ps` for each process's command, `comm=`, after the state, and `stopTree` records it. `terminateRecorded` then signals a recorded pid only while its command matches too. A record with no command, as the mutation supervisor's and the probe's are, matches by its start alone, as before. This narrows the window to another copy of the same program started in the same second; it does not close it. [Issue #352](https://github.com/melian-agent/melian/issues/352) stays the place for a finer identity. The check has one cost: a process that runs `exec` between the read and its signal has a new command, and is left running. Git's transports run `exec` as they start, long before any stop reads the table. The parent is not compared as well: a process whose parent ends is re-parented, so a live child would stop matching. The maintainer agreed to this on 2026-11-16, in the coordinator's session, as [issue #480's record](https://github.com/melian-agent/melian/issues/480#issuecomment-6905491530) says.

`ProcessTable`, `terminateRecorded`, `parseProcesses` and their types moved from `packages/pipeline/src/mutation-process.ts` to `packages/core/src/process-tree.ts`, unchanged, so one copy of the code chooses which pids every part of Melian signals. The new file is in the mutation check's signal set.
