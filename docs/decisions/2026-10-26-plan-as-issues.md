# The plan's work lives in GitHub issues

Choice: Each open step of a milestone, or each build part of a step, is a GitHub issue in that milestone, labelled `plan step`. The issue body is the builder's brief: the goal, the decisions to read, the scope, what done means, and the agent rules. GitHub's own relationships record the order: an issue is "blocked by" each issue it needs, and an agent never starts one with an open blocker. A writer marks an issue `status: ready` when an agent may take it. An agent claims an issue as its first action: it adds `status: in progress` and comments with its name, where it runs (local, cloud VM or Codex) and its branch. If another claim landed first, it stops. The draft pull request says `Closes #N`, so the merge closes the issue. A builder works in a checkout of its own, which may be on another machine or a cloud VM, so a brief names nothing outside the repository and GitHub. There is no dispatcher. `docs/design-implementation-plan.md` keeps each step's design and reasons; the milestone's issues hold its status.

Why: The coordinator wrote every brief into a scratch file, so a brief was invisible to every agent but the one handed it, and it was gone when the session ended. Agents running in cloud VMs can't read the coordinator's scratch directory at all. An issue is readable by every agent wherever it runs, survives the session, and carries its dependencies in a form GitHub enforces. A dispatcher would be one more process that has to reach every machine. A claim label is enough: two agents rarely claim one issue in the same minute, and the second one sees the first claim and stops. Only a writer's `status: ready` makes an issue workable, because anyone can open or edit an issue, and agents act only on writers' instructions.
