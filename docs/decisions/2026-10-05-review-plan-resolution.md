# Review plan resolution

Choice: A route's `accept`, `unavailable`, and `acceptOverridden` come only from the root `melian.yaml`. A preference file that sets one is a configuration error naming the key, and so is a nested `melian.yaml`, until the plan resolves routes per path. A route with `acceptOverridden: false` must name a model or an `accept`. Without `accept`, a committed route accepts its own model and fallbacks.

The resolver substitutes and derives only for a committed route. When none of its models has credentials, the first accepted model with credentials stands in. Failing that, `unavailable: fail` fails the tier. Otherwise `derive` takes the same model from another provider with credentials, matched by catalogue name. The match removes any provider prefix and parenthesised qualifier, and prefers a name without a qualifier. Failing that, it takes the model with credentials whose price, input plus output per million tokens, is nearest on a log scale. The candidate must match the wanted model in reasoning, and have a context window at least the wanted model's or 200,000 tokens. Ties go to the larger window, then by provider and ID. A route from a preference file or `--model` is never replaced.

A check that `unavailable: fail` or `acceptOverridden: false` refuses never runs: it records `failed` with the reason. A refused route drops every fallback outside `accept`. A lens a preference file moves to another tier stays under its committed tier's policy, and records `failed` if it finishes on a model that policy refuses.

A check records lineage on the model its lens finished on. It records it when a preference file, `--model`, or a derivation moved its tier off a committed route's model, inside `accept` or outside it, and whenever the model is outside `accept`. It records none where no committed route names the tier. A lens task is reused only for the same routes, so the lineage always names the route that ran. The plan's JSON is stored in the verdict's provenance, and `melian findings` reads it from there.

Secrets files hold `api_key` credentials only. A `melian.secrets.yaml` git tracks under any case of its name is refused. A command source runs only from the user-level secrets file, and only when the user owns it, its mode is 600, and no one else can write its directory unless it is sticky. `melian.secrets.yaml` holds literal and environment sources only, and is never read through a symlink. The user-level files live in `$XDG_CONFIG_HOME/melian/`, else `~/.config/melian/`.

Why: The [review plan decision](2026-10-04-review-plan-and-routes.md) set the keys and the outcomes but not the order of the lookup. A preference file that could set `acceptOverridden` would let the override it carries wave itself through. So would one that moved a lens to an unguarded tier, which is why a moved lens keeps its committed tier's policy. A nested route policy the plan never reads would fail open, so it is refused until the plan plans per path. A maintainer who names a model in their own file, or on the command line, has said what they want. Swapping it behind their back would spend their money on a model they did not choose, so a missing credential there fails as it always has. Deriving the same model from another provider first is the case the plan exists for, a contributor holding only Bedrock credentials. Price stands in for capability until calibration scores arrive in milestone 4. Running a check whose result cannot count spends tokens for nothing, so a refused check fails before it asks a model. A lineage drawn from the plan rather than the run would misstate which model reviewed the change, after a failover or a reused task. pi-ai's catalogue names no model family, so the verifier's cross-family route reads one from the name in step 6. No check on a file in the working tree holds under every umask: a patch applied under umask 077 lands as the user's own file, mode 600, already ignored. So a command, which runs on the reviewer's machine, lives only outside every repository.
