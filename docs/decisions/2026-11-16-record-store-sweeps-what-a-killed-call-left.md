# The record store sweeps what a killed call left, once its maker is gone

Amends: [The git record store refuses a stray file by where it sits](2026-11-14-git-record-store-refuses-by-location.md), the row "The same, left by a process killed mid-call, and a fetch ref left by a call whose deadline ran out before it could delete the ref"

Status: for [issue #460](https://github.com/melian-agent/melian/issues/460). The maintainer accepted on 2026-11-15, in the coordinator's session, that these leftovers wait for this issue. The method below is the coordinator's choice of approach, given on 2026-11-16 in messages to the builder, with the conditions it set; it is not a ruling. Its first form compared start times, and the coordinator replaced it the same day with the pid alone, after Codex's review showed a start time that reads differently under another time zone. The host's hash in each name is the builder's addition, which the coordinator agreed to on 2026-11-16, asking that its limit be stated here.

## Problem

A call on the git record store makes three things and removes them before it returns: a temporary index inside `records.git`, a half-made repository beside it while the store is first created, and a fetch ref under `refs/melian/fetch/`. A process killed mid-call removes none of them, and neither does a call whose deadline runs out between its fetch and the ref's deletion. Example: `melian doctor` is killed during its fetch. The fetch ref it made pins every object it fetched, and nothing ever deletes it, so each such kill leaves one more.

Two processes can share one state directory, so a sweep that removed every leftover it found would delete the temporary index of a call still running beside it. An age proves nothing either: a caller sets its own deadline, so a call can legitimately run for longer than any cut-off.

## Choice

Each leftover's name records its owner: the first 16 hex digits of a SHA-256 of the host's name and the pid, then a UUID that keeps two names of one call apart. Opening the store sweeps the state directory. It removes a leftover only when all of these hold:

- Its name parses as an owner, and the host's hash is this host's.
- The process table, read through core's `ProcessTable`, lists no process with that pid.
- It is the kind of thing the store makes under that name: a directory for a half-made repository, a regular file for an index or its lock, and a ref directly under `refs/melian/fetch/`.

The sweep lists the leftovers before it reads the table. A call still running when the table is read is in it, and a call that started after the listing made nothing the listing holds.

The cost is a reused pid. A leftover whose pid now belongs to another process stays, kept and named, until that process ends. That costs disk and loses nothing.

Everything else is kept: a live owner's leftover, a leftover from another host, one whose name records no owner, as an earlier build's UUID names do, one whose name does not parse, and an entry of the wrong kind, a link included. The sweep never follows a link, deletes a fetch ref that is a symbolic ref itself and never the ref it names, and removes nothing outside the state directory and `records.git`'s refs. When the table cannot be read, or does not list this process with its own parent, it sweeps nothing and names every leftover it found as kept: a table that parses to nothing would read every pid as gone. When the table does not list this process with its own parent, as a table read from another pid namespace may not, the call names what it makes by a UUID alone, which no sweep removes. A removal that fails is recorded, and the store still opens. The sweep shares the open's deadline: once none is left, it removes nothing more, counts the stale leftovers it did not reach, and the next open removes them. No failure inside the sweep fails the open. A listing that fails, of the state directory, `records.git` or the fetch refs, or a stat of a listed entry that fails for any reason but its being gone, removes nothing and reports `unlisted`, and with no time left to list the fetch refs the sweep starts no listing and reports `unlisted` too. A removal that fails is recorded under `failed`. The rule's edge is the repository itself: the open still fails when `records.git` cannot be read, is not a directory or cannot be created, when its configuration check refuses, and when it holds a shallow history, since none of those is housekeeping. The open reads the process table twice, once to name its own leftovers and once in the sweep, and each read is bounded by its own five seconds, not by the open's deadline. A stalled `ps` can take an open about ten seconds past a short deadline, and the step after the reads then fails as past it. [Issue #507](https://github.com/melian-agent/melian/issues/507) bounds both reads by the time left. `melian doctor` names every leftover the sweep kept, every one it could not remove, and a table it could not read, so a person knows what is safe to remove by hand.

## Why

A pid the table does not list names no live process on this host, so a sweep that finds it absent knows no live call owns the leftover. Keeping whatever it cannot prove gone means a mistake costs disk, never a live call's index.

A start time would tell a reused pid apart, as core's rule for signals uses it, but only when both readings come from one `ps` setting. `ps` prints the start time in the caller's time zone and locale: one process reads `02:28:53` under UTC and `13:28:53` under `Australia/Sydney`. On Linux it derives the time from the boot time, so a stepped clock moves it too. A leftover named under one setting and swept under another would read a live call as gone and delete its index. Example: a CI job that sets `TZ=UTC` runs beside a developer's shell in Sydney on one machine. The pid alone has no such failure, and its cost is the disk a reused pid holds.

The host's hash keeps a state directory shared with another host, or with a container whose processes this table cannot see, from reading that host's live call as gone, since its pid is absent here. It is a guard, not a guarantee: two hosts or two containers that report the same host name read as one, so a state directory shared between them can still have a live call's leftovers swept. Melian does not support sharing a state directory across hosts. A container's pid namespace could be told apart from what the kernel reports; [issue #460](https://github.com/melian-agent/melian/issues/460) records that for later.
