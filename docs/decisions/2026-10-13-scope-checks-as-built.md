# How step 17 runs the scope checks, and the choices it made

Problem: [the decision that lets the verifier lower a severity and set scope](2026-10-12-verifier-lowers-severity-and-sets-scope.md) leaves four choices to the step that builds it, and its text and its own example disagree on one point. Rule (d) refuses a hunk that "deletes lines inside the function that holds" the failure. The example of a re-scope that holds is a change that edits a comment inside that function, and an edit deletes a line.

Example: a lens reports a finding over a function, lines 10 to 40, because the change reworded the comment on line 20. Read to the letter, rule (d) refuses every such re-scope, and the route the decision built reaches nothing.

Choice: step 17, "The verifier lowers severity and sets scope", builds the rules as below. This refines the decision and replaces none of it.

- **A deleted comment is not a deleted guard, and added code refuses too.** A hunk refuses under rule (d) when a line it deletes or adds inside the function that holds the failure holds code. The decision names deleted lines only. An added line can break the function as surely: a statement that empties a list above the read that fails passes rules (a) to (c), and the verifier's word would then be all that stood behind the re-scope. A line holds none when it is blank or reads as a comment, no syntax node starts or ends on it, and no node without children, such as a template literal, runs across it. A line reads as a comment when it starts with `//`, or opens a block comment with `/*`, or follows such a line before its `*/`. Whatever the two tests disagree on counts as code, so a continuation line that starts with `*` still refuses.
- **The caller check matches names, and does not ask the compiler.** The failing symbol is the name of the function that holds the failing lines: a method by its own name, a constructor by its class. A hunk in any file that adds a line naming it, as a whole word, refuses. Why not the compiler: the call graph needs the whole project opened from a head worktree, under the head's own configuration, to answer a question the diff already answers more strictly. A name match refuses a comment that mentions the symbol too, which errs the right way. A default export is called by whatever name its importer chose, and a computed or quoted name by whatever it evaluates to, so Melian refuses both outright. A function or class declared `export default` with a name of its own is a default export too.
- **A name match needs the name to be the only one.** Problem: the base may already hold `const decode = parseRecord`, and a head that adds `decode(raw)` adds a caller without spelling the symbol. Solution: Melian searches the head for every line that names the symbol. Each must call it, declare it, or pass it through an import or export list on one line without `as`. Any other line refuses, since it may give the function another name. So does a search that finds more lines than it lists. The cost is reach: a comment, a type reference or a multi-line import that names the function refuses too.
- **A name is matched by the letters it spells.** `p\u0061rseRecord` is `parseRecord` to the compiler. Melian resolves unicode escapes in every hunk and on the trigger's lines before it matches, and searches the head for the name however escapes spell it. A search shows the first 300 characters of a line, so a line that long which names the function refuses: the rest may give it another name.
- **Every function on the named path is held to the guard check, and so is the support for each answer.** Problem: the guard may sit in a caller. A head can delete the validation in `run`, leave the line that calls the failing function alone, and edit only a comment in the failing function. Solution: for the trigger and each location on the path, as for the failing lines, Melian finds the function that holds it at the base and at the head, and refuses when a hunk deletes or adds code there. A named location outside every function is refused. The base lines the verifier gives for each of the four answers must also be lines the change left alone.
- **The trigger check matches names too.** Melian reads the identifiers on the trigger's lines, less the language's keywords. A hunk in any file that adds or removes a line naming one refuses. That is the cross-check for "a configuration key or a default that the named trigger reads". It refuses more than it must, since a name the trigger reads may be a local.
- **A copy is a hunk that adds the failing lines.** Melian normalises whitespace on both sides, as a finding's ID does, and refuses when any hunk's added lines contain the failing lines.
- **The failing lines must overlap the finding, in the finding's file.** The verifier gives them at the head with the line they start on at the base. Melian finds the base file through git's rename map and compares the bytes. A file the head added has no base file, so its lines cannot be read there.
- **A binary file in the change refuses.** Git gives a file it reads as binary no hunks, and a search skips it. One NUL byte in a comment would hide a new caller from every check, so a change that holds such a file, other than one it deletes, cannot be re-scoped.
- **Code outside every named function is refused**, for the failing lines, the trigger and each location on the path. So is a file the compiler does not read, and one larger than the 512 KiB the change prompt reads.
- **A refused proposal still records the verdict.** `report_verdict` refuses the lowering or the re-scope, says why in its result, and stores the verdict without it. When the fence holds and an equal report already stored keeps the claim where it was, the result says the proposal was not kept.
- **Verification picks its candidates from the findings as the lenses reported them.** Problem: a lowering can change which finding speaks for a merged defect, and the candidates name the speaker. A repeat review would then read as new input, clear the stored judgements and verify again. Solution: the read that builds candidates attaches each verification and applies none. The reasons a re-scope is refused name paths and symbols the change wrote, so the result quotes them as data.
- **A lowering carries its own reason**, beside the verdict's, because the reason a claim is true is not the reason it is narrow.
- **A member is carried when another revision first sighted it.** The findings document already records the revision that first saw each finding. The terminal and the JSON have no pull request to ask, so adjudication reads that record. The ledger renders the same state from the verdict each round stored.
- **The JSON keeps a member in its resolution group** and lists it again under `preExistingImportant`, with its state, its original severity and, when re-scoped, its original scope and the reason. A consumer that reads only the groups still sees every finding.
- **A member at advisory does not count toward the status.** The decision says a member never changes the verdict or the exit code unless a cap asks for an acknowledgement. So a review whose only findings are members reads `passed` and exits 0, with the members listed. This changes what a pre-existing P0 or P1 did before step 17: it made the review read `findings`. An ordinary pre-existing finding, a P2 or lower that no verifier re-scoped, still counts as it did.
- **The base line of the failing lines is Melian's to say.** The verifier gives it, and Melian checks it against the line the head's lines came from, by the hunks above them. The same bytes in another function at the base would otherwise pass rule (b) and send the guard check to the wrong function.
- **A default export is read from the compiler's modifiers**, never from the text, where a comment may sit between `export` and `default`.
- **A member is carried by its own reports.** A dismissed report that a live finding only lists beside it does not make that finding carried.

What step 18 still owes: the `resolution.preExisting` cap key, and with it how an acknowledgement is recorded for a carried finding. Until then the cap is fixed at advisory, and a member never asks for one.

What the name match still cannot see: a name built at run time, as `module["parse" + "Record"]` is, or a call through `eval`. No reading of the text finds those, and the compiler's call graph would not either. The verifier's own answers are all that stand against them.

What this gives up: reach, again. The name matches refuse a re-scope whenever the change mentions the failing function or anything the trigger reads, anywhere, and any code the change adds to a function on the path refuses it. A real old defect then keeps its `introduced` cause and may block.
