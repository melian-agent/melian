# Actions rounds run only the default branch's code with the logins

Choice: the `melian round` workflow runs only when dispatched from the default branch. That commit supplies Melian, which reviews the pull request as `"#N"`, and every helper script that runs while a login is present. A pull request's base and head are review data only.

Why: fix pass 1 of [pull request #275](https://github.com/melian-agent/melian/pull/275) built Melian from the pull request's base commit, so that the head could not change what judges it. Melian's round on that head showed the base is no safer. A pull request can target another writer's unmerged branch, and `gh workflow run --ref <branch>` lets any branch supply the workflow's scripts. Either way a branch no review had passed could run with `CLAUDE_CODE_OAUTH_TOKEN` and the Codex login. The default branch is protected and every change to it is reviewed, so it is the one revision a writer cannot choose on the day. The maintainer chose this over keeping the base as the build and refusing pull requests whose base is not the default branch.

Melian's round on the next head showed that the code is not enough: `melian review "#N"` reads `melian.yaml` and every lens from the pull request's base, so a base a writer chose could still supply a policy that runs no checks. The gate therefore also refuses a pull request whose base is not the default branch, as the maintainer chose over trusting a writer's base.

What this gives up: a stacked pull request gets no Actions round until its parent lands and it retargets to the default branch. A host round from the branch's own build still covers that case. The workflow also cannot exercise a pull request's changes to Melian's own review code, so such a pull request needs a host round from its own build as well; the review loop in `docs/design.md` and `AGENTS.md` say so.

The workflow is a builder's round, not the Actions review host of `docs/design/hosts.md`. It keeps no state branch and dispatches no continuation: its store lives in runner storage and is thrown away. A round that times out or loses its runner starts again from nothing when it is dispatched again, and pays again for the lenses it had finished. A builder's round is short beside the job's 150 minutes, and milestone 3's host brings the continuation.

Fix pass 3's review of record showed that the head's code is not the only way in: a head's `biome.json` that extends `/proc/<pid>/environ` makes Biome quote the logins in its parse error, which Melian keeps as the check's error. GitHub masks secrets in the log only, not in a comment or an artefact. So nothing a static tool printed leaves the job. The artefact holds a public copy of the verdict, with each check's name, status and route, and each finding's rule, place and resolution, and a static finding's text replaced. The job writes no summary, and no checkout keeps a token in `.git/config`. `secrets.yaml` has no read-once file source, and Melian reads `CLAUDE_CODE_OAUTH_TOKEN` and `GH_TOKEN` only from the environment, so the logins stay in some process's starting environment; the redaction is the defence. What this gives up: the comment no longer says why a check did not run, and a builder reruns the round locally to see it.

Codex's adversarial review of fix pass 3 showed that the default branch's name is not enough. A rerun keeps the run's first commit and ref, so once the default branch moves past a fix, a rerun would build the old code and hand it the logins, and "Re-run failed jobs" can skip the gate. So the round job asks the repository which branch is the default now, and where it points, before any step holds a login, and refuses to run unless both are the run's own ref and commit. The event's own default branch is no answer: a rerun replays the event, so it would still name a branch the repository has since replaced. What this gives up: a round whose default branch moved while it waited, or before its rerun, has to be started again.

Melian's final round on fix pass 7 showed that the workflow's refusal of other refs protects nothing on its own. Repository secrets reach every branch's workflow, so a writer can push a branch whose `melian-round.yml` drops every check and sends the logins out, then run it with `gh workflow run melian-round.yml --ref <branch>`. The maintainer ruled to keep the logins in a GitHub Environment, `melian-round`, whose deployment branches are limited to `main`, so GitHub withholds them from any other branch's run. The round job, the only job that reads them, declares `environment: melian-round`, and `scripts/melian-round-workflow.test.mjs` requires every job that reads either login to declare it. The Environment, not the workflow's own check, keeps the logins from a branch's workflow; the check stays to refuse a stale or wrong-branch run early.

The maintainer sets it up once, in the repository's settings:

1. Create the Environment `melian-round`.
2. Under its deployment branches and tags, choose selected branches and add `main` alone.
3. Add `CLAUDE_CODE_OAUTH_TOKEN` and `CODEX_AUTH_B64` to it as Environment secrets, for example with `gh secret set <name> --env melian-round --repo melian-agent/melian`.
4. Delete both from the repository's secrets.

What this gives up: a branch's copy of the workflow, run to try a change before it merges, gets no logins, so it reviews with no model and reads as not reviewed.
