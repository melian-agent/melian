# The state branch stores each pull request's JSONL storage, and a lease keeps one writer

Status: built for [issue #244](https://github.com/melian-agent/melian/issues/244), in two pull requests: the `state-git` package first, then the CLI. The maintainer ruled the two choices under Rulings in the builder's session on 2026-11-07, as [the issue's comment](https://github.com/melian-agent/melian/issues/244#issuecomment-6706989407) records.

Amends: [the coordination decision](2026-11-08-how-melian-coordinates.md), as the state branch's form of its rule 2
Amends: [the coverage ledger decision](2026-10-23-coverage-ledger-and-delta-review.md), its "Sharing, for milestone 3" section: the state branch lands before the ledger, which [issue #307](https://github.com/melian-agent/melian/issues/307) carries onto it, and the lease is taken by this clone's checkout of a changeset

## Problem

Only the coordinator's clone holds a pull request's storage: its rounds, its marker secret, its ledger comment ID and its dismissals. A builder's Actions round throws its store away, so it cannot publish, resolve a thread or keep a dismissal. Losing that one clone loses all of it, the risk-table row "losing the one clone that reviews Melian".

## Rulings

1. A pull request's working store is Pi's `JsonlStorage`, in a directory this clone keeps for the state branch. A range stays on SQLite. The alternative, pushing the SQLite file itself, would leave every reader alone but add a whole binary blob to the branch at every publish.
2. A pull request that already has a local SQLite store keeps using it, with no lease and no push, and Melian says so. Pi has no generic copy of one store into another backend. A fresh store would mean a new marker secret, an orphaned ledger comment and lost dismissals. Open pull requests finish within days, so the old path empties itself.
3. When the branch cannot be fetched or pushed for any reason but another run's lease, Melian warns and works in this clone's copy. A later command that reaches the branch pushes it, or the branch's copy wins if someone else pushed meanwhile. Anyone who cannot push cannot write the branch anyway, and the `melian round` job's token cannot push.
4. Every command that writes a pull request's store takes the lease and pushes when it finishes: `review`, `publish`, `dismiss` and the `compare` writes.
5. Within one clone, the operating system decides whether the process holding a copy is alive: an exclusive SQLite transaction on a lock file, not a timeout. Three review rounds in a row found two processes in one clone writing one store: through the shared holder, through a stalled process losing a lock file it had stopped touching, and through a stalled process inside a socket lock's timed takeover. So the class was raised as a design question, as [the convergence rules](2026-10-15-review-loop-convergence-rules.md) require, and the maintainer chose a lock with no takeover at all.
6. Every file on the branch is encrypted under a writers' key, which comes from Melian's secrets file, and the secrets file may delegate it to an environment variable. The storage holds the publisher secret that signs Melian's markers, and anyone who can read the repository can fetch the branch, so a pull request's author could otherwise forge a marker. The CLI half reads the key.
7. `melian publish` refuses, before any GitHub call, unless it took the branch's lease and so holds the branch's latest copy: no key, an unreachable branch or a refused lease stops it, naming why. Ruling 3's offline work stays for every other command. Codex's review of 26338cc showed the stake: a clone publishing its own stale copy could post a passing verdict over a newer blocking status another clone had pushed.
8. `melian publish` stores the pull request's storage on the branch, the publisher secret and target included, before its first GitHub call, keeping the lease, and fails when its final push is refused or out of reach, keeping the copy. A clone's SQLite storage from before the state branch publishes only under the pull request's lease, which it reserves on the branch without storing a copy, under the same copy lock a checkout takes, confirms before posting and releases after; it refuses when the branch holds the pull request, the lease cannot be taken, or another process in the clone holds the lock. A command whose copy nothing changed, or nothing ever wrote, moves only the lease, so it never puts an empty changeset on the branch that would refuse such a reservation. Codex's review of ff4b2e1 showed that a single check before publishing leaves a window for another clone to store a newer round. Two Codex rounds in a row found `publish` acting on state it did not hold for certain, so the maintainer ruled for this rule, which keeps the secret that signed what GitHub holds on the branch before anything is posted. Codex's review of f54d1a61 found that one check still let a publisher that stalled past its lease post over the run that took it, so on 2026-11-08 the maintainer ruled that `publish` stores the copy and renews the lease before every write to GitHub: each status, review, reply, thread resolution and ledger write. A check that fails ends publication with nothing more posted. The moment between a check and its write stays open, as [the coordination decision](2026-11-08-how-melian-coordinates.md) accepts for statuses.

## The branch

`melian/state` on the repository's own remote holds exactly two things at its root. `index.json` is the state index. `changesets/<id>/` holds one changeset's storage, the files Pi's JSONL backend writes and no others: `main.jsonl`, `doc-<n>.jsonl` and `task-<n>.jsonl`. A branch holding anything else, at its root, in `changesets/` or in a changeset's tree, is refused before a byte of it is written locally and before anything is pushed over it, since anyone with push permission can write the branch. Problem: an earlier draft read a missing index as empty and skipped entries it did not know, so its next push would have deleted every stored changeset. Solution: a branch this build cannot read whole is never read in part. A push refuses a local copy that holds anything Pi's storage never writes, rather than push part of it.

Melian builds each commit with git's plumbing: `hash-object`, `mktree` and `commit-tree` in the clone's own object database. It never checks the branch out. Problem: [the design](../design.md#state-storage) planned a worktree of the branch, but one clone can review two pull requests at once, and a checkout of the branch would rewrite the other changeset's files under its open storage. Solution: each changeset's copy is a plain directory, and only the branch's trees join them.

## The lease

The index holds each changeset's lease, core's `Lease`, as [the coordination decision](2026-11-08-how-melian-coordinates.md) sets: its holder, a run in a clone, when it was taken, when it expires, an incarnation, and a fencing generation that rises every time it is taken. The incarnation is a random identifier minted when the changeset's record is first created and kept by every later taking; a record disposed and created again gets a new one, so its generations count afresh. Beside the lease the index records the generation the changeset's latest write was made under, within the record's incarnation. A checkout fetches the branch, refuses with `LeaseHeld` while another clone's lease is live, and otherwise takes the lease, one generation higher, by pushing the index with `--force-with-lease`, which is the compare-and-set. A lease two hours old or more is taken by anyone. A push expires the lease rather than deleting it, so the next taking's generation rises past it. A push lands only under the latest lease, by incarnation and generation together: a run whose lease another run took since, whatever its expiry said, is refused, and so is a run whose record was created afresh, whatever its generation, so the fence, not the expiry, is the safety. Each push's commit names the incarnation and generation it was made under. Within one clone, a checkout first opens `<id>.lock` beside the copy with `node:sqlite` and begins an exclusive transaction, which it holds until the checkout closes. A second process gets `SQLITE_BUSY` and refuses with `CopyInUse`. SQLite's lock is the operating system's: the kernel frees it when the process dies, and a stopped or stalled process keeps it. Nothing guesses from a clock and nothing is ever unlinked or taken over, so no stall can let a second process in. So a live lease of the checkout's own clone on the branch is one a crashed run left, and it is taken over. A clone is its copies directory: the branch mints an unguessable ID there, owner-only, beside the copy locks, and a lease names its clone by the caller's label and that ID. The maintainer ruled so on 2026-11-08, after two rounds showed that two copies directories given one label would each take the other's live lease as a crashed run's. A lease two hours old or more is taken by anyone. A long review that outlives its lease is still safe, because the push below checks both the lease and the changeset.

Each run fetches into a ref of its own, without writing `FETCH_HEAD`, so runs on two changesets in one clone never contend. Every push names the tip it fetched with `--force-with-lease`. When the remote reports stale info, or two pushes creating the branch collide on its ref, another run pushed in between, so the run fetches again and decides afresh: a run on another changeset never blocks this one. Before each retry it waits a random time below a bound that doubles from 50 ms to a second, so writers on several changesets that collided spread out; after ten lost races in a row it gives up with `pushFailed`, naming whether the branch moved or the remote could not lock it. The review of record at 853b4a2d found three attempts with no wait starved four of six writers. A refusal for any other reason, such as a hook or branch protection, is `pushFailed` at once.

## Sealing

Every file a push puts on the branch is sealed with AES-256-GCM under a subkey of the writers' 32-byte key, with the changeset and the file's name as associated data, so a file moved to another changeset or name fails to open. Its nonce is an HMAC of the name and the content under another subkey, so an unchanged file seals to the same blob on every push, and two contents never share a nonce. A checkout opens every file before it writes any, and a file this clone's key cannot open is `invalidBranch`. The index stays plain, since it holds only leases and the key's commitment: an HMAC of a fixed label under the key. The first push records it, and every read checks it before a lease is taken or a copy pushed, so a clone holding another key refuses rather than add a changeset no writer can open, or rewrite a cached copy under its key. A holder outside 1 to 200 characters is refused before any git command, since a lease the next read refuses would make the whole branch unreadable.

## Pushing and resuming

A push stores this clone's copy of the changeset and releases the lease, in one commit. It is refused, and the copy stays as it is, when the lease is no longer this run's, or when the changeset's tree on the branch is not the one this clone last synced with. Either way another run has written the changeset. A checkout keeps this clone's copy only when it still holds the synced tree whole, as Pi's own storage judges: two rounds of Codex's review each found a new kind of local damage the marker alone let through, so on 2026-11-08 the maintainer ruled that Pi, the authority on what it wrote, opens the copy before Melian keeps it, beside a check that its main log starts with the tree's, since Pi reads a missing main log as an empty store. The maintainer also ruled, that day, that git's own low-speed limit bounds a fetch or push. Melian's round on 325383fc then found that the limit measures throughput, not time, and does not apply to SSH at all, the second review to raise the class, so the maintainer ruled the same day for a wall-clock deadline: core's `git` stops the git process it started, by that process's own pid, once a fetch or push has run two minutes, and a stalled or dripping transfer on any transport reads as an unreachable branch. The low-speed limit stays as an earlier detector. A transport git started, such as ssh, is not signalled; it ends when its connection does, and can finish a push after git was stopped. So, as the maintainer ruled on 2026-11-08, a push stopped at its deadline fetches the branch again, under the same deadline, and counts as landed when the tip is the commit it sent. A transport that lands later still leaves the branch moved after Melian said it did not; the fence keeps that safe, and the next checkout reads the branch's copy.

The next checkout sees that the branch has moved past this clone's copy, sets the copy aside beside it and takes the branch's. The branch's copy decides what is done, so a resumed review attaches to the tasks the other run finished and redoes only what the branch lacks. Pi's JSONL log is one writer's history, so two copies are never merged.

A store a newer build wrote is refused when this build opens it, by Pi's document versions, as today. The branch is not overwritten: a push after the refusal stores the copy unchanged.

## The CLI

A pull request's storage is this clone's copy of the branch's, through `ChangesetStore`. Every command that writes it checks it out and pushes it when it finishes; a command that only reads it opens it under the copy's lock and touches no remote. A range, scripted mode and a pull request with SQLite storage from before keep SQLite. The writers' key is a credential for the provider `melian-state` in a secrets file, which the model catalogue never sees. A checkout that cannot reach the branch, or has no key, keeps the copy's lock and says why, as ruling 3 sets.

## What this gives up

- The lease is no lock. A run that holds the lease longer than two hours can be raced; the push then decides, and the loser redoes its delta.
- A set-aside copy stays in the clone until someone deletes it.
- A copies directory copied whole, by a VM snapshot, a restored backup or a copied `MELIAN_STATE_DIR`, carries its clone ID, so two hosts can share one identity and the second takes the first's live lease as a crashed run's. The fence still refuses the loser's push, so only that run's time is lost. The maintainer ruled on 2026-11-09 to accept this.
- A command's work reaches the branch only when the command ends, and before `publish` posts. A runner killed mid-review loses its checkpoints, and its replacement waits out the lease and redoes them. The maintainer ruled on 2026-11-08 to leave pushes at checkpoints, and handing a dead runner's lease to its continuation, to the Actions host in milestone 3, as [issue #319](https://github.com/melian-agent/melian/issues/319) carries.
- A writer can roll a changeset back. Sealing keeps the branch from readers, not from writers: one who lacks the key can still push a commit that reuses an older sealed tree from the branch's history, and every file of it still opens. Writers are trusted, as [the coverage ledger decision](2026-10-23-coverage-ledger-and-delta-review.md) rules under "No signature or attestation now", and anyone who can push the branch can push anything to the repository. Codex's review of dd4358b raised it; authenticating each state commit becomes worth building when an untrusted writer must be kept out.
- The lease lives on the branch, so every checkout and every push is a network round trip, a second or so against reviews that take minutes.
- The branch keeps every push's commit, and a sealed file never deltas against its last version, so a fetch of the whole history grows with every push while Melian reads only the tip. Past some size a fresh runner's fetch passes the deadline and reads as unreachable. The maintainer ruled on 2026-11-09 to take this in a follow-up, [issue #361](https://github.com/melian-agent/melian/issues/361).
