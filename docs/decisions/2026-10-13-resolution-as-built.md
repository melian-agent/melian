# How step 18 builds resolution per lens and per rule, and the choices it made

Problem: [the decision that makes resolution configurable per lens and per rule](2026-10-12-resolution-per-lens-and-per-rule.md) leaves one choice to the step that builds it, and is silent on eleven more. The open one is how an acknowledgement is recorded for a carried pre-existing finding, which [the scope decision](2026-10-13-scope-checks-as-built.md) passed on.

Example: a root file sets `preExisting: { P0: acknowledge }`. A pre-existing P0 resolves `acknowledge` at the first revision of a pull request, and a maintainer answers it. At the second revision the same finding ID is sighted again. Nothing in the decision says whether it asks again.

Choice: step 18, "Resolution per lens and per rule", builds the rules as below. Where the decision could be read two ways, the step took the narrower reading. This refines the decision and replaces none of it.

- **An acknowledgement of a pre-existing finding is a dismissal.** A maintainer answers it with `melian dismiss` and a reason, as for every other finding that resolves `acknowledge`. The findings document already keeps a finding's lifecycle by ID across revisions, with who dismissed it, why, and when. So a carried finding that was acknowledged stays dismissed at the next revision. It leaves "Pre-existing, important" and the verdict, and is listed with the dismissed findings. No stored field was added.
- **A lens's declared default is not part of the lens's version.** A lens's version names the findings it produced. A declared `resolution` changes what a finding requires, never which findings the lens reports. So a lens that gains a default keeps its stored findings. Adjudication reads the default from the lens as it applies at the finding's path, from the same source as the lens.
- **A refuted report does not count beside one that stands.** A merged defect takes the strictest result among its reports. A lens report whose every claim a verifier refuted is left out, unless every report of the defect is one. Before this step the speaker took the highest severity, so a defect could block on a refuted P1 beside a confirmed P3.
- **The cap on an unjudged lens finding applies to a report, not to a defect.** Before this step a defect that lenses alone reported was capped at `advisory` when any claim of it had no verdict. The decision applies each cap per member. A judged report beside an unjudged one now resolves in full, and the unjudged report alone is capped.
- **A notice of a changed resolution reads tables only.** The decision says no mapping and no ceiling under `guardrails` applies to the two new notices. The step reads that to the letter. Such a notice resolves through the files' severity tables alone, and then the `acknowledge` floor applies. The notice is marked in the typed field beside its class, and the floor reads the mark. A notice on a `LENS.md` that leaves its resolution alone has no floor, as before.
- **A check name no check could carry is refused.** A key under `resolution.checks` must be `guardrails`, or start with `lens.` or `static.`. A key under `guardrails.rules` must start with `guardrail/`. Any other is an `invalidValue` error naming the file. The loader does not check that the lens or rule exists, since a nested folder may define a lens the file cannot see.
- **`melian doctor` lists by structure, and skips what a file restates.** A farther value is listed when the file speaks for a finding the value would have decided, even where the result is the same. That is the decision's fourth case. A value the nearer file restates in an entry of its own is not listed, so a root that restates a lens's ceiling draws no line for it.
- **Which file decided is stored with the finding, outside the fingerprint.** `melian findings` reads a stored verdict. So adjudication stores the file that spoke, the entry the requirement came from, the ceiling in force, and the cap or floor that then moved the result. For a merged defect it stores the report that gave the strictest result. The verdict's fingerprint leaves the field out, so a change in which file decided posts no new review. It leaves out what a guardrail finding matched too, which the finding's message already says. A verdict published before this step therefore keeps its fingerprint when it is decided again.
- **Sightings of one finding ID share its severity and cause.** The findings document merges every producer's sighting of one ID before adjudication, at the highest severity and the strongest cause, as it did before this step. Such a finding resolves once for each check that reported it, at that severity and cause. That differs from a merged defect, whose reports have IDs of their own and keep their own severity and caps. Two lenses that share a rule ID, as every lens shares `melian/injection-attempt`, meet this case.
- **The important floor reads the defect, not a report.** A merged defect takes the strongest cause any report proved. A defect that an introduced report belongs to is not pre-existing. It is no member of "Pre-existing, important", and takes no floor from a pre-existing report within it.
- **The lowering fence reads every report.** The verifier may not lower a claim to a severity that resolves `silent`. With per-check keys that depends on the check. The fence lists a severity any report of the defect resolves `silent`, so it refuses a little more than a fence per claim would.
- **Every guardrail finding names its rules.** The decision asks for the matched rule names on a `forbidden-patterns` finding. The step stores them for `forbidden-paths` and `required-files` too, and for a line `forbidden-patterns` could not scan, which names every rule left unchecked there.

Why: each point keeps the rule a maintainer can hold in one sentence, that the nearest file which mentions a finding decides it. A second record of an acknowledgement would need its own reopen rule, and the lifecycle already has one. An entry no finding could match would leave a maintainer trusting a ceiling that never applies.

What this gives up: a dismissed pre-existing finding reopens as any dismissal does, when its trigger changes. A pre-existing finding has no trigger in the change, so in practice it stays dismissed for the pull request. A lens-only defect with one judged claim and one unjudged claim is no longer held at `advisory`. Two sightings of one ID are not resolved apart. Where a table asks more of a higher severity, the shared severity and cause never resolve below what either sighting would alone. A table that asks less of a higher severity for one check can.
