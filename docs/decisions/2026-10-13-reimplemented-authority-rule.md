# The re-implemented authority rule and its boundary

Choice: the `design` lens rule `reimplements-an-authority` reports hand-written code that parses a format, or re-derives an answer, that a dependency of the base already parses or answers. An authority is a package the base's manifest declares or a tool the base's code already runs. A dependency the reviewer knows of and the repository does not use is not one. A finding names the authority and the base line that declares or uses it, the hand-written lines, and one input the hand-written code reads wrong that the authority reads right.

Three cases are not findings. The base has no such dependency. The change calls the authority. Or the authority cannot run where the answer is needed and the change states the gap, as [ask the authority](2026-10-12-ask-the-authority.md) allows. The lens checks the stated reason against code it reads, and a reason the code shows false leaves the finding standing. Under a gap that holds, the hand-written code stays `design`'s: it reports an input the code answers wrong, or guesses at, where it should refuse or take the safe wide answer.

`design` owns the defect. `correctness` and `conventions` each carry a `design` hand-off for it, so they leave it only when `design` reviews the same files. `correctness` keeps a wrong result only where the repository has no such dependency. It leaves one under a stated gap to `design` too, since a rule that split the gap between two lenses would have both report a guessing fallback. `conventions` leaves the hand-written code to `design` even where a standard names the dependency.

Why: the rule has no decision file to judge against, unlike the lens's other nine, so its baseline had to be named: the base's own dependencies. A baseline of every library the model knows would flag any parser, in any repository. Requiring one misread input keeps the finding grounded, as the lens's other rules require a failure scenario. The author of a change does not write the excuse for it, so a comment that states a gap is a claim to check, not an exemption.

The boundary is stated on both sides because [the lens backlog boundaries](2026-10-04-lens-backlog-boundaries.md) measured what happens otherwise: two lenses report one defect under two rules. Example: a header parsed by splitting each line at a colon returns a quoted title with its quotation marks. That is a wrong result, which `correctness` claims, and a re-implementation, which `design` claims. Each round of [pull request #102](https://github.com/melian-agent/melian/pull/102) reported one such wrong result, and none named the cause. `design` reports the hand-written code once and lists the inputs.

What this gives up: the hand-offs change the versions of `correctness` and `conventions`, so a stored review of either reads as an older lens. `conventions` hands over a breach it could have quoted; when `design` then accepts a stated gap, nobody reports the standard. The `design` lens sits outside the default `full` tier, and where it does not run the hand-offs do not render, so the other two lenses keep what they had.
