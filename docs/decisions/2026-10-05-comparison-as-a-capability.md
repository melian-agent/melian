# Comparison as a capability

Choice: A comparison with external reviewers is a Melian capability, reached through `melian compare`, not a file an agent writes. An external finding has one shape. It names its reviewer, `codex`, `claude-code`, `coderabbit`, or `human`, with a version. It holds the file, line range, title, body, and the reviewer's severity. It keeps a stable source reference, the time posted, and whether its thread was resolved. A comparison holds, for one changeset at one head, the external findings, Melian's, and the matches between them, in a document in the changeset's storage. Importers read a pull request's review threads through GitHub's GraphQL API, filtered by author login, with CodeRabbit's `coderabbitai[bot]` first. Others read a file: Codex's adversarial review JSON, or the external-finding shape for any other local reviewer. Matching is mechanical: the same file, with lines that overlap or lie within three lines. A `Decider` question may refine it in milestone 4. `melian compare adjudicate` records valid, noise, or duplicate, a severity, and for a valid miss one reason: `owned-missed`, `no-owner`, `needs-execution`, or `out-of-scope`. It records too whether a golden is owed and for which lens, with the git author and time, as a dismissal is. `melian compare stats` gives recall and precision per reviewer, misses by reason, and repeat findings as candidate checks. `melian compare backlog` lists owed goldens, and `melian compare export` writes today's markdown record from the stored document. Every third comparison record is followed by a backlog pull request that ships at least two owed goldens and re-measures their lens. A `needs-execution` miss is scope for the verifier, judged on whether it would have caught it, and for the tool manifest. In a customer's repository the comparison stays in the maintainer's clone, and only an explicit export writes it anywhere.

Why: The hand-written records stopped producing goldens or checks. The records for pull requests [#55](https://github.com/melian-agent/melian/pull/55), [#60](https://github.com/melian-agent/melian/pull/60), and [#61](https://github.com/melian-agent/melian/pull/61) owe no golden, because their findings sat outside what the lenses' goldens measure. BACKLOG.md still holds entries from milestone 1, and nothing shows which findings repeat, so a repeat becomes a check only when someone remembers it. A record does not say why Melian missed a finding, so a lens that read badly looks like a defect only running the code would show. On #61, Codex found a leaked key by running the YAML library, and `trust-boundary`, which owns that rule, missed it. Recall lives in a sentence per record, so nothing sums it. The customer repositories Melian will join run CodeRabbit, whose findings live in review threads, and the REST comment list carries no thread state. A capability on the CLI serves Melian's repository and theirs alike, as `AGENTS.md` requires of every capability. A fixed list of reasons turns each miss into an action: a golden, a new check, verifier scope, or nothing. Mechanical matching by site is the merge's rule already, and it needs no model.

Supersedes: no decision file. It supersedes two rules in milestone 1's parallel tracks in design-implementation-plan.md. The comparison-reviews track made every valid difference a golden and every noise finding a negative golden. The golden-fixtures track grew the corpus by one golden per comparison difference. It also supersedes BACKLOG.md's hand-kept list as the source of owed goldens.
