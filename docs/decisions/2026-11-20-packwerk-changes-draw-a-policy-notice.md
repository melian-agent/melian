# A head's change to a Packwerk file Enola read draws a policy notice

Amends: [Enola's policy paths come from Enola](2026-11-16-enola-policy-paths-come-from-enola.md), the Packwerk files it leaves to the head
Amends: [Analyser configuration changes](2026-10-03-analyser-configuration-changes.md), a change to a Packwerk file Enola read acknowledges rather than blocks

Status: the maintainer ruled on 2026-11-18, on [issue #538](https://github.com/melian-agent/melian/issues/538), for the first option there. A head that changes `packwerk.yml` or a `package.yml` gets a policy notice at acknowledge. The head's copies still run. How the notice is raised is the coordinator's answer on approach, given in its session, not a ruling.

Problem: Enola 0.4.40's Packwerk check reads `packwerk.yml` and each package's `package.yml` from the head. A head that sets `enforce_dependencies: false` in a `package.yml` turns the check off for that package, and the review said nothing. The review of record on [pull request #534](https://github.com/melian-agent/melian/pull/534) showed it. Replacing the files with the base's copies, as Melian does for Enola's other policy, would judge a head that adds or moves a package by packages it no longer has.

Solution: the Enola check raises `guardrail/policy-change-review` for each Packwerk file Enola read at the base or the head that the head changes, adds, deletes or renames, or that is a symbolic link or lies under one, as Links below says. The notice uses the guardrail's own sentence, "Review the change to `<path>`, which configures Enola's Packwerk check.", at the folder's `guardrails.policy-change-review.severity`, P2 by default, which resolves at acknowledge. A folder that turns `policy-change-review` off draws none. A repository where Enola finds no Packwerk package draws none.

Why the Enola check raises it, and not the guardrails check: only Enola knows which files it read. Packwerk finds packages through `packwerk.yml`'s `package_paths`, and on a scratch repository the pinned binary read a `package.yml` only where its own matching found a package. A bare string, `**/`, or no key found none, and a nested `packwerk.yml` or a `packwerk.yaml` was ignored. Matching `**/package.yml` by name would notice files Enola never reads and miss none it does only by luck. So the runner asks the authority: each revision's `facts.jsonl` lists a `module` fact with `props.packwerk: true` and the `package.yml` it came from. The runner reads both revisions' facts. Each Packwerk module adds its `package.yml` and the `package_todo.yml` beside it, and `packwerk.yml` joins the list when either revision has a Packwerk module.

Why `package_todo.yml`: it records a package's known violations, so a head that adds its own new violation there hides it from the check. The review of record on [pull request #601](https://github.com/melian-agent/melian/pull/601) found it. To learn what else Enola reads, the builder traced the pinned binary's file opens with `strace` on a scratch Packwerk repository, through `--generate` and `check`, and then changed each file in turn and compared the facts. Enola opened `packwerk.yml`, each `package.yml`, each `package_todo.yml`, the root `package.yml` and `deprecated_references.yml`. Only `packwerk.yml`, a module's `package.yml` and its `package_todo.yml` changed the facts: a violation recorded in `package_todo.yml` became `packwerk_todo_dependencies`, while the same record in `deprecated_references.yml`, or a changed or deleted root `package.yml` with no code of its own, left the facts byte for byte the same. So the list holds those three. The coordinator gave this approach, on [issue #538](https://github.com/melian-agent/melian/issues/538).

Links: Enola follows a symbolic link, and a head's change behind one touches no path Enola's facts name. A directory link `packs/c -> ../lib/c` lets a head edit `lib/c/package.yml` while `packs/c/package.yml`, the path Enola reports, never appears in the diff. So the runner asks git's tree, at the base and at the head, whether each listed path, or a directory above it, is a link, and never follows one itself. A path that is, at either revision, draws the notice whatever the change touched. Its sentence says why it appears on a pull request that changed nothing there: the file reaches Enola through a symbolic link, so Melian cannot tell whether this change altered it. The cost falls on a repository that commits such a link: every pull request draws the notice for each Packwerk file behind it, until the link is replaced by the files themselves. The coordinator chose this, the first of the options the builder put to it, on [issue #538](https://github.com/melian-agent/melian/issues/538), over following links by hand, which repeats what git and the filesystem already answer. A dismissed notice behind a link must not stay dismissed after the link's target changes, and git's diff of the Packwerk path cannot see that change. So the trigger of a notice behind a link also hashes the head commit's tree, which changes whenever any content in the head changes. Codex's review on [pull request #601](https://github.com/melian-agent/melian/pull/601) found the old trigger, which hashed only the path's own objects, kept such a notice dismissed for good. The cost is a fresh acknowledgement on every push that changes anything, for each Packwerk file behind a link. A merge or empty commit that leaves the tree unchanged keeps the dismissal. The coordinator chose this, on approach, over hashing the target's content, which would mean following links by hand. Enola's facts fail closed: a missing or unreadable `facts.jsonl` fails the check, as an unreadable SARIF log does.

The notice resolves under its own check and under the guardrail's, and the stricter result stands. It carries the guardrail match an analyser's configuration notice carries, so resolution reads `resolution.checks.guardrails` and the rule's `analyser` class. It also reads `resolution.checks.static.enola`, since every report resolves under its own check, by [the exact-rule decision](2026-10-17-acknowledge-status-exact-rule.md). So a repository cannot quieten this notice from the guardrails table while its Enola table is stricter, nor from the Enola table while its guardrails table is. The coordinator first answered that it resolve under the guardrails check alone; a round showed that broke the exact-rule decision, and the coordinator then chose both, which never lowers what blocks. Its ID is the guardrail's, which ignores the producing check, so a dismissal matches it as it would the guardrails check's. The policy-change floor keys on the rule and the path, so it treats both alike; a `package.yml` is not a `melian.yaml`, so no floor applies. It is stored under `static.enola`, so a later Enola run replaces it and a guardrails run leaves it alone. `melian findings` shows it with Enola's mark beside the guardrail's rule, since Enola raised it. Stored findings carry no tool text, by [the decision of 2026-11-16](2026-11-16-shared-static-findings-carry-no-tool-text.md): the notice is Melian's fixed sentence and the path.

Its severity is the guardrail's `severity`, not `analyserSeverity`, which blocks a change to an analyser's configuration at P1. This narrows the 2026-10-03 decision that an analyser's configuration change blocks, for these files alone, and the ruling made that choice: a Packwerk file is ordinary project structure, which a head adds whenever it adds a package, so a block would stop every pull request that adds one.

The check request keys the checks' code by its recorded hashes, which this change moves, so no run a build stored before the notice existed is reused for a head that changes a Packwerk file.

Raise the Packwerk list with the pin. A later Enola that reads another file for Packwerk, or reads `packwerk.yml` elsewhere, needs `EnolaFacts.packwerkFiles` changed and its test with it.
