# `melian compare` addresses a stored round by its head commit

Problem: once a pull request merges, `melian compare` and `melian findings` cannot reach its stored rounds. A range changeset's ID hashes the range's mode and the canonical names of its base and head. After the merge `origin/main` is the merge commit, so `origin/main...HEAD` collapses, and no other range names the changeset that was reviewed. A round run from a worktree on the branch is also only one revision of a branch changeset, and no command addresses any revision but the latest.

Example: the last five comparison records were written by hand. The records for [pull request #114](../../packages/evals/comparisons/2026-10-14-pr-114.md#how-this-record-was-made), [#116](../../packages/evals/comparisons/2026-10-14-pr-116.md#how-this-record-was-made), [#117](../../packages/evals/comparisons/2026-10-14-pr-117.md#how-this-record-was-made) and [#113](../../packages/evals/comparisons/2026-10-14-pr-113.md#how-this-record-was-made) each quote the refusal, `Melian has no review of <sha>; run melian review <range>`, for three or four ranges they tried. The record for [#111](../../packages/evals/comparisons/2026-10-13-pr-111.md#how-this-record-was-made) worked around it with a scratch clone whose `origin/main` was reset and a copy of the store, which reached only the latest revision. So none of these five feeds `melian compare stats` from the shared store, and its recall and precision say nothing about the pull requests they cover. The record for [#102](../../packages/evals/comparisons/2026-10-12-pr-102.md) did reach the store, because its rounds ran detached and were adjudicated before the merge, one changeset per round.

Choice: a stored round gets an identity of its own, and is found by its head commit, not by the range that made it.

- Each review writes a round record in its changeset's storage, in the commit that starts the review: a round ID, the changeset ID and revision, the base and head commits, the pull request number when the target is `#N`, and the start time, with the finish time written when the review ends. The round ID hashes the changeset ID and the revision, so two changesets that reviewed one base and head pair still have two rounds. The record is a stored shape, with a version and a reopen test. Rounds reviewed before it exist have no record, and read their times as unknown.
- `melian compare --head <sha>` and `melian findings --head <sha>` read every round whose head is that commit, across changesets, and list each by round ID. A read may span several rounds. A write, `adjudicate`, `match` or `unmatch`, names exactly one round: with `--head`, it is refused when more than one round matches, and the refusal prints the round IDs to pass as `--round <id>`. `export` takes either.
- `melian compare "#N"` on a merged pull request reads its heads from GitHub: its commits, and the heads its force-push events name. It gathers every round whose head is one of them, in the order the round records' start times give, and rounds without a record after them in their heads' commit order.
- `melian compare adjudicate "#N" <id>` adjudicates an ID that recurs across rounds. It writes the same adjudication into each round that showed the ID, one commit per changeset, each replacing that round's adjudication as an adjudication already does. A crash leaves some rounds written; a rerun writes the rest and changes nothing in the written ones. The command prints every round it wrote. No pull-request-wide document is added: each round still holds its own adjudications, as [the comparison decision](2026-10-05-comparison-as-a-capability.md) sets out.

How `compare stats` counts a pull request whose rounds sit in several changesets stays [readiness question 3](../readiness-check-questions.md); this decision changes what can be addressed, not how statistics count.

This is a prerequisite of the [review outcome task](2026-10-15-review-outcome-task.md), which reads a merged pull request's whole history.

What this gives up: a review writes one more document. `#N` needs GitHub to list a merged pull request's heads, so a comparison of a pull request is not offline. A head commit reviewed under two pull requests, such as a stacked branch retargeted onto `main`, belongs to both, and the comparison shows it under each. The hand-written records are not imported; they stay as history, as [the evals guideline](../guidelines/evals.md#comparisons) already says.
