# Domain objects over their JSON

Choice: A domain class over stored JSON has three constructions. `from(stored)` trusts JSON Melian wrote and validates nothing; `parse(input)` validates input from anywhere else; `create(input)`, or a named factory such as `Changeset.resolve`, builds one from a producer's values. The class declares its fields in the order the stored shape holds them, and `toJSON()` writes them in that order. A durable task's input and a document's value hold the JSON, never the object. A function over an array of domain objects becomes a static of the class when it constructs or picks among them, as `Lens.select` does, or a method of the object that holds the array, as `Adjudication.defects()` and `verdict.attention()` are. Rendering is a method of the object rendered, `finding.render(rendering)`, `log.render(rendering)`, and `verdict.render(rendering)`, and `Rendering` holds only the options they share. A closure inside a method, such as the one `verdict.fingerprint()` strips each finding's dismissals with, is part of that method and reaches no caller, so it is not a free function. Merging claims is a method of the finding that speaks, `speaker.mergeClaims(members)`, since the speaker was that function's first parameter. A `Defect` is the speaker and the reports merged into it, which is all a stored verdict keeps of the member findings. A lens's version hashes its fields without `file` and `nearer`, so `Lens` can declare `version` before `file`, where the loader builds `file` first, and no version changes; the lens tests pin the built-in versions and the version a `melian.yaml` override gives.

Why: The [decision that domain objects carry behaviour](2026-10-04-domain-objects-carry-behaviour.md) named `from` but not what it checks. Validating every read would have changed behaviour: a reader of a stored verdict never validated, and old stored shapes read through migrations, not through the schema. Pi Durable copies a task's input and a document's value as strict JSON and refuses a class instance, so the JSON must be what is stored. A verdict's fingerprint and a lens's version hash JSON, and `JSON.stringify` follows key order, so a class that declared its fields in another order would change every stored fingerprint and every lens version, and publishing would post a second review of a verdict already posted. The pipeline merges stored sightings, which carry no lifecycle status, as well as findings, so the merge reads the speaker and its members rather than a group the verifier has not yet built.
