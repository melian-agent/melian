# Enclosing functions in the change prompt

Choice: At a level that reads `functions`, the change prompt carries the head's function around each hunk of a TypeScript file, after the diffs, each in a `function` block of its own with numbered lines. The compiler finds the bounds: TypeScript 7's native syntax tree, asked through `HeadProgram`, a virtual file system holding the head's text from git. The innermost named function holds a hunk: a declaration, method, constructor, accessor, or a function value that a variable, property, or default export names. A callback passed to a call has no name, so the function around it holds the hunk. A deletion belongs to the function that holds both lines it sits between. Every other case, a file in another language, a hunk outside any function, a function past 250 lines, a file past 512 KiB or past the first 200 TypeScript files, and blocks and the not-shown listing past 64 KiB together, stays with the instruction: the lens reads the function with `read_file`. The instruction says so unconditionally: the lens reads with `read_file` every hunk that has no function block, whatever the reason. The prompt also names each case it left out, so the lens is never told a function is carried when it is not: a note says when more than 200 TypeScript files changed, when a file was past 512 KiB, when a file could not be read at the head, when the diff was cut, and when the compiler could not start, in which case the note on the lens's record says too that it read the functions itself. A deleted file has no head and is not counted. The notes sit outside the attach key, as the blocks do.

Why: Problem: at `functions` the lens spent its tool budget reading the function around each hunk, and `deep`'s budget of 60 tool calls was counted against reads Melian could have made. A parser for each language was the obstacle, and a guess from indentation or braces would show the model a wrong scope as fact. Solution: TypeScript is the language Melian's own repository and most customers' repositories use, and the compiler's tree is exact. The other languages keep the instruction, which was always right and only costs tool calls. The prompt gains at most 64 KiB of blocks and listing, bounded apart from the 200 KiB diff, which a cut diff never receives. A function's name keeps its first 200 bytes, the listing holds at most 100 entries and says how many more it left out, since a name can be as long as a 512 KiB file. Function bounds come from a line table that breaks only at LF, the numbering of git's hunks and of `read_file`; the compiler's own line map also breaks at a lone CR, U+2028 and U+2029, and would drift from both. The compiler reads text from git, never the working tree and never an author's path: the virtual files carry names the compiler chooses, so a path cannot reach it. The function text enters the prompt inside a `function` boundary with the review's nonce, as every line from the head does. The reader is `HeadProgram` in `compiler-graph.ts`, beside the step 11 compiler graph of [pull request #89](https://github.com/melian-agent/melian/pull/89), so Melian has one path to a TypeScript program. The graph opens a project from a checkout; `HeadProgram` opens the same compiler over text.

## The function blocks stay outside the lens task's attach key

Problem: the function blocks come from a best-effort read, and the instruction fingerprint hashed the prompt rendered with them, so the attach key depended on whether that read succeeded. Example: a review reads the functions and is killed during a lens's first model request, and the rerun cannot start the compiler. Keyed on the prompt, the rerun missed the attach, cleared the earlier sightings, aborted the first task and ran every lens again. The [caller context decision](2026-10-07-caller-context-outside-the-attach-key.md) found the same fault for the caller section.

Choice: the fingerprint renders the prompt without the blocks, and `selectionOf` holds none. A repeat call attaches to the first call's lens task. That task's stored input carries the prompt that call rendered, blocks included, so the resumed lens keeps the first call's functions. A run also stores `unread`, the reason the first call could not read the functions, and the lens's record derives its note from the stored runs, never from the finishing call's read. Otherwise a repeat that attached, finished the task, and could not read the functions would write a note the first call did not, and the verdict's fingerprint would change between calls.

Gives up: a changed function read on the same head does not re-run lenses, and `--rerun` does not refresh it. A new head, or a rerun after a failed lens, reads fresh. A task an older Melian created carries no `unread`, so its records carry no such note.

## The read is bounded in work as well as in bytes

Problem: the limits on files, bytes, lines and prompt size left the work unbounded. A 512 KiB file of `function f1(){}` lines holds about 32,000 named functions and as many added lines, and a scan of every function for every added line costs a billion comparisons per file, run synchronously before any lens exists.

Choice: a sweep with a heap finds each added line's innermost function in one pass over the file's sorted functions, so the cost is linear in lines and functions, never their product. Five caps bound the rest, and each leaves what it cuts to `read_file`: `anchorsPerFile` (5,000 added lines) and `callablesPerFile` (20,000 named functions) skip a file whole, `anchors` (20,000) and `callables` (100,000) skip a file that would take the files together past them, and `found` (2,000) stops taking functions. A skipped file carries no function, never a partial list, since a partial list would show an outer function as the innermost. When any cap held something back, the prompt says so in a closing note. `blocks()` skips a block it can already tell will not fit, so a spent budget costs no rendering.
