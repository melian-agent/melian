# How the mutation check reruns only later changes, as built

Supersedes: [the mutation decision](2026-10-08-mutation-testing-as-a-static-check.md). Its incremental cache clause, the `incremental: true` setting's line and the paragraphs "Incremental results across runs" and "Cost", is replaced below. Every other clause still in force is restated at the end of this file, word for word.

The mutation decision's "Related tests" and "Bounds" paragraphs stay superseded by [the selection decision](2026-10-12-mutation-test-selection-asks-vitest.md), and are not restated.

[The rerun decision](2026-10-15-mutation-reruns-later-changes-only.md) set the direction and listed the open questions; this file is the full decision it asked for, and answers them in the next section. The code in [pull request #125](https://github.com/melian-agent/melian/pull/125) was written before this file was attacked, because its brief predated the rule that the full decision comes first; that pull request's review rounds were the attack.

## Reuse while iterating, final run cold

Problem: four review rounds each found another way a reused kill goes stale. A change Stryker's diff does not read, such as a configuration, a setup file, a test helper, a snapshot or a fixture, keeps every earlier kill. So does a change to another mutated file that a kill depended on. Each guess at which changed files are safe was wrong for some file a test loads.

Choice, in the maintainer's words: "Reuse while iterating, final run cold." A run that builds on an earlier head is fast and provisional. Only a cold run, the normal full run with no earlier results, can let a review pass.

- A run is provisional when Melian handed Stryker an earlier head's report. That is Melian's own fact, not the head's: the count of reused results in Stryker's log is the head's text, so a head that printed "0 of 5 reused" would otherwise read as cold.
- A provisional run's check record has the status `provisional`, with the reason "provisional: Stryker reused X of Y results from an earlier head; a cold run decides approval", or, when the log gives no count, that Stryker was handed an earlier head's results. The record still carries its findings and version, so its findings count as a run's do.
- A provisional record leaves the review `not reviewed`, even with no finding. The verdict is never `passed`, the exit code is 2, and the published `melian/review` status is `error`, naming the provisional check. A blocking finding still blocks. The terminal, the JSON, the review body and the ledger list the check under "Provisional", apart from the checks that did not run.
- `melian review --cold` runs the check with no earlier results. It is part of the run's identity, so a provisional run of the same head never stands in for it. A cold run still publishes its results, marked cold, so the next head can build on it. A plain review of the very head a cold run judged reuses that run's results whole and is not provisional; a review of any later head is.
- A run that keeps cold standing stays cold through a whole-suite repeat. The runner restores an earlier report only for a provisional run. It is told so by Melian, and does not read it from a file in scratch, which the head's tests could write. A plain review of a cold-judged head therefore repeats from nothing.
- Whether a run is provisional is decided when it starts. A task a crash interrupted after it published reads its own published head on the rerun: cold if it was cold, provisional if it was not.
- `melian publish` publishes a provisional review as not yet approved rather than refusing it. Its status is `error`, never `success`, and its body says the result is provisional and that a cold run decides approval. Problem with refusing: the pull request would then carry no status and none of the iteration's findings, and an absent status is easier to mistake for a pass than one that says "not reviewed".
- Iterate with reuse, and run `--cold` before the queue.

## The open questions, answered

- The partition key holds only what stays fixed across a pull request's heads: the review target, the base, the base-policy commit, the Stryker version and the installation identity. The mutate entries belong to a run.
- Both runs trusted alike. A run reuses a partition only when the leave it records equals the run's own, `writer` or `reviewer`.
- The plant-then-revert forgery. A head can plant a hook that makes every mutant read `Killed` and a later head revert it, and a provisional run can keep the planted kills. The cold final run reruns everything, so the planting never decides approval.
- Whether the final run reuses the cache: [readiness question 16](../readiness-check-questions.md), answered by the maintainer. It does not; it runs cold.
- Publication only from a descendant head: a run never publishes over a newer head's results, as the last section says.
- What starts cold: `--cold`, a force-push or rebase that drops the last judged head, a base change, an installation change, and a different leave.

## The review target is the changeset ID

The changeset ID already names a review target independent of its head. A pull request's is a hash of its provider, repository and number. A branch range's is a hash of the range mode and the canonical names of both sides, so `origin/main...HEAD` on one branch gives the same ID at every head. A range that names a bare commit hashes the commit, so it gets an ID per head: it runs cold at each new head and warm only on a rerun of the same one. The check task already stores the changeset, so a task a crash left pending resumes with its target. A caller of `runStaticTool` that names no target shares nothing: the head stands in for it.

## The partition stores the judged head and its leave

`<cache>/mutation/<identity>/partition.json` holds `{ version: 3, head, trust, cold, at, report }`: the last judged head, the leave its tests ran under (`writer` or `reviewer`), whether its results are a cold run's, when it was published, and Stryker's incremental report. A file without `cold` reads as not cold, and one without `at` as published at once. One file, replaced by one rename, so the head and the report never come from two runs. The identity hashes the review target, the base, the base-policy commit, the Stryker version and the installation identity, with the identity version 3; the head and the mutate entries are not in it.

The leave is the host's decision for the run, `StaticRunInput.headCode`, which the check task takes from `WriterTrust`. A run reuses the partition only when the recorded leave equals its own. A partition with any other value, or none, starts cold. The ancestor test is `git merge-base --is-ancestor <judged> <head>`; any exit but 0 starts cold. Nothing else is guessed: what reruns is Stryker's to decide.

A run that starts cold says why in its notes. The reasons read:

- "the review asked for a cold run with --cold";
- "this review target has no earlier judged head";
- "the run that judged ... was trusted as ..., not as ...";
- "the last judged head ... is not in this head's history, which was rewritten".

The check records of a run and the verdict that read them are stored shapes. The checks document rose to version 4 and the verdicts document to version 9, so an older Melian refuses them rather than read a provisional record as a run; a reopen test reads what versions 3 and 8 wrote.

## What Stryker reruns, as read in its code

Melian still mutates the whole pull request's changed lines; Stryker's incremental mode decides which results stand. Stryker 10.0.0's `IncrementalDiffer` sits in `node_modules/@stryker-mutator/core/dist/src/mutants/incremental-differ.js`. It reuses a result only when all of these hold:

- The mutant's code is unchanged, by a text diff of the old and new file.
- For a killed mutant, a test that killed it is unchanged, by a diff of its test file, name and position.
- For a survivor or an uncovered mutant, no test was added to those that cover it. The dry run still runs the related tests to learn coverage, so only the mutant runs are saved.

A test with the real Stryker in `packages/pipeline/test/mutation-real.test.ts` proves it on four heads of one target. A change to line 50 runs line 50's two mutants and reuses line 10's survivor. A change to the test that kills line 50's mutants runs them again. A head that changes neither reuses all three. Each head still reports the line-10 survivor: Stryker reports reused mutants beside those it ran, so the review's result covers the whole pull request. A survivor whose line a later head takes out of the diff is dropped, because findings come only from changed lines.

## A whole-suite repeat starts from the earlier head

A related run that fails or reports `NoCoverage` repeats with the whole suite, and [the selection decision](2026-10-12-mutation-test-selection-asks-vitest.md) has the repeat discard the related run's results. It now starts from the last judged head's results instead of from nothing: the stage writes a second copy of the earlier report, and the repeat restores it. Without that, any head whose related run reported `NoCoverage` would run cold.

## The notes count what was reused

"Stryker reused 1 of 3 mutant result(s) from bb98d3366f87, the last judged head, and ran 2." The counts come from Stryker's "Incremental report" log line, read from the attempt that decided the result. The head's tests write to the same log, so the counts are a note and decide nothing.

## What still holds from the superseded paragraphs

The head's tests never see the cache: the run writes staged copies in its scratch. Melian publishes after a successful run, only if no later review has taken the revision (`holdsAuthority`). The published report must be a regular file within 16 MiB, not a symlink, and parse as JSON; otherwise the partition keeps what it had. Reads refuse symlinks and files over the bound, with 1 KiB more for the partition's wrapping. An unreadable, oversized or malformed partition is removed before Stryker starts. The scratch sweep removes dead partial writes and keeps completed partitions. The installation identity is unchanged: a digest of each lockfile the checkout has, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `bun.lockb`, the resolved versions of Stryker core, its Vitest runner and Vitest, the Node runtime version, and the selection version. Stryker reuses a kill by test identity and the linker supplies the checkout's dependencies, so a dependency change starts cold even at an identical head. A version-one or version-two partition is never read, and a reopen test reads one written by each earlier version's code.

## The limits of a provisional result

A provisional result is a guide for the next fix, not a judgement. These are the ways it can be stale, and the cold run is the remedy for each:

- A change Stryker's diff does not read. Stryker diffs the files it mutates and the test files it ran. A changed configuration, setup file, test helper, snapshot or fixture, or a Markdown file a test reads, such as a skill or a lens file, can change what a reused kill meant.
- A kill that depends on another mutated file. Stryker reruns a changed file's own mutants, not the mutants of other files whose tests reach it.
- A file named as a test that is fixture data, such as a golden's `*.test.ts`, is not a test Stryker runs.
- Reuse is per test file, not per test. Stryker's Vitest runner 10.0.0 reports no test position, so the differ gives every test a range from the file's start to its end, and any change to a test file changes every test in it. Example: the second round on this pull request reused 1 of 170 results. Its fix pass had added tests to `mutation-static.test.ts`, which kills most of the check's mutants.

## What it gives up, beyond the rerun decision

- A pull request reads policy from its base branch's tip, which moves whenever `main` takes a commit. Keying by the base-policy commit, as the rerun decision requires, makes the next push after such a move cold even when the merge base is unchanged. A branch range reads policy at its merge base and is not affected.
- The cold final run costs a full run per pull request. On a branch the size of [pull request #98](https://github.com/melian-agent/melian/pull/98)'s, that sits near the 7,200-second timeout.
- Concurrent runs of one target each publish their own head, with one rule. Problem: a run of an older head, such as one a crash left pending that a later review resumed, could finish after a newer head's run and put the older results back. The next head then reran everything the newer one had judged. Solution: a run never publishes over a partition whose head has its own head in its history, as the rerun decision requires. It replaces nothing, its own head, or a head in its own history.
- A head of another line, after a force-push, a run replaces only when that head was published before the run's task was made. The partition records when it was published, and the check task's input records when the task was made, durably, so a task a crash left pending keeps its own time when it resumes. A task of the old line made before the new line published is a late run, and leaves the new line's results. A caller that gives no task time never replaces another line.
- The read of the held head, the check and the rename happen under one lock, a directory made with `mkdir` beside the partition, so a newer head cannot publish between them. A lock older than two minutes is a crashed holder's. The next publish removes it only while it is still the lock it inspected, by its inode, and fails rather than wait for ever when it cannot remove it. A lock made in the moment between that second look and the removal can still go, which costs speed only: the partition never decides approval. The cost of the descendant rule falls on a branch rewound to an exact older commit: its run is not stored, so the next push after it starts cold too, once.

## The mutation decision's other clauses, restated

Choice: `static.mutation` runs Stryker on Vitest over the lines the head adds or edits, in the head's worktree. A mutant that survives, or that no test covers, becomes a P2 finding of rule `mutation/untested-behaviour`, with the mutator and the mutated text in its message and the nearest test file in its "What to do". `Timeout`, `RuntimeError`, and `CompileError` mutants are notes. The check is off by default and on in Melian's own `melian.yaml`, in the `full` tier only. Stryker 10.0.0 is an exact-pinned root dev dependency of this repository. It runs from the reviewed checkout's own install, and Melian carries no copy. Its 161 packages should not ride into every install, so a checkout without Stryker records a skip that leaves the review not reviewed, and `melian doctor` warns while the check is on. It runs the head's tests unconfined, only where the host allows the head, and a head it may not run leaves the review not reviewed. Lenses report `untested-behaviour` at their usual severity. When the maintainer adjudicates a round, a finding on code a fix pass wrote counts as advisory unless it guards a trust or durability property.

Problem: a guard counts as tested only when a test fails with it removed, and a lens can only read for that. Example: a function `if (age >= 18) return "adult"` with a test that asserts `typeof classify(30)` is a string passes, and so does every mutant of it. [The first decision](2026-10-07-tested-means-a-failing-mutation.md) records the cost: fifteen rounds on one pull request, 27 unproven guards found by one inventory pass. Solution: run the mutation and let the tool say which guards no test missed. On that example the check reports two findings, covering six mutants on lines 2 and 3, in 3 seconds; it reports none once the test asserts both sides of 18.

Settings in `stryker.config.json`, one line each:

- `testRunner: vitest` and `plugins`: the Vitest runner, loaded by name.
- `vitest.related: true`: after the initial run, only tests related to the mutated file run for each mutant.
- `vitest.configFile: vitest.stryker.config.ts`: the repository's Vitest configuration plus `strykerTestNames`. Stryker 10.0.0 picks the tests that cover a mutant by a regular expression of their names joined with spaces, and Vitest 5 matches it against names joined with " > ", so a test inside a `describe` never matched. The mutant ran no test and survived: 380 of 456 mutants on this branch's own change, and the same 27 of 31 on one file. The plugin lets each space match either separator. A repository on Vitest 5 needs it until a Stryker release supports Vitest 5.
- `coverageAnalysis: perTest`: a mutant runs only the tests that cover it.
- `reporters: [json]`: the JSON report is the only output; no HTML, no dashboard, no clear-text.
- `inPlace: true`: mutate the files of the throwaway worktree. Stryker's sandbox copy rewrites `tsconfig` files with `ts.parseConfigFileTextToJson`, which TypeScript 7 lacks.
- `disableTypeChecks: false`: the default writes `// @ts-nocheck` into every `src` and `test` file, which shifted the line numbers a golden's test reads.
- `ignoreStatic: true`: a static mutant sits in code that runs when a module loads, so every one reruns the whole suite. On this branch's own change, 80 of 536 mutants were static and Stryker estimated they would take 84% of the run's time, which on an 8 minute 26 second suite is hours. They come back `Ignored`. The cost is that a changed top-level constant or regular expression is not judged, and a changed authentication pattern or permission table is exactly that. The trade-off is in `stryker.config.json`, a policy file that a maintainer reads. The maintainer chooses this per path, like the line budget. One P3 advisory `mutation/unmutated` notice per run counts lines omitted by each reason, budget and `ignoreStatic`, and combines both when both apply. A mutation the configuration excludes by name stays a note.
- `concurrency: 4`: four test processes. Two took 3,535 seconds on a branch of 1,359 changed source lines and overran the 3,600 second timeout at 1,678 lines, with Stryker's own process idle at 0% CPU while its workers waited on child processes. Four finished the same 1,616 mutants in 2,681 seconds on a 12-core host, which leaves the lenses and the host their cores.
- `timeoutMS: 30000` and `timeoutFactor: 2`: how long a mutant's tests may run before the mutant counts as a `Timeout`.
- `dryRunTimeoutMinutes: 20`: the initial run used to execute the whole suite, which took 8 minutes 27 seconds to 9 minutes 38 seconds on this repository with two workers, so 10 minutes left no room. Melian's runner now overrides it with `static.mutation.timeout` in whole minutes, rounded up, after the related run on [pull request #98](https://github.com/melian-agent/melian/pull/98) hit the 20 minutes; the committed value applies only to a hand-run Stryker.
- `cleanTempDir: always`: no `.stryker-tmp` left behind.

Melian sets the mutate ranges, the reporter, the incremental file, and `--inPlace` on the command line, so a head's configuration cannot widen or empty them. The head's `stryker.config.json` otherwise drives the head's run, as `biome.json` does, and a change to it is a policy change. So is a change to what that configuration loads: `vitest.stryker.config.*`, any `vitest.config.*`, and `scripts/stryker-test-names.*`, which decide how a test is named and selected. They raise `policy-change-review` at the analyser severity. This does not stop a trusted writer's own tests from faking kills, since a test can assert nothing and pass; the trust gate on the writer remains the real control, and the policy notice only makes the configuration change visible.

The bound is 2,000 changed production lines, `static.mutation.maxLines`. Stryker's cost is one initial run of the related tests, plus a test run for each mutant. A compiler fallback runs the whole suite. This repository's suite took 8 minutes 27 seconds for the initial run, and a mutant of 21 on one 26-line range finished in about 30 seconds more. A 2,000-line change yields on the order of 2,000 to 4,000 mutants. At a few seconds a mutant on two workers, that is hours. So 2,000 is a ceiling, not a target, and the timeout of 3,600 seconds in `melian.yaml` ends a run well before it. A change past the bound has a share of every file mutated. Problem: taking the first `maxLines` lines in path order let an author spend the bound on harmless files that sort early and leave a risky file, last in path order, unjudged, and a note about it was not a finding. Solution: each file gets a share of the bound in proportion to its changed lines, rounded down, and the lines left over go to the largest remainders, ties in path order. A file keeps at least one line while the bound has one for each file. Example: files `a` and `b` of 10 changed lines and `z` of 2, with a bound of 11, mutate 5, 5, and 1 lines. Budget and `ignoreStatic` omissions share one P3 advisory `mutation/unmutated` notice per run, counting lines by reason and naming the budget. The maintainer chose both policies. Timeout still raises its P2 finding for acknowledgement. I chose proportion over a list of trust and durability paths because a list is repository policy this check would have to know, and a change can route around any list by naming; proportion needs no knowledge of the repository. The bound counts changed lines, which is a coarse guard on wall time, and the timeout is the real one: a run past `static.mutation.timeout` records a skip with its reason, not a failure, and the finding it raises names every changed file, those past the bound too.

What it gives up:

- Wall time. The initial run executes the related tests before any mutant, so the check takes minutes on a small change, and it delays the review that waits on it. It stays out of the fast tiers.
- Only changed lines. A mutant is judged by the line it starts on. An old line whose behaviour the change altered from elsewhere is not mutated. A deletion-only hunk adds no line, so a deleted guard is not seen.
- Only the head. The base is not mutated, so there is no baseline to diff and no `pre-existing` finding.
- Vitest only, and TypeScript production files only. A test, fixture, golden, declaration, config file, or `dist` file is never mutated.
- One finding per line. Mutants on a line merge, and the message names the first.
- Survivors that code outside a test also reaches. Under `ignoreStatic`, Stryker runs a mutant that is covered both inside tests and outside any test, such as in a `beforeAll` hook, a `describe` body, or at module level, against the covering tests only. Problem: a test that asserts on a value computed in `beforeAll` is not run, so a mutant that test kills reads `Survived` with every other test passing. Example: a `beforeAll` that calls `grade(50)` and an `it` that asserts on the result; the mutant of `>= 50` is reported `Survived` with one test run, and `Killed` with `ignoreStatic: false`. Two survivors of round two had this symptom, killed by hand and `Survived` in the check; they were fixed before the cause was reproduced, so this is the mechanism reproduced, not one confirmed on those two mutants. Solution for the check: the report marks such a mutant `static: true`, and the finding for a survivor with that flag says so and tells the author to move the call into the test. The plugin is not the cause: parametrised names from `it.each` and `describe.each` reach Stryker as the strings Vitest reports, and a nested `describe` holding `it.each` kills its mutant with the plugin.
- Dismissals that do not follow a review to the real model. `melian dismiss` writes to the changeset's storage, and a review that runs on a scripted model (`MELIAN_TEST_SCRIPT`) keeps its storage in a `scripted/` directory apart from a real-model review's. A finding dismissed after a scripted round, such as an equivalent mutant, reappears in the next round on real routes, and `dismiss` cannot reach it until that round's head is the checked-out `HEAD`. Follow-up: share dismissals between the two stores, or let `dismiss` name the store.
- Equivalent mutants. Stryker reports some survivors that no test could kill. They are P2, which acknowledges and does not block.
- A head's own tests run, unconfined, where the host allows the head. A head that fails its tests fails the initial run, and the check fails closed. The head's test code can also write the report, so the check is only as trustworthy as the head's writer, which is why the guard decides whose head runs. The run's file-size limit is 1 GiB, not the 16 MiB of a static tool's report: Melian's own cache tests write 128 MiB archives, and the 16 MiB limit ended their processes with SIGXFSZ and failed the initial run.

The one skip that lets a review go on. A skip is not in `checks.allowSkip`, so by default it leaves a review not reviewed. The review grants leave itself for one skip of `static.mutation`: a change with no production TypeScript lines, where the check looked and found nothing to judge. Problem: the first version matched the reason text with regular expressions, and the head's own content decides the reason. Solution: the record carries a typed `cause` (`noProductionLines`, `headNotAllowed`, `timeout`, or `unmutated`), and the review decides leave on the cause alone; a record with the right words and no cause has none. The first three versions also gave leave to a run past its timeout, to a head the host would not run, and to a host with no sandbox. [The unconfined decision](2026-10-14-static-checks-run-unconfined.md) took those away: a configured static check that did not run leaves the review not reviewed. A timeout still raises one P2 finding of rule `mutation/unmutated` at the first changed line, naming every file whose changed lines were not judged. The no-production-lines leave holds only when no changed file with added or edited lines is production TypeScript: a TypeScript file outside `test/`, `tests/`, `*.test.*`, `*.spec.*`, `fixtures/`, `dist/`, the golden and verifier corpora, and declaration files, which hold no behaviour. A `.config.ts` can hold logic, so it counts as production. A tool loads it to run the mutants, though, and Stryker is not asked to mutate it. A change that edits only such files gets the cause `unmutated` and no leave. When other files are mutated the run goes ahead, and each file set aside raises a P2 `mutation/unmutated` finding at its first changed line beside a note. Three kinds of file are set aside: a configuration file, a file that sends process signals, and a path with a comma, which Stryker's `--mutate` list cannot name. Problem: the first version left only the note, so a well-tested neighbour turned an unjudged `.config.ts` from not reviewed into a clean run. A TypeScript production file that git calls binary, or whose name is not UTF-8, lists no changed lines, so it is not in that count. The check finds it among the revision's files. It raises a `mutation/unmutated` finding for it and gives the skip the cause `unmutated`. A deletion-only change adds no line and so is not counted.

Whose code runs. This is the first check that executes head code: Biome, tsc, and Enola read the head's files and configuration but never run its JavaScript, while Stryker executes the head's test files, setup files, and `vitest.config.*`. The first design ran it inside a sandbox Melian built, seatbelt on macOS and bubblewrap on Linux, behind a writer-trust gate. That sandbox is archived at the tag `archive/sandbox-boundary-r5` and does not land. The command now runs as an ordinary child process with `PATH`, `HOME`, `TMPDIR` and `LANG` and no other variable the Melian process holds. The host decides whether a head may run at all. It allows the reviewer's own checked-out commit and a head a writer pushed to the base repository; a fork's head waits for milestone 3's credential-free job. [The unconfined decision](2026-10-14-static-checks-run-unconfined.md) records that guard, the timeout, and what it gives up; [the head-writer decision](2026-10-12-trusted-writer-requires-base-repository-head.md) records how a writer is read. A writer's tests can still read the reviewer's files and fake a kill; the `forged-mutation-kill` guardrail below is a warning, and the guard is the control.

The worktree's `node_modules` omits `.cache`, `.vite`, and `.vite-temp`, so the head's tests write none of them into the checkout through a link. The run happens in a linked worktree of the clone, as Biome's and tsc's do, so a test that asks git about the tree it runs in sees the clone's history and refs.

A mutation task also answers to the review that asked for it. Problem: a task a crash left pending keeps the trust it was created under, and a newer review that revoked trust made a different run key. The pending task then resumed, ran the head's tests, and wrote findings into the revision's slot. Solution: a run that asks for `static.mutation` records itself as the revision's owner in the checks document, in a commit that creates no task. Then it aborts the live mutation tasks of other runs, and only then starts its own. A mutation task checks the owner before it runs head code and again in the commit that writes its findings, and ends `aborted` when another run owns the revision. A document written before this change has no owner and retires nothing. A run that asks again for an identity that lost the revision starts a new task, since the old one ended aborted. Every known tier records its run key as the revision’s mutation owner, including a tier without the check, so an older task cannot resume under superseded policy. The same durable commit retires the old authority; abortion follows before the new task starts. Cost: trust that flips between two values reruns the suite each time.

What the head's own text can hide. Stryker marks a mutant `Ignored` for three kinds of reason. Problem: the first version raised a finding for every `Ignored` mutant on a changed line, and `ignoreStatic` ignores static mutants by design, so this branch's own run produced 36 findings no maintainer could act on, and the branch never converged. Solution: a line whose mutants `ignoreStatic` skips contributes once to the run’s single P3 advisory `mutation/unmutated` notice, combined with budget omissions and counted by reason. A mutant the configuration excludes by name is a note naming the lines, because that file is a policy file whose change gets `policy-change-review`. The check does not read `statusReason` to tell them apart, because a `// Stryker disable` comment can carry any text, including the exact sentence a setting gives, and the head writes the comment. Round three of this pull request showed the forgery. The check reads what the head's text cannot write: the report's own `config`, which Stryker fills from the options it ran with, and the mutant's `static` flag and mutator name. A mutant is ignored by configuration when `config.ignoreStatic` is true and the mutant has `static: true`, which contributes to the advisory, or when its `mutatorName` is in `config.mutator.excludedMutations`, which is the note. Every other `Ignored` mutant is a finding of rule `mutation/ignored-mutant`, P2, one per line, naming the line and the reason Stryker gave. That reason is the head's text and is only shown, such as a `// Stryker disable` comment, an ignorer plugin, an absent reason, or a wording a later Stryker changes. A comment that disables a mutant the configuration would ignore anyway is treated as the setting's, since the setting decided it. Off the changed lines an ignored mutant is nothing. A `forbidden-patterns` rule in the root `melian.yaml` also flags the `Stryker disable` comment on added lines of source files; its paths leave out `test/`, `*.test.*`, and `*.spec.*`, where a test that quotes the phrase would trip it. Stryker reads each `--mutate` entry as a glob, so each glob character in a path is escaped, and a requested file that produced no mutants gets a note.

Lenses report `untested-behaviour` at their usual severity. When the maintainer adjudicates a round, a finding on code a fix pass wrote counts as advisory unless it guards a trust or durability property. The convention belongs to the maintainer’s adjudication in [AGENTS.md](../../AGENTS.md#validation). Nothing in the pipeline applies it.

Mutator scope. Melian excludes `StringLiteral` in `stryker.config.json`. A changed command flag or message string is a configuration change; tests of the command judge its behaviour. Excluded mutants on changed lines remain configuration-ignored notes. The configuration is policy and its changes still receive policy review.

Process lifetime. A crashed macOS reviewer left Stryker and its workers alive. A supervisor starts the command paused, watches Melian's pid and start time every 100 ms, and every tick records each descendant of the command with its start time, in a control directory the head's code cannot write. The mutation task records the control directory, the supervisor and the root durably before it releases the command. When the command exits, or Melian disappears, the supervisor sends SIGTERM to each recorded process that still has its recorded start time, waits up to a second, then sends SIGKILL. Recovery and authority retirement do the same from the durable record and the supervisor's file, before replaying or ending the task. Signal rule: Melian never signals a negative pid, 0, -1 or a process group, in source or tests, and never signals a pid it did not see as a descendant of its own command. An earlier version killed a process group; a group id of 1 made that `kill(-1)`, which ended every process the user owned and took the session down. Fakes prove the guards: a fake process table and a fake `kill` record the calls. One real-process test starts a throwaway controller, kills it by its own pid, and checks that the recorded pids are gone. Cost: a process that starts and orphans itself within one 100 ms tick is not recorded, and a start time has one-second resolution.

Forged kills. The `forged-mutation-kill` guardrail is a warning, not a gate: a P2 forbidden-patterns finding that a maintainer acknowledges, and a trusted writer's test can still fake a kill in ways no pattern sees. The control is the host's guard on whose head runs. Two further changes narrow the gap. Vitest and Stryker setup files, `vitest.setup*`, `vitest.stryker.setup*` and `stryker.setup*`, are now policy files: a change to one raises `policy-change-review` at the analyser severity, P1, because the head's copy decides what a kill is. A repository with setup files under other names lists them in `guardrails.policy-change-review.files`.

Cold budget. The cold run of 1,678 changed lines took 2,489 s under the 3,600 s timeout, 1.48 s per line, so 3,600 s admits about 2,400 lines at that rate and any slower suite overran it. Aim: a cold run under 40 minutes (2,400 s) with a fifth to spare, so 1,920 s. 1,920 / 1.48 = 1,294 lines; the repository's `static.mutation.maxLines` is 1,250, the largest multiple of 50 inside that, about 31 minutes. Lines past it yield one P3 advisory `mutation/unmutated` notice per run, naming their count and the budget. A test holds the value and checks that 1,300 would break the spare. The product default of 2,000 is unchanged: it suits suites faster than this one, and a repository sets its own.

Authority survives a policy key returning. A replacement check parent owns the revision through its fresh task ID, committed with its creation. Its children carry that authority. Every earlier child, including one from an earlier parent with the same policy key, remains retired. Takeover writes a retirement token before aborting pending children; a crash there cannot revive them.
