# A deleted guard stays with correctness

Choice: `correctness`'s hand-off to `removed-behaviour` leaves it a deleted rethrow or error branch, even when a `catch` the change wrote now swallows the failure, but no longer a deleted throw as such. A deleted guard, a check that refused an input before an operation ran, is `correctness`'s as well as `removed-behaviour`'s: `correctness` reports what the refused input now does, and `removed-behaviour` reports the lost invariant.

Why: Problem: [pull request #42](https://github.com/melian-agent/melian/pull/42)'s commit 917be2e rewrote the hand-off as "Leave a deleted throw, rethrow, or error branch to it", while [the boundaries decision](2026-10-04-lens-backlog-boundaries.md) keeps a removed guard with both lenses and `correctness-deleted-guard` expects both. Example: that golden deletes `if (!Number.isInteger(port) || port < 1 || port > 65535) throw new Error(...)`, a guard whose refusal is a throw. In [run 8](../../packages/evals/runs/2026-10-05-live-goldens-8.md) `correctness` read the deleted throw as `removed-behaviour`'s and reported nothing, in six passes with Melian's overrides and without them. Solution: the hand-off names a rethrow and an error branch, which carry a failure someone else raised, and says a deleted guard stays `correctness`'s too. Three passes of `correctness-deleted-guard` then found both expected findings each time, and three passes of `removed-behaviour-dropped-error-path` drew `removed-behaviour`'s `dropped-error-path` alone each time, so the deleted rethrow still has one owner. The built-in `correctness` version moves from `c22842327fa3` to `05037e7ba4a2`.

Supersedes: 2026-10-04-lens-backlog-boundaries.md, in its sentence that a deleted throw is `removed-behaviour`'s `dropped-error-path` alone when `removed-behaviour` runs.
