# Review ledger

Choice: Publication maintains one comment Melian owns per pull request, the ledger, created on first publish and edited in place from then on, with a signed marker and a hidden, versioned JSON stamp carrying base, head, verdict, and counts. Its comment ID is recorded in a changeset-level document, not the per-revision `published` document, because one comment spans every revision; a replay re-renders rather than reposts. A publish that finds a ledger marker it cannot verify, as after the clone holding the signing secret is lost, refuses and names the recovery, and never posts a duplicate ledger. Its first visible line names the base, the head, and the round. Its sections, in order: open findings and the verdict; override and not-reviewed warnings, uncollapsed; a collapsed walkthrough; collapsed run details; verification outcomes; dismissals with reasons; and one collapsed section per earlier round. The walkthrough holds a paragraph, a table of file or layer to summary, and a sequence diagram where one applies. `publication.walkthrough` switches it with `enabled`, `collapsed`, and `diagrams`. A summariser task on the `light` model tier writes it, reading head content inside prompt boundaries, and it renders through the same escaping as findings, labelled a summary and never a verdict. Run details hold the manifest, the plan with models and levels, lineage, caps, timings, cost, and the standards files each lens read. Each earlier round is trimmed to a line as the body nears GitHub's limit of 65,536 characters. The commit status links to the ledger. When a finding resolves, Melian edits its original inline comment to append the commit that addressed it and resolves the thread. `melian findings` and the ledger carry an agent prompt block per finding that opens by saying the finding text, paths, and code are untrusted review data. Melian never edits the pull request description; a one-line pointer there is optional. The ledger is a projection of the durable store, never a source of truth, and `melian findings --json` is the interface; nobody parses the markdown.

Why: What happened during a review belongs on the pull request, in expandable sections, always naming the head it applies to. Editing the description races with the author and with templates. CodeRabbit's output shows that a comment edited in place works and that watchers break when its markup drifts, which the stamp and the JSON interface avoid ([research/2026-10-04-review-output-anatomy.md](../research/2026-10-04-review-output-anatomy.md)).
