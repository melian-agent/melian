## The maintainer's rulings [Building Melian]

1. The delta is "any changed code that wasn't covered by the checks at the level configured for it". A round reviews exactly the delta. When the delta is empty and nothing above advisory is open, the review is valid.
2. A delta can pass. "Any series of reviews that together cover the full diff at the configured level for the files in the diff, are a valid review." The earlier rule that only a full round passes goes.
3. A later milestone's pull-request agent, on GitHub Actions, must be able to continue a pull request whose earlier rounds ran locally with a differential review.
4. The coverage ledger is the shared store's purpose: a durable document in Melian's store, in the local SQLite store in milestone 2 and on milestone 3's `melian/state` branch, shared between writers and the agent. The ledger comment on a pull request is a human view only, never an input.
5. On 2026-10-24: Stryker leaves the hot path entirely, and there is no cold final run. Mutation evidence comes from a decision drafted in parallel, "mutation evidence by enumeration and verification": `melian mutants list` and `melian mutants verify`, language adapters, and verification records that apply a mutant and run the named test. This file names the interface the ledger needs from it and designs no verification.

## Problem [Building Melian]

Every round reviews the whole pull request again, whatever the fix pass changed. On 2026-10-22 and 2026-10-23, every fix pass on pull requests [#162](https://github.com/melian-agent/melian/pull/162), [#165](https://github.com/melian-agent/melian/pull/165), [#167](https://github.com/melian-agent/melian/pull/167), [#168](https://github.com/melian-agent/melian/pull/168), [#171](https://github.com/melian-agent/melian/pull/171), [#172](https://github.com/melian-agent/melian/pull/172) and [#174](https://github.com/melian-agent/melian/pull/174) was followed by a full round of 15 to 70 minutes. [Pull request #174](https://github.com/melian-agent/melian/pull/174) took five rounds of about 35 minutes for fixes of under 50 lines each. A full round also samples, so it can miss the few lines that changed, and the convergence rule that the last round is full costs a whole round at the end of every pull request.

The earlier design kept every full round's cost at the end: a delta round could never approve. The rulings above take a different view. What a review covers is a fact about lines, lenses and levels, and a store can hold that fact. Once it does, the question "has this diff been reviewed at the configured level" has one answer whatever rounds produced it.

## Choice [Melian's flow]

Melian keeps a coverage ledger per changeset, a Pi Durable document, `melian.coverage`, in the changeset's storage. For each changed line of the diff from the base to the current head, and for each check the tier names, it says which round covered the line, at what level, and under what identity. The delta is every changed line that no round covers for some check that applies to it. `melian review` reviews exactly the delta: the first round's delta is the whole diff, a round after a fix pass covers what the fix changed, and a round whose delta is empty spends nothing. A review is valid when the ledger shows an empty delta and nothing above advisory is open. `melian review --cold` ignores the ledger and reviews the whole diff.

## Coverage [Melian's flow]

A changed line is a line a hunk adds at the head, keyed by its file and line at the head, or a line a hunk removes from the base, keyed by its base file and line at the base. The base is fixed for a changeset, so a removed line never moves between heads; an added line does. Both kinds are reviewed: the `removed-behaviour` lens reads deletions.

A changed line at the current head is covered for a check by a round when all of these hold:

1. **Same base, policy and standards.** The round reviewed the same base commit under the same policy fingerprint and, for a lens, the same standards. The policy fingerprint is the run identity's: the configuration and policy source the checks ran under and Melian's tool pins; mutation coverage carries the inputs its verification records name instead. A different base, tier, or `melian.yaml` voids every line's coverage from that round. A changed lens definition, which changes the lens's `name@version`, voids that lens's coverage alone. A changed standards file voids the coverage of every lens whose recorded standards paths include it, and of every lens with no recorded paths. A changed verifier version voids no line, and re-judges every carried finding its level verifies.
2. **The line maps unchanged.** Melian diffs the round's head and the current head with the review's own diff flags and rename detection, and moves each added line by the hunks before it. A line inside a hunk's old range, or in a file git calls deleted, or an insertion inside a cited range, is uncovered again. A removed line is covered when the current diff still removes it; a line the delta restores leaves the diff. A renamed file is tracked under both its old path and its new one, as the review-coverage record takes `oldPath ?? path`, so coverage follows the rename.
3. **Every lens that applies reviewed it at the required level.** For each lens whose coverage the line's file lies in, the round delivered the line to that lens and the lens's record is `ran`, at a level at or above the required level. The required level is the lens's band floor at the path, which is `careful` for a pull request or a range reviewed from a revision until a calibrated decider answers triage, as [triage as built](2026-10-05-triage-as-built.md) sets. A record that is `ended`, `failed`, or `skipped` without leave covers nothing for its files. A lens delivered a line when the change prompt rendered the hunk holding it for that lens, or a `read_file` or `search` result carried it, as the review-coverage artifact counts reads. The prompt can omit hunks past its 200 KiB cap, and today `ChangePrompt.renderInput` renders nothing when one file exceeds it: a 210 KiB file beside a small one gave 399 bytes, cut. The delta prompt renders the hunks that fit, smallest file first; a hunk no prompt can carry is delivered by reads alone, and the gap names it. One exception keeps a dependency bump mergeable: a hunk over the cap in a file `analyserConfigNames` or a lockfile pattern names is covered by the policy-change notice, as `ignoreStatic` lines were, because the notice already asks the maintainer to read the file and [pull request #160](https://github.com/melian-agent/melian/pull/160)'s Vite bump would otherwise block every merge under the required status. Any other such hunk stays a gap, which the maintainer closes by narrowing the lens's paths or by `--cold` with reads.
4. **Every finding on the line is settled at the current head.** A finding citing the line, by its own location or any evidence location at the head, has a sighting at the current head's key: new, carried, or restated, with its verification where its level verifies, and adjudication resolved it. A finding the carry could not map, or a changed finding the verifier did not judge, leaves its line uncovered.

Static checks cover what they ran over. Guardrails, Biome, tsc and Enola run over the whole range in every round, as today; their coverage is the whole diff at the head they ran on and needs no mapping.

Mutation coverage comes from verification records, as the mutation-evidence decision defines them; Stryker leaves the hot path and there is no cold final run. The interface the ledger needs from that decision, per mutant: its identity, the claim made for it (killed by a named test, or equivalent), the verification result, and the head and inputs it was verified at. A changed production line is covered for mutation when every mutant on it has a verification record whose head maps the line unchanged and whose inputs still hold, with the result killed, or a maintainer's dismissal. Every line a mutation finding cites is re-checked at each head, a survived mutant and one no test covered alike: today a `NoCoverage` mutant's finding (`packages/core/src/mutation.ts` lines 25 and 304) would vanish at the next head, since nothing re-sights it; under the ledger its line is uncovered until a verification record or a dismissal answers it. A stale kill, where a later change to `b.ts` revives a mutant in `a.ts` that an earlier record killed, is that decision's to settle through the inputs a record names; the ledger voids what the record's inputs say is void and judges nothing itself.

## The ledger [Melian's flow]

What the review-coverage artifacts already prove, per lens and file: which lines each lens received through `read_file`, which it matched through `search`, at the head or the base, which changed hunks those reads intersected, and which enclosing declarations the delivered lines fell inside, computed from durable transcripts and keyed by the run's nonce and conversation IDs, stored by content ID in the cache with the ID on the lens's check record. They prove delivery, not judgement, and they count tool reads alone: the hunks the change prompt rendered are not in them, and the cache is outside the state branch. They are also stored only by `CallerContext.recordCoverage`, which returns nothing without Enola graph parts (`packages/pipeline/src/callers.ts` line 152), so a repository without `static.enola` has none. The ledger therefore reads the lens transcripts and the stored prompts itself, through `ReviewTranscript` and the lens task's input, and never depends on the artifact or the graph cache.

The ledger adds, as a document in the changeset's storage, versioned and migrated like the others:

- per record: the coverage producer's identity, an explicit algorithm version for the mapping and the delivery computation, beside the document version. It is part of the record's compatibility identity: a record whose producer identity differs from the reader's is void for the coverage it carries, or recomputed from the originating rounds' transcripts and prompts where those are still in the store. A changed mapping or delivery rule bumps the identity, never only the shape;
- per round: the base, the head, the tier, the policy source and fingerprint, each lens's standards paths, the Melian version, the writer leave, and the mapping from the last decided round's head to this head as the hunks git reported;
- per round and lens: `name@version@level`, the required level per file, the record's status, and per changed file, under its old path and its new one when renamed, the hunks the prompt rendered and the lines tool reads delivered;
- per round and whole-range check: that it ran over the whole range at this head;
- for mutation: a reference to each verification record by mutant identity, with the lines each mutant sits on at this head;
- per round: the coverage it carried from the last decided round after mapping, in this head's coordinates, so reading coverage at a head needs one record and never walks the chain.

The Melian version is recorded for diagnosis and voids nothing by itself; the identities above decide. Two Melians whose documents differ in version already refuse one store, and two whose producer identities differ recompute or void, as above.

`melian findings` and `melian review` show a coverage gap under a `Coverage` heading: complete, with the rounds that cover the diff, or incomplete, with each check and the files and lines it has not covered, each with its reason: changed since round `rN`, lens ended at its budget in `rN`, never delivered, finding unsettled. JSON carries `coverage: { complete, rounds, gaps: [{ check, file, lines, reason }] }`.

## A round over the ledger [Melian's flow]

1. **Intake** reads the ledger at the last decided round, by mint order as `Round.compare` orders rounds, since a crashed round has no ledger record and a resumed earlier round decided after a later one does not stand. It maps that coverage to the new head, applies the voids below, and computes the delta per check. The delta is fixed in the round's input, so a resume after a crash reviews the same lines.
2. **Static checks** run over the whole range, as today. Mutation evidence is read from verification records, never produced by the round: Stryker leaves the hot path, the incremental partition and the `provisional` status go with it, and there is no cold final run. The `provisional` status stays readable in stored shapes for records an earlier build wrote, and covers nothing.
3. **The carry** copies the last decided round's lens sightings, per producer, into the new head's key under the producer prefix `carried/`, mapped by git. It copies lens sightings only; a deterministic check re-sights at the new head. A `--cold` round deletes the `carried/` producers at its key. A carried copy keeps one `carried/` prefix and the first round's `carriedFrom`, however many heads it crosses, so membership counts it once. A finding whose cited lines no delta hunk touched carries with its lines moved and its verification copied. A finding whose cited line a delta hunk overlaps, or whose file git calls deleted, is changed, never gone: a heavily edited rename reads to git as a delete and an add. A changed location maps to the first new-side line after the hunk it overlapped, or to the file's last line when no line follows, which covers a moved block and a pure deletion. The carry never lowers, drops or reopens a finding; cause and trigger are computed again against the full range at the new head through `Revision.classifyCause`, so the reopen rule compares the right hunk.
4. **Lenses** run on the delta. A lens runs when its delta is not empty: a changed line in a file its coverage reaches that it has not covered. Its prompt renders the delta's hunks as the change under review, then the rest of the diff as context within the cap, smallest file first, then the whole diff's file list, and the read tools read the new head or the base as today. It runs at the higher of the last decided round's level and its default within its band. Triage does not run on a delta, so a fix pass cannot steer a lens to `quick`. Escalation applies. A lens whose delta is empty records a skip with leave, "nothing uncovered", as a lens with no paths does. Every carried finding of a lens that runs is handed to that run through escalation's hand-off, with its file, lines and rule: it restates by the same ID or the same file and rule on overlapping lines, refutes by ID, or leaves it. A restated finding counts once and keeps the stricter of its carried and restated severity. A lens's refutation of a carried finding is a verifier candidate, never a drop: escalation's hand-off drops a refuted quick finding today (`review.ts` lines 553 to 556, `lens-tools.ts` lines 948 to 950) with no verifier, and the trust floor reads verifier verdicts alone (`packages/core/src/findings.ts` line 1481), so a drop there would take a protected claim past the floor. The refutation is stored as a verification on the carried claim, which is what `trustFloor` reads, not as a lens-side list, and a protected claim keeps its trust-floor minimum through it. At a level with `verify: false` a refutation never lowers anything: the claim stays as carried. Only the trust floor or the verifier lowers a carried finding. A changed finding its lens did not restate goes to the verifier against the new head. An untouched finding its lens left keeps its verification. The built-in lenses' paths are `**`, so each runs on every delta and is handed every finding it owns, including one a fix elsewhere, such as a new test, answers. A lens a repository narrowed to paths outside the delta does not run, and its findings stay as carried until it does or the maintainer dismisses them.
5. **Cause** is classified against the full range, base to new head, never against the delta. A fix that reverts a line to its base text leaves base code, so a finding there is `pre-existing`.
6. **The verifier** judges the delta's new sightings and the changed findings that reach it. Untouched carried findings keep their judgement unless the verifier version changed.
7. **Adjudication** decides the whole head: carried and new findings together, the manifest, and one more check record, `review.coverage`. It is `ran` when the ledger after the round covers every changed line for every check that applies. Otherwise it is `skipped` without leave, naming the gaps, which leaves the review not reviewed. Melian writes it from the ledger at intake and from the round's own records. Nothing the head writes reaches it. `review.coverage` joins every manifest without a tier entry, and a file naming it in a tier or in `checks.allowSkip` is refused when the file is read, in every layer the loader reads: the root `melian.yaml`, a nested one, `melian.local.yaml` and the user's configuration file, since `checkPreference` restricts only trust, comparison and route keys. A base `melian.yaml` with `checks: { allowSkip: [review.coverage] }` loads today and would make `Manifest.complete()` true over a gap.
8. **A repeat review** whose delta is empty under an unchanged identity attaches to the current decided round at the head and prints it, spending nothing, as a repeat review of the same base and head does today. `--rerun` runs the failed checks and lenses again. `--cold` reviews the whole diff from nothing and replaces the ledger's coverage of the head.

## The status [Melian's flow]

`melian/review` is `success` when the round's verdict has nothing above advisory open and `review.coverage` ran. An incomplete ledger makes the verdict not reviewed, so the status is `error` naming the gaps, as a check that did not run names itself. The merge-group job, `melian status merge-group`, is unchanged: it copies a writer's `success` with the reviewed-base suffix, and reads no ledger.

`melian publish "#N"` publishes the current decided round at the pull request's base and head. Its body and ledger comment say which lines the round reviewed, which rounds cover the diff, and any gap. A carried finding has a sighting at the head, so publication diffs it as still open and keeps its thread.

## Voids [Melian's flow]

Coverage from a round is void, in whole or in part, when:

1. **Base change.** The current revision's base differs from the round's. Voids all. A merge of `main` into a branch moves a three-dot range's merge base, and a retarget changes a pull request's base.
2. **Force push or rebase.** The round's head is not an ancestor of the current head, `git merge-base --is-ancestor` exits non-zero, or the round's head cannot be resolved. Voids all from that round, since nothing maps its lines.
3. **Merge commit.** `git rev-list --merges ^<round head> <head>` is not empty. Voids all. A merge brings in work its author did not write as a fix, and the round's context no longer describes the tree.
4. **Policy or standards change.** A changed `melian.yaml`, lens file, or analyser configuration, as `Revision.policyFiles` lists them, or a policy fingerprint that differs, voids all. A changed standards file voids the lenses whose recorded standards paths include it, and every lens without recorded paths.
5. **Review-identity change.** A different tier voids all. A different `name@version` for a lens voids that lens. A required level raised above the level a lens ran at voids that lens for the files where it rose. A different verifier version re-judges carried findings and voids no line.
6. **A failed lens.** A record that is `failed`, `ended`, or `skipped` without leave covers nothing for its files.
7. **A check record that did not run.** A verifier record that failed, hit `toolFailed`, timed out, or was skipped as untrusted covers nothing, and so does a verification record whose result is anything but killed. A `provisional` record from an earlier build covers nothing: its kills rest on an earlier head's report.
8. **A dependency, configuration or test change.** A changed lockfile, `package.json`, `tsconfig*.json`, Vitest configuration or test setup file voids every static check's coverage; the whole-range checks rerun anyway, so this voids mutation coverage whole. So does a changed file the mutation check's own production-file rule, `production()` in `packages/pipeline/src/mutation-paths.ts`, rejects, which catches `test/`, `tests/`, `fixtures/`, a colocated `*.test.ts`, `__tests__/`, snapshots, goldens and declaration files alike. A production test helper, as `packages/pipeline/src/testing.ts` is, passes that rule, so a change to it is in the delta and re-verified; it voids the mutation coverage of each production file whose verification records name a test that imports it. The cost: a fix pass that adds a test voids mutation coverage whole, and the verification records for every mutant are checked again against their inputs. A delta that removes a line a `forged-mutation-kill` finding cited voids mutation coverage whole. What a record's inputs cover, and so what narrows this void, is the mutation-evidence decision's.
9. **A delta over its bound.** A delta over 1,000 changed lines, `review.delta.maxLines` in the base's `melian.yaml`, or over half the full diff's changed lines, runs cold: the carried coverage is small and the carried findings' context is stale. The 1,000 and the half are guesses; the build records each round's size in the progress log and the maintainer may tune them.

A void never deletes a ledger record; it leaves the lines uncovered at the current head, and the round reviews them. A cold round covers everything it reviews, so after it the ledger is whole again.

## Round identity and attachment [Melian's flow]

A round's key comes from one method over base, head and scope: `Revision.key(scope)`, where the one scope today is the whole diff and gives `<base>..<head>`, and a scope the method does not know is refused. No caller builds `${base}..${head}` for a round. Problem: `revisionKey()` has 54 call sites across the packages' sources, and some build or split the key by hand: `revisionKey` itself in `packages/pipeline/src/findings.ts` at line 115, the publisher migration in `packages/pipeline/src/publish.ts` at line 583, which compares `${round.base}..${round.head}`, and its `endsWith(`..${head}`)` at line 294, `legacyRound`'s split on `..` in `rounds.ts`, and the display sites in `packages/cli/src/commands.ts` at line 538, `packages/core/src/comparison.ts` at line 733, `packages/core/src/comparison-export.ts` at lines 26 and 70, and `packages/github/src/ledger.ts` at lines 158 and 321. Solution: build 0 routes every site, storage and display alike, through the method before any ledger is written, with a display form beside the key, and a `forbidden-patterns` guardrail refuses a new `${...}..${...}` in source files.

The earlier design put the scope in the key so a delta round could never stand for a full one. Under the ledger the key carries no approval: a review passes only when the ledger's delta is empty, which no key can forge. So every round at a base and head shares the key `<base>..<head>`, as the rounds decision built it, and its scope, the lines it reviewed, is recorded on its `melian.rounds` record and in the ledger. Rounds at one head are told apart by their IDs, `r<n>`, as today. A `--cold` round at a head replaces its producers' sightings at that key, as `--rerun` does.

`melian.rounds` rises to version 2: each record gains `scope`, the changed lines the round reviewed per check, and `coverage`, the ledger record's ID. A version-1 record reads as a round whose scope is unknown, which covers nothing, so a review after the upgrade starts from the whole diff. Minting, keeping and freezing follow the rounds decision. Step 23's builds 3 and 4 also raise `melian.rounds`; the second to land takes the next version, migrates both earlier shapes, and adds a reopen test from a fixture the first's real code recorded, as the parallel-bump learning in `AGENTS.md` requires.

A carried sighting is stored at the head's key under its own producer with the prefix `carried/`, as `carried/lens.correctness@<version>@careful`, beside its copied verifications, and records `carriedFrom: <round ID>`. The findings document rises to version 11. The merge step treats a carried sighting as one more sighting, so a carried finding never loses to a weaker new one.

## Membership [Melian's flow]

A `#N` write with no `--round` goes to the newest decided member round at GitHub's head whose ledger covers the head. With none, it refuses and lists the rounds. The rounds decision's rule 2 said a range round's exact-base test "excludes a delta round"; a round over the ledger stores the pull request's base and head, so it is a member like any round at that head, and those words are withdrawn. Export and stats label each member's scope. A carried finding counts once per pull request, at the round that first sighted it, which its one `carriedFrom` names across every head it crossed. An identical snippet the delta inserts earlier in a file renumbers a carried finding's ID; a later round's finding with the same file, rule and normalised snippet, differing only in occurrence, counts as the same finding.

## Sharing, for milestone 3 [Melian's flow]

The ledger is why the state branch exists. The CLI pushes a changeset's storage to `melian/state` when it publishes, as [the design](../design/hosts.md#github-actions) planned; the Actions host opens it, computes the delta from the ledger, runs that, and publishes under the GitHub App.

- **Who may write the branch.** Writers, by push permission on the repository, and the App. Nobody else can push to it, and a fork's workflow has a read-only token.
- **What a writer's local run records there.** Everything its storage holds for the changeset: rounds, sightings, verifications, check records, the ledger, dismissals, the signing secret and the ledger comment ID. A local run records no status and no acceptance. **What only the agent records:** for each local round it relied on, the head writer and permission it verified and the policy fingerprint it recomputed; and the published status under the App.
- **A write from a stale or other build is refused by document versions, as today.** Pi refuses a document newer than its code, and a migration reads an older one. An agent pinned to an older Melian than a writer's refuses the store and reads not reviewed, naming both versions; the maintainer pins the two in step. A writer's older Melian refuses a store the agent upgraded and says to upgrade.
- **One writer per changeset.** The state index on the branch holds a lease per in-progress changeset: run ID, heartbeat, attempt count. A writer's `melian review "#N"` fetches the index first, refuses to run when it finds a live lease, and otherwise takes the lease by pushing the index before it runs; the agent's job waits on it as the concurrency group makes it wait on another job. The lease is race-free only because a writer that fetches a live lease refuses rather than pushes; two pushes decide the race by `--force-with-lease`, and the loser refuses. A refused push means another writer or the agent moved the branch. The refused run keeps its results locally and publishes nothing to the branch. To resume, the writer fetches, takes the branch's copy of the changeset's storage as authoritative, and runs `melian review` again: the ledger on the branch decides the delta, so only the work the branch lacks is redone. A lost push costs the delta, never the pull request. The storage cannot be merged: Pi's JSONL log is one writer's history.
- **What the agent accepts from the store.** A round whose head is a commit of the pull request in the base repository, pushed by an identity that held write, maintain or admin permission, read through [the head-writer rule](2026-10-12-trusted-writer-requires-base-repository-head.md), and whose policy fingerprint equals the one the agent computes from the base commit itself. It recomputes the mapping and the voids from git; it never trusts a stored claim of coverage at a head it did not map. A round whose head GitHub no longer holds, after a force push, is void: the agent cannot verify its writer. A verification record's inputs include the runtime it ran on, so an agent on another Node than the writer's voids every local mutation record and verifies again; that is a cost of keeping the inputs honest, and the maintainer pins the two in step. **What it never accepts:** anything derived from a fork's head; a round whose policy source was `worktree`, which only a range review on a checked-out commit has; a status; a round under `trust.writers: false`, where the agent runs the full gate.
- **No signature or attestation now.** Writers are trusted by decision, and the branch is writable by writers alone, so a signed record would prove what push permission already proves. Git records who pushed each commit of the branch, and the agent reads the pusher through GitHub, as it reads a head's. Milestone 3 binds the required check to the App; a record the agent did not rely on sets no status. An attestation becomes worth having when `trust.writers: false` must still let some local record count, which no ruling asks for.

## What this gives up [Building Melian]

- The residual, in degree. A defect whose cause spans a delta hunk and an earlier-covered line is read together only when the earlier line reaches the delta prompt as context, within the cap, or a read fetches it. N full rounds sample the unchanged context N times; delta rounds sample it once, at the round that covered it, and then as context when the cap allows. A defect in unchanged code that no round's reading reached waits for a maintainer or a `--cold` round. A single full round carries the same risk once: a lens samples what it reads, and the ledger records delivery, not understanding. The cross-round golden in the plan demonstrates this; it does not measure it.
- A fix pass that adds a test voids mutation coverage whole, and every mutant is checked again against its verification record's inputs. Whether a forged or stale kill survives that is the mutation-evidence decision's to settle; `--cold` remains the reviewer's choice for lenses.
- A ledger record from an earlier mapping or delivery algorithm is recomputed from its rounds' transcripts and prompts where the store still holds them, and void where it does not.
- The whole-range static checks run in every round, minutes each.
- A narrowed lens that does not run leaves its carried findings as they were.
- A lost push to the state branch repeats the delta.

## For the attack [Building Melian]

Trust and blocking rules, numbered for the attacker. Each is to be broken as written.

1. A review passes only when `review.coverage` ran, which Melian writes from the ledger and the round's own records; nothing the head writes reaches it. `review.coverage` joins every manifest without a tier entry; a file naming it in a tier or `checks.allowSkip` is refused in every layer the loader reads, nested and preference files included.
2. The delta is computed from the ledger at the last decided round, by mint order, and git at intake and fixed in the round's input; a resume reviews the same lines; a resumed earlier round decided later does not stand.
3.
