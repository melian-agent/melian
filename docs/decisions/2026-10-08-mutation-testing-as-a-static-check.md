# Mutation testing runs as a static check on the changed lines

Choice: `static.mutation` runs Stryker on Vitest over the lines the head adds or edits, in the head's worktree. A mutant that survives, or that no test covers, becomes a P2 finding of rule `mutation/untested-behaviour`, with the mutator and the mutated text in its message and the nearest test file in its "What to do". `Timeout`, `RuntimeError`, and `CompileError` mutants are notes. The check is off by default and on in Melian's own `melian.yaml`, in the `full` tier only. Stryker 10.0.0 is an exact-pinned root dev dependency of this repository. It runs from the reviewed checkout's own install, and Melian carries no copy. Its 161 packages should not ride into every install, so a checkout without Stryker records a skip that leaves the review not reviewed, and `melian doctor` warns while the check is on. It runs the head's tests only inside a sandbox, and a host without one records a skip with leave. A lens-raised `untested-behaviour` on code a fix pass wrote resolves to advisory, unless it guards a trust or durability property.

Problem: a guard counts as tested only when a test fails with it removed, and a lens can only read for that. Example: a function `if (age >= 18) return "adult"` with a test that asserts `typeof classify(30)` is a string passes, and so does every mutant of it. [The first decision](2026-10-07-tested-means-a-failing-mutation.md) records the cost: fifteen rounds on one pull request, 27 unproven guards found by one inventory pass. Solution: run the mutation and let the tool say which guards no test missed. On that example the check reports two findings, covering six mutants on lines 2 and 3, in 3 seconds; it reports none once the test asserts both sides of 18.

Settings in `stryker.config.json`, one line each:

- `testRunner: vitest` and `plugins`: the Vitest runner, loaded by name.
- `vitest.related: true`: after the initial run, only tests related to the mutated file run for each mutant.
- `vitest.configFile: vitest.stryker.config.ts`: the repository's Vitest configuration plus `strykerTestNames`. Stryker 10.0.0 picks the tests that cover a mutant by a regular expression of their names joined with spaces, and Vitest 5 matches it against names joined with " > ", so a test inside a `describe` never matched. The mutant ran no test and survived: 380 of 456 mutants on this branch's own change, and the same 27 of 31 on one file. The plugin lets each space match either separator. A repository on Vitest 5 needs it until a Stryker release supports Vitest 5.
- `coverageAnalysis: perTest`: a mutant runs only the tests that cover it.
- `reporters: [json]`: the JSON report is the only output; no HTML, no dashboard, no clear-text.
- `incremental: true`: Stryker keeps results in a file. Melian points `--incrementalFile` into the repository cache, partitioned by base-policy commit and writer trust, so a later run can reuse it.
- `inPlace: true`: mutate the files of the throwaway worktree. Stryker's sandbox copy rewrites `tsconfig` files with `ts.parseConfigFileTextToJson`, which TypeScript 7 lacks.
- `disableTypeChecks: false`: the default writes `// @ts-nocheck` into every `src` and `test` file, which shifted the line numbers a golden's test reads.
- `ignoreStatic: true`: a static mutant sits in code that runs when a module loads, so every one reruns the whole suite. On this branch's own change, 80 of 536 mutants were static and Stryker estimated they would take 84% of the run's time, which on an 8 minute 26 second suite is hours. They come back `Ignored`. The cost is that a changed top-level constant or regular expression is not judged, and a changed authentication pattern or permission table is exactly that. The trade-off is in `stryker.config.json`, a policy file that a maintainer reads, but a note under that decision went unseen, so each file with changed lines that hold such mutants is one `mutation/unmutated` finding naming the lines, at P2 for a maintainer to acknowledge. A mutation the configuration excludes by name stays a note.
- `concurrency: 2`: two test processes, so the check does not starve the lenses and the host.
- `timeoutMS: 30000` and `timeoutFactor: 2`: how long a mutant's tests may run before the mutant counts as a `Timeout`.
- `dryRunTimeoutMinutes: 20`: the initial run used to execute the whole suite, which took 8 minutes 27 seconds to 9 minutes 38 seconds on this repository with two workers, so 10 minutes left no room.
- `cleanTempDir: always`: no `.stryker-tmp` left behind.

Melian sets the mutate ranges, the reporter, the incremental file, and `--inPlace` on the command line, so a head's configuration cannot widen or empty them. The head's `stryker.config.json` otherwise drives the head's run, as `biome.json` does, and a change to it is a policy change. So is a change to what that configuration loads: `vitest.stryker.config.*`, any `vitest.config.*`, and `scripts/stryker-test-names.*`, which decide how a test is named and selected. They raise `policy-change-review` at the analyser severity. This does not stop a trusted writer's own tests from faking kills, since a test can assert nothing and pass; the trust gate on the writer remains the real control, and the policy notice only makes the configuration change visible.

The bound is 2,000 changed production lines, `static.mutation.maxLines`. Stryker's cost is one initial run of the related tests, plus a test run for each mutant. A compiler fallback runs the whole suite. This repository's suite took 8 minutes 27 seconds for the initial run, and a mutant of 21 on one 26-line range finished in about 30 seconds more. A 2,000-line change yields on the order of 2,000 to 4,000 mutants. At a few seconds a mutant on two workers, that is hours. So 2,000 is a ceiling, not a target, and the timeout of 3,600 seconds in `melian.yaml` ends a run well before it. A change past the bound has a share of every file mutated. Problem: taking the first `maxLines` lines in path order let an author spend the bound on harmless files that sort early and leave a risky file, last in path order, unjudged, and a note about it was not a finding. Solution: each file gets a share of the bound in proportion to its changed lines, rounded down, and the lines left over go to the largest remainders, ties in path order. A file keeps at least one line while the bound has one for each file. Example: files `a` and `b` of 10 changed lines and `z` of 2, with a bound of 11, mutate 5, 5, and 1 lines. Each file with lines left out is one P2 `mutation/unmutated` finding naming its line ranges. I chose proportion over a list of trust and durability paths because a list is repository policy this check would have to know, and a change can route around any list by naming; proportion needs no knowledge of the repository. The bound counts changed lines, which is a coarse guard on wall time, and the timeout is the real one: a run past `static.mutation.timeout` records a skip with its reason, not a failure, and the finding it raises names every changed file, those past the bound too.

What it gives up:

- Wall time. The initial run executes the related tests before any mutant, so the check takes minutes on a small change, and it delays the review that waits on it. It stays out of the fast tiers.
- Only changed lines. A mutant is judged by the line it starts on. An old line whose behaviour the change altered from elsewhere is not mutated. A deletion-only hunk adds no line, so a deleted guard is not seen.
- Only the head. The base is not mutated, so there is no baseline to diff and no `pre-existing` finding.
- Vitest only, and TypeScript production files only. A test, fixture, golden, declaration, config file, or `dist` file is never mutated.
- One finding per line. Mutants on a line merge, and the message names the first.
- Survivors that code outside a test also reaches. Under `ignoreStatic`, Stryker runs a mutant that is covered both inside tests and outside any test, such as in a `beforeAll` hook, a `describe` body, or at module level, against the covering tests only. Problem: a test that asserts on a value computed in `beforeAll` is not run, so a mutant that test kills reads `Survived` with every other test passing. Example: a `beforeAll` that calls `grade(50)` and an `it` that asserts on the result; the mutant of `>= 50` is reported `Survived` with one test run, and `Killed` with `ignoreStatic: false`. Two survivors of round two had this symptom, killed by hand and `Survived` in the check; they were fixed before the cause was reproduced, so this is the mechanism reproduced, not one confirmed on those two mutants. Solution for the check: the report marks such a mutant `static: true`, and the finding for a survivor with that flag says so and tells the author to move the call into the test. The plugin is not the cause: parametrised names from `it.each` and `describe.each` reach Stryker as the strings Vitest reports, and a nested `describe` holding `it.each` kills its mutant with the plugin.
- Dismissals that do not follow a review to the real model. `melian dismiss` writes to the changeset's storage, and a review that runs on a scripted model (`MELIAN_TEST_SCRIPT`) keeps its storage in a `scripted/` directory apart from a real-model review's. A finding dismissed after a scripted round, such as an equivalent mutant, reappears in the next round on real routes, and `dismiss` cannot reach it until that round's head is the checked-out `HEAD`. Follow-up: share dismissals between the two stores, or let `dismiss` name the store.
- Equivalent mutants. Stryker reports some survivors that no test could kill. They are P2, which acknowledges and does not block.
- A head's own tests run, inside the sandbox below. A head that fails its tests fails the initial run, and the check fails closed. The head's test code can also write the report, so the check is only as trustworthy as the head's writer, which is why the trust gate stays beside the sandbox. The run's file-size limit is 1 GiB, not the 16 MiB of a static tool's report: Melian's own cache tests write 128 MiB archives, and the 16 MiB limit ended their processes with SIGXFSZ and failed the initial run.

Skips that let a review pass. A skip is not in `checks.allowSkip`, so by default it leaves a review not reviewed. The review grants leave itself for four skips of `static.mutation`, as it does for a lens with no paths, and keeps the reason in the record: a change with no production TypeScript lines, a run past its timeout, a writer that is not trusted, and a host with no sandbox (cause `noSandbox`). Problem: the first version matched the reason text with regular expressions, and the head's own content decides two of the four. Its tests set how long Stryker runs, and its file names decide which lines count as production, so a head could move logic into a `.config.ts`, or slow its suite, and read as `passed`. Solution, in three parts. First, the record carries a typed `cause` (`noProductionLines`, `untrustedWriter`, `noSandbox`, `timeout`, or `unmutated`), and the review decides leave on the cause alone; a record with the right words and no cause has none. Second, a timeout keeps its leave, but the run also raises one P2 finding of rule `mutation/unmutated` at the first changed line, naming every file whose changed lines were not judged, so a maintainer acknowledges what went unmutated. The record is still `skipped`; the finding rides beside it. Third, the no-production-lines leave holds only when no changed file with added or edited lines is production TypeScript: a TypeScript file outside `test/`, `tests/`, `*.test.*`, `*.spec.*`, `fixtures/`, `dist/`, the golden and verifier corpora, and declaration files, which hold no behaviour. A `.config.ts` can hold logic, so it counts as production. A tool loads it to run the mutants, though, and Stryker is not asked to mutate it. A change that edits one gets the cause `unmutated`, no leave, and a note in the run when other files are mutated. A TypeScript production file that git calls binary, or whose name is not UTF-8, lists no changed lines, so it is not in that count. The check finds it among the revision's files. It raises a `mutation/unmutated` finding for it and gives the skip the cause `unmutated`. A deletion-only change adds no line and so is not counted, as before. The check is advisory in nature, and a required status must not error on the speed of a host. Every other skip, such as a disabled check or a checkout without Stryker, still leaves the review not reviewed.

The trust rule for any check that executes head code. This is the first check that does: Biome, tsc, and Enola read the head's files and configuration but never run its JavaScript, while Stryker executes the head's test files, setup files, and `vitest.config.*`. A fork's pull request could add a test that reads `~/.pi/agent/auth.json` or `melian.secrets.yaml` and sends it out. Three layers apply, and a new check of this kind must take all three:

1. The sandbox. The command runs where it can reach no remote host and read only what the run needs.
2. The command gets a `HOME` and `TMPDIR` inside the run's scratch directory, and no variable the Melian process holds beyond `PATH` and `LANG`.
3. The check runs only when the head's writer is trusted. The committed `trust.writers` policy must hold, as it does for publication, and the host must vouch for the writer. For a pull request, its author needs write, maintain, or admin permission on the repository. A range review is the reviewer's own to run only when its head is the checked-out commit. Problem: `melian review main...pr12` on a fetched fork head took the range's trust, though the same code reviewed as `#12` would skip. Solution: any other range gets an untrusted writer, which records the same skip. Otherwise the check records a skip with leave whose reason says the writer is not a trusted one, and runs nothing. A review that names no writer gets the skip too, and `trust.writers: false` skips it for every writer.

The writer-trust gate stays as the second line behind the sandbox, not in its place. The sandbox stops a test from reading what it should not and sending it out. It does not stop a trusted writer's test from passing without testing, and the gate is what answers for that.

The sandbox. Problem: layers 2 and 3 alone left head test code with the reviewer's user and the open network. Example: a test that calls `os.userInfo()`, reads `auth.json` from the real home, and posts it with `fetch`. Solution: `Sandbox`, in `packages/pipeline/src/sandbox.ts`, wraps the Stryker command, with no route off the machine. A host without a working sandbox runs nothing.

- macOS runs `sandbox-exec` with a profile Melian writes to the run's scratch directory. It starts from `(deny default)`. It allows process execution and fork, signals within the sandbox, and `sysctl-read`. It allows reads of the system libraries and frameworks Node needs to start, the Node installation, the checkout's installed dependencies (its `node_modules` and each workspace package's), and scratch, which holds the worktree. It allows writes under scratch, and to `/dev/null`. It names one Mach service, `com.apple.bsd.dirhelper`, which only returns the per-user temporary directory the `/usr/bin/git` shim looks for, and no unix-domain socket. The command cannot reach the ssh agent or the Docker daemon, or ask launchd to start a process outside. It may also read and write the shim's `xcrun_db` cache file in that directory, and nothing else there. Its network is loopback only: it may accept and make connections to localhost, and nothing else. Problem: Stryker 10 starts a logging server on a port it picks, and its workers connect to it, so a profile with no network at all failed the first real run with `listen EPERM`. Cost: on macOS loopback is the host's, so head test code can reach a service the reviewer runs on localhost, which the Linux backend does not allow. It can stat the directories above its allowed paths and nothing else outside them. The reviewer's home, the checkout's shared `.git` directory, and every other path are unreadable.
- Linux runs `bwrap --unshare-all --die-with-parent --new-session`. It binds `/usr`, `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64`, `/etc/alternatives`, `/etc/ld.so.cache`, `/etc/hosts`, `/etc/nsswitch.conf`, `/etc/passwd`, `/etc/group`, and `/etc/localtime` read-only where the host has them, and no other part of `/etc`. It mounts a private `/proc`, `/dev`, and `/tmp`. It binds the Node installation and the checkout's installs read-only, binds scratch read-write, and starts in the worktree. `--unshare-all` gives it a network namespace of its own, whose loopback reaches only the command's own processes, and it sees no home.
- The worktree holds a git repository of its own while the command runs. Problem: a linked worktree's `.git` file names the checkout's git directory, which the sandbox hides, so a test that asked git about the tree it runs in failed with "not a git repository", and Melian's own doctor test did. Solution: Melian swaps the file for a directory made by `git init`, fetches the head commit at depth 1 from the checkout, detaches HEAD there, and reads the tree into the index. The command sees one commit and none of the checkout's configuration, remotes, hooks, or history, and then Melian puts the link back so git can remove the worktree. A test that needs history or another branch fails the initial run, and the check fails closed.
- The command's environment tells it where it is. `MELIAN_SANDBOX` names the backend, so a test of a sandbox, which cannot start another inside this one, skips. `DEVELOPER_DIR` names the developer tools on macOS, so the `git` shim runs the real one without asking `xcode-select`.
- The command's `PATH` holds only what it can read: the developer tools' `bin` on macOS, so `git` is the real one and not the `xcode-select` shim, Node's `bin`, and the system's. A program elsewhere, such as `gh` under Homebrew, is missing and not an `EPERM`. The worktree's `node_modules` omits `.cache`, `.vite`, and `.vite-temp`, which the checkout's install would link to places the command may not write.
- Detection runs the backend: `sandbox-exec` on a trivial profile on macOS, `bwrap` on a read-only bind of `/` on Linux. A host that forbids nested sandboxes, such as Melian run under another seatbelt, or unprivileged user namespaces has no sandbox. The check then records a skip with the cause `noSandbox`, which has leave, and says so in its reason. `melian doctor` names the backend it found, or warns while the check is on and none works. The backend is part of the run's identity, so installing one runs the check again.
- Cost: on a host without a sandbox the check never runs and the review can pass without it. `melian doctor` is the signal. The CI workflow installs bubblewrap and proves it works before the checks, and the Linux test skips where `bwrap` is absent.

The maintainer decided this on 2026-10-08.

What remains after the sandbox. The sandbox confines what head test code can read, send, and write. A trusted writer's tests can still read the worktree and the checkout's installed dependencies, and they can fake kills. A test that asserts nothing passes. A setup file that throws only while Stryker runs a mutant passes the dry run and makes every mutant read `Killed`. Two controls answer for that. A built-in `forbidden-patterns` rule, `forged-mutation-kill`, flags the variables Stryker sets for the active mutant in any JavaScript or TypeScript file a head adds or changes, whatever the repository's `melian.yaml` says. It reports at P2, the severity of a policy change, because a P1 would also raise the severity of every unscannable line in a TypeScript file. A CLI test reviews a scratch repository whose setup file forges kills, with the check on, and requires that the review is not clean. The writer-trust gate is the other control, as above. The sandbox is also not a container: it shares the host kernel, so a seatbelt or namespace escape is outside this decision. The check stays off by default and is for repositories whose writers are already trusted with the reviewer's machine.

A mutation task also answers to the review that asked for it. Problem: a task a crash left pending keeps the trust it was created under, and a newer review that revoked trust made a different run key. The pending task then resumed, ran the head's tests, and wrote findings into the revision's slot. Solution: a run that asks for `static.mutation` records itself as the revision's owner in the checks document, in a commit that creates no task. Then it aborts the live mutation tasks of other runs, and only then starts its own. A mutation task checks the owner before it runs head code and again in the commit that writes its findings, and ends `aborted` when another run owns the revision. A document written before this change has no owner and retires nothing. A run that asks again for an identity that lost the revision starts a new task, since the old one ended aborted. A run whose tier lacks the mutation check takes no ownership. Cost: trust that flips between two values reruns the suite each time.

What the head's own text can hide. Stryker marks a mutant `Ignored` for three kinds of reason. Problem: the first version raised a finding for every `Ignored` mutant on a changed line, and `ignoreStatic` ignores static mutants by design, so this branch's own run produced 36 findings no maintainer could act on, and the branch never converged. Solution: a mutant that `ignoreStatic` skips becomes one `mutation/unmutated` finding per file, and a mutant the configuration excludes by name is a note naming the lines, because that file is a policy file whose change gets `policy-change-review`. The check does not read `statusReason` to tell them apart, because a `// Stryker disable` comment can carry any text, including the exact sentence a setting gives, and the head writes the comment. Round three of this pull request showed the forgery. The check reads what the head's text cannot write: the report's own `config`, which Stryker fills from the options it ran with, and the mutant's `static` flag and mutator name. A mutant is ignored by configuration when `config.ignoreStatic` is true and the mutant has `static: true`, which is the finding, or when its `mutatorName` is in `config.mutator.excludedMutations`, which is the note. Every other `Ignored` mutant is a finding of rule `mutation/ignored-mutant`, P2, one per line, naming the line and the reason Stryker gave. That reason is the head's text and is only shown, such as a `// Stryker disable` comment, an ignorer plugin, an absent reason, or a wording a later Stryker changes. A comment that disables a mutant the configuration would ignore anyway is treated as the setting's, since the setting decided it. Off the changed lines an ignored mutant is nothing. A `forbidden-patterns` rule in the root `melian.yaml` also flags the `Stryker disable` comment on added lines of source files; its paths leave out `test/`, `*.test.*`, and `*.spec.*`, where a test that quotes the phrase would trip it. Stryker reads each `--mutate` entry as a glob, so each glob character in a path is escaped, and a requested file that produced no mutants gets a note.

The advisory rule: once this check runs, a lens that raises `untested-behaviour` on code a fix pass wrote is duplicating the mutation result with a guess. Its finding resolves to advisory unless the code guards a trust or durability property, where a survivor still matters whatever the tool says. The rule is a reviewing convention in [AGENTS.md](../../AGENTS.md#validation). Nothing in the pipeline applies it yet.

Supersedes: none. It builds the static check the [first decision](2026-10-07-tested-means-a-failing-mutation.md) promised and ends its note that every `untested-behaviour` finding keeps its severity.

Mutator scope. Melian excludes `StringLiteral` in `stryker.config.json`. A changed sandbox profile string or command flag is a configuration change. Tests cannot judge it line by line; the sandbox probes judge its behaviour. Excluded mutants on changed lines remain configuration-ignored notes. The configuration is policy and its changes still receive policy review.

Incremental results across runs. A per-run file threw away the test and mutant identities Stryker had learned. Runs now share `<cache>/mutation/<identity>/incremental.json`. `CacheLocation` keys the cache by repository under the existing state directory. The partition identity hashes the base-policy commit and the head writer's trust class. A missing writer counts as untrusted. A trusted run never reads an untrusted partition. An unreadable, oversized or malformed JSON file is removed before Stryker starts. The existing scratch sweep visits mutation cache partitions and removes dead partial writes; it retains completed reports. Seatbelt allows reads and writes in that one partition. Bubblewrap binds that directory read-write. Neither backend grants the rest of the cache. The host supplies writer trust through the same gate that decides whether head code may run.

Cost: an incremental report is trusted only within one writer-trust class and one base-policy commit. Head test code can change it inside its partition. This is cached evidence, not an independent verdict. Stryker compares test and mutant identities on reuse; policy or trust changes start a new partition.

Related tests. The whole-suite dry run took 7 minutes 58 seconds in the sandbox, before any mutant ran. Melian now starts from the changed production files it will mutate. Step 11's `CompilerGraph` resolves imports in a temporary project over the head's sources, tests and JavaScript, with `@melian-agent/source`. Reverse imports select every `.test.ts` and `.test.mjs` whose closure reaches a target. Literal Vitest setup files in the configuration's import closure are always included. Computed setup paths force the whole suite. `MELIAN_MUTATION_TEST_INCLUDE` carries the path of a JSON include list through the sandbox environment. `vitest.stryker.config.ts` reads it and replaces `test.include` after merging the base configuration; merging the arrays would silently retain the whole suite. The test-name plugin stays installed.

Bounds: at most 10,000 repository source files, 30 seconds, and a 512 MiB JavaScript heap for the compiler child. A missing source, compiler failure or bound hit falls back to the whole suite, with a note. When no test reaches any target, there is no dry run. Melian uses the checkout's Stryker instrumenter inside the same sandbox to enumerate the target mutants, honours excluded mutators, and reports uncovered mutants as `NoCoverage`. It does not start Stryker's runner. Cost: the compiler misses runtime paths it cannot resolve, such as a computed dynamic import or a spawned process. The fallback covers failed or bounded computations; the `NoCoverage` path exposes a target the graph finds no test for. Neither proves runtime reachability absent from the compiler.
