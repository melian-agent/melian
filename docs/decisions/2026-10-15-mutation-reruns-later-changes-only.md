# The mutation check reruns only what changed since the last judged head

Problem: `static.mutation` keys its incremental cache by the exact head commit, so every push starts cold over the whole pull request. A fix that touches one line pays for every mutant on the branch again.

Example: on [pull request #98](https://github.com/melian-agent/melian/pull/98), each new head re-ran about 1,050 mutants in 22 files. Round ten's cold run fitted inside the provisional 7,200-second timeout. Round twelve's took 8,466 seconds and read `not reviewed` for the timeout alone, though every lens and the verifier found nothing above advisory. The branch sat at the limit because each fix pass reset the cache, not because the fixes were large.

Choice: key the cache per pull request, and reuse it across that pull request's heads. The maintainer asked for it: once the mutation gaps of a changeset are found, rerun only the later changes, not the whole pull request.

- The partition is keyed by what stays fixed across a pull request's heads: repository, base-policy commit, installation identity, Stryker's version, the run's test-selection settings, and the review's target. The target is the pull request number for `#N`, and the canonical head ref name for a branch range. A range that names a bare commit has no target to share, and runs cold. The mutate entries change with every head, so they are a run's input and not part of the key.
- A run reuses the partition only when all of these hold. The partition's last judged head is an ancestor of the new head. The base and the installation identity are unchanged. The earlier run was trusted in the same way as this one: both a writer's head, or both vouched for with `--trust-head`, as each run's stored `WriterTrust` records.
- Stryker's incremental mode decides which mutants run again: those on lines changed since the last judged head, and those whose covering tests changed. Melian does not compute that set by hand.
- An earlier survivor on an unchanged line stays open as a finding until a change kills it or a maintainer dismisses it with a reason.
- A force-push that drops the last judged head, a base change, or an installation change starts cold, in a new partition.

Why per-head keying was chosen, and what changed: the first design ran heads inside a sandbox, behind a gate meant to admit heads Melian did not trust. A head's test code could change its own staged copy of the incremental file, so keying by exact head kept one head's results, honest or planted, from reaching another head's run. The maintainer then decided that static checks run unconfined and only for trusted heads, and that a mutation result is forgeable by the head's own tests, which write the report Stryker reads, with human review before merge as the control ([the unconfined decision](2026-10-14-static-checks-run-unconfined.md)). Reuse across heads does not authenticate the cached bytes; nothing does today, for one head or many. It carries a result forward only within one pull request whose every judged head was trusted in the same way, so a forged `Killed` in it could equally have been forged at the head that reads it.

What this gives up: a result planted by an earlier head of the pull request persists into later heads until the line or its covering tests change, where per-head keying would have dropped it at the next push. A mutant whose result depends on code Stryker does not see as changed, such as a test helper reached at run time and not by import, can keep a stale `Killed`. The coordinator asks for a cold run in a new partition before the queue when a branch's history was rewritten, or when a pull request changes who pushes to it. Reuse also depends on Stryker's incremental mode staying sound, a dependency's behaviour Melian pins and does not re-derive.

It is planned as step 22, the first step after [pull request #98](https://github.com/melian-agent/melian/pull/98), and is not built. Until step 22 lands, [the mutation decision](2026-10-08-mutation-testing-as-a-static-check.md)'s per-head partition stands. The pull request that builds step 22 adds a decision file that supersedes the mutation decision, replaces its cache clause with this one, and restates every other clause.
