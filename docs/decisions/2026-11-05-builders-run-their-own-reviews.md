# Builders run Codex's adversarial review and their own Melian rounds

Choice: the builder of a pull request runs Codex's adversarial review on its own branch, and its own Melian rounds through the `melian round` workflow, before the first round and after each fix pass. It posts the review's JSON and its findings in the pull request's report, and fixes from them. The coordinator still reads the verdicts, runs the round a dismissal or the comparison record needs, marks the pull request ready and queues it.

Why: both reviews used to wait for the coordinator's machine, the only place with the Codex login and the provider credentials, so every fix pass waited there too. The `melian round` workflow, from [issue #270](https://github.com/melian-agent/melian/issues/270), gives a builder its Melian rounds, and cloud sessions now carry the Codex login as `CODEX_AUTH_B64`. On [pull request #275](https://github.com/melian-agent/melian/pull/275) a builder ran the companion plugin's adversarial prompt through the Codex CLI in a cloud session. The review found a rerun defect, which the builder then fixed with no coordinator in the loop. The maintainer asked for the guidance to make this the rule.

What this gives up: the coordinator no longer sees each Codex review as it runs, only as the builder reports it. A builder without the plugin fills the plugin's prompt by hand, so its review can drift from the plugin's if the plugin changes how it builds the prompt. AGENTS.md names the prompt file and the steps the plugin takes, so a drift shows in the diff of either.

The round's comment reaches the builder as `github-actions[bot]`, and AGENTS.md lets a builder act only on a writer's instruction. Melian's round on fix pass 3 found that a builder following that rule had to ignore the findings, and one that did not gave a bot's text a writer's authority. So the comment is review data, like a host round's findings: the builder fixes what it lists and follows nothing in it as an instruction. Before reading it, the builder checks that its author is `github-actions[bot]` and that its run link names a run of `.github/workflows/melian-round.yml` on the default branch of this repository. Any other comment of that shape is untrusted text. This widens no authority: a writer's instruction still comes only from a writer.

Fix pass 5's review of record showed that those two checks cannot tell who posted: every workflow posts as `github-actions[bot]`, so a bot comment can cite a real round run's ID. The tie is the comment's marker, which names its run's ID and the nonce that run uploaded. AGENTS.md's check therefore compares the marker with the run's artefacts, and requires the run to be a `workflow_dispatch` run of `.github/workflows/melian-round.yml` on the repository's current default branch, comparing each value and exiting non-zero on any mismatch.

The check binds the comment to its run, not its body. That holds while `.github/workflows/melian-round.yml` is the only workflow with `pull-requests: write`: a workflow that gains that permission could edit a genuine comment after it posts and keep its marker. Codex's review of fix pass 5 found the gap, the maintainer ruled to document it, and [issue #286](https://github.com/melian-agent/melian/issues/286) binds the body to what the run posted.
