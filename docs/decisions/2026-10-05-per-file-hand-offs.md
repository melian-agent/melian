# Hand-offs hold per file

Choice: A lens hands a defect to a neighbour in the files the neighbour reviews among its own, and keeps it in the rest. When the neighbour reviews some of the lens's files, the lens's instructions name the neighbour, the defects it owns, and those files, quoted as the change's data, and tell the lens to leave those defects to it there and report them under its own rules in every other file. When the neighbour reviews every file, the instructions say so without a list, in the words they used before. When it reviews none, no hand-off renders. A list holds at most 40 files and 4 KiB; past either, the hand-off to that neighbour is left out, the lens keeps its defects in every file, and the lens's check record names the neighbour. A renamed file counts as one file: a neighbour selected through its old path covers its head path, and one over its head path covers its old path, so a rename never pushes a neighbour over every file into the listed form. The standards section keeps the stricter rule: a breach goes to `conventions` only when `conventions` reviews every file the lens reviews. Melian's own repository extends the built-in `correctness` and `removed-behaviour` at `.melian/lenses/correctness/LENS.md` and `.melian/lenses/removed-behaviour/LENS.md`, each with a `handoffs` entry for `durability` and nothing else, so both leave a write, an effect, a key, or a stored shape that goes wrong only with a crash, a restart, a replay, a resumed or superseded task, or a record an earlier run stored to `durability` on the files `durability` reviews.

Why: Problem: a hand-off rendered only when the neighbour reviewed every file the handing lens reviews, so a neighbour with narrower paths never received one. Example: `durability` reviews `packages/pipeline/src/`, `packages/github/src/`, and `packages/cli/src/`, and `correctness` reviews every file a Melian pull request changes, documents included. A hand-off from `correctness` to `durability` could not render in a pull request that also changed a document, which is nearly every one, so the boundary stayed one-sided, and in [the seventh live run](../../packages/evals/runs/2026-10-05-live-goldens-7.md) 20 of the 24 extras on `durability`'s goldens were `correctness`, `removed-behaviour`, or `trust-boundary` restating its defects. Solution: the hand-off holds file by file. A lens running without its neighbour still keeps every defect, so the `pre-push` and `comment` stages, which run `correctness` alone, lose nothing, and a lens beside a neighbour narrowed to fewer files keeps the defects in the files the neighbour leaves out, as the every-file rule meant to. A built-in lens cannot name a repository lens, since the built-ins ship to every user and `durability` exists only in Melian's repository; `extends` already layers `handoffs`, so the hand-off lives in Melian's overrides. The overrides set nothing else, so the body, rules, levels, and paths stay the built-ins', and only the version moves, because it hashes the hand-offs. The listed files are author-controlled paths, so they enter the system prompt inside the review's boundary, where the injection policy reads them as data. The cap exists because the change prompt's 200 KB bound does not reach the instructions: without it, a change of thousands of files under a narrower neighbour's paths would repeat every path in the system prompt, once for each such neighbour. Leaving the hand-off out rather than cutting the list keeps ownership exact, and costs only the duplicate reports the hand-off would have prevented. The standards section is left on the every-file rule because no shipped configuration narrows `conventions` and a per-file version would change its prompt for no measured gain; [the eighth live run](../../packages/evals/runs/2026-10-05-live-goldens-8.md) measures the change.
