# The walkthrough runs beside the lenses

Status: built for [issue #254](https://github.com/melian-agent/melian/issues/254).

Amends: [Spans time a review's work between tasks](2026-10-24-review-spans.md), its rules that one step is open at a time and that no span overlaps a task, for the walkthrough alone.

Amends: [A reasoning level per model tier](2026-10-19-tier-thinking-routes.md), its rule that the walkthrough's revision cache and rerun rules remain unchanged: a summary written on another light route or thinking level is written again.

Amends: [Pending walkthroughs do not spend retry attempts](2026-10-06-walkthrough-settled-attempts.md), its rule that the next review resumes an indexed pending walkthrough: a review harness aborts every live walkthrough as it opens, and an aborted walkthrough costs no attempt. Within one process, a pending task on the wanted route still resumes before the limit is checked.

Amends: [Resumed tasks unlock their stored providers](2026-10-08-resumed-task-credential-providers.md), its walkthrough clause: no walkthrough survives the harness's open, so none adds a provider to `ReviewHarness.resumedProviders()`.

## Problem

The walkthrough summarises the change for the reader. It needs the change, not the verdict, yet `melian review` ran it only after adjudication. Each round on 2026-10-26 and 2026-10-27 ended with 13 to 16 seconds of walkthrough and nothing else running, by the prepare spans of [pull request #206](https://github.com/melian-agent/melian/pull/206).

It waited for one reason: `summarizeReview` read the verdict's stored provenance. That told it the review was of a pull request, and which plan routed its light model. Adjudication writes that provenance, so started any earlier, the summariser found none and did nothing.

## Decision

- `reviewChangeset` takes an optional `lensesStarted` hook. It calls the hook once it has recorded its lens run in the review index and aborted any run that replaces, just before it waits for that run. A review that runs no lens never calls it.
- `melian review` starts the walkthrough from that hook, for a pull request without `--no-walkthrough`. It awaits the walkthrough after the review returns and before printing, and also before it closes storage, on every path. A review that fails before triage starts it once the review returns, as before.
- `summarizeReview` takes `origin` and `plan` from its caller. When `origin` is given, the two stand for the stored provenance: only a `pull-request` origin is summarised, and `plan`, or the configuration without one, routes the light model. A caller that passes no `origin` reads the stored provenance as before.

## Why

- At the lens run, not at the start or after triage, because `summarizeReview` calls `harness.resume()`, which starts every pending task. Until the review has recorded its lens run, the index still names any run a crashed review left, and that run passes every ownership check. Started then, the walkthrough could resume that run on a superseded plan, and it would spend tokens and write sightings before the review aborted it. Once the review has recorded its own run and aborted the replaced one, nothing stale is left to resume. Melian's design lens found the earlier placement, after triage, open to this.
- The host passes the plan the review is running under, the same object `reviewChangeset` stores in the provenance, so the summary still quotes the review's plan. A summary that a crash interrupted attaches to its task by revision on the next review, which passes that review's plan, as the provenance would.
- The summariser already stores a note for every failure and never throws, so a failed walkthrough still leaves the verdict and the exit code alone.
- The review's spans time its own steps, one at a time, so the walkthrough task now runs while they are open. That is the overlap this change is for, so the walkthrough task is the one task a span may overlap. Every other task still waits with no span open.
- The walkthrough's credential unlock is a span of its own, `unlock` under the parent `walkthrough`, recorded by `PrepareSpans.concurrent`. It may overlap any review step or task. `walkthrough` names no review step, so the ledger's preparation row, which sums the top-level spans, never adds the unlock's time to the review's own. Two rounds disagreed here: one found that timing the unlock under the open review step misattributed it, and the next found that leaving it untimed hid it. The maintainer ruled on 2026-11-08, in the builder's session, for a concurrent span. The next round found that a parentless span inflated the preparation row, and the maintainer ruled, the same day and in the same session, to give it the `walkthrough` parent.

- A walkthrough records the light route that wrote it, `provider/model@thinking`, in the verdict document's `walkthroughRoutes` beside it. A review whose plan routes the walkthrough to another model or thinking level writes it again, as `--rerun` would, so a verdict never pairs with a summary another plan's model wrote. Melian's design lens found that a review failing after its lenses start could leave such a summary; a successful review under one plan could already leave one for a later review under another. The maintainer ruled on 2026-11-08, in the builder's session, to bind the summary to its plan. A walkthrough an older Melian stored has no route and stands, and so does one whose light route has no credentialed model now. The verdict document goes to version 14 with it, so an older build refuses a store this one wrote, rather than rewrite a walkthrough and leave the other route's entry standing beside it. Codex's adversarial review found the skew, and the maintainer ruled on 2026-11-09, in the builder's session, for the bump. A walkthrough task writes only while the summary index still names it, so a second call that replaced it is never overwritten; Melian's design lens found the race.

- Publication posts a stored walkthrough only when the light route that wrote it is one of the light models, at the light thinking level, of the plan the revision's verdict was decided under. A re-review that dies after its lenses start can rewrite the walkthrough under a new plan while the earlier verdict stands. A change of lens selection already ends such a publish as a review in progress, since the replacement drops the index's adjudication, but a change to the light route alone leaves the selection, and the verdict, as they were. The review of record found the path, and the maintainer ruled on 2026-11-08, in the builder's session, for this check at publish. A walkthrough an older Melian stored without its route, or a verdict stored without a plan, posts as before. A walkthrough the check drops leaves the ledger the fixed note "No walkthrough available. Another light route wrote it.", so the section never sits empty; Melian finding 7dc6c29607b4ecff found it empty, and the maintainer ruled on 2026-11-08, in the builder's session, for the note.
- A repeat review attaches to a live walkthrough task only when it runs on the light route the review wants. Problem: the index named the task by revision alone. Example: a review under plan A started the walkthrough and died; a review under plan B attached to the pending task, which wrote A's summary and recorded A's route beside B's verdict. Solution: the review aborts a live task on another route, and the attachment commit refuses one, so it creates a task for B's route. Melian's design lens found the path, and the maintainer ruled on 2026-11-08, in the builder's session, to fix it here rather than in [issue #343](https://github.com/melian-agent/melian/issues/343).
- A walkthrough never outlives its process. `ReviewHarness.open` aborts every live walkthrough task, and an aborted walkthrough costs no attempt. Problem: each fix for a stale walkthrough left another way one resumes. Example: a review under plan A crashed during its walkthrough; the next review, under plan B, waited on its deterministic checks first, and that wait resumed every pending task, so A's walkthrough ran and could spend the last attempt before B's guard saw it. Solution: nothing from an earlier process is left to resume, so the summariser always creates its own task on the route it wants. Three rounds in a row found a new instance, so the builder raised the class, and the maintainer ruled on 2026-11-08, in the builder's session, to abort at open. A crash loses the one in-flight light request.

## What this gives up

- A review that fails after its lenses start can still store a walkthrough for the revision, where before it stored none. Publication reads a walkthrough only beside a decided verdict whose plan's light route wrote it, so nothing posts it beside another plan's verdict.
- The summariser's light model and triage's can now be asked at once. Credential commands still run once per process, because the store caches each read as a promise.
