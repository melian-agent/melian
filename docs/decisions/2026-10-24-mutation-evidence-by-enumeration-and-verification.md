## The maintainer's rulings

1. Remove Stryker from the hot path entirely. No cold final run, no mutation-only pre-round run, no periodic full sweep is required.
2. Build `--verify`: apply a mutant and run only the named test.
3. Make enumeration and verification extensible to any language.
4. Make enumeration and verification available to downstream Melian customers, so they can use them in their own builders' prompts.
5. For all Melian users, this repository and customers alike, the tests lens uses enumeration and verification.

## Problem

**[Building Melian]** `static.mutation` runs Stryker on every full round. It costs 15 to 70 minutes of host time, with an 8- to 19-minute dry run. Under load it made rounds read `not reviewed`, and a stopped run leaves locked scratch worktrees. Six enumeration-first passes on 2026-10-22 to 2026-10-24 left it nothing real to find: [pull request #168](https://github.com/melian-agent/melian/pull/168) fixes 1 and 2, [pull request #171](https://github.com/melian-agent/melian/pull/171) and its fix, [pull request #174](https://github.com/melian-agent/melian/pull/174), and [pull request #186](https://github.com/melian-agent/melian/pull/186). Every claim Stryker could check held. Before enumeration, hand inventories missed coverage, not accuracy: on [pull request #168](https://github.com/melian-agent/melian/pull/168) the builder covered 18% of 242 mutants, and all ten of Stryker's survivors sat in the rest. [Issue #177](https://github.com/melian-agent/melian/issues/177) holds the summary.

**[Melian's flow]** A builder's claim that a named test kills a mutant is checked today only by a whole Stryker run, or by hand. The `tests` lens reads for an untested behaviour and names "the mutation every test lets through" in prose. Nothing runs that mutation, so a verifier judges a guess against a guess. Enumeration covers TypeScript and JavaScript alone, through Stryker's instrumenter, so a repository in another language gets no mutation proof at all, as [issue #170](https://github.com/melian-agent/melian/issues/170) records.

Example: the `tests` lens reports "deleting the `attempts--` in `fetchWithRetry` passes every test". The verifier reads the tests and agrees it is plausible. Nobody deleted the line and ran the tests. On [pull request #116](https://github.com/melian-agent/melian/pull/116), the late rounds found such gaps one at a time, and each took a round.

## Choice

Mutation evidence is a record that a named test killed a named mutant at a named head, made by activating the mutant and running that test twice against it, between that test's leading and trailing shared baseline and inert runs, all from pristine state. Melian enumerates mutants deterministically, a builder or a lens claims which test kills each, and a verification run checks each claim. The `tests` lens receives the enumeration and backs each `untested-behaviour` finding with a probe that shows the mutant survives. Stryker leaves Melian's own tiers. `static.mutation` stays in the product as an opt-in audit.

### 1. The CLI **[Melian's flow]**

`scripts/enumerate-mutants.mjs` and `scripts/mutant-sample.mjs` fold into three commands. The capability lives in the packages, reachable from the CLI, because the skills only call the CLI.

- `melian mutants list <range|#pr> [--json] [--limit N] [--all]` enumerates the mutants of the changed production lines. It writes the inventory, version 2 below. `--limit` keeps today's default of 200 rows and reports the omitted count; `--all` lists every row. It runs no test and no head code: it reads committed source through git and instruments it in an empty scratch directory. For a pull request it fetches the head as `review` does. Exits `0`; `1` when the range cannot be resolved or no adapter handles the changed files; `64` for arguments it cannot read.
- `melian mutants sample <inventory>` prints the probes a classified inventory owes, by today's rule: every `new-test` and `equivalent` claim, then one probe per represented survivor class, mutator and file, then 20% of each file's remaining `killed` claims, rounded up. SHA-256 of the JSON tuple `[file, line, column, endLine, endColumn, mutatorName, replacement]` orders candidates and ties, lowest first, and the output prints each probe's hash so a reviewer reproduces it. An incomplete inventory, an unclassified claim, missing evidence or an unknown class label is refused. Exits `0`, `1` refused, `64` usage.
- `melian mutants verify <inventory> [--all] [--json] [--jobs N] [--out <path>] [--trust-head]` applies each sampled mutant, or with `--all` every mutant that carries a claim, and runs the named test. It records each outcome in the inventory, which it rewrites at `--out`, by default the inventory's own path, and in the repository's mutation cache as a verification record. It exits `0` when every verified claim held and no `new-test` claim remains. It exits `1` when a claim did not hold or a `new-test` claim still waits for its test, listing each. It exits `2` when verification could not run: no leave to run the head, which it names `--trust-head` for, a missing adapter tool, an inventory whose `range.head` is not the working directory's checked-out `HEAD`, or a run past its bound. `64` is usage. `--jobs N` runs N claims at once, each compared run in a fresh worktree of its own. Output names each mutant, its claim, the test, the outcome and the time taken.

The inventory is a versioned JSON document, `melianMutants: 2`:

- `range`: `base` and `head` commits, and the review target when it was a pull request.
- `adapters`: each language adapter that enumerated, with its identity: the adapter name and version and the enumerator tool's version, such as `typescript: stryker-instrumenter@10.0.0`.
- `installation`: the installation identity the mutation cache already computes, a digest of the checkout's lockfiles, the test runner's version, the Node runtime version, the platform and the architecture.
- `mutants`: one row per mutant, keyed by `id`, the hex SHA-256 of the identity tuple above. Each keeps `file`, `line`, `column`, `endLine`, `endColumn`, `mutatorName`, `replacement`, `status` (`generated` or `ignored`), and for an ignored mutant `ignoredBy`, `config` or `comment`, with the instrumenter's `statusReason` shown and never read. `config` means the mutator is in the `excludedMutations` of the policy source's `stryker.config.json`, which Melian reads itself; every other ignored mutant is `comment`, the name for any reason the head's own text decides, a `// Stryker disable` comment above all. [The mutation check decision](2026-10-08-mutation-testing-as-a-static-check.md) explains why `statusReason` cannot decide it: a comment can carry the exact sentence a setting gives. and the builder's `claim`, `evidence` and `survivorClasses`. A `killed` claim's evidence is `{ test: { file, name } }`, the test file and its full name, as the runner reports it. An `equivalent` claim's evidence is `{ reason }`. A `new-test` claim's evidence is `{ test }` for the test the builder will write. `verification`, when present, is the record below.
- `unmutated`: the changed production files the enumerator set aside, with the reason, as today.

A version-1 inventory, today's shape with string evidence, is accepted by `sample` and refused by `verify`, which says to enumerate again: a string cannot name a test the runner can run. The survivor class labels stay the builder's judgement and the eight names of today.

### 2. The language adapter **[Melian's flow]**

A `MutationAdapter` is a class in the pipeline, since enumeration and verification spawn processes. It answers four questions, and nothing else:

1. `enumerate(files)`: the mutants of the given files' changed line ranges, from the file text at the head. It never runs the repository's code or loads its configuration.
2. `apply(mutant, files)`: how one mutant comes into effect, and it declares which of two ways, `applies: switch` or `applies: text`. A switch adapter compiles every mutant of a file into one instrumented file and switches one on at run time, so the baseline and every mutant run identical text. A text adapter splices the mutant into the source at its byte range. `invalid` is `apply`'s parse verdict on its own input and nothing else. The adapter is the authority on positions and parsing.
3. `testCommand(test, root)`: the command that runs one named test, `{ file, name }`, in the run's fresh worktree at `root`, how it activates a mutant, and how to read its result.
4. `classify(outcome, baseline)`: `killed`, `survived`, `flaky`, `invalid`, `invalid-claim`, `load-error` or `timeout`, from the runner's report of the mutated and unmutated runs and the duration against the bound. A test's identity in the report is its `ancestorTitles` plus `title`, never `fullName`, which is space-joined: a nested `suite > works` and a top-level `it("suite works")` share one `fullName`. The named test must appear exactly once in the runner's report of both runs, read `passed` in the round's shared baseline and inert runs, leading and trailing, and `failed` in two separate mutated runs to be `killed`, and `passed` mutated to be `survived`. A test that is `skipped` or `todo`, absent from the report, or a name the file holds twice is `invalid-claim`. A mutated module the runner cannot load is `load-error`. A test file that fails to collect in the mutated run, with the test present in the baseline, is `load-error`; this precedes the absent rule. A run whose `hitCount` exceeds `hitLimit` is `timeout`, whatever the test read.

An adapter also declares whether it must build the head to enumerate. PIT and cargo-mutants do; the instrumenter and tree-sitter do not. One that must enumerates only under the leave that verification needs, below, so a head that may not run cannot be enumerated by building it.

The TypeScript adapter is the first, and it is a switch adapter. Problem, found by two attacks: a text-spliced mutant is a different file, and a test can tell. A test that snapshots a function's `toString()` kills every mutant; esbuild normalises whitespace, so a neutral edit did not change it. A whitespace-stripped comparison with `git show HEAD:<file>` kills every mutant too. Each is a universal oracle, and a reviewer of the test file sees only an odd assertion. Solution, in the coordinator's ruling: apply a mutant by activating it at run time in the instrumenter's switched build, as Stryker does, never by splicing source text. The mechanism, read in `node_modules/@stryker-mutator/instrumenter` and `vitest-runner`: `Instrumenter.instrument(files, options)` returns, for each input, one instrumented file holding every mutant as a branch, `stryMutAct_9fa48("<id>") ? <mutated> : <original>`, placed by expression, statement and switch-case placers, with three helpers at the top. `stryNS_9fa48()` returns `globalThis[namespace]`, `__stryker__` by default; `stryMutAct_9fa48(id)` answers `ns.activeMutant === id` and counts hits against `ns.hitLimit`; `stryCov_9fa48(ids)` records coverage per `ns.currentTestId`. Stryker's core writes those files over the originals, and its Vitest runner prepends `stryker-setup.js` to Vitest's `setupFiles`, which reads `inject('mode')`, `inject('activeMutant')`, `inject('mutantActivation')` and `inject('hitLimit')` from values the runner `provide`s, and sets `ns.activeMutant` in `beforeAll`, or at load for `static` activation. In dry-run mode it sets `ns.activeMutant` to `undefined` and records each test's ID. Stryker's planner sets `hitLimit` to 100 times the mutant's dry-run hit count, so an activated infinite loop ends as a `Timeout`.

Melian does the same with the instrumenter's output and a setup file of its own. Enumeration already instruments the changed files; `verify` and a probe write that instrumented file over the source in each run's fresh worktree, and prepend a setup file that sets the namespace from values Melian provides. The setup file is the same text in both runs and sets the same keys: `hitCount: 0`, `hitLimit`, and `activeMutant`, which is `null` in the baseline, never `undefined`. The child environment never carries `__STRYKER_ACTIVE_MUTANT__`. Both rules close one door: the instrumenter's header copies that variable into an `activeMutant` it finds `undefined`, so either would let the environment choose the mutant. The mutant is activated when the setup file loads, never in `beforeAll`, so mutants in module-level code activate. `hitLimit` is 100 times the mutant's `stryCov` count in the shared coverage run of the next paragraphs and section 3, or unset when that count is 0 or unknown. A run whose `hitCount` exceeds `hitLimit` is `timeout`, whatever the test read. The header throws once the count passes the limit, and a test reads that throw as a failure, so without the rule an activated loop would count as a kill. The baseline runs the same instrumented build with no mutant active. Baseline and every mutant then run identical text, so a test that reads source, an AST, a `toString()`, a hash or `git show` cannot tell them apart. What remains is a test that reads the switch's state: the namespace's `activeMutant`, `hitCount` or `hitLimit`. The counts `stryCov_9fa48` records would be a fourth, since an active mutant skips its site's call, and the coverage sink below blanks them for an honest test. The `forged-mutation-kill` guardrail flags the literal names. A test that builds them, such as `globalThis["__stry" + "ker__"]`, or scans `globalThis`, evades it. Two controls back it. Each test that a claim names runs once a round with an inert mutant active, the shared inert run of section 3: a numeric ID Melian adds to the instrumented file, among the real ones, behind a branch whose two sides are the same expression. A test that fails under it reads the switch, not the behaviour, and every claim on it is `invalid-claim`. The review body lists every test that killed on more than one file, for switch adapters too. A test that finds the inert branch by parsing the instrumented file remains, within writer trust, as it does for `static.mutation`. The neutral edit of the first revision goes; it was the text adapter's answer to a text adapter's problem.

Coverage state is blanked during verification. Problem, found by Codex's adversarial review at `10e5286f`: the instrumenter puts `stryCov_9fa48(ids)` on the original branch only, so an active mutant leaves its own coverage entry out, while the inert mutant, placed elsewhere, leaves real coverage alone. Example: a test that scans the namespace with computed names, finds the coverage object and expects the entry for the code it calls fails when that mutant is active. It passes the baseline and the inert run without testing behaviour, and it kills in one file only, so the multi-file kill list misses it too.

Two fixes were weighed. An inert twin at every placement, skipping the same coverage call and hitting the same way, has to copy each placer's shape, expression, statement and switch case, and a test can still tell the twins apart by which ID is missing. Blanking coverage removes the signal from an honest test's view in every run and needs nothing but the namespace the header already reads. It is the stronger fix, and the choice. The setup file sets `mutantCoverage` to a sink whose `static` and `perTest` discard every write and read as empty, in the baseline, the mutated run and the inert run alike. The instrumenter 10.0.0 header's `stryCov_9fa48` writes into `ns.mutantCoverage` when one is present and creates it only when absent, so the sink makes every coverage call a no-op. A `Proxy` whose `set` trap returns true discards a write without throwing, even in a strict-mode module; a frozen object would throw there. A probe of the header's cover helper over such a sink, run on Node 24, left `static` and `perTest` empty. The sink does not make the oracle impossible; a test that replaces it is the writer-trust case below.

`hitLimit` therefore comes from a separate coverage run beforehand: the named test once, with no mutant active and a real coverage object, whose count for the mutant sets the limit. That run is never compared with anything. A test that behaves differently there moves only the limit, and a wrong limit ends in `timeout`, from the hit limit or from `mutants.timeout`, never in a kill.

**[Melian's flow]** **Instrumentation state is within writer trust.** Codex's review of `b1da6d2b` showed that a test can find the namespace, replace `mutantCoverage` before it imports the target, and forge a kill. It was a new instance of a class earlier rounds had patched one at a time, and the maintainer ruled on the class on 2026-10-24: verification proves honest claims. It does not stop a writer who deliberately reads or overwrites the instrumentation, just as it does not stop a writer who writes a malicious test. `static.mutation` has the same exposure today, which [the core guideline](../guidelines/core.md) accepts: "A writer's own tests can still fake kills." The cheap controls stay, and no further mechanism is added: the `forged-mutation-kill` guardrail, the inert mutant, the multi-file kill list for every adapter, and one more line. Before any repository setup runs, Melian's setup file makes the namespace on `globalThis`, and its `mutantCoverage` property, non-writable and non-configurable with `Object.defineProperty`. What remains is a test that reaches the instrumentation through computed names and reads or alters what the setup file left writable. It is accepted for three reasons. The head is a writer's, or one the reviewer vouches for. A fork's head never runs. And the review body lists the kills for a human to read.

Its operator set is the instrumenter's less the `mutator.excludedMutations` of the `stryker.config.json` read from the policy source the host chose, the base for a pull request, never the head's copy; an excluded mutant stays in the inventory as an ignored row marked `config`, so it is seen and noted, never verified: the script reads the head's today, so a head could shrink its own enumeration. It runs one test through Vitest, `vitest run <file> -t <pattern>`, with the head's configuration untouched apart from the prepended setup file, and reads Vitest's JSON reporter. The pattern is the test's `ancestorTitles` and `title` joined by ` > `, regex-escaped and anchored. The JSON reporter prints `fullName` as `suite works`, yet `-t '^suite works$'` matches nothing and exits 0 with every test skipped. The exact-once rule turns that into `invalid-claim`, never a kill. `-t '^suite > works$'` is the pattern that runs it. Two tests with one name both run and are `invalid-claim` too. Vitest strips types without checking them, so a type error is not `invalid` here, and the instrumenter generates only parse-valid mutants, so `invalid` is rare for this adapter. The instrumenter comes from the checkout's install when it has one, and otherwise from Melian's own pinned copy, as Biome and tsc do; `melian doctor` says which, and the record names the version, since mutant identity depends on it.

What the switched build costs. The instrumented file is several times its source and loads slower, and every mutant of the file is compiled whether or not it is probed; Stryker pays the same. A test that imports the mutated module imports the instrumented copy, so `verify` writes it into every fresh worktree, once per compared run. A text adapter needs none of this.

Other adapters plug in the same way, each a class behind the interface, selected by `melian.yaml`:

```yaml
mutants:
  evidence: required          # or advisory, the default
  languages:
    typescript: { enumerate: stryker-instrumenter, test: vitest }
    rust: { enumerate: cargo-mutants, test: "cargo test {name} --exact" }
    ruby: { enumerate: tree-sitter, grammar: ruby, test: "bundle exec rspec {file} -e {name}" }
```

- A dedicated tool's adapter, for cargo-mutants, mutmut, PIT, Stryker.NET or mutant, wraps the tool's own enumeration and reads its mutant list into the inventory shape. PIT and Stryker.NET switch at run time and declare `applies: switch`. cargo-mutants and mutmut splice source and declare `applies: text`. Each is its own class and its own pull request.
- The tree-sitter fallback of [issue #170](https://github.com/melian-agent/melian/issues/170) enumerates from the grammar's syntax tree with a fixed operator table and a small reviewed map per language from node types to operators. It applies by byte range, `applies: text`, and its `classify` reads a mutant that fails to parse or compile as `invalid`, never `killed`. It is a floor, not a match for a dedicated tool's semantics, and it is milestone 3 work.

A text adapter's kills are weaker evidence, since a test can tell a spliced file from the original. Two controls back them. The `forged-mutation-kill` guardrail gains patterns for a changed test file that stringifies an imported function in an assertion, spawns `git show`, or reads a path under a production source directory, at P2 acknowledge. A maintainer then sees the oracle before the kill counts. And the review body lists every test that killed on more than one file, as it does for every adapter, since a universal oracle kills everywhere and a real test kills where it looks.

`mutants.languages` is policy: a `test` command executes, so only the committed root `melian.yaml` sets it. A nested file or a preference file that sets it is refused when the file is read, as a committed `melian.yaml` refuses a credential command. A pull request's review reads it from the base, so a head cannot name the command that proves its own kills. `{file}` and `{name}` are the two placeholders. They substitute into argv elements, never into a shell string, because a test name is head text. The command runs in the environment section 3 sets out, never the caller's.

### 3. Verification as evidence **[Melian's flow]**

A verification run executes the head's tests. It carries the same trust as `static.mutation` does today, by [the unconfined decision](2026-10-14-static-checks-run-unconfined.md): a head a writer pushed to the base repository, or one the reviewer vouches for with `--trust-head`. A fork's head waits for milestone 3's credential-free job. Nothing confines the run.

**[Melian's flow]** `melian mutants verify` takes no leave of its own. It runs head code only under that decision's two cases: the reviewer's explicit `--trust-head`, or a head a writer pushed to the base repository under the existing writer rule, which `leaveOf` decides. Otherwise it refuses, exits `2`, and names `--trust-head`. An earlier revision let it run whenever the inventory's `range.head` was the checked-out `HEAD`, with leave `reviewer` and no flag. Melian's design lens found that a fail-open default: nothing git records says whose code a head is, and a fork checked out with `gh pr checkout` is the case [the unconfined decision](2026-10-14-static-checks-run-unconfined.md) names. The maintainer's trust ruling stands: fork code run locally is skipped. The check that `range.head` is the checked-out `HEAD` stays as a further guard, exit `2` otherwise, and never grants leave. The record keeps the leave it ran under, `writer` or `reviewer`. A review's probe runs under the review's own leave, and a review without leave runs no probe. `trust.writers: false` in the base's policy refuses a probe or a verification for a writer's head, as `leaveOf` refuses `static.mutation` there.

The run works in a scratch worktree of the head, linked to the checkout's install as static tools are, with the head's own test runner. Every run gets a fresh worktree of its own, as the kill rule below says, and `--jobs` runs that many claims at once.

**[Melian's flow]** Melian builds the test command's environment itself, so the environment is policy, not an input. Problem, from Codex's review of `b1da6d2b`: `PATH`, `HOME`, `TMPDIR`, `LANG`, the platform and the architecture reached the run without being keyed, so two machines could disagree about a kill and share the record. The ruling of 2026-10-24: the child gets `LANG=C.UTF-8` and `TZ=UTC`, a fresh scratch `HOME` and `TMPDIR` per run, and `PATH` from the installation, and nothing else is inherited. Platform, architecture and the Node version join the installation identity. A repository whose tests need another variable declares it, name and value, under `mutants.env` in the committed root `melian.yaml`, read from the base like `mutants.languages`, so it enters the policy digest.

For each test a claim names, once per round, and then for each mutant claimed on it:

1. **Shared runs.** Before the test's mutated batch, the test runs three times with no real mutant active, each in a fresh worktree: the shared baseline, the instrumented build with `activeMutant` set to `null`, or for a text adapter the unmutated source; the shared inert run, with the inert mutant of section 2 active, for a switch adapter; and the coverage run, which sets `hitLimit` for every mutant claimed on the test. Every claim on the test shares them. A shared baseline or inert run that fails runs once more in a fresh worktree: one that fails again makes every claim on the test `invalid-claim`, since a failing test kills nothing and a test that fails under the inert mutant reads the switch; one that passes the second time makes every claim on it `flaky`.
2. **Apply.** A switch adapter activates the mutant when the setup file loads; a text adapter splices it in. A mutant `apply` cannot parse is `invalid`.
3. **Run.** The named test runs against the active mutant in a fresh worktree, under `mutants.timeout`, 120 seconds by default.
4. **Classify.** The named test, identified by `ancestorTitles` plus `title`, must appear exactly once in the runner's report of the shared baseline and the mutated run. One that read `passed` in the baseline and `failed` mutated is a candidate kill, which steps 5 and 6 must confirm. One that passes mutated is `survived`. A run past the bound, or one whose `hitCount` exceeds `hitLimit`, is `timeout`. A mutated module the runner cannot load is `load-error`. A test file that fails to collect in the mutated run, with the test present in the baseline, is `load-error`; this precedes the absent rule. A test `skipped`, `todo`, absent, or present twice is `invalid-claim`.
5. **Second mutated run.** A candidate kill runs the mutant again in another fresh worktree. A pass makes `flaky`; a second failure stays a candidate until step 6.
6. **Trailing controls.** After the test's mutated batch, its shared baseline and inert runs run once more, each in a fresh worktree. If both pass, every candidate kill for the test that round is `killed`. If either fails, or disagrees with its leading run, every candidate kill for the test that round is `flaky`.
7. **Discard.** Every run's worktree is removed; nothing is restored in place.

The rule, whole: A kill needs the test to pass in the round's shared baseline and inert runs both before and after its mutated batch, and to fail in two separate mutated runs, all from pristine state. Nothing else counts, so neither a `flaky` nor an `invalid` mutant is ever `killed`, and a `timeout` or `load-error` becomes a finding, as section 6 says, as a survivor does.

**[Melian's flow]** A kill takes two mutated failures. Problem, from Codex's attack on `d60bc2bc`: one mutated failure counted whenever the baseline passed. Example: an honest test with timing, randomness, a fixed port or shared files passes the baseline, fails once against the mutant by chance, and passes the inert run, without reading any instrumentation. Rule: A kill needs the test to pass in the round's shared baseline and inert runs both before and after its mutated batch, and to fail in two separate mutated runs, all from pristine state. Pristine means a fresh worktree of the head for every run, shared or mutated: each starts in a new worktree made through `Run.worktreeCommand`, with the install linked and the instrumented file written, and the worktree is removed afterwards. The other choice, `git clean -ffdx` plus restoring from git, was rejected for two reasons. Its `-x` also deletes the linked install, which must then be linked again, so it saves little. And it leaves what `git clean` does not see: the worktree's administrative directory under the common `.git`, where a test can keep a ref or a config entry, and modes a test changed on tracked directories. A fresh worktree carries none of that. Each run also gets a fresh `HOME` and `TMPDIR`. State outside the worktree, such as the linked install or an absolute path, is not reset; a test that keeps a counter there can still fake the pattern, and that is a test a writer chose to write, within writer trust. An inconsistent result is a new outcome, `flaky`: one mutated run failed and the other passed, a shared run failed once and passed once, or a trailing control failed or disagreed with its leading one. A `flaky` record covers nothing, leaves its mutant `unverified`, and the review body lists it.

**[Melian's flow]** The baseline and inert runs are shared, by the maintainer's ruling on cost of 2026-10-24. Every run starts from a fresh worktree, so nothing carries from one run to the next, and neither the baseline nor the inert run depends on which real mutant is active. So they run once per test per round and serve every mutant that test claims, and so does the coverage run, which records the count for every mutant at once. Each kill keeps its two mutated failures, each from its own fresh worktree. A survivor needs one mutated run: a test that passes against the mutant is not a kill, whatever it does next time. The cost, at the measured 3.3 seconds a run and 0.85 seconds to write a fresh worktree of the head's 3,047 tracked files at a load average of 18: about 2 runs per kill, 8 seconds, and 1 per survivor, plus 5 per test, the leading baseline and inert run, the coverage run, and the trailing baseline and inert run, about 21 seconds.

**[Melian's flow]** The shared controls trail as well as lead. Problem, from Codex's review of `1acb1c0f`: the shared baseline and inert runs ran before a test's mutated batch, so a failure that starts afterwards and persists fails both mutated attempts and records a kill. Example: another process takes the test's fixed port, the host's load climbs past a timing assertion, or an external dependency goes down, between the leading controls and the mutated runs. A fresh worktree resets none of that, since it lies outside the worktree. Rule: the cost ruling stands, and one more shared baseline-and-inert pair runs after each test's mutated batch, each in a fresh worktree. If either trailing control fails, or disagrees with its leading one, every candidate kill for that test that round is `flaky`. The cost is 2 more runs per test.

**[Melian's flow]** A record is reused only on the executor that made it. Problem, from Codex's attack on `d60bc2bc`: the allow-listed environment keeps variables from leaking in, but two installations with the same lockfile can still run different binaries. Example: a native package built against glibc on one machine and musl on another, a different `git` on `PATH`, or a different Node build with the same version. Rule: until a hermetic executor image exists, which is not milestone 2 work, a verification record is reused only on the executor that made it. The executor identity is a random local ID that Melian writes once beside the install, in the mutation cache's installation directory, and reads on every run; a new clone, a new machine or a reinstalled `node_modules` gets a new one. Any other executor reruns. This matches [pull request #185](https://github.com/melian-agent/melian/pull/185)'s GitHub agent, which verifies again and never trusts a local record. It also means a review on another executor than the builder's reruns the claims it relies on, at the cost section 5 measures.

The record is `{ version: 1, head, mutant, test, outcome, baseline, source, executor, adapter, installation, policy, leave, at, ms }`. `source` is the role: `claim` for `melian mutants verify`, `probe` for a lens probe or a test a verifier names. `executor` is always the physical local ID, whoever produced the record. Records live in the repository's mutation cache under `CacheLocation`, `mutants/<head>/<executor>/<installation>/<adapter>/<policy>/<mutant id>.json`, beside the partition `static.mutation` keeps there. They are cached evidence, not state: losing them costs a run. A record is keyed by the exact head, so a record from another head is never evidence; the stale-kill section says why. The identity rule, in one sentence the coverage ledger quotes: A verification record is evidence only at the head it names, and only when its executor (the local ID Melian stores beside the install that ran it), its installation identity (the lockfiles, the test runner's version, the Node version, the platform and the architecture), its adapter identity and its policy digest (the SHA-256 of the effective base-sourced mutation policy, declared environment variables included, and the resolved test-command argv) each equal the reader's; a record that differs in any is rerun, never reused. A review also reads a record only when it has leave to run the head, writer or reviewer. The policy digest exists because a head's base moves. Example: a stacked pull request is retargeted onto `main` when its parent lands, or reviewed after its base gained a commit, and the base's `mutants.languages` now names another test command. A record made under the old command proves what the old command ran, not what the new one would. The digest covers the adapter's `mutants.languages` entry, `mutants.timeout` and the `excludedMutations` read from the policy source, as canonical JSON, and the argv after `{file}` and `{name}` are substituted. The record's `leave` is kept for the ledger, and either leave is reusable at the same head: both answer that the head's tests may run here, and the record is that head's tests run.

What a record cannot prove: a writer can write a record into the cache by hand. Under a switch adapter, no test can tell the baseline from a mutant by the file, since both run identical text, so a test that fails on cue must read the switch's state: the namespace's `activeMutant`, `hitCount` or `hitLimit`, and the coverage counts, blanked for an honest test. The `forged-mutation-kill` guardrail flags the literal names, the inert-mutant check catches a test that builds them and reads the switch, and the review body lists every test that killed on more than one file. A test that reaches the instrumentation through computed names and overwrites it is within writer trust, by the ruling in section 2. Under a text adapter, a test can tell by the file, and the guardrail's new patterns and the same list make it visible. What remains is within writer trust, as it is for `static.mutation`'s staged report today, and human review before merge is the control.

Cost, measured on this repository at a load average of 25 while another lane's gate ran, and bounded rather than assumed. A named unit test in `packages/core` takes 0.5 seconds inside Vitest and 3.3 seconds of wall time with process start. A CLI test that spawns `melian` takes 2 to 60 seconds. A probe with no named test runs the related tests, and `packages/core/src/mutation.ts` relates to 172 of 195 test files, so such a probe runs most of the suite, and the 3.3-second figure does not hold for it. The bounds: a named-test verification costs two mutated runs for a kill and one for a survivor, plus the test's five shared runs once a round, as section 3 counts, each under `mutants.timeout`; a related probe is bounded by the same timeout and by the lens's probe budget; a whole-suite fallback has its own budget, in section 4. A later build may run the TypeScript adapter's probes through Vitest's node API in one process, as Stryker's runner does, and cut the per-mutant cost to the test's own time.

### 4. The tests lens **[Melian's flow]**

The lens receives the enumeration of its files' changed lines as context, inside the review's boundary under the label `mutants`, since a replacement is head text. The section lists each mutant's ID, file, line, mutator and replacement, with its record at this head when one exists: `killed by <test>`, `survived`, `flaky`, `timeout`, `invalid`, or `unverified`. It holds at most 400 mutants and 64 KiB; past either, it lists counts per file and names the tool that lists the rest. Two tools join the lens: `list_mutants(file)` lists a file's mutants with their records, and `probe_mutant(id, test?)` runs a verification probe. `probe_mutant` always runs; a cached record is context the lens can read, never the outcome. A probe with a named test checks that test alone. A probe without one runs the tests the test runner relates to the mutated file, Vitest's own `related` selection for the TypeScript adapter. A related run only nominates a candidate, its first failed test, and nominating never classifies. The candidate goes through the whole verification of section 3 by its ` > ` name: the round's leading and trailing shared baseline and inert runs for that test, and two mutated runs, each in a fresh worktree. `killed` makes it the killer, and `flaky` makes the probe's outcome `flaky`. Any other outcome excludes it, and the probe runs the related tests again without it, within the same timeout. A related run therefore never names a test that fails anyway, or fails once, as the killer.

The evidence is weaker than Stryker's in five places, and each has its handling:

- **Spawned-only code.** `packages/cli/src/bin.ts` relates to no test, because the CLI suite spawns it. A probe whose related selection is empty falls back to the whole suite, under `mutants.suiteTimeout`, 1,200 seconds by default, at most `mutants.suiteRuns` times per round, 1 by default. The counter is Melian's, kept in the round's own records, never the head's. It counts per round, not per review, because a round run from a detached worktree is its own changeset, so no review record spans its rounds. That restores the `NoCoverage` fallback Stryker had, bounded by its own budget rather than the probe's. The cost per round is up to 20 host minutes at the default of 1, and up to 40 at 2, which is a Stryker run.
- **Widely imported code.** `packages/core/src/mutation.ts` relates to 172 of 195 test files, so a related probe runs most of the suite and times out under `mutants.timeout`. A probe that times out takes the same whole-suite fallback while its budget lasts, and is otherwise `timeout`, which makes the probe unavailable for that finding, below. The builder's named-test claim, verified in seconds, is the path for such code.
- **The lost `NoCoverage` fallback.** Stryker reran a `NoCoverage` related run with the whole suite. The fallback above is the replacement; past its budget, a mutant stays `unverified`, which `required` makes visible.
- **The hit-limit kill.** Stryker reports a mutant that passed its hit limit as `Timeout`, which its score counts as detected. Here that run is `timeout`, never `killed`, and becomes a finding the maintainer acknowledges or dismisses, as section 6 says. An activated infinite loop therefore costs a maintainer's reading where Stryker counted it caught.
- **A forged kill silencing the tests lens.** A probe that killed refuses the lens's report, so a test that reads the switch's state and fails on cue silences a true `untested-behaviour` finding, not only a survivor of the check. Two controls answer it: the review body's list of the kills that refused a report, below, and the inert-mutant check of section 2, which makes such a test's claims `invalid-claim`.

An `untested-behaviour` finding is backed by a probe. `report_finding` under that rule takes `mutant`, the ID of a mutant the lens probed:

- A mutant whose probe survived backs the finding. The finding's failure scenario is the mutation itself, and the verification record is its proof.
- A mutant whose probe killed refuses the report, naming the test that killed it. The lens can look elsewhere.
- No mutant, or an unprobed one, is refused while a probe is available: "probe the mutant first".

A refusal under rule 4 applies only to a mutant the enumerator generated on the finding's line, whose probe at this head read `survived` or `killed`. A `timeout`, `flaky`, `invalid` or `invalid-claim` outcome, a line without a mutant, and an exhausted probe budget each make the probe unavailable for that finding, which goes to the verifier as today, with the outcome in the lens's record. A refused report is recorded on the lens's record as a note naming the mutant, the killing test and its file. A review body lists the kills that refused a report, so a forged kill that silences the lens is visible to the maintainer.

The verifier receives each probe-backed finding with its record in the state. A `survived` record against related tests is not proof that no test exists: a spawned-only file relates to none. So a verifier may refute a `survived` finding only by naming a test; Melian verifies that test against the mutant through the same classifier as any claim, and the outcome decides: `killed` refutes, anything else, `flaky` included, leaves the finding standing. The verifier may lower a standing finding one step within the existing fence. The probe is a third finding-verification executor, `probe`, beside `llm` and `decision-model` in the finding's `verification.executor` that `packages/core/src/verification.ts` defines, with the mutation record's ID as its evidence. That record carries `source: "probe"` and the physical `executor` ID like every other mutation record; the two fields share a word and never a value. A refutation by `probe` keeps the trust floor, so a protected claim refuted by a named test still needs the maintainer's acknowledgement; that is the amendment to [the trust floor](2026-10-17-trust-floor-exact-rule.md): the probe executor's verdicts count under it as a verifier's do.

The work is bounded per round. Each `tests` lens run has `budget.probes`, 12 by default at `careful`, 6 at `quick`, 20 at `deep`, and `mutants.timeout` per probe. The lens chooses which mutants to probe; Melian only counts. A probe past the budget is refused with a note on the lens's record. The record stays `ran`; the refusal is a note, never a budget end, and the lens goes on reading and reporting. Every probe writes a record, so a later round at the same head reads it as context. A lens at a head without leave records that probes were unavailable and why.

This replaces `static.mutation`'s survivors as the source of `untested-behaviour` in Melian's own repository. Three things stay.

- `static.mutation` leaves every tier of Melian's `melian.yaml`. It was never in a default tier.
- The check stays in the product as an opt-in audit, unchanged, with its partition, its provisional status and its `--cold` run. It is the one exhaustive run, every mutant against its related tests, and the only measure of what enumeration and claims miss. A repository turns it on for an audit; Melian's own loop no longer runs it on rounds. Removing it would delete working code that the audit needs, and the enumerator shares its selection with it, so the two cannot drift. If an audit shows nothing for three milestones, a later decision may remove it.
- The `forged-mutation-kill` guardrail and the policy-change rules for Stryker's configuration files stay, since the check stays. The guardrail now also guards probes: a switch adapter's probe sets the same `__stryker__` namespace Stryker does, and its new patterns for text adapters are above.

### 5. Stale kills **[Melian's flow]**

Problem: a later change to `b.ts` makes an earlier-killed mutant in `a.ts` survive. A test that reached the mutant through `b.ts` no longer does, and `a.ts` is unchanged, so nothing about the mutant or its test file changed. A whole-pull-request Stryker run caught this; nothing else did.

Two options were measured. The first re-verifies a claim when any file in its named test's import closure changes, with Vitest's related selection as the authority. The second re-verifies every claim at the head the review passes on.

The cost of the second, measured with `melian mutants list`'s predecessor on this repository: [pull request #168](https://github.com/melian-agent/melian/pull/168) has 328 mutants in 4 files, [pull request #167](https://github.com/melian-agent/melian/pull/167) 123 in 4, [pull request #174](https://github.com/melian-agent/melian/pull/174) 75 in 1, and [pull request #186](https://github.com/melian-agent/melian/pull/186) 72 in 1. With fresh worktrees, a kill costs about 8 seconds, two mutated runs, and each test about 21 more for its five shared runs once a round. If every mutant is killed and, at worst, each names a test of its own, the largest costs about 159 minutes serial and 40 with four workers; at four mutants a test, about 74 minutes serial and 18 with four. The others, 72 to 123 mutants, cost at worst 35 to 60 minutes serial and 9 to 15 with four. These are upper bounds for named unit tests, and the in-process runner of section 3 would cut the per-run cost. Stryker took 15 to 70 minutes a round on the same pull requests.

Choice: the second. A verification record is evidence for the exact head it names and no other. A review at head `H` reads only records at `H`. A builder runs `melian mutants verify --all` at each head before pushing, at the cost bounded above, and a review on the same executor reuses those records, while one on another executor reruns them; the lens probes what has none. Nothing carries across heads, so nothing can go stale, and Melian never re-derives which files a kill depended on. The first option was rejected because Vitest's related selection follows imports alone, and [the coverage ledger decision](2026-10-23-coverage-ledger-and-delta-review.md) found the list of what else can stale a kill, a fixture, a snapshot, a setup file, a Markdown file a test reads, a spawned child's module, and kept growing it. A hand list is the class [the ask-the-authority decision](2026-10-12-ask-the-authority.md) names.

What it misses. A test that fails mutated by chance twice in a row while passing its shared runs; the two-failure rule of section 3 makes that rare and turns any inconsistency into `flaky`, but cannot exclude it. A mutant the enumerator does not generate. An `equivalent` claim, which is a judgement and becomes a survivor finding for the maintainer to dismiss. And the minutes a whole re-verification costs at each head, which the measurement bounds.

### 6. The coverage ledger **[Melian's flow]**

Mutation coverage comes from verification records, not from Stryker's report. [The coverage ledger decision](2026-10-23-coverage-ledger-and-delta-review.md), open in [pull request #185](https://github.com/melian-agent/melian/pull/185), must change in these places; this decision names them and edits none of that pull request's files.

- Its amendment of [mutation reruns, as built](2026-10-16-mutation-reruns-later-changes.md) becomes an amendment of this decision. Its coverage rule for `static.mutation` becomes: a changed production line is covered when every mutant on it has a verification record at the current head that reads `killed`, or is the subject of a survivor finding settled at the current head, or of a dismissal. Lines the enumerator sets aside, and mutants with `ignoredBy: config`, are covered with a note. A mutant with `ignoredBy: comment` on a changed line raises a P2 `mutants/ignored-mutant` finding, one per line, and covers nothing, as `mutation/ignored-mutant` does today, because the head wrote the comment. Static mutants need no `ignoreStatic` here: verification activates module-level mutants at load.
- Its round step 2 and attack rule 8, Stryker over the delta's production lines and every carried survivor's line with `--force`, go. Nothing mutates in a round; the lens probes, and the records decide.
- Its voids 7 and 8 for mutation coverage simplify to one sentence: a mutation record from another head is never evidence. The `provisional` status, the dependency and test change list, and the head-written test list no longer apply to mutation coverage; they still apply where a repository audits with `static.mutation`.
- Its ledger record per round and static check keeps, for mutation, the IDs of the verification records relied on per changed line, and the adapter identity, installation identity and policy digest, in place of the lines Stryker mutated and the test files it ran. The ledger takes the identity rule of section 3 verbatim.
- Its sharing section's rule that the agent voids every mutation record from another Node runtime becomes: the agent is another executor, so no local record is evidence to it, and it verifies again every mutant it relies on, as this decision's executor rule requires.
- Its `review.coverage` record absorbs the `mutants` record this decision adds at adjudication, once both are built; until then the two records are written side by side and either leaves the review not reviewed.

Until the ledger lands, adjudication writes one check record of its own, `mutants`, from the enumeration and the records at the head, as `review.coverage` will. The same step turns records into findings. A `survived`, `timeout` or `load-error` verification record at the head becomes one `mutants/untested-behaviour` finding per mutant. Its discriminator is the SHA-256 of `[mutatorName, replacement, column, endColumn, text of the range, occurrence]`, where `occurrence` is the zero-based index, in line order, of the mutant among the file's mutants with an equal five-tuple, and the trigger hash supplies the line: a line-numbered discriminator broke dismissals whenever code above the mutant moved. The finding carries no snippet, so the discriminator is its ID input, and the discriminator appends the occurrence index among equal tuples in the file, so two identical lines do not collide. The build passes it to `Finding.create` with `snippet` absent and `discriminator` set. `findingId` in `packages/core/src/findings.ts` then hashes the length-prefixed file, rule, empty normalised snippet and discriminator; `Finding.create` stores the discriminator as `properties.discriminator`, and `Finding.parse` refuses a finding whose ID disagrees. A snippet that normalises to anything but the empty string would make `findingId` hash `properties.occurrence` and ignore the discriminator, so the range text goes into the discriminator, never into a snippet. Two mutants on one line are then two findings, and a dismissal of one never covers the other. An `invalid` record covers its mutant with a note, since there is nothing to test, and never blocks. A config-ignored mutant is covered with a note; a comment-ignored one on a changed line is a `mutants/ignored-mutant` finding and covers nothing. An `invalid-claim` record leaves its mutant `unverified` and names the bad claim. A `flaky` record leaves its mutant `unverified` too, and the review body lists it. Under `mutants.evidence: required` the record is `ran` when every mutant on a changed production line has a record at the head: killed, a survivor, timeout, load-error or ignored-mutant finding a maintainer has settled, an invalid or config-ignored note, or a dismissal. Otherwise it is `skipped` without leave, naming the count of unverified mutants and the command that verifies them, and the review is not reviewed. A `timeout` or `load-error` therefore never blocks for ever and never passes unseen: a module that throws at import is a finding a maintainer acknowledges or dismisses, as a survivor is, not a mutant that satisfied `required` with no test run. Under `advisory`, the default, the record is `ran` with the counts in its notes. Melian writes it; nothing the head writes reaches it. Like `review.coverage`, it joins every manifest without a tier entry, and a `melian.yaml` naming it in a tier or in `checks.allowSkip` is refused when the file is read. Melian's own root `melian.yaml` sets `required`.

A dismissal records the mutant discriminators it covers, and a surviving mutant it does not name reopens the line. A line-keyed dismissal would hide a different mutant that later survives on that line. A finding per mutant, with the line-free discriminator, keys the dismissal to the mutant and survives code moving above it, and the trigger hash still reopens it when the line's own code changes.

### 7. Customers **[Melian's flow]**

The three skills gain a section, "Prove the tests", for a builder agent: after writing code and tests, run `melian mutants list origin/main...HEAD --all --json` into a scratch file, classify every mutant with a claim, structured evidence and survivor classes, run `melian mutants sample` and verify its probes, then `melian mutants verify --all`, with `--trust-head` only at the user's word, before pushing, and relay what each prints. A claim is never written as held until `verify` says so. An `equivalent` claim is the user's to confirm; the review raises it as a finding for them to dismiss. The skills run only `melian`, as today, and the skill passes `verify --trust-head` only when the user says they have read the change and want its tests run, as for `review`; never on its own judgement. `melian doctor` stays the one command without a trigger.

`melian doctor` gains a `mutants` line per configured language: the adapter, the enumerator's source and version, the checkout's or Melian's, the test runner and its version, and `mutants.evidence`. For a dedicated tool or grammar it says found or not found, and warns when a configured language has no tool. It runs none of them.

The customer reads `docs/design/mutation-evidence.md`, the skill section, and the `melian.yaml` keys in the core guideline's table: `mutants.evidence`, `mutants.languages`, `mutants.timeout`, `mutants.suiteTimeout`, `mutants.suiteRuns`.

### 8. Building Melian **[Building Melian]**

Once this is built, `AGENTS.md` changes in these places. It is not edited now. A builder's own branch is not a writer's pushed pull request yet, so each `melian mutants verify` below takes `--trust-head`, given by the coordinator who has read the change.

- Validation: "The `static.mutation` check runs this proof on the changed lines of every pull request in the `full` tier" becomes: the `tests` lens runs it with probes, and `melian mutants verify --all` runs it before a push. "A surviving mutant the check itself reports keeps its P2 severity" becomes: a survivor a probe or a verification shows keeps its P2 severity.
- Briefs: `node scripts/enumerate-mutants.mjs <base>...HEAD --json --limit 10000` becomes `melian mutants list <base>...HEAD --all --json`; `--sample <inventory.json>` becomes `melian mutants sample <inventory>`; "Run every selected probe" becomes `melian mutants verify <inventory>` for the sample and `--all` before the push. The sentence "The host's `static.mutation` remains the authority; enumeration runs no tests" becomes: the verification records are the authority, and `melian mutants list` runs no tests. The evidence field names a test file and name, not a string.
- Converging: "Run the mutation check on the fix commits before pushing them", with its `melian.local.yaml` and `--trust-head` recipe, becomes `melian mutants verify --all` on the fix commits' inventory. "Before a branch's first full round, run the mutation check alone on the host and kill or explain every survivor" goes. The Learnings entries that give that recipe stay as history, with one line added saying it no longer applies.
- Ready and queued: nothing names `--cold`, since Melian's tiers no longer run the check. The round script's `FINAL=1` cold run goes with it.
- Delegation: "A Codex task cannot run Stryker, because the seatbelt denies `ps`" becomes: a Codex task can run `melian mutants verify` on its own inventory, which spawns no process listing, but the seatbelt denies writes under `.git/melian/`, so it writes no records. The host runs `melian mutants verify --all` after a Codex pass, as it runs the whole gate.

The root `melian.yaml` drops `static.mutation` from `full` and its `static.mutation` settings, and adds `mutants: { evidence: required }`. That is a policy change the build pull request's review will notice.

## What this gives up

- Exhaustiveness on every round. Stryker ran every mutant against its related tests; a round now runs the builder's records and up to 12 probes. A mutant nobody claimed and no lens probed is `unverified`, which `required` makes visible and blocking, and `advisory` only lists.
- A record is one test. Stryker's related run could show a mutant killed by a test the builder never thought of; a record shows only what was asked. The `survived` outcome of a probe without a named test still runs the related tests, so a lens's probe is as broad as Stryker's per-mutant run.
- The whole-suite fallback is bounded. Stryker fell back to every test whenever it related none; a probe falls back at most `mutants.suiteRuns` times a round, and past that a mutant stays `unverified`.
- Writer trust still covers a faked kill, a test that finds the inert branch by parsing the instrumented file, and a hand-written record, as it covers Stryker's staged report today.
- Up to 40 minutes per head for `verify --all` with four workers, measured above, on the builder's machine, and again on any other executor that relies on the records.
- A second finding-verification executor to keep in step with the LLM one: a third value of a finding's `verification.executor`, and one more kind of evidence the verifier reads.
- Time. A kill takes two mutated runs in fresh worktrees and each test five shared runs a round, against one run for Stryker, as section 5 measures.
- The switched build. The TypeScript adapter depends on the instrumenter's output format and helper names, `stryMutAct_9fa48` and `__stryker__`, and on writing an instrumented file over the source in each fresh worktree, as Stryker's sandbox does. An instrumenter release that changes them changes the adapter, and the record's adapter version makes that visible.
- Text adapters keep the universal-oracle gap, narrowed by the guardrail's patterns and the multi-file kill list, never closed.

## For the attack

Trust and blocking rules, numbered for the attacker. Each is to be broken as written.

1. A kill needs the test to pass in the round's shared baseline and inert runs both before and after its mutated batch, and to fail in two separate mutated runs, all from pristine state. The shared runs are once per test per round, and the record names the exact head. The named test, identified by `ancestorTitles` plus `title`, never `fullName`, must appear exactly once in the runner's report of the shared baseline and each mutated run, and read `passed` in the baseline and `failed` mutated; `skipped`, `todo`, absent, or a name the file holds twice is `invalid-claim`. For the TypeScript adapter, the pattern is the ` > `-joined name, regex-escaped and anchored. `invalid`, `load-error`, `timeout`, `invalid-claim` and a failing baseline are never `killed`; `invalid` is `apply`'s parse verdict on its input and nothing else, and a mutated module the runner cannot load is `load-error`. A test file that fails to collect in the mutated run, with the test present in the baseline, is `load-error`; this precedes the absent rule. A run whose `hitCount` exceeds `hitLimit` is `timeout`, whatever the test read. The shared baseline runs the same command as the probe with no mutant active.
2. A verification record is evidence at its own head only. A verification record is evidence only at the head it names, and only when its executor (the local ID Melian stores beside the install that ran it), its installation identity (the lockfiles, the test runner's version, the Node version, the platform and the architecture), its adapter identity and its policy digest (the SHA-256 of the effective base-sourced mutation policy, declared environment variables included, and the resolved test-command argv) each equal the reader's; a record that differs in any is rerun, never reused. A review at `H` reads records at `H` only when the review itself has leave to run `H`.
3. Verification and probes run head code under [the unconfined decision](2026-10-14-static-checks-run-unconfined.md)'s leave: a writer's head in the base repository, or `--trust-head`. `melian mutants verify` takes the same leave, with no shortcut: without `--trust-head` or a writer's pushed head it refuses, exits `2` and names `--trust-head`. That the inventory's `range.head` is the checked-out `HEAD` is a further guard, exit `2` otherwise, and never leave. `trust.writers: false` refuses a probe or a verification, as `leaveOf` refuses `static.mutation`. `{file}` and `{name}` substitute into argv elements, never into a shell string, because a test name is head text. A review without leave runs no probe. An adapter that must build the head to enumerate declares it and enumerates only under leave.
4. An `untested-behaviour` report names a probed mutant whose record reads `survived`; one naming a killed mutant is refused; one naming none is refused while a probe is available. A refusal under this rule applies only to a mutant the enumerator generated on the finding's line, whose probe at this head read `survived` or `killed`. A `timeout`, `flaky`, `invalid` or `invalid-claim` outcome, a line without a mutant, and an exhausted probe budget each make the probe unavailable for that finding, which goes to the verifier as today, with the outcome in the lens's record. A refused report is recorded on the lens's record as a note naming the mutant, the killing test and its file, and a review body lists the kills that refused a report.
5. A verifier may refute a `survived` finding only by naming a test; Melian verifies that test through the same classifier, and the outcome decides. The verifier may lower a standing finding one step within the fence. A refutation by `probe` keeps the trust floor.
6. `budget.probes` bounds a lens run's probes and `mutants.timeout` bounds each. A refused probe is a note on the lens's record, which stays `ran`; it is never a budget end and does not end the lens. `probe_mutant` always runs; a cached record is context, never the outcome. A related run's first failed test is only a candidate; it goes through the full verification, shared runs and two mutated runs, `killed` makes it the killer, `flaky` makes the probe `flaky`, and any other outcome reruns the related tests without it, within the same timeout. A probe whose related selection is empty or times out falls back to the whole suite under `mutants.suiteTimeout`, at most `mutants.suiteRuns` times per round, 1 by default, with the counter Melian's and kept in the round's own records.
7. `mutants.languages` and its test commands come from the committed root `melian.yaml`, read from the base for a pull request; a nested or preference file that sets them is refused.
8. The `mutants` check record is written by Melian at adjudication from the enumeration and the records; nothing the head writes reaches it. A `survived`, `timeout` or `load-error` verification record at the head becomes one `mutants/untested-behaviour` finding per mutant. Its discriminator is the SHA-256 of `[mutatorName, replacement, column, endColumn, text of the range, occurrence]`, and the trigger hash supplies the line; an `invalid` record and a config-ignored mutant cover with a note, and a comment-ignored mutant on a changed line is a P2 `mutants/ignored-mutant` finding that covers nothing. Whether a mutant is config-ignored comes from the policy source's `excludedMutations`, never from `statusReason`. The finding carries no snippet, so the discriminator is its ID input, and the discriminator appends the occurrence index among equal tuples in the file, so two identical lines do not collide. It reaches the ID through `Finding.create` with no snippet and `discriminator` set, which `findingId` hashes with the file and rule. The record joins every manifest without a tier entry, and a `melian.yaml` naming it in a tier or `checks.allowSkip` is refused. Under `required`, an unverified mutant on a changed production line leaves the review not reviewed.
9. The enumerator runs no head code: it reads blobs through git and instruments in an empty scratch directory. The instrumenter is the checkout's or Melian's, never a file in the revision's tree, and the record names its version. Its operator set is the instrumenter's less the `excludedMutations` of the `stryker.config.json` read from the policy source, never the head's copy, and those mutants stay as ignored rows marked `config`; every other ignored row is `comment`.
10. A mutant's identity is the SHA-256 of `[file, line, column, endLine, endColumn, mutatorName, replacement]`; sampling and records key on it, and a row without end coordinates is refused.
11. `static.mutation`, where a repository enables it, keeps every rule of [mutation reruns, as built](2026-10-16-mutation-reruns-later-changes.md). Melian's own tiers no longer name it.
12. A dismissal records the mutant discriminators it covers, and a surviving mutant it does not name reopens the line. It carries across heads by its trigger hash, as any dismissal does, and is the only way an `equivalent` claim stops counting.
13. `--jobs` runs that many claims at once. A kill needs the test to pass in the round's shared baseline and inert runs both before and after its mutated batch, and to fail in two separate mutated runs, all from pristine state. The shared baseline and inert runs run once per test per round before its mutated batch and once after, and serve every claim on it; a text adapter has no inert run. A trailing control that fails, or disagrees with its leading one, makes every candidate kill for that test that round `flaky`. A shared run that fails twice makes every claim on its test `invalid-claim`, and once makes them `flaky`. Two mutated runs that disagree are `flaky`. `flaky` covers nothing, leaves the mutant `unverified` and is listed in the review body.
14. The TypeScript adapter applies a mutant by activating it at run time in the instrumenter's switched build, never by splicing source text; the baseline runs the same build with no mutant active, so baseline and mutant run identical text. An adapter that must splice declares `applies: text`. Its kills are backed by the `forged-mutation-kill` guardrail's patterns for a changed test file that stringifies an imported function in an assertion, spawns `git show`, or reads a path under a production source directory, at P2 acknowledge. The setup file is the same text in both runs and sets `hitCount: 0`, `hitLimit` and `activeMutant`, `null` in the baseline; the child environment never carries `__STRYKER_ACTIVE_MUTANT__`; the mutant activates when the setup file loads. `hitLimit` is 100 times the mutant's `stryCov` count in a separate coverage run beforehand, unset when that count is 0 or unknown. In the shared, mutated and inert runs the setup file sets `mutantCoverage` to a sink that discards writes, and makes the namespace and that property non-writable and non-configurable before any repository setup runs. A test that reaches the instrumentation through computed names is within writer trust. The child environment is Melian's own: `LANG=C.UTF-8`, `TZ=UTC`, a fresh `HOME` and `TMPDIR` per run, `PATH` from the installation, and the base's `mutants.env`, nothing inherited. Each test that a claim names runs once a round with an inert mutant active, and a test that fails under it makes every claim on it `invalid-claim`. The review body lists every test that killed on more than one file, for every adapter.
15. Until a hermetic executor image exists, a verification record is reused only on the executor that made it, identified by the local ID Melian stores beside the install; any other executor reruns. `executor` is always that physical ID, for a claim and a probe alike, and `source` names the role.
