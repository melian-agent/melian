# Reports of one defect merge by a shared cause

Choice: two findings from different checks, in the same file, are one defect when their lines overlap and each cites a `cause` evidence location at head that overlaps one of the other's: the same file, with overlapping lines. The snippet rule stays as a second way in, so a finding with no `cause` location at head, such as every static and guardrail finding, merges only by its snippet, as before. Every other rule of the merge stands: findings from one check never merge, only findings with the same lifecycle status merge, `ruleAliases` with `distinct: true` keeps two rules apart, the speaker takes the highest severity and the strongest cause, and `mergeClaims` keeps every claim. Melian's fixed lens instructions gain one sentence: put a finding on the line or lines that break, and cite any wider span as evidence.

Why: the merge depended on which lines a model chose to cite. The snippet is the head's text at the finding's lines, so two lenses that cite different ranges for one defect have different snippets, and the "no fuzzy matching" rule kept them apart. On seven design goldens, Opus finders left one fail-open default in `src/publish.ts` as two to four findings: the design lens's `fail-open-default` at lines 6-7, the trust-boundary lens's `fail-open` at lines 5-7, and the removed-behaviour lens's `dropped-guard` at lines 3-8. Sol finders cited line 6 alone in every lens, so the same reports merged and precision was 1.00. [The cross-cells record](../../packages/evals/runs/2026-10-16-finder-verifier-cross-cells.md) holds the runs. The lenses do agree on the cause: each cites `src/publish.ts:5-7`, or lines inside it, as a `cause` location. A cause the lens cites is checked against the diff and quoted by Melian, so it is a location, not the model's wording, and matching on it keeps the merge mechanical. The instruction sentence narrows the finding's own range, so the snippet rule catches more of the same cases without relying on evidence.

The risk: two distinct defects that share a cause line now merge. Example: a null dereference and an unhandled rejection on the same call each cite the call as their cause, and become one finding that lists both rules in `alsoReportedAs`. A dismissal of the merged finding then answers both. That is the cost the snippet rule already accepts for two defects on one expression, now over a wider span. `ruleAliases` with `distinct: true` is how a repository keeps such rules apart.

A finding in another file still does not merge, even with the same cause. Example: on the same goldens, the correctness lens reports the caller at `src/cli.ts:8` and cites `src/publish.ts:5-7` as its cause. It stays its own finding. That is accepted: the caller is where a second fix may be needed, since `republishCommand` must pass the policy's answer whatever `canPublish` defaults to, and an author reading the review reads each file's comments where they sit. Merging across files would also move a finding off the lines its comment is posted on.

The removed-behaviour lens's `dropped-guard` in the goldens cites its cause at the base, `src/publish.ts:3-6 at base`, and the head lines only as `context`. Under this rule it stays apart: base and head line numbers are not comparable without the diff, and the rule matches head locations only.

The instruction sentence changes every lens's version hash, since the fixed block is part of each lens's rendered instructions. The pinned versions and golden snapshots are updated in the same change, deliberately, and a sighting stored under an older version stays a sighting of that version.

No earlier decision file records the merge rule; [docs/guidelines/core.md](../guidelines/core.md#dedupe-across-sources) and [design.md](../design.md#the-pipeline) set it out, and both change with this one.
