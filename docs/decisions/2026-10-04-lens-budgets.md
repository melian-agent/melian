# Lens budgets

Choice: A level's `budget.tokens` caps the input and output tokens of its lens conversation's model responses, cache writes counted as input and cache reads left out, and `budget.tools` caps its calls to the read-only tools; `report_finding` counts only against `budget.findings`. A call past `budget.tools` is refused. Once a round of tool calls spends either budget, every call in that round asks Pi Durable to end the run, so the conversation stops after the round with the findings it reported. The lens's check record is `ended` and names the budget that ended it, its limit, and the tokens and calls used, and an `ended` check makes the verdict not reviewed. A level may set `budget.ended: count`; its lens then records `ran`, with that ending, and its findings so far count. The built-in levels do not set it. Tokens come from Pi's per-conversation usage record and calls are recorded by call ID in the lens's own document, so a replay after a crash counts nothing twice.

Why: A lens its budget ended reviewed less than its level promised, and a required status must never turn green from reduced coverage. A large or adversarial change could otherwise exhaust a lens before it reached the defect, and the review would pass. A repository that accepts the cost of a cut-short lens says so per level. Cache reads re-read context a provider already counted, and counting them would charge a long conversation for every earlier turn again. Counting `report_finding` would let reading starve reporting, when the findings budget already bounds it. Pi Durable's hooks can read documents but not write them, so the counters live where a tool's commit can keep them durably.
