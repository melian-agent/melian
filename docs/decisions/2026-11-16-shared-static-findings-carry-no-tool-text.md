# A shared static finding carries no tool's text

Amends: [A shared record carries no text a tool, a provider or the head wrote](2026-11-16-shared-records-carry-no-outside-text.md), a record's sightings and Enola's receipt
Amends: [Melian stores no Biome or tsc text](2026-11-06-static-configuration-stays-in-the-checkout.md), the Enola and mutation follow-ups, for exported records alone

Status: the coordinator's answer of 2026-11-16 on [issue #516](https://github.com/melian-agent/melian/issues/516#issuecomment-6913692853), on approach. It is not a maintainer's ruling.

## Problem

A record a review exports keeps each finding it holds whole. Biome and tsc findings already carry Melian's fixed sentence, but Enola's and the mutation check's keep the text their tool wrote. That text can quote what the head led the tool to read, outside the checkout too.

Example: a mutant's replacement, a mutator's name, an ignored mutant's reason from a disabling comment, and the test files named to kill it all reach the finding's message and explanation. Enola's message on a symbol does the same. A head that makes either tool print a login sends it into a record any reader of the store can fetch. Enola's receipt went out whole as well, with any field Enola added.

An Enola result with no code to go by, such as a broken constraint, took its message as its discriminator. The discriminator is stored with the finding, and the message decides its ID, so the text reached the record whatever the export rewrote.

## Decision

- `ReviewRecords` rewrites every static finding a record holds, in a check's or a lens's sightings and a dismissal's, Biome and tsc included. Core's `staticFindings` gives those two a fixed sentence now, but a build from before [issue #281](https://github.com/melian-agent/melian/issues/281) stored their text, and the check's name says nothing of which build wrote a sighting. Melian's round two found the first form, which left Biome and tsc alone by their check's name, trusting a label. Any static check, one Melian adds later included, is rewritten: the rule denies by default.
- A rewritten finding's message and `explanation.what` read "`<check>` reports `<rule>` here.", then the fixed sentence `withheld`. Its `whyHere` and `whatToDo` are `withheld`. It keeps its rule, place, snippet, trigger and ID, which are the head's own content. Core's `Finding.parse` takes the ID from path, rule, snippet and discriminator, never from the message, so the rewritten finding still parses with its ID.
- A finding of a tool other than Biome and tsc with no code to go by takes `message <sha256 of the tool's message>` as its discriminator, in core's `identify`. A hash is the first kind of string a record may hold. Two results of one rule with different messages keep distinct IDs, identical ones still merge into one, counted, and a repeat review of the same head gives the same IDs. Biome and tsc keep their place, `line L, column C`.
- An Enola rule ID is kept only when it is the name of one of Enola's built-in checks, or exactly the `id` of a rule the base's policy declares, in `enola/constraints/` or `enola-intent.yaml`. Any other becomes `rule-<first 16 hex of its sha256>`, so `enola/rule-<hash>` in the finding, and the rule Enola wrote moves into the local message, which the export withholds. Problem: a rule ID is also the tool's text. The rewritten sentence and the record's `ruleId` both carried it, and the rule feeds the finding's ID, so the export cannot rewrite it alone. Solution: ask the authority. The pinned Enola 0.4.40, run on a scratch repository, names a broken constraint's result by that rule's `id`, which `EnolaPolicy` already reads from the base. A built-in check names its result by the check's name, such as `exported-surface`, and `enola help check` lists those names for the pinned version, so Melian keeps that fixed list beside the pin. So a rule ID in a shared record is Enola's fixed name, the repository's own policy text, or a hash. Codex's second adversarial review found that a first form, which kept declared rules alone, hashed every built-in check's rule, and with it `enola/god-class`, which core's edited-symbol rule matches by name. A shape check would not do: a login token has the shape of a rule name. This part is the coordinator's answer of 2026-11-16 on [the issue](https://github.com/melian-agent/melian/issues/516#issuecomment-6916894748), also on approach. The mutation check's rule IDs are three fixed words and need nothing.
- Enola's receipt keeps only the three fields Melian checks, `format_version`, `snapshot_id` and `enola_version`, re-serialised, and only when each has the shape Melian accepts. A receipt that is not that is `withheld`. The payload schema is unchanged.
- A static check's sightings leave the host only when the check run that wrote them proves, by its own request, a version of the check's code that stores no tool text: Biome, tsc, Enola and the mutation check at version 2 or later. The rewrite above cannot cover a sighting an earlier build stored. Example: a build from before [issue #281](https://github.com/melian-agent/melian/issues/281) stored Biome's message as the finding's discriminator, and a build from before this decision stored Enola's rule as the tool wrote it. The rule and the discriminator decide the ID, so the export must keep them, and with them the text. Codex's fifth adversarial review found that a review given bare check records, or a run of an older build, exported those sightings. The version comes from the run's request, never from a field beside it: `CheckRun.asked` is the request `runChecks` keyed, its key must equal the run's `request`, and core's `KeyedRequest` gives no other way to build one. A run that does not prove it exports the check as `failed`, with the code `withheld` and no sightings, so a reader on another host reads the round as not reviewed, never as passed while the host's own verdict blocks. The same holds for a dismissal: `ReviewRecords.dismissal` refuses a static sighting with `DismissError` `unprovenRun` unless the facts carry the proving request. To share such findings, a user reviews the revision again under the current build, whose run proves its version. This part is the coordinator's answer of 2026-11-16, recorded on [the issue](https://github.com/melian-agent/melian/issues/516), also on approach.
- The local store and terminal keep every finding's text as the tool wrote it.

`packages/pipeline/test/review-records-static-text.test.ts` feeds a made-up token through Enola's and Stryker's real normalisers, Enola's rule ID among them, a made-up static check, a dismissal and a receipt, and asserts no record's bytes hold it. `packages/pipeline/test/review-records-unproven-run.test.ts` plants a sighting holding a token, as an earlier build stored it, and reviews from bare records, an older build's run, a run whose request is not its key and a run with no request. It asserts no record holds the token and the reader reads not reviewed.

## What this gives up

A reader of another host's round sees which rule a static tool reported where, not the tool's words. It reads the reviewing host's terminal or store for them.

An Enola finding with no code to go by gets a new ID once, so a dismissal of one reopens once after the upgrade.

An Enola result whose rule is neither a built-in check's name nor one the base's policy declares, such as a recipe Enola expands, gets a hashed rule and so a new ID. A dismissal of such a finding reopens once. A `melian.yaml` resolution entry or rule alias that named the rule Enola wrote no longer matches it, and must name `enola/rule-<hash>` instead, which the terminal shows. A built-in check's rule and a declared constraint's rule, and their IDs, are unchanged. The check request key raises `static.enola` and `static.mutation` to version 2, so no check run an earlier build stored, whose findings held the tools' text, is reused.

A round reviewed from bare check records, or from a run of an earlier build, reads not reviewed on every other host when a static check sighted anything, however the reviewing host decided it. The reviewing host's own verdict is unchanged.

The hash of a short message a reader can guess can be checked by guessing. A login is not short or guessable, and the message's other content is the head's own.

The published review on a pull request still prints Enola's and the mutation check's text. That is the older follow-up of [the 2026-11-06 decision](2026-11-06-static-configuration-stays-in-the-checkout.md), and this decision does not change it.
