# Credential files

Choice: Credentials live in `melian.secrets.yaml`, git-ignored, mode 0600, beside the root `melian.yaml`, and in a user-level file under `~/.config/melian/`, so one file serves every repository an engineer works on. Preferences live in `melian.local.yaml` per clone and in a user-level configuration file in the same directory, with `melian.yaml`'s schema; the per-clone file wins over the user-level one, and both win over the committed file. A credential entry has a name, a provider, a type, and a value that is literal, an environment variable name, or a command, as Pi's store takes `!command`. A command source is allowed only in files the user owns, never in the committed `melian.yaml`; committed policy may name credentials and environment variables, nothing that executes. Resolution order: the secrets files, then Pi's store, then environment variables. Routes and stacking rules name credentials and never contain them. On Actions the secrets file arrives in one repository secret and the preferences file in a repository variable, which stays readable where a secret does not; each is optional. The credential references in `melian.yaml` join the policy-change list. `.gitignore` lists both local files, a guardrail blocks committing them, and `melian doctor` fails when either is tracked. GitHub masks a secret's whole value and not its substrings, so on Actions Melian registers every credential value with the `add-mask` command at startup, and the pool never puts a value in a message. User documentation says, neutrally, that whether a subscription may be used in automation or shared across a team is a question for the provider's contract, and that Melian takes no position.

Why: Routes and secrets want different handling, a reference to a secrets manager is not a secret, and the committed file must never execute anything: a merged change that runs a command on every engineer's machine at review time is a supply-chain hole.
