# A probing run's attach key holds its whole environment, and no moving context

Amends: [A trust-boundary level that probes](2026-11-07-trust-boundary-level-that-probes.md), the lens task's attach key

Status: ruled by the maintainer, 2026-11-09, in the builder's session for [pull request #296](https://github.com/melian-agent/melian/pull/296).

Problem: the lens task's attach key drew a new finding in five fix passes running. The last two came from the Actions round at `00804e57`. A run a quick level escalates to added no probing environment to the key, so a changed `probe.read` reused the old run. And the planner's earlier findings sat inside the instruction fingerprint. Re-reviewing the same head after a dismissal, or after another revision, therefore missed its attach and ran every lens again, though the review-attachment decision says a repeat call attaches. The same code could show a later revision's findings to the planner as the earlier revision's.

Choice: every run's selection, the first and the one a quick run escalates to, names its whole probing environment as one JSON value, so any change to its writer, the policy's word, its time limit, its grant or its host runs it again. The host is one value: the sandbox's platform and kind, and the CPU architecture and version of the Node that runs the probes. The coordinator chose that on 2026-11-14, applying the shared-record decision the maintainer adopted on 2026-11-13, that a check's request holds its host facts. [The identity guideline](../guidelines/identity.md) lists what about the host is left out, and why. The planner's decisions at base and its earlier findings leave the instruction fingerprint, as the caller-context decision kept caller context out, and stay in the prompt. That exclusion was a builder's choice; the maintainer accepted it on 2026-11-13, in the coordinator's session, after a host round at `4f83a8a6` raised it. The fingerprint holds the probing protocol as the build renders it, so a Melian release that changes it runs the level again: each role tool's name, description and schema, the fixed limits, and the table of every fixed wording the planner and the prober read, the planner's role and context among them. The prompt functions build their text from that table and hold no wording of their own, so every branch of each counts, and a test fails when one does. The verifier's version hashes the wording it reads of a claim's probe, a table of its own, the same way. Beside each table, each key hashes its prompts as `probingRenderings` renders them over fixed samples, one for each branch the render functions hold, so a change in how a prompt is put together, its order, separators or quoting, runs the level again or judges stored claims again. The maintainer ruled on that on 2026-11-13, in the coordinator's session, after the host round at `4f83a8a6` found the tables held every word and none of the assembly. A branch added later counts only once a sample renders it, and nothing enforces that. On 2026-11-13, in the builder's session, the maintainer ruled to hash the source of the code that renders each prompt, after a host round found that sampled renderings left a prompt's other branches outside the key. A function's source differs between loaders, as Vitest's, Node's and a published package's do, so a crash resume under another loader started the level again. On 2026-11-13, in the coordinator's session, the maintainer replaced that ruling with the table, which reads the same under every loader. The maintainer ruled on that on 2026-11-12, after two rounds running found fixed probing input outside the key. Its earlier findings come from the revision reviewed before this one, never one reviewed after it.

What it gives up: a repeat review of a head plans from the decisions and findings its first run read, not from those the head's base and history hold now, until something in its key changes. The selection names the paths a probe may read, not what they hold, so a reinstall of `node_modules` between two reviews of one head reuses the old probes; the head's lockfile fixes what should be installed. The maintainer accepted that gap on 2026-11-13, in the coordinator's session.
