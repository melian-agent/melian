## The problem

A probing level's planner, prober and verifier read fixed text written for the trust-boundary lens, and the schema let any lens set `probe`. Example: a `tests` lens at a level that probes would be told to plan "every way something untrusted could cross a boundary in this change". It would read that "a change that moves nothing across a boundary gets an empty plan", and to "exit 0 when the boundary holds". That text follows the lens's own instructions, so it contradicts them: the planner would return an empty plan for a change whose only defect is an untested branch. Of 45 past defects another reviewer found only by running code, 21 are test gaps, surviving mutants or wrong results, which probing cannot reach while only one lens can use it.

## The choice

`lensProbingWording` in `packages/core/src/probing-wording.ts` holds six strings for each built-in lens that may probe. They say what that lens's roles do: the plan the planner writes and its reminder, how it plans from earlier findings, what a probe shows and how it exits, what a finding cites, and how the verifier judges a probe. `trust-boundary`, `tests` and `correctness` have entries. Every other line those roles read is shared by every lens and stays in `packages/pipeline/src/probing.ts`.

- **A table in core, not `LENS.md`.** A lens's probing wording tells a model what a sandboxed program must show before a finding may cite it, and the verifier reads it as the rule a claim is judged by. A repository's lens file is the head's text when a round reviews a change to it, so wording there would let a change write the rule its own claims are judged by. Core ships the built-in lenses, so the table ships with the code that reads it, and a test can scan every entry. A repository's lens takes the wording of the built-in its `extends` chain reaches, through every farther lens, by the maintainer's two-lens ruling of 2026-11-16. A lens that extends a built-in keeps that built-in's purpose and adds to it, so the built-in's words fit it. `Lens.load` knows the chain: each `extends` resolves against the lens of that name as layered so far, and the built-ins enter first, marked by Melian's own files, so no folder name or front matter can fake the chain. A lens that extends no built-in with wording cannot probe until a later issue lets `LENS.md` carry wording that is read from the base and judged as the rest of a lens is. Refusing is the safe default, since a lens with another's words probes for the wrong thing. For the same reason a lens that takes a built-in's name probes only when it extends that built-in, through every farther lens of the name. One that takes the name without `extends` replaces the built-in with a purpose of its own, which the built-in's words were not written for. The coordinator first let the name alone decide, and corrected that after the second Melian round on [pull request #490](https://github.com/melian-agent/melian/pull/490) found it.
- **A probe without wording is refused at load.** `Lens.load` throws `LensError` with code `missingField`, naming `levels.<level>.probe`, the lens, the level and the lenses that have wording, for a level that sets `probe` in a lens whose `extends` chain reaches no built-in the table names. A lens built in code with `Lens.from` skips that check, so the pipeline throws too, before it renders a probing turn. `Lens.load` refuses `probe` in the same way on any lens whose chain reaches `tests`, at any level, naming [issue #493](https://github.com/melian-agent/melian/issues/493). It also refuses it on a lens that takes a built-in's name without extending that built-in, telling it to extend it.
- **A lens of another name records whose words it reads.** A lens with a level that probes, whose chain reaches a built-in of another name, carries `probesAs`, that built-in's name. Its lens version hashes it, and its run's `probe` carries it, so the lens request keys that built-in's wording and the verifier judges its claims in that built-in's words. A lens that probes in its own name's words, or does not probe, has no `probesAs`, so its version and key are unchanged. The prober's first line still names the lens itself, `trust-boundary-probes`, since the policy that follows is that lens's own; the coordinator chose that on 2026-11-16. A golden test runs the trust-boundary lens's turns through a lens renamed `trust-boundary-probes`, and they match main's byte for byte once the name is swapped back.
- **The trust-boundary lens keeps its words.** Its entries are the strings it read before, moved unchanged, so its planner's and prober's prompts are byte for byte what they were, which a golden of the captured requests shows.
- **Tool descriptions are neutral.** `record_plan`, its `reason` and `passing` fields, `run_probe` and the line `run_probe` returns for a probe that passed named a boundary. They are one definition offered to every lens, so they now say "why a probe might show a defect there, and what supplies its input", "prints when it shows no defect", "Exit 0 for the attack's passing outcome" and "so it showed no defect". The trust-boundary lens's sense still reaches its planner and prober through its own entries, which name the boundary. A tool per lens would have doubled every tool's schema in the key and the tests for one word.
- **The verifier judges each claim in its lens's words.** A probe evidence block carries the judgement of the claim's lens. `verifierVersion` still hashes the shared evidence wording and the trust-boundary lens's judgement, the text it hashed before, so it is unchanged. The verification request gains `judges`, the judgement of each lens whose claims in it rest on a probe, only when one does. A verification of claims without probes keys as before, and a change to one lens's judgement asks again only the verifications of that lens's probed claims. The wave version needs no `judges`: a lens task with a level that probes starts no wave, so no wave holds a probed claim.
- **The lens request keys the wording its lens reads.** A run that probes keys the shared lines and its own lens's entries, so a change to the `tests` lens's words asks no trust-boundary run again. A quick run that escalates to another level keys the shared lines, which carry its findings on; the run it escalates to keys its own lens's words.

## What it costs once

The trust-boundary lens's resolved wording is the value its key held before, but its key changes, since the probing tools' descriptions are in it. That costs nothing: a finished probing run is never reused, and no committed level probes. Every quick run that escalates keys the shared lines rather than the whole old table, so its key changes, and each head reviewed before the upgrade and again after it asks those quick runs once more. They run on the `quick` tier's route, Terra at `low` here, so the cost is a part of one round, which cost $3.57 to $9.85 on recent pull requests, once for each such head. A run that neither probes nor escalates keys as before. No verification is asked again, since none rests on a probe until a level probes.

## What it gives up

- The `tests` and `correctness` wording is unmeasured. No committed lens sets `probe`; turning it on is the maintainer's decision.
- A lens that extends a built-in probes in that built-in's words even when it replaces the built-in's description and rules with another concern, so only the built-in's concern is probed. A lens that extends `correctness` to add performance rules plans no attack on latency. The loader reads only the `extends` chain, not what a lens says it reviews. The maintainer's ruling on this is [recorded on pull request #490](https://github.com/melian-agent/melian/pull/490#issuecomment-6907367569).
- The `tests` prober copies the head's tree under its scratch folder to change a line and run a test, since the test runner writes beside its dependencies. The builder ran that under the real sandbox for [issue #483](https://github.com/melian-agent/melian/issues/483): unchanged and changed, the run took 5.2 and 6.4 seconds of a 30-second limit, and the pull request has the details.
- A `tests` probe whose test already fails on the unchanged copy cannot show whether the test covers the behaviour, so it exits 125, as `git bisect` reads "cannot test", and reports no finding. Melian still reads 125 as a failed probe, and an attack any probe answered counts as probed, so such an attack counts as answered and the lens can finish clean. So the `tests` wording ships, but `Lens.load` refuses `probe` on the `tests` lens until [issue #493](https://github.com/melian-agent/melian/issues/493) decides what an attack whose probes showed nothing counts as, and lifts the refusal. Only a lens built in code, as the fake-model tests build one, reaches the `tests` wording before then.
- A review in flight across this upgrade that holds a probing run of a lens the table does not name is not carried over. Before this change any lens could set `probe`, so such a run can exist. If its planner finishes under this build, the lens ends failed and the review reads not reviewed, with `ReviewError` `lensFailed`. If a claim already rests on its probe, the review stops with an error before it has a verdict. Neither is retried, and neither leaves a verdict that reads reviewed; the tests under "when its probing wording is gone by the time it resumes" in `packages/pipeline/test/probing-wording.test.ts` show both. A new review of the change is refused at load. No task version or migration carries such a run on, by the coordinator's choice of 2026-11-16, because three facts held that day. The level that probes merged on 2026-11-15, in [pull request #296](https://github.com/melian-agent/melian/pull/296). No committed lens had set `probe` but the eval goldens', whose `trust-boundary` lenses extend the built-in and still probe. No release had shipped it, since every package was at version 0.0.0. If any of these no longer holds, the choice needs making again.
- A stored probing run or verification of a lens other than trust-boundary, started before this change and resumed after it, is judged in that lens's new wording, though it was planned in trust-boundary's. Nothing refuses it, since no task version changes. Codex's adversarial review found the case. The coordinator answered on 2026-11-16 that it stays unmigrated, for the three facts above and because a version bump would collide with the lens task versions [issue #493](https://github.com/melian-agent/melian/issues/493) and [issue #489](https://github.com/melian-agent/melian/issues/489) have claimed. To be safe, review such a change again with `--rerun` when the lens failed, or else under a `MELIAN_STATE_DIR` of its own, since `--rerun` runs again only what failed and a finished review is printed from the store.
