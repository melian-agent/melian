## The problem

A probing level's planner, prober and verifier read fixed text written for the trust-boundary lens, and the schema let any lens set `probe`. Example: a `tests` lens at a level that probes would be told to plan "every way something untrusted could cross a boundary in this change", that "a change that moves nothing across a boundary gets an empty plan", and to "exit 0 when the boundary holds". That text follows the lens's own instructions, so it contradicts them: the planner would return an empty plan for a change whose only defect is an untested branch. Of 45 past defects another reviewer found only by running code, 21 are test gaps, surviving mutants or wrong results, which probing cannot reach while only one lens can use it.

## The choice

`lensProbingWording` in `packages/core/src/probing-wording.ts` holds, for each built-in lens that may probe, the six strings that say what that lens's roles do: the plan the planner writes and its reminder, how it plans from earlier findings, what a probe shows and how it exits, what a finding cites, and how the verifier judges a probe. `trust-boundary`, `tests` and `correctness` have entries. Every other line those roles read is shared by every lens and stays in `packages/pipeline/src/probing.ts`.

- **A table in core, not `LENS.md`.** A lens's probing wording tells a model what a sandboxed program must show before a finding may cite it, and the verifier reads it as the rule a claim is judged by. A repository's lens file is the head's text when a round reviews a change to it, so wording there would let a change write the rule its own claims are judged by. Core ships the built-in lenses, so the table ships with the code that reads it, and a test can scan every entry. A repository's lens of another name cannot probe until a later issue lets `LENS.md` carry wording that is read from the base and judged as the rest of a lens is. Refusing is the safe default, since a lens with another's words probes for the wrong thing.
- **A probe without wording is refused at load.** `Lens.load` throws `LensError` with code `missingField`, naming `levels.<level>.probe`, the lens, the level and the lenses that have wording, for a level that sets `probe` in a lens the table does not name. A lens built in code with `Lens.from` skips that check, so the pipeline throws too, before it renders a probing turn.
- **The trust-boundary lens keeps its words.** Its entries are the strings it read before, moved unchanged, so its planner's and prober's prompts are byte for byte what they were, which a golden of the captured requests shows.
- **Tool descriptions are neutral.** `record_plan`, its `reason` and `passing` fields, `run_probe` and the line `run_probe` returns for a probe that passed named a boundary. They are one definition offered to every lens, so they now say "why a probe might show a defect there, and what supplies its input", "prints when it shows no defect", "Exit 0 for the attack's passing outcome" and "so it showed no defect". The trust-boundary lens's sense still reaches its planner and prober through its own entries, which name the boundary. A tool per lens would have doubled every tool's schema in the key and the tests for one word.
- **The verifier judges each claim in its lens's words.** A probe evidence block carries the judgement of the claim's lens. `verifierVersion` still hashes the shared evidence wording and the trust-boundary lens's judgement, the text it hashed before, so it is unchanged. The verification request gains `judges`, the judgement of each lens whose claims in it rest on a probe, only when one does. A verification of claims without probes keys as before, and a change to one lens's judgement asks again only the verifications of that lens's probed claims. The wave version needs no `judges`: a lens task with a level that probes starts no wave, so no wave holds a probed claim.
- **The lens request keys the wording its lens reads.** A run that probes keys the shared lines and its own lens's entries, so a change to the `tests` lens's words asks no trust-boundary run again. A quick run that escalates to another level keys the shared lines, which carry its findings on; the run it escalates to keys its own lens's words.

## What it costs once

The trust-boundary lens's resolved wording is the value its key held before, but its key changes, since the probing tools' descriptions are in it. That costs nothing: a finished probing run is never reused, and no committed level probes. Every quick run that escalates keys the shared lines rather than the whole old table, so its key changes, and each head reviewed before the upgrade and again after it asks those quick runs once more. They run on the `quick` tier's route, Terra at `low` here, so the cost is a part of one round, which cost $3.57 to $9.85 on recent pull requests, once for each such head. A run that neither probes nor escalates keys as before. No verification is asked again, since none rests on a probe until a level probes.

## What it gives up

- The `tests` and `correctness` wording is unmeasured. No committed lens sets `probe`; turning it on is the maintainer's decision.
- The `tests` prober copies the head's tree under its scratch folder to change a line and run a test, since the test runner writes beside its dependencies. The builder ran that under the real sandbox for [issue #483](https://github.com/melian-agent/melian/issues/483): unchanged and changed, the run took 5.2 and 6.4 seconds of a 30-second limit, and the pull request has the details.
