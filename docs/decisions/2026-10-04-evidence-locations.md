# Evidence locations

Choice: Every lens finding carries a failure scenario and one or more evidence locations, `{ file, line, endLine, role, revision }`. `role` is `cause` or `context`, and `revision` is `head` unless the lines are ones the change deleted, which are read from the base. A finding outside the diff is `affected` only when a `cause` location overlaps the change: at head, a hunk's new lines; at the base, a hunk's old lines, in the file as the base names it; on either side, any line of a file the change renamed without editing, since the rename is what the change did to it, but only for a finding in a file the change edited or left alone. Moving files changes none of their lines, so no rename promotes a finding in a file the change only moved, whether its evidence names that file or a sibling moved with it, by either path. A `context` location never promotes a finding. Melian reads and stores the snippet at every location from the revision it names, and neither field enters the finding's ID. When findings merge, each keeps its own scenario and evidence, as [the merged finding claims decision](2026-10-04-merged-finding-claims.md) records. A findings, verdict, or published document stored before the change reads tolerantly: its single evidence location becomes one `cause` at head, and a missing failure scenario stays absent.

Why: A verifier needs something to attack. A finding that names a line and a worry gives it nothing; a concrete scenario and the code the claim rests on give it a claim to confirm or refute. Promotion stays structural, so prose still cannot cross the cause boundary. A deleted line is changed code: a removed guard that breaks a caller is the change's to answer for, and a pure deletion has no new lines for a head location to overlap, so a base location on the old lines is the only proof that case has. A pure rename breaks consumers that still name the old path, not the code it moved: a lens marks a defect's own line as `cause`, so counting the renamed file for its own findings would let an old defect block a pull request that only ran `git mv`. Excluding only the finding's own file is not enough: `git mv src/db src/database` moves every file in the directory, and a defect in `query.ts` could cite `conn.ts`, which also only moved. The tolerant read keeps a maintainer's stored reviews and dismissals across the upgrade, since a document Pi Durable cannot migrate fails every read of the changeset.
