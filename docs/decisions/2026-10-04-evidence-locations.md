# Evidence locations

Choice: Every lens finding carries a failure scenario and one or more evidence locations, `{ file, line, endLine, role, revision }`. `role` is `cause` or `context`, and `revision` is `head` unless the lines are ones the change deleted, which are read from the base. A finding outside the diff is `affected` only when a `cause` location overlaps the change: at head, a hunk's new lines; at the base, a hunk's old lines, in the file as the base names it; on either side, any line of a file the change renamed without editing, since the rename is what the change did to it. A `context` location never promotes a finding. Melian reads and stores the snippet at every location from the revision it names, and neither field enters the finding's ID. A findings, verdict, or published document stored before the change reads tolerantly: its single evidence location becomes one `cause` at head, and a missing failure scenario stays absent.

Why: A verifier needs something to attack. A finding that names a line and a worry gives it nothing; a concrete scenario and the code the claim rests on give it a claim to confirm or refute. Promotion stays structural, so prose still cannot cross the cause boundary. A deleted line is changed code: a removed guard that breaks a caller is the change's to answer for, and a pure deletion has no new lines for a head location to overlap, so a base location on the old lines is the only proof that case has. The tolerant read keeps a maintainer's stored reviews and dismissals across the upgrade, since a document Pi Durable cannot migrate fails every read of the changeset.
