# One finding per repeated shape

Choice: every lens, built in or Melian's `durability`, reports the instances of one shape as one finding. A shape either repeats in the change, or the change cannot close it case by case, as with a deny-list each new spelling slips past. The lens says which in the explanation, with the number of instances. It reports the finding at the instance its failure scenario traces. It cites each other instance as a further evidence location, in the role its own line has, up to the ten `report_finding` takes. For a shape closed case by case, the failure scenario names every input the lens found that slips past. "One strong finding beats several weak ones" still holds, for weak findings that are not instances of one class. The verifier judges such a claim at its own file and line, and names in its correction any cited instance that code prevents, without refuting the claim for it.

Why: rounds found one instance of a class a round, so the fix took a round per instance. Example: each round of [pull request #116](https://github.com/melian-agent/melian/pull/116) found one more spelling past the re-scope check's name matching: an alias, a default export, a binary file, a Unicode escape, a comment inside `export default`. Each early round of [pull request #117](https://github.com/melian-agent/melian/pull/117) found one more input missing from one attachment key. The lenses told the model that one strong finding beats several weak ones, and a findings budget capped the rest. A lens that saw the second instance had no instruction to report it.

One finding beats one per instance. Findings from one check never merge, so three reports would stand as three findings. A reader would fix three lines and not see the class. The golden scoring counts a second report of a found defect as a false positive. The evidence list already holds ten locations, `Finding.mergeClaims` keeps them, and the renderer prints each. Neither the failure scenario nor the evidence enters a finding's ID, so a later round citing more instances keeps a dismissal.

What this gives up: a finding's ID hashes the reported instance only. When the author fixes that instance and leaves the others, the next round reports the class at another instance, under a new ID. An instance past the tenth location is named only in the explanation. A dismissal covers the class, so an author who dismisses it for one instance's reason dismisses all.
