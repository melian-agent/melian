# One finding per repeated shape

Choice: every lens, built in or Melian's `durability`, reports the instances of one shape as one finding. A shape either repeats in the change, or the change cannot close it case by case, as with a deny-list each new spelling slips past. The lens says which in the explanation, with the number of instances. It reports the finding at the first instance the change caused in file and line order, so the reported instance, and with it the ID, does not move between rounds, where its own report instructions put a finding: `contracts` at a broken dependant, the others mostly on changed lines. It cites each other instance the change caused as a further evidence location, in the role its own line has, up to the ten `report_finding` takes. An instance that predates the change is cited as `context`, since a `cause` location on changed lines would make an old instance the change's. For a shape closed case by case, the failure scenario names every input the lens found that slips past. "One strong finding beats several weak ones" still holds, for weak findings that are not instances of one class. The verifier judges such a claim at its own file and line, and names in its correction any cited instance that code prevents, without refuting the claim for it.

Why: rounds found one instance of a class a round, so the fix took a round per instance. Example: each round of [pull request #116](https://github.com/melian-agent/melian/pull/116) found one more spelling past the re-scope check's name matching: an alias, a default export, a binary file, a Unicode escape, a comment inside `export default`. Each early round of [pull request #117](https://github.com/melian-agent/melian/pull/117) found one more input missing from one attachment key. The lenses told the model that one strong finding beats several weak ones, and a findings budget capped the rest. A lens that saw the second instance had no instruction to report it.

One finding beats one per instance. Findings from one check never merge, so three reports would stand as three findings. A reader would fix three lines and not see the class. The golden scoring counts a second report of a found defect as a false positive. The evidence list already holds ten locations, `Finding.mergeClaims` keeps them, and the renderer prints each. Neither the failure scenario nor the evidence enters a finding's ID.

What this gives up: a finding's ID hashes the reported instance only. When the author fixes that instance and leaves the others, the next round reports the class at another instance, under a new ID. An instance past the tenth location is named only in the explanation. A dismissal covers the class, so an author who dismisses it for one instance's reason dismisses all. The verifier confirms the claim at its reported line, so a cited instance that code guards stays in the evidence, flagged only in the correction. When code guards the reported instance but not a cited one, the verifier answers plausible rather than refute the class.

One limit weakens a dismissal, and is open for the maintainer. An `introduced` finding's dismissal reopens only when its own hunk changes. So an instance a later push adds, which the lens cites on the dismissed finding, is hidden with it, where before it was a finding of its own. Closing it needs code: a reopen keyed on every cited `cause` hunk, as [the affected-finding trigger](2026-10-04-affected-finding-trigger.md) keys one on every proving hunk, or a grouped finding with an identity, cause and status per instance. Neither is built.
