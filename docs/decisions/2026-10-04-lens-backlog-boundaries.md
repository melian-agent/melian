# Lens backlog boundaries

Choice: `trust-boundary`, `removed-behaviour`, `tests`, and `conventions` ship as built-in lenses in the default `full` tier, each one angle with its own rules, and each body says which defects belong to a neighbour. A wrong value, a null dereference, or a dropped error in a line the change wrote is `correctness`'s; `removed-behaviour` reports what a deleted or moved line stopped doing, citing the deleted lines at the base. A deleted check that stood between untrusted input and something that trusts it is `trust-boundary`'s, not `removed-behaviour`'s. A deleted or weakened assertion is `tests`'. `correctness` hands back in turn: a deleted cleanup, error path, or ordering goes to `removed-behaviour`, a value an author or outside party controls reaching a sink or passing a check goes to `trust-boundary`, and a defect in a test goes to `tests`, each through its `handoffs` and only in a review that runs the owner; otherwise `correctness` keeps the coverage it had before the owner existed. A removed guard stays with both `correctness` and `removed-behaviour`, because `correctness` reads it as declaring the inputs it rejected. `trust-boundary` reports hostile input only when code it read says who controls it, and leaves a loosely pinned dependency to the standards or a static rule. `tests` reports a missing test only where the repository tests that code or the code beside it, and reports a vacuous test once, at the test, not again as untested behaviour. `conventions` reports only a rule it can quote word for word from the standards and a line that breaks it, reports nothing when the repository has no standards, and reports a stale document at the document's line with the changed code as `cause`. A golden declares a second finding for one defect only where a second lens's own instructions claim it: `correctness-deleted-guard` and `removed-behaviour-dropped-guard` each expect both `correctness`'s `wrong-result` and `removed-behaviour`'s `dropped-guard`.

Why: The first two live runs showed that two lenses reporting one defect under two rules halves precision, and that a lens follows its rule descriptions over its body when the two disagree ([runs/2026-10-03-live-goldens-2.md](../../packages/evals/runs/2026-10-03-live-goldens-2.md)). Any edit is a deletion and an addition, so `removed-behaviour` would otherwise restate every `correctness` finding on a modified line. The [sixth live run](../../packages/evals/runs/2026-10-04-live-goldens-6.md) measured the boundaries as first written: most defects drew two or three reports, mostly from `correctness`, which nothing told about the new lenses, so the boundary has to be stated on both sides. Stated unconditionally, it left a hole: the `pre-push` and `comment` stages run the `standard` tier, which holds `correctness` alone, so a deleted cleanup or a hostile input there went unreviewed, and a custom tier or a disabled lens did the same. A missing test in a repository with no tests is not a defect this change made, and saying so on every change is the noise the design exists to avoid. A convention that cannot be quoted is a preference, which [the comparison of review tools](../research/2026-10-04-review-tools-compared.md) shows the cleanup angle refusing to report.
