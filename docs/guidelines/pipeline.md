# Pipeline guidelines

The pipeline package is the only place review flow lives, and the only package that talks to Pi Durable. These rules come from the [Pi Durable spike](../spikes/pi-durable.md).

## The harness wrapper

`packages/pipeline/src/harness.ts` is an import quarantine. It and `src/testing.ts` are the only modules that import Pi Durable, pi-ai, or Chord.

It quarantines import paths, not churn. It re-exports Pi's API unchanged, so callers compile against Pi's experimental contracts: an upstream rename moves one import in the wrapper, but a changed signature still breaks every caller. That is acceptable while the spike's tests are the only callers. As steps 5 and 7 add callers, a narrow Melian-owned facade grows in front of the wrapper, and raw Pi types do not cross out of `packages/pipeline`.

- Re-export Pi's concepts under Pi's names, so Pi's README stays the reference. Give Melian names only to helpers Melian adds, such as `openHarness` and `createFakeModels`.
- Export only what Melian code uses. Add an export in the same change as its first caller.
- Keep test helpers in `src/testing.ts`, published as `@melian-agent/pipeline/testing`. `src/index.ts` exports runtime API only.
- When upgrading Pi, read the changelog and the type declarations, run the spike tests, and update the spike report where behaviour moved.

## The findings document

`FindingsDocument` in `src/findings.ts` holds a conversation's findings keyed by stable ID. It is rewindable and forks `asOf`, so a fork taken at a revision's entry sees that revision's findings and nothing reported after it.

A revision is a base and a head, never a head alone. `revisionKey({ base, head })` writes it as `<base>..<head>`, and every document a review keys, the findings' sightings, the review index, and the verdicts, uses that key; below, "at a revision" means at that key. Problem: everything was keyed by head, and a stacked pull request retargeted after its parent lands keeps its head but has a new diff. Example: reviewed against its parent, the child passed; retargeted onto `main`, its second review attached to the first lens task with no model call and read `passed` for the parent's code no lens had seen. The other way round, a finding in the parent's code stayed `introduced` and blocking after the parent landed. Solution: a new base is a new revision, so it gets its own lens task, which classifies cause against its own diff, and its own verdict. `test/review.test.ts` retargets a child both ways.

Each ID holds sightings and one lifecycle record. A sighting is what one producer, a lens's name and version, reported at one revision: the finding without its status. Sightings are keyed by revision, then producer, and only the same producer at the same revision ever replaces one. The lifecycle record is Melian's: `status`, `dismissedBy`, `dismissedReason`, `dismissedAt`, `firstSeenRevision`, `lastSeenRevision`, a `history` of dismissals that no longer stand, reopened or replaced, and, for a finding sighted as `affected`, the `proof` its dismissal is tied to. Problem: a lens reports the same finding again on every revision, and an upsert that replaced the whole finding would reset it to `new`. Example: an author dismisses `eval(input)` as safe because the input is a constant; the next push reruns the security lens, which reports it again, and the dismissal vanishes. Solution: a producer only ever writes its own sighting.

Problem: one producer record per ID raced. Example: the correctness and contracts lenses both declare `null-dereference` and report one ID at one head; the second either replaced the first's severity and source, or, as a first fix did, was refused. A review of an older head that crashed and resumed after the next push wrote over the record the newer head read. Solution: immutable sightings per head, producer, and ID, merged on read.

- The document belongs to the changeset's root conversation, never to a lens's child conversation. Problem: a lens conversation ends with its task, and a fork of the root taken to rerun a revision would not carry a document kept in a child, so the next revision would see every finding as new. Solution: `upsertFinding`, `dismissFinding`, and `readFindings` take the root conversation's ID, and step 5's `report_finding` tool is constructed with that ID and writes through it, whichever conversation calls it.
- A lens's sightings name it by `lensSource(name, version, level)`: the check `lens.<name>` and the version `<version>@<level>`, so one lens at two levels of one revision is two producers, and an escalated run never overwrites the quick run's sightings. A lens conversation an older Melian created names no level, and its findings keep the version alone.
- Write findings only through `upsertFinding(tx, rootConversationId, finding, revision)`. It validates with core's `Finding.parse`, replaces the sighting of `properties.source` at `revision`, and keeps the lifecycle record. The lifecycle starts as `new` when the ID is first seen.
- The document lists the heads reviewed, oldest first. `reviewChangeset` calls `recordRevision` in the commit that creates its lens task, and `upsertFinding` appends a head it has not seen. `lastSeenRevision` moves to `revision` only when `revision` is not older than it, so a resumed review of an old head cannot move it back. A dismissed finding stays dismissed unless a sighting at the last-seen head or a newer one has a trigger whose code changed materially, which for now means its normalised `trigger.snippet` differs from the merged finding's at the last-seen head; then its status becomes `new` and the dismissal moves to `history`. A moved or reindented trigger is not material. An invalid finding throws `FindingError` and aborts the whole transaction.
- A replayed or retried `upsertFinding` writes the same state again, so a tool that calls it is an idempotent upsert and can be marked `replay: "safe"`.
- Dismiss with `dismissFinding(tx, rootConversationId, id, { by, reason, at })`. The caller supplies `at`, so a replay writes the same timestamp. An unknown ID throws `FindingError` `unknownFinding`, and a blank dismisser or time, or a reason core's `dismissalReason` refuses, `invalidDismissal`. Dismissing a dismissed finding replaces its reason and moves the old dismissal to `history` with `replacedAt`, and returns it. A host dismisses through `recordDismissal`, below, which also decides the verdict again.
- Read with `readFindings(reader, rootConversationId, revision, context)`, which merges the sightings at `revision` into one core `Finding` per ID with the lifecycle's status, in ID order, and treats an absent document as empty. The highest severity wins, a tie goes to the producer whose check, then version, sorts first, and `properties.reportedBy` lists every producer that sighted the ID. The winner takes core's `Finding.mergeClaims` of the sightings: it keeps its own failure scenario and evidence, takes the strongest cause with the `cause` locations that prove it, and carries every other sighting's claim in `otherClaims`. So a `P1` with a `cause` location in the change beside a `P0` without one reads as an `affected` `P0`, which blocks, not a `pre-existing` one, and the `P1`'s scenario survives beside the `P0`'s. A finding with no sighting at `revision` is not returned, even if an earlier revision reported it. Pass `{ producers }` to merge only those producers' sightings; `reviewChangeset` passes the lenses and versions it ran. Problem: the document keeps every sighting at a head, so a lens that configuration later disabled, or retiered to a new version, left its findings in every later review of that head. Solution: a review returns only what its own lenses reported. Each finding carries its lifecycle's `dismissal` while it stands and its `history` as `pastDismissals`, which `upsertFinding` strips from what a producer sends. It returns deep copies typed `readonly Finding[]`: `snapshot()` hands back the harness's cached document, so a caller that changed a returned finding would change what every later reader sees without a commit.
- A change to the stored shape bumps the document's version and gives it a `migrate`. Pi Durable
  refuses to read an older version without one. A changeset whose findings cannot be read cannot be
  reviewed again. Version 6 of the findings document reads version 5 unchanged and adds optional
  per-sighting verification maps. Version 5, version 3 of the verdict document, and version 2 of the
  published document turn a finding's single evidence location into a list through core's
  `Finding.upgrade` and `Verdict.upgrade`; [the core
  guideline](core.md#findings-stored-before-evidence-became-a-list) says why. Pi Durable migrates on
  read and stores the new version on the next write, and `test/findings.test.ts` stores each old
  shape in SQLite through a token of the old version and reads it back. A lens task created before
  the upgrade keeps the `ReviewState` it was created with, whose files carry no `oldPath`, so for
  that task a base `cause` location naming a renamed file by its old path never promotes a finding;
  a review started after the upgrade does.
- The functions take and return core's types. The document token stays inside the package. `upsertFinding` takes Pi's transaction, so its callers, such as step 5's `report_finding` tool, live in the pipeline.

## Credentials

`createReviewModels()` builds the models a review runs on, as a `ReviewModels` handle from `src/models.ts`. The handle is opaque: it wraps pi-ai's collection, which only the pipeline unwraps with `modelsOf`, so `ReviewOptions`, `openReviewHarness`, and the evals API name no Pi type. The testing entry's `createFakeModels()` returns the same handle as `review`, beside the raw collection a test passes to `openHarness`. The collection holds every built-in provider, resolving credentials as pi-ai does, a stored credential first and the provider's environment variables second. The store is the class `PiCredentialStore`, pi-ai's `CredentialStore` over Pi's `auth.json`, the file `pi` writes on `/login`: `$PI_CODING_AGENT_DIR/auth.json`, or `~/.pi/agent/auth.json`. `createReviewModels` constructs `PiCredentialStore` directly, and `piCredentialStore()` remains as a thin factory for callers that already use it. Constructing the store does no I/O, so its constructor is public; a class whose construction does I/O or validates input has a private constructor and a static `open`, as Pi's `SqliteStorage` does. One `pi` login covers Melian.

The store is read-only, and that has two consequences that read like bugs:

- An OAuth login that has expired, or expires within seven minutes, reads as absent, so the provider's environment variable or the tier's next model applies, and a refresh pi-ai attempts anyway fails with "run pi to refresh". Seven minutes is pi-ai's refresh window, five minutes (`DEFAULT_OAUTH_MINIMUM_VALIDITY_MS` in its `auth/resolve.js`), plus two of margin: a token selected four minutes before expiry is refreshed by pi-ai before its first request, and that refresh is a write. Recheck the window when upgrading pi-ai. pi-ai refreshes a token by writing it back through the store, and providers such as Anthropic rotate the refresh token on every refresh. A Melian that refreshed in memory without writing would leave Pi holding a dead refresh token. Expiry is checked in the store because pi-ai's `checkAuth` ignores it, and model selection relies on `checkAuth`.
- A malformed `auth.json` is a `PiCredentialsError` with no cause: V8's JSON `SyntaxError` quotes the text around the fault, which can be part of a key.
- A key Pi resolves at use, `!command` or one containing `$VAR`, reads as absent, so the provider's environment variable applies. Melian runs no commands from Pi's credential file.

Anthropic resolves in pi-ai's order, with one alias Melian adds:

1. Pi's store.
2. `ANTHROPIC_AUTH_TOKEN`, sent as a bearer token.
3. `ANTHROPIC_OAUTH_TOKEN`.
4. `CLAUDE_CODE_OAUTH_TOKEN`, the name Claude Code keeps the same kind of token under. Melian reads it only when `ANTHROPIC_OAUTH_TOKEN` is unset, and pi-ai still labels the source `ANTHROPIC_OAUTH_TOKEN`.
5. `ANTHROPIC_API_KEY`.
6. Workload identity federation.

Melian never logs or reports a credential's value; errors name the file and the provider only.

`createReviewModels({ credentials })` puts the named credentials of the secrets files, as core's `loadSecrets` returns them, in front of Pi's store, through `MelianCredentialStore`, which wraps a `PiCredentialStore` and, like it, never writes. A provider's first usable named credential applies, in precedence order, before Pi's store. An unread command counts as present until the review unlocks it. A command runs through `/bin/sh` at the provider's first read, once per process, with a 60-second limit; a failure, output over 64 KiB, or an empty value is a `CredentialError` naming the credential and its file, never what the command printed. A named credential whose provider the catalogue does not know, such as a misspelt one, is `CredentialError` `unknownProvider` when the models are built, rather than a credential that silently goes unused. pi-ai wraps a store's error in its own, which names only the provider, so the CLI calls `unlockCredentials(models, plan.providers())` before a review, which runs those commands and lets the named error through. `planInputs(models)` returns what the review plan resolves against: pi-ai's chat models as core's `CatalogModel`s. It also maps each provider with credentials to where they come from: a named credential and its file, Pi's login, or the source pi-ai's check names, such as `ANTHROPIC_API_KEY`. It asks the store to describe a named credential rather than read it, so it runs no command. `providersWithCredentials` reads the same map.

`MelianCredentialStore` takes an explicit lookup of each provider's auth kinds. `createReviewModels` reads these from the collection's `getProvider(id).auth`. API keys win when supported; an OAuth-only provider receives `{ type: "oauth", access, refresh: "", expires }`. JWT `exp` is seconds, converted to pi-ai's milliseconds without signature verification. A numeric claim at most 30 days ahead supplies the expiry. A larger claim or a value without a credible expiry gets a rolling one-hour lease on every read. The same seven-minute cutoff as Pi's login prevents refresh attempts with an empty refresh token. pi-ai does not skip refresh for an empty token, and `minOAuthValidityMs` can increase its five-minute window. Melian never calls a provider to refresh: its store refuses every write. A caller requiring more validity than remains gets that refusal. Refresh through the tool that owns the token, then review again.

Planning describes only credentials whose type the provider accepts. Literal and environment bearers are checked for expiry; a command is provisional until read, and doctor never runs it. Unlocking checks the selected bearer before storage opens. An unusable command bearer throws `CredentialError` `tokenExpired`, naming the credential and asking for refresh through its owning tool, even when Pi holds a usable login. A provider accepting neither kind cannot count as credentialed. `createReviewModels` refuses a named credential for it with `CredentialError` `unsupportedAuth`, which doctor reports as a failure.

There is no credential pool yet; one credential per provider, the first usable named value, else Pi's, else the environment's.

## Reviewing a changeset

`reviewChangeset({ harness, changeset, config, lenses, standards, models, policy, tier, checks })` runs deterministic checks when its wrapper has an environment, then lenses and adjudication, and returns a `Review`: the root conversation's findings at the head and the `Verdict`. The harness must hold `lensExtension`, which carries both tasks; open a `ReviewHarness` with `openReviewHarness` and pass the wrapper for automatic checks. A raw harness requires explicit `checks`, with the extension installed in its registry. `ReviewHarness` owns the Pi harness and closes it, and its storage, with `close()`; an open that fails closes the storage too. Without it a task would sit blocked forever, so `reviewChangeset` checks `harness.inspect()` after creating each task and throws `ReviewError` `notInstalled`.

1. `Lens.select` picks the lenses the changed paths and configuration call for, and the changed files each covers. A renamed file is offered under its old path and its new one, so a lens whose paths held the file before a move still reviews the move. The review adds the file's head path to that lens's coverage as `moved`, for that review alone, so `report_finding` accepts a finding in the moved file; the lens's paths are unchanged for every other file. No model is asked.
2. Each lens runs at a scrutiny level triage chose, as [Triage and escalation](#triage-and-escalation) describes, `careful` without a decider. The level's tier resolves through `resolveModelForTier` to its route: the model and fallbacks the collection knows and holds credentials for, in order. A tier with none is `ReviewError` `noAvailableModel`. With `options.plan`, core's `ReviewPlan`, the plan's `routes()` replace the configuration's first. The plan judges each lens at the level triage chose, never at intake. A lens on a tier it refuses there, `unavailable: fail` with no accepted model credentialed or a route `acceptOverridden: false` refuses, is left out and recorded `failed` at that level, with the plan's reason and the route's lineage, so it asks no model. A tier the plan refuses still counts as runnable for triage, so a lens it chose there records the refusal rather than quietly running at another level. A lens triage put on a routed level runs, whatever the plan says of its other levels. An escalation whose next level the plan refuses is capped with the plan's reason. `plan.mark` judges each record at the level of the run that stands for the lens. A host's own `lens.*` records give way to the lens step's; the plan's refusal is the lens step's own record.
3. One root commit creates the lens task, whose input carries the revision under review: the repository, base, head, and changed files. The same commit records the task in the root's `ReviewIndex` document under the revision, with the selected lenses by `name@version@level` and the route each resolved, each at the level triage chose. It also records the band that level was held to, `triage.escalateAt`, and the run a quick run escalates to or why it is capped, since all of them decide what the task escalates. A review under another plan then runs the lenses again rather than attach to a task that ran on the old route. A replacement run must also be the only run the verdict reads. Problem: sightings are keyed by `lens.<name>@<version>`, without the route. The replaced run's sightings stayed at the revision beside the new run's, and a crashed replaced task could resume and keep writing. Solution, in five parts. The commit that creates the replacement drops the replaced run's sightings of the selected lenses at the revision, lifecycle records kept. `runLenses` aborts the replaced task before anything resumes it. A review harness, as it opens, and every review, as it starts, abort any live lens task the index no longer names. A process that died between the two left such a task behind. A lens task asks no model once the index names another task, or none, for its revision. A review that selects no lens rewrites the entry this way. `report_finding` refuses a report from a lens whose task the index no longer names. `reviewChangeset` then settles each lens from the runs the task's stored input holds, never from its own fresh computation. A review that attached follows the escalation the task made. Problem: a repeat review after `escalateAt` moved from `P1` to `P2` attached to a finished task that had not escalated a quick run's `P2`. It returned the quick run's verdict. Solution: either input is part of the selection, so a change to it starts a task of its own. Problem: `harness.resume()` restarts a crashed review's task, and a second call created another, so after a crash every lens ran twice. Solution: `reviewChangeset` looks the revision up first, inside that commit. When the same lenses reviewed it, it waits for that task, running, crashed, or finished, instead of creating one. A different selection, such as a disabled or retiered lens, starts a new task and replaces the entry. `test/review-crash.test.ts` kills a review in each lens's first model request, calls `reviewChangeset` again, and expects exactly one more request per lens. A task that ended without deciding anything, `aborted`, `faulted`, or `orphaned`, is not attached to. The commit reads the task's record and replaces the entry with a new task. Problem: an aborted lens task stayed in the index, so every later review of the head attached to it and failed the same way. When `reviewChangeset` aborts a task no extension defines, it also removes the task from the index. The adjudication task follows both rules.

A failed task is a decision, but not always a lasting one. Problem: a repeat call with the same input attached to an adjudication task that had ended `failed`. A policy that could not be read once, such as a base commit a shallow clone had not fetched yet, then failed every later review of that head. Solution: a failed adjudication task is always replaced on the next call, because adjudication is cheap and deterministic. A lens task that left a lens failed is replaced only with `options.rerun`, because rerunning lenses costs tokens; the CLI will expose it as `--rerun`. A lens that finished on a model the plan refuses, a fallback outside a guarded `accept`, counts as failed here too: its outcome says `done`, but `plan.mark` records it `failed`, so `rerun` asks the plan before it reuses the task.
4. The task's first phase creates every lens conversation in one commit, configured with its model,
its instructions at its level (`lens.renderInstructions`), and an explicit tool list, and records
the lens's policy, the level's budgets among it, and that revision in its `LensDocument`. Each lens
carries its own revision, never a shared record on the root: a crashed review's lens task resumes
alongside the next push's, and a shared record would move the old lenses to the new head mid-review.
The second phase submits the change, rendered by the review's `ChangePrompt` with only the files
that lens covers, to each lens in parallel, with a request ID per lens so a rerun does not submit
twice. Before the task starts, `reviewChangeset` gives each lens its neighbours: every other lens it
selected, with the files that lens covers among this one's, `every` when it covers them all, and
none when it covers none. A lens covers the changed files `Lens.select` gave it and, for a file it
reached through an old path alone, the file's head path, so a neighbour selected through an old path
holds the hand-off for the moved file; and a neighbour over a renamed file's head path covers its
old path too, so a rename alone never turns a neighbour over every file into a list. The lists reach
the instructions through `quoteUntrusted` with the `listing` label, since a path is the change's
data. A neighbour whose list passes core's cap gets no hand-off, and the lens's `ran` record carries
a `reason` naming it, which the verdict prints beside the lens's level.
5. A lens whose model fails moves down its route. Problem: the route used to be cut to its first model before the task ran, so a provider outage failed the lens with its fallbacks unused. Solution: the route travels in the task's input. A request ends `unanswered` with a `model_error` that pi-ai would retry, after Pi Durable's own retries gave up, or one that names a failed authentication. Then the task configures the lens conversation with the next model and advances the lens's attempt index in the same commit, and submits a short hand-over input asking the new model to continue. Each attempt has its own request ID, `lens:<key>:<attempt>`, where the key is `name@version@level`, so a crashed review resumes on the model it had reached and never resubmits to one that already failed. `isFailoverError` in `src/harness.ts` classifies the failure: pi-ai's `isRetryableAssistantError` for transient failures, and a pattern for authentication, which pi-ai does not classify. Any other failure, such as a malformed request, fails the lens without trying another model.
6. Each lens becomes a `CheckRecord` named `lens.<name>`, from the run that stands for it, its last after any escalation, with the level that run ran at: `ran`; `ended`, with `budgetEnded`, when a budget ended its conversation, or `ran` with `budgetEnded` when its level sets `budget.ended: count`; or `failed` with the reason it did not finish, a route that ran out included. With a plan, `plan.mark` adds the `lineage` of the model the lens finished on, which the lens task's outcome records after any failover. A lens that finished on a model its policy refuses, a fallback outside a guarded `accept`, records `failed` with the plan's reason, whatever it would otherwise record. They join `options.checks`, the records of the review's other checks, as [The manifest](#the-manifest) describes.
7. The adjudication task decides the verdict and records it, as [Adjudication](#adjudication) describes.
8. A review whose lens task a later review replaced records no verdict: it is `ReviewError` `superseded`, and it leaves the review index naming the newer run, whose selection it no longer holds. A lens whose route runs out is `ReviewError` `allModelsFailed`, naming the lens in `lenses`, every model it tried in `models`, and the last failure in the message. A lens that does not finish for any other reason is `lensFailed`. Both carry what was reported and the `not-reviewed` verdict already recorded. A host that publishes catches the error and publishes that verdict.

`ReviewOptions.standards` takes core's `Standards`, or a flat section array for callers that give every lens the same standards. Each running lens unions the chains of its covered files, with both sides of a rename. A cap omission joins its check record's notes and records `ended`, leaving the verdict not reviewed. A lens opting out gets no sections or paths. Worktree sections render inside separate `quoteUntrusted("standards", ...)` blocks, heading included. Revision sections stay plain only when their resolved commit equals the validated policy commit. Flat arrays lack provenance and are quoted, as are mismatched revisions. The lead-in names attempts to change review behaviour as `melian/injection-attempt`. This leaves the conventions neighbour rule unchanged.

Lens selection includes stable instruction fingerprints for first and escalated runs. The hash includes raw standards and provenance alongside rendered text; fresh boundary nonces do not affect it.

### Triage and escalation

Triage runs when `options.decider` is given, and the harness must hold `decisionExtension` for it, as `ReviewHarness.open` installs it with `decider`; otherwise `reviewChangeset` throws `notInstalled`. It asks one choice question per selected lens name. Two folder variants of a lens share a name, so they share a question offering every option either offers. Each holds the answer to its own band, read per selection, never per name. It asks them in one `melian.decision` task per revision and question set. The task's input carries the request. Its terminal commit writes the decision, with its whole distribution, or the decider's failure, into `DecisionDocument` on the root, read with `readRecordedDecision`. The state is the change prompt inside the review's boundary, after `triageBoundary`. That text tells the decider that anything there steering a lens's level is a reason to look closely. A repeat call attaches to the task when the decider's name and the questions match. The state stays out of the match, since its nonce differs on every call. The LLM fallback's name carries its model, so a review that routes triage to another model asks again. A task resumed by a harness holding another decider ends aborted without storing an answer or failure. That review uses the default level; a later review with the original decider asks again. Only `rerun` asks again, and only after a decision that did not complete: one that failed, or one a crash left undecided. Problem: a decision asked afresh after a crash could choose other levels, change the selection, and rerun every lens. Solution: the stored decision is the decision. A failure leaves every lens at `careful` within its band, and its record says triage failed. The task's commit checks that the document still names it, as adjudication's does, and ends `superseded` otherwise. A rerun or a changed question that replaces the task aborts the old one, as a replaced lens task is. Pi Durable allows no abort inside a commit, so a process that dies between the two leaves the old task live. The sweep that aborts stale lens tasks also aborts any live decision task the document no longer names. It runs at open and at the start of every review. Before waiting for a pending decision, its commit removes any live lens task for that revision from the review index, then the sweep aborts it. That commit also removes any adjudication task for the revision from the index, even when its lens task finished. It clears the revision's stored verdict, provenance, and decision in the same commit. Findings and publication refuse the old verdict until replacement adjudication records a new one. The sweep aborts unnamed adjudications before waiting, and their terminal commits write nothing if replayed. Waiting starts every pending task, so leaving it named would resume the previous selection before triage chose its replacement. A recorded decision returns without starting the scheduler. Finished lens tasks stay available for attachment.

Under a `pull-request` origin, or a policy read from a revision, the default floor is `careful` unless the decider is calibrated. A head the host does not trust writes the change triage reads. A range review whose policy is the working tree keeps `quick`. When every lens's standing run is at `quick` after a decision, each record notes that the whole review looked lightly. Each model tier any selected lens declares a level on resolves first, to its credentialed route or why it has none. Only levels on a routed tier are offered or run. A lens with none in its band fails the review with `noAvailableModel`, naming each level and why, before any lens runs. So does a lens whose default level has no route. When a decider triages, each level the band holds that it could not offer is noted on the lens's record. The default level must run, so the next level an escalation from `quick` reaches always has a route. The cap for one without a route remains for a lens task's stored input. `options.triageSkipped`, the host's reason for having no decider, is noted on each lens's record. Each lens's band is core's `LevelBand.across` the configuration of every file it reviews, read through `configLookup` from `options.policy`, or `config` for every path without one. A policy that cannot be read throws before any lens runs. `lens.triage(band, levels, decision)` picks the level, where `levels` is `lens.runnableLevels(band, routed)`. A lens triage skips is not a neighbour of any other, so no lens hands it a defect.

`ChangePrompt.renderInput` returns the prompt and whether its 200 KiB limit omitted any file's diff. When it did, triage cannot skip any lens, even above a policy floor of `skip`. A skip answer runs at the lowest routed level in that lens's band. Triage may still choose another level within the band. `DecisionDocument` and the task input keep `inputCut: true`, and the attachment key includes it. Each running lens records that the input was cut and skipping was disabled. The optional field needs no migration; earlier records have none. `readRecordedDecision` returns it alongside the original decision.

A lens at `quick` carries `escalation`: the run at its next level the band allows, built up front with its own route and instructions, or nothing when the ceiling stops it. The task's input carries `triage.escalateAt`. When a quick run finishes, the task reads its sightings at the revision under its own producer and the budget that ended it. It then asks core's `EscalationRule`. On a trigger, one commit creates the next run's conversation and records it in the checkpoint's `children` and `attempts` under its own key. The same commit records the trigger under the quick run's key in `escalations`, so a crash after it continues that run and never decides again. The escalation's checkpoint entry also lists the IDs the quick run carries, its findings at or above `escalateAt`. The escalated run's first input appends each with its ID, severity, rule, file, and first and last lines, quoted with the `findings` label, since a model wrote them. It says how to confirm or refute each. When the escalated run finishes, the task reads which carried findings it restated and which it refuted. A restatement is a sighting of its own with the same ID or the same file and rule on overlapping lines. A refutation is in `spend.refuted` in its `LensDocument`, which `report_finding` writes, in place of a sighting, for a call whose `refuted` names the carried ID. The quick run's outcome names the trigger, the run it moved to, and the carried, kept, and refuted IDs. A capped one names only the trigger. `reviewChangeset` follows each lens to its last run. That run's record, with notes saying what became of the carried findings, and its producer, `<version>@<level>`, stand for the lens. The quick run's producer joins the review's producers with `ids`, the findings kept, so `readFindings` counts only those of its sightings. A restated finding is the escalated run's alone, so it speaks. Version 2 of the lens task added these fields. Its migration strips each version 1 run's `level`. A task an older Melian left behind then writes its findings under the lens's version alone, as the review that created it reads them. It never writes under a producer a review after the upgrade also writes.

### Prompt boundaries

Everything that originates from the head revision reaches a lens inside a boundary from `quoteUntrusted(label, text, nonce)` in `src/untrusted.ts`: `<untrusted-NONCE label="LABEL">`, the text, `</untrusted-NONCE>`. Labels are `diff`, `file`, `search`, `listing`, `evidence`, `findings` and `standards`. `reviewChangeset` draws the nonce once per review with `reviewNonce()` and stores it in the lens's `ReviewState`, so a replayed tool quotes with the same one.

- A `ChangePrompt` over the changeset and the review's nonce renders each lens's input, `render(only?)`: it puts the changed-file list in one `listing` block and each file's diff in its own `diff` block whose first line names the file. Problem: a removed line `-- src/fake.ts` renders as `--- src/fake.ts`, a header for a file that is not there. Solution: a file starts where its block starts, not at a line that looks like a header.
- `read_file`, `search`, and `list_files` quote their results, and `report_finding` quotes the first line of each evidence location. Melian's own notes, such as "more matches not shown", stay outside the block, and never repeat a path from the head.
- Paths pass through core's `visibleText` everywhere they reach a prompt, so a path holding a newline cannot forge a line in a listing.
- Text that holds the nonce has it replaced with `[nonce]`, which cannot happen by chance and would otherwise close the block.
- Every lens conversation is configured with `extensions: [lensExtension]` and nothing else, so its `injection_policy` section renders first and its `instructions` last. The section names the nonce, says that everything inside a boundary is data, and tells the lens to report an instruction found there under `melian/injection-attempt`. `reviewChangeset` adds that rule to any lens that does not declare it, so the hook never refuses the report the policy asks for.
- A new tool that returns head content quotes it the same way. A test asserts on what the model was shown, not only on what it returned: `test/review.test.ts` strips every boundary from a prompt and checks that no path or line from the head remains.

### Lens tools

`read_file`, `search`, and `list_files` read the head commit through core's `readRevisionFile`, `searchRevision`, and `listRevisionFiles`, never the working tree. `read_file` also takes `revision: "base"` and then reads the base commit. Problem: a lens could cite deleted code as `revision: "base"` evidence but could read only the head, so it numbered base lines by guessing from the diff. Solution: it reads the base as it reads the head, with the same line numbers evidence uses. They bound output per call, never the file: `read_file` takes `startLine` and `maxLines`, at most 2000, reads the window from the whole blob, and ends with a note naming the next `startLine`, so any line is reachable. `report_finding` checks a line against the file's true line count.

Pi Durable cuts a tool's result at 50 KB or 2000 lines unless the tool sets `outputLimits`, keeping the head. That cut dropped a boundary's closing tag and Melian's notes. Each lens tool therefore bounds the body it quotes at 48 KiB and sets `outputLimits` above it, so Pi never cuts. A new tool that returns head content does the same. They find the head through the calling conversation's `LensDocument`. All three are replay-safe because they only read.

`report_finding` takes a file, a line, an optional end line, a rule, a severity, an explanation (what, why, fix), a failure scenario, and evidence locations. The model supplies nothing else:

- The snippet is the head revision's text at those lines, read by Melian, so the finding's ID does not depend on how the model quoted the code. Its occurrence among identical snippets in the file comes from core's `snippetOccurrence`.
- Each evidence location's snippet is read by Melian too, from the head, or from the base for `revision: "base"`, and stored with the location. A file the named revision lacks is refused with a message, and at head the message suggests `revision: "base"` for deleted lines. So is a location past the file's end, on blank lines only, or over 60 lines long. No stored snippet, the finding's, its trigger's, or a location's, holds more than 2 KiB: the tool passes the finding's whole snippet to `Finding.create`, which takes the ID from it and stores it cut, and cuts the others with core's `capSnippet`.
- Cause comes from core's `revision.classifyCause` with the evidence. Code inside a hunk is `introduced`; anywhere else it is `affected` when a `cause` location overlaps the change's new lines at head or its old lines at the base, and `pre-existing` otherwise. The tool's result names the cause, and for a `pre-existing` finding says that no `cause` location overlaps the change, so a lens that meant to cite the change learns it missed. It then quotes, in an `evidence` boundary, each location's role, file, line, and first line as Melian read it. Problem: a lens that miscounted a line number cited a blank brace or the wrong function and never knew. Solution: it sees what each number resolved to, and can report the finding again with the right lines, which replaces its earlier sighting.
- `prepareArguments` runs before schema validation and refuses a call whose failure scenario is
  missing, blank, or too long, or whose evidence is prose, a single object, empty, too long a list,
  or holds a location without a `role`, with a message saying what each must be. Pi Durable
  validates against the schema before any hook, so without it the model would read only a schema
  error such as `evidence: must be array`.
- Source comes from the lens's name and version, and status from the document. The tool stores no resolution: only adjudication writes one, so a pre-existing P1 never arrives marked to block.

It refuses a file outside the lens's coverage, its folder and `paths` less any folder a nearer lens
of its name covers, plus the head path of each file the review moved out of them. It upserts into
the root conversation's findings document at the head revision, never the lens's own, so one review
has one document. A trigger carries the hunk's added lines as its snippet, cut at 2 KiB, and
`snippetHash` of them whole as its `hash`, so a dismissal reopens only when that code changes,
however long the hunk. An `introduced` finding's trigger is the hunk it sits in. Problem: only an
`introduced` finding had a trigger. Example: a caller in an untouched file, broken by a changed
signature, was dismissed; a later push changed the signature again, but both heads compared an empty
trigger, so the finding stayed dismissed while its cause moved under it. Solution: the hunks that
prove the cause are the trigger. An `affected` finding's trigger names the first hunk a `cause`
location marked `proves` falls on, by file then index, with that hunk's added lines as its snippet,
and lists every such hunk in its `proof` as `{ file, hash }`, the hash being `snippetHash` of the
hunk's added and removed lines, each keeping its `+` or `-`. A rename proves a cause without a hunk,
and adds none; a finding proved only by renames has no trigger. Problem: a trigger hashed from the
hunks the lens cited changed with the citation. Example: the lens cited one hunk of `src/price.ts`
for a broken caller in `src/cart.ts`, which was dismissed; on the next push, which touched only
another file, it cited both hunks, the hash changed, and the dismissal was dropped. Solution: the
proof is a set kept by the findings document, and the diff decides. `upsertFinding` takes the
revision's hunks, as `{ file, hash }` pairs, which `report_finding` passes from its review inside
the commit, and stores on the lifecycle record the union of every proof sighted since the finding
last reopened, less any hunk that has since changed. A dismissed finding sighted again as anything
but `introduced` reopens only when a hunk in that union has no hunk of equal content in the same
file at the new revision. Citing another hunk adds it to the union; citing fewer, or none, changes
nothing, since the code did not change. On a reopen the union starts again from the sighting that
reopened it. A record stored before the proof reads its last sightings' triggers, and a trigger with
a single `hash` counts as a proof of that one hunk. `upsertFinding` refuses a sighting with a proof
and no hunks, since it could not tell whether the proof still stands.

### The policy hook

`lensPolicyHook` runs before every tool call in a conversation that has a `LensDocument`, and passes every other call untouched. It blocks a tool the lens did not list, a severity outside its `severities`, and a rule outside its `rules`, listing the rules that exist. The one exception is an injection attempt at P1: the injection policy orders every lens to report one at P1, so `conventions`, which declares P2 and P3, can still do so; an injection attempt at any other severity is bounded like any finding. The model reads the reason as the tool result and can correct itself.

The budget is checked only inside `report_finding`'s commit, never in the hook. Problem: the hook cannot tell a new finding from a correction of one the lens already reported. Example: a lens with `budget.findings: 1` reports a finding, and the process dies after the commit and before the tool result. On resume the replay-safe tool reruns, and the model, which never saw a result, calls `report_finding` again. A hook that counted committed findings refused that call at the full budget. Solution: the commit refuses only a finding the lens has not yet reported at its head, so a replay or a correction always passes. The commit also sees every finding a parallel round committed before it, which the hook, reading a snapshot, does not. `test/review-crash.test.ts` kills a review at exactly its full budget and checks both the replay and the correction.

One storage holds every review of a changeset, so the root's findings document accumulates across pushes. The budget counts only the lens's own sightings at its own head, and `reviewChangeset` returns only findings sighted at the head it reviewed. Without that, a lens that used its budget on the first push could report nothing on the second, and a fixed finding would come back as current.

A finding's ID names no lens, so two lenses that share a rule ID can report one ID. Each writes its own sighting, neither is refused, and each counts it against its own budget. The read merges them.

### Token and tool budgets

A level's `budget.tokens` and `budget.tools` end a lens conversation once they are spent; [the lens budgets decision](../decisions/2026-10-04-lens-budgets.md) says what each counts. Four rules make that durable and exact.

- Counters live in durable state, never in memory or a hook. Pi Durable's hooks read documents but
  cannot write them, and a counter in memory would restart at zero after a crash. Tokens come from
  `pi.usage`, Pi's per-conversation `UsageDoc`, which Pi writes in the commit that records each
  response: input, cache writes, and output, summed over every model. Calls to the read-only tools
  and to `report_finding` are recorded by the ID of their tool task, `api.taskId`, in the lens's
  `LensDocument`, under `spend`, in a commit each of those tools makes before its work. Problem: a
  replay-safe tool reruns after a crash, so a count would grow twice for one call. Solution: Pi
  mints a tool task per call and reruns the same task on replay, so the set of task IDs holds a
  replayed call once. The provider's call ID will not do: some providers reuse one, such as
  `call_0`, in every round, and the set would hold three rounds' calls as one. Only a call that runs
  is recorded, never one the budget refused, so the count a budget's end reports never passes
  `budget.tools`. `test/review-crash.test.ts` kills a review inside a counted `read_file` and checks
  that the lens still gets its second call under a budget of two. It also kills one inside the
  `read_file` that ended a lens, at its tools budget and at its token budget, after the commit that
  recorded the ending and before Pi stored the result, and checks that the replay ends the lens
  without asking the model again; the tokens come from the killed process's response, which Pi
  recorded before the crash.
- Every call of a round decides alike. Problem: parallel calls commit in any order, so a call that
  committed first would see a smaller count than its siblings. Solution: each call numbers the
  round's counted calls from Pi's `LiveDoc`, whose slots list them all in call order when the round
  starts, each with its task, after every earlier round's recorded calls. Only a call that reaches
  its tool takes a number. Problem: a call that never runs, such as a `report_finding` the policy
  hook blocks or a call whose arguments fail validation, still has a slot. Example: under
  `budget.tools: 2`, a round holding a blocked report, a read, and a search numbered the search 3,
  refused it, and recorded a budget end after one call. Solution: a slot carries no arguments, so
  the tool's commit reads them from the assistant entry that started the round, named in its tool
  task's input, and leaves out a call the tool's `prepareArguments` or pi-ai's
  `validateToolArguments`, the validator Pi applies, rejects, or the lens's policy refuses. The
  entry never changes, so every call and every replay agrees. The policy hook cannot read the entry
  and counts every slot by name, so it may let through a refused call that the tools' count leaves
  out; that call's tool refuses it. A read numbered past `budget.tools` is refused with a note and
  runs nothing, and a read numbered at the budget says it was the last. The refusal records `tools`
  in `spend.ended`. Problem: the note tells the lens to report what it has confirmed, and a lens
  that does so and then finishes never sends the read that would end its conversation. Example:
  under `budget.tools: 2`, a lens reads once, then reads, searches, and lists files in one round;
  the search and the listing are refused, it reports, and it answers "Done." With nothing recorded,
  its record read `ran`, and a required status turned green from two reads that never ran. Solution:
  the refused read records the end in its own commit. A report past the budget never records one,
  because it is never refused. `test/review.test.ts` pins both. The round that crosses the budget
  does not end the conversation. Problem: ending it threw away the reads that ran in it, unread.
  Solution: the model sees them, and the refusals, and can report; the next round that holds a read,
  which starts with the budget used, ends the conversation, and so does a round that starts with the
  tokens recorded before it at `budget.tokens` or more. Every call of such a round, `report_finding`
  included, hands off, and its reads are refused unrun, since the model would never see them. The
  first records which budget in `spend.ended`, unless a refused read already has, and the lens task
  reads it, with the counts, when the lens settles.
- Any one call ends the run, on every path. Pi Durable ends a run after a round when every call of the round returns `control: { terminate: true }`, or when any one returns `control: { handoff }`; `finishToolRound` in Pi's `harness/generation.js` reads both. Problem: with `terminate`, one call that returned no control kept a spent lens running round after round: a read of a missing file throws, and so does a `report_finding` past the findings budget. Solution: every call of a spending round returns a handoff carrying the budget note, and the tools turn an error into an error result, rendered as Pi renders a throw, so it carries the handoff too. Pi writes the handoff as a reset entry holding the note; nothing reads a finished lens conversation's context, so that costs nothing.
- The policy hook cannot end a run: a `beforeTool` result carries a block or new arguments, never control. In a round that spends a budget, the hook lets a call its policy refuses go on to its tool, which checks the same policy, refuses the call, and ends the run. A call Pi answers itself never reaches Melian: one whose arguments fail validation, which Pi checks before any hook, and one naming a tool the request did not offer. Pi offers no boundary there that can end a run: `afterTools` returns nothing, `beforeRequest` only replaces the request's messages, and Pi reports and ignores a hook that throws. A round made only of such calls therefore makes one more model request, and the next round with a call that reaches a lens tool ends the run. `test/review.test.ts` pins this.

`report_finding` counts against `budget.tools`, numbered with the round's reads, because each call reads the code at every location it cites and quotes its first line back: uncounted, a lens could read the repository through repeated corrections. The budget never refuses a report, so a lens out of reads can still report what it confirmed, and only a round that holds a read ends the conversation for the tools budget. A lens may correct one finding three times in one conversation; `spend.reports` keeps the tool task of every report by finding ID, so a replay passes, and a fourth correction is refused with a note rather than an error.

## Check tasks

`runChecks(harness, { rootConversationId, changeset, config, source, tier }, context)` runs a tier's checks on one revision. Core's `checksOfTier` expands the tier: a name that is a tier expands to its checks, and `static` to every static tool. The harness's registry must hold `checksExtension`, in every process that opens the storage, so a check task left pending by a crash resumes.

`reviewChangeset` calls `runChecks` before lenses when given a `ReviewHarness` opened with `checkout`. Pi's public harness exposes neither its registry nor its environment, so the wrapper carries that capability. It takes the original configuration before the plan replaces routes, and maps `rerun` to `rerunFailed`. Supplying `options.checks`, even an empty array, opts out. A raw harness must supply records; absent records throw `ReviewError` `notInstalled` before any task starts. Pass the wrapper to request automatic checks. A wrapper without an environment leaves absent records not reviewed. Automatic checks require `policy`; a missing source throws `ReviewError` `missingPolicy` before any task starts. A `CheckError` propagates without adjudication. The existing checks document and task identity provide replay safety.

- One task per check. A `melian.checks` task in the root conversation creates one `melian.check` child per deterministic check, `guardrails`, `static.biome`, or `static.tsc`, and waits on them with `allSettled`, so one failure does not abort the rest.
- Every check writes into the root conversation. A check task replaces its findings at the revision, `revisionKey` of its base and head as the lens task and adjudication key it, through `replaceCheckFindings` with the root's ID, and writes its record to the `melian.checks` document, in one commit with its terminal outcome. A crash before that commit reruns the check, which runs the tools on the same commits and writes the same findings, so the task is replay-safe.
- A check's findings at a revision are replaced, never added to. Problem: a failed rerun wrote no findings and left the earlier run's in place, so the findings document disagreed with the latest record. Solution: `replaceCheckFindings` removes the check's sightings at that revision, of any tool version, then upserts what it reported now; a failed or skipped check reports nothing. A finding left with no sighting anywhere is removed unless it was dismissed, so its dismissal survives if it returns. A removal counts toward the revision's findings version, as an upsert does, so a review after a rerun that cleared a finding adjudicates afresh.
- Records are stored per run. A run's identity is its base, head, tier, configuration hash, and task ID; `runChecks` returns it with the records, and `readCheckRecords` takes it. Problem: records were keyed by head, so a `fast` and a `full` run of one head wrote over each other. Solution: each run keeps its own records, and a rerun of failed checks is a new task with its own identity.
- Every check leaves a record, a `CheckRunRecord` in the shape of core's `CheckRecord`: `ran` with the tool version its findings name, its finding count, and notes; `skipped` with a reason; or `failed` with the error's code as `reason` and its message as `error`. `reviewChangeset` takes `run.records` as `options.checks` unchanged. Problem: a check that fails silently looks like a check that found nothing, and adjudication would call the revision clean. Solution: a failed check writes no findings and a `failed` record, and adjudication reports the revision as not reviewed by it. A `lens.*` or `decisions.*` name is recorded as skipped, since those run elsewhere; any other unknown name fails with `unknownCheck`.
- Asking twice runs once. The `melian.checks` document maps a run's identity to its task: base, head, tier, and a hash of the configuration and the source, as canonical JSON. A second `runChecks` with the same identity, from this process or a new one, waits for the first task instead of starting another. Problem: the key was `<head> <tier>`, so a changed base, configuration, or source returned the earlier run's results, and a transient failure stayed for good. Solution: anything that decides the results is in the key, and `rerunFailed: true` starts a run that repeats only the failed checks, keeping the other records, or the whole tier when the earlier run did not complete.
- Static checks get their environment from the harness's `env` option through `runtime.env()`. A durable task's input is JSON, so it cannot carry a live environment; a task resumed in a new process finds the new process's environment the same way. A harness without one fails each static check with `noEnvironment`.
- `config` is the repository root's configuration, read from `source`. It names the tier's checks and the static tools' settings. A check stores no resolution on its findings; adjudication writes it from each path's configuration.

## Static tools run in the execution environment

`runStaticTool` in `src/static.ts` runs Biome or tsc on one commit. Everything it executes goes through an `ExecutionEnv`, Pi Durable's `FileSystem` plus `Shell`, never through the Melian process. Biome and tsc load the repository's configuration and plugins, so running them runs the revision's code. Version one passes `createNodeExecutionEnv`, because a local run reviews the maintainer's own code; a container environment implements the same interface and replaces it without touching the runner.

- One worktree per revision. The runner checks the commit out with `git worktree add --detach` into a temporary directory, runs the tool there, and removes the worktree in a `finally`. Never run a tool against the user's checkout: its working tree holds whatever is checked out, edits included, and the tool would review that instead of the commit. Because the tool runs in the revision's tree, it reads the revision's own `biome.json` or `tsconfig.json` by construction. That hands the head the configuration its own results are judged by, so core's policy-change-review reports every change to a tool's configuration.
- Cleanup never takes the caller's context. Problem: a cancelled context makes every `ExecutionEnv` call return `aborted` at once, so the `finally` left the worktree registered. Solution: removal runs under `backgroundContext`. A cancelled run fails with `aborted`, not `toolFailed`, so a cancellation never reads as a broken tool.
- A crashed run's worktree is removed by the next run. Problem: after SIGKILL the worktree's directory still exists, so `git worktree prune` keeps it registered for good. Solution: the runner never runs `git worktree prune`, which would also drop the user's own stale worktrees; it removes only its own, by path, which works even when the directory is gone. It adds each worktree with `--lock` and the reason `melian-static pid <pid>`. Before adding its own, it reads `git worktree list --porcelain -z` and removes, with `--force --force`, every `melian-static-*` worktree whose locking process `kill -0` no longer finds. A live run's worktree stays. `test/static.test.ts` kills a run parked in `test/fixtures/static-crash.ts` and checks that the next run removes what it left.
- Every command runs with `inheritEnv: false` and four variables from the Melian process: `PATH`, `HOME`, `TMPDIR`, and `LANG`. Problem: the tools load the revision's configuration and plugins, and inherited the whole environment, provider keys and tokens included. The design says anything that executes head code runs with no secrets, unconditionally. Solution: nothing else passes, on a local trusted run too, because a rule that bends for local runs is the rule a CI runner gets wrong. A test sets a secret and reads what the tool saw.
- git runs with the hook's repository variables unset, `core.hooksPath=/dev/null`, and `core.fsmonitor=false`. Problem: `git worktree add` runs the post-checkout hook, and a repository using husky points `core.hooksPath` at a directory the revision controls. Solution: no hook runs during checkout, so nothing executes outside the tool's timeout.
- Never execute a binary from the revision's tree. Problem: the runner preferred the worktree's `node_modules/.bin/<tool>`, and ran it with `--version` before any analysis, so a head that tracked `node_modules/.bin/biome` ran arbitrary code with the runner's access to the host, not merely an empty report. Solution: the tool is the checkout's `node_modules/.bin/<tool>`, which the maintainer installed from the lockfile, or the Biome or tsc Melian depends on. A `node_modules` the revision tracks, at any depth, is deleted from the worktree before anything runs and named in the check's notes. When the checkout itself tracks `node_modules`, as it does when the head under review is checked out, the runner uses neither it nor its binaries, and says so. `test/static.test.ts` commits a `node_modules/.bin/biome` that writes a sentinel file and checks the file never appears.
- A worktree has no `node_modules` of its own. The runner links the checkout's install into it entry by entry, so tsc resolves the repository's dependencies. Problem: one link to the checkout's whole `node_modules` made npm's workspace links, such as `node_modules/b -> ../packages/b`, resolve to the checkout's sources, so with the head checked out, a head that broke a sibling package showed the break at base too and it read as pre-existing. Solution: an entry that resolves inside the checkout and outside any `node_modules` is a workspace package, linked to the worktree's own copy; every other entry links to the install, and a workspace package's own `node_modules` is linked the same way. A dependency bump in the checkout but not at the revision is accepted with a note when the lockfiles differ; `package-lock.json` is analyser configuration, so the bump is reviewed as policy. `test/static.test.ts` checks a two-package workspace.
- Bounds are failures. `static.<tool>.timeout` (300 seconds by default) caps each command, and `ulimit -f` with a check before reading caps what the tool writes at `staticOutputLimit` (16 MiB). A timeout, a crash, an unexpected exit, a missing report, or output too large is a `CheckError` with its code, never an empty log. The tool controls its output files, so the runner resolves a report to its target, requires a regular file, checks the target's size, and reads it line by line with a byte cap. Only a missing file means no report; any other failure to stat or read it is `toolFailed`. Problem: the runner checked the size with `lstat`, read through symlinks without a cap, and treated every stat error as no report, so a tsc that replaced its output with a FIFO and exited 0 read as a clean run.
- A solution-style `tsconfig.json`, with `references` and `files: []` and no `include`, checks nothing itself, so a run of it read as clean. The runner reads the project, as JSON with comments, and runs `tsc -p` on each referenced project in turn, recursing through nested solutions, and names the projects it checked in the check's notes. A project with an empty `files`, no `include`, and no references is a failed check, `nothingToCheck`. A project with neither `files` nor `include` checks every file below it, as tsc does. The runner reads the file itself, not what it `extends`.
- tsc exits non-zero when it reports anything, including diagnostics Melian drops as outside the worktree or under `node_modules`, such as a broken `.d.ts` with `skipLibCheck` off. A non-zero exit whose every diagnostic was dropped is a run with no results and a note counting them; only a non-zero exit with no diagnostics at all is `toolFailed`.
- Output goes to files, not the shell's stream. `Shell.exec` interleaves stdout and stderr, which would corrupt a JSON report, so the runner redirects each tool to a file in its scratch directory and reads that.

## Adjudication

The adjudication task, `melian.adjudication`, reads the root conversation's findings at the revision under review through `readFindings` with the producers the review selected, runs core's `Adjudication`, and writes the verdict's JSON into `VerdictDocument` on the root under that revision. Like the findings document, the verdict document belongs to the root, is rewindable, and forks `asOf`, so a fork of the root at a revision carries that revision's verdict. Read it with `readVerdict(reader, rootConversationId, revision, context)`, where `revision` is a `revisionKey`, which returns a copy or `undefined`.

The task has one phase. It reads, decides, and commits the verdict and the task's terminal outcome
together, so a crash before that commit reruns the phase, which reads the same findings and writes
the same verdict. Everything it decides from is in its input, fixed when `reviewChangeset` creates
it: the root, the repository, the base and head, the manifest, the check records, the skips allowed,
the producers, the configuration, and the findings version. The findings document counts, per
revision, every write that could change what a read of it returns: a sighting there, or a lifecycle
change, such as a dismissal, of a finding sighted there. Problem: the input held no lifecycle state,
so a repeat review after a dismissal attached to the finished task and returned the verdict from
before it. Solution: the input carries that count, so a dismissal makes new input and a new
adjudication. The producers come from the manifest, the same list `Review.findings` is read with:
each lens the review ran as `lens.<name>` at its version, so a lens that configuration has since
disabled or retiered leaves its sightings at that head out of the verdict too, and every other check
of the manifest by name, at the version its record names or at any version when it names none.

A repeat review of a head attaches to its adjudication task as it does to its lens task. The commit that creates the task records it in the root's `ReviewIndex` entry for the head, with its input as JSON; a later call with the same input waits for that task instead of creating one. Input that differs, such as a check record from static analysis that has since run, creates a task and records it in its place. Problem: a crashed review's adjudication task resumes when the harness does, and could commit after a newer review of the head, putting the older verdict back. Solution: the task's final commit reads the index, and a task the index does not name exactly ends `superseded` without writing; `reviewChangeset` throws `adjudicationFailed` for it. An entry naming no adjudication task counts as naming another. Problem: a review with a new lens selection replaces the head's entry before it creates its own adjudication task, and a first fix that let an entry with none through had the crashed task write in that gap. `test/review-crash.test.ts` kills a review inside adjudication, starts one with another selection, and expects the old task to write nothing.

The same commit records, under the same key, the task that decided the verdict and the findings version it read before reading the findings, read with `readDecision`, and the verdict's provenance, read with `readProvenance`: the review's `origin` (`options.origin`, a `range` unless the host says it fetched a pull request, with the repository, number, and the base and head its provider reported). It also holds the policy source as `worktree`, `revision:<sha>`, or `config` when the review named none, the tier's checks, each lens as `name@version@level`, at the level of the run that stands for it, and the review's plan as JSON. `ReviewPlan.from` reads that plan, so a summary written after a crash quotes the plan the review ran under. The provenance is part of the task's input, so a review of the same revision from another origin or policy is a new adjudication. Publishing reads it; see [Publishing](#publishing).

Resolution is per path. With `options.policy`, the source `config` was loaded from, the task calls `loadConfig` for each finding's path, so a nested `melian.yaml` that lowers `P2` to `advisory` for `docs/` applies there. Without it, `config`'s `resolution` and `ruleAliases` apply everywhere. A lens stores no resolution, so `Review.findings` carry none: they are not yet adjudicated. The verdict's findings carry the resolution adjudication decided, and a host reads what blocks from the verdict, never from `Review.findings`.

### The manifest

The tier's check list is the review's manifest. `reviewChangeset` expands `options.tier`, or the tier configuration maps the `pull-request` stage to, with core's `checksOfTier`, and every check in it must produce a record by adjudication. Problem: the records of other checks were optional and defaulted to none, and the producers held only the lenses. Example: a static tool's stored `P0` sighting never reached the verdict, and a review whose Biome run never started read `passed`. Solution: a check with no record is `skipped` with the reason `no record`, so the verdict is `not-reviewed`, and the producers are derived from the manifest, so a static or guardrail check's sightings count beside the lenses'.

Only lenses the manifest names run. The lens step records each of them, and a record named `lens.*` in `options.checks` gives way to it. A lens of the manifest that did not run is recorded as:

- `failed`, `no lens is named <name>`, when no lens of that name is loaded.
- `skipped`, `lenses.<name>.enabled is false`, when configuration switches it off. That is an exclusion, and the design reports an exclusion as not reviewed unless the repository lists the check in `checks.allowSkip`.
- `skipped`, `no paths`, when no changed file is in its paths, a renamed file by its old path or its new one. This skip is allowed, whether or not another lens ran: a change that touches only paths every lens excludes, such as Melian's own goldens, passes on its deterministic checks, and the terminal and JSON output list each lens with that reason. [decisions/2026-10-05-lens-with-no-paths.md](../decisions/2026-10-05-lens-with-no-paths.md) records why.

The review records every `decisions.*` check itself, as it does every lens, and a record of either from `options.checks`, such as `runChecks`', gives way. A `decisions.*` check is skipped and allowed while no decision provider is configured, as the design lets the fast tier degrade. Once a provider is configured it is skipped with the reason that Melian has no adapter for one yet, and the skip is not allowed. Problem: with a provider set, nothing recorded `decisions.fast`, so every default-tier review read not reviewed with the reason "no record" ([issue #24](https://github.com/melian-agent/melian/issues/24)). Solution: a record that says why; the CLI refuses the provider before a review starts. A lens triage skipped above a floor of `skip` is `skipped`, `triage skipped it, as its floor allows`, and allowed. Every check `config.checks.allowSkip` names joins the allowed skips. Any other check, such as `guardrails` or `static.biome`, records itself through `options.checks` as `{ name, status, reason?, error?, version? }`, where `version` is the tool version its findings name; without a record it is `no record`.

`runChecks`, from [pull request #18](https://github.com/melian-agent/melian/pull/18), keeps one record per check of a tier in the `melian.checks` document under a run identity of base, head, tier, policy hash, and task, and its records are this shape. A static check's `ran` record carries `version` from the head's SARIF driver, so the review counts only that version's sightings; a guardrail's names none, so every version counts. It records `lens.*` and `decisions.*` checks as skipped, which the review's own records replace. Its findings sit under the same `revisionKey` the review reads. `reviewChangeset` runs checks when `checks` is absent and its review harness has a checkout. A host may instead call `runChecks` and pass `run.records` as `options.checks`, as `test/checks.test.ts` does under the default `fast` tier.

## Dismissing

`recordDismissal({ harness, revision, id, dismissal, repoRoot })` dismisses a finding of a stored review and decides that review's verdict again, so `melian findings` and `melian publish` read a verdict that counts it out. Dismissal writes lifecycle status and nothing else; adjudication, which alone writes resolution, reads it. The ID must name a finding of the verdict stored for `revision`, or `DismissError` `unknownFinding`; no verdict is `notReviewed`. A finding with that exact ID wins; otherwise the ID names the speaker a member was merged into. A live speaker's `alsoReportedAs` also lists the dismissed reports of its defect, which it never absorbed, and those are no path to it. Problem: the lookup matched any speaker listing the ID, live ones first. Example: contracts' report was dismissed at one head; at the next, correctness reported a `P1` on the same line, listing the dismissed report beside it; dismissing the old report again to change its reason dismissed the `P1` with it, unseen. Solution: the exact ID first, and members only from a speaker's merged reports. It dismisses the finding as the verdict shows it: the speaker and every report adjudication merged into it, unless `only` is set, which dismisses the report the ID names alone and leaves the others live. Problem: core's dedupe never merges a dismissed finding with a live one, so dismissing only the speaker of a merged defect turned another check's report of it into a live speaker. Example: correctness's `null-dereference` absorbed contracts' `changed-return` on the same line; dismissing the first posted "Dismissed" in its thread and opened a new thread for the second in the same round. Solution: the defect leaves the verdict whole, and visibly. `RecordedDismissal.also` lists the other reports with their rule and check, which the CLI prints, and the terminal rendering lists every finding's merged reports beforehand, because the merge is by site, not meaning, and can join two defects on one expression.

One commit records the dismissal and creates an adjudication task over the review's own input, read back from the review index, with the findings version the dismissal moved to. The input keeps the review's checkout while it exists, since another worktree may hold another `melian.yaml`, and takes the caller's `repoRoot` only once it is gone. The commit names the task in the index, keeping the input's key order, so a later `reviewChangeset` of the revision computes the same input and attaches to it rather than deciding a third time. A dismissal and its adjudication therefore land together or not at all. A dismiss cut short after its commit leaves the stored verdict from before it, and the task undecided: `publishReview` refuses with `notReviewed`, as the Publishing section below describes, and the next `reviewChangeset` attaches to it. The same dismisser giving the same reason again changes nothing, so it computes the same input and waits for that task rather than adding history. When the task fails, the dismissal stands and `DismissError` `adjudicationFailed` says the next review decides the verdict. The lookup reads the stored verdict inside the dismissal's commit, so a review that recorded another verdict just before decides what the ID names and which reports go with it. A review that records an adjudication task of its own after the dismissal's commit ends the dismissal's task `superseded`; its own task reads the dismissal, so `recordDismissal` waits for it and reports its verdict rather than failing.

Open the harness with `DismissHarness.open(storage, models)`, which installs the adjudication task alone. Problem: `resume()` resumes every pending task the registry defines, and the review harness defines the lens task, so a dismissal after a crashed review would resume its lenses and spend tokens. Solution: the lens and publish tasks stay blocked in a dismiss harness, as a review stays blocked in a publish harness.

## Publishing

`publishReview({ harness, provider, changeset, pullRequest, base })` publishes the verdict recorded
for a pull request's base and head through a `ReviewProvider` from core, such as
`packages/github`'s. `base` is the merge base the pull request diffs from now, which the host reads
with git, since the provider reports only the base branch's tip. The harness must hold
`publishExtension(provider)`, which carries the publish task, `melian.publish`; install it again
after a restart so an interrupted publication resumes. `openPublishHarness` opens a
`PublishHarness`, whose `harness` holds nothing else, so a review a crash interrupted does not
resume during a publish. It refuses with `PublishError` `staleReview` when the changeset's head is
not the pull request's, or its base is not `base`, `notReviewed` when no verdict is recorded under
their `revisionKey` or the verdict is not decided, and `notPublishable`, naming the mismatch, unless
the verdict's provenance is a `pull-request` review of the same repository and number whose
provider-reported head is the pull request's head now and whose policy source is `revision:` of the
provider-reported base. A verdict recorded without provenance is refused too. A review of a range,
of a working tree, of an older push, or of the pull request before a retarget is never posted.

A verdict is decided when the adjudication task the review index names for the revision is terminal,
`completed` with `recorded`, the verdict document records that task as the one that decided the
stored verdict, and the findings version it read is the revision's version now. Problem: the guard
looked for the indexed task in `harness.inspect()`, and Pi's inspection lists live tasks only.
Example: a dismissal's adjudication ended orphaned, which takes it out of the inspection; the guard
read its absence as success and published the verdict from before the dismissal, still blocking on
the dismissed finding. Solution: the task is read by its ID with `getTask`, its outcome must be a
recorded verdict, and the message names what it ended as. A verdict an older Melian recorded, with
no decision beside it, takes the findings version from the task input the index holds. A revision
whose index entry names no adjudication task, as after a crash between a review's new lens selection
and its adjudication, publishes its stored verdict only while its findings version is the one that
verdict was decided from.

The task is not replay-safe: a post and the commit recording it are two steps, and GitHub takes no idempotency key. Two records guard it instead of a memo, which would vanish with the task:

- `PublishedDocument` on the root conversation, keyed by head and then by finding ID, holds each
  review posted for the head, the fingerprint of the verdict the last one posted, every finding open
  on the pull request with the comment that starts its thread, the findings this revision resolved,
  each reply under core's `replyKey` of its finding, its thread, and the version of the dismissal it
  gave, and the status. Before posting a review the task commits its plan as `pending`, with the
  verdict it renders and a round number from the head's `rounds` counter, which only grows, so a
  verdict that recurs at a head is never mistaken for its earlier review, and posts exactly that
  plan on a rerun, so a verdict that changes between a crash and the rerun cannot get the old
  review's threads. Problem: the rerun once rendered the body from the head's current verdict.
  Example: a post failed, a fresh review turned `not-reviewed` into findings, and the next publish
  posted the old round's comments under a body saying the new verdict. Solution: the round keeps its
  verdict, and once it is posted the task plans a second round for the current verdict, so the last
  review matches the status. Each post is recorded in a commit of its own, straight after the post.
  Unlike the findings and verdict documents it keeps only its latest value and a fork carries it as
  it stands: a post is a fact about the pull request, and a fork that forgot one would post it
  again. It stays keyed by head, not by `revisionKey`, because what it records is on the pull
  request at that head, and every marker names the head. Beside the last review's fingerprint it
  records the `revisionKey` that review published, and a head counts as published only for that
  revision. Problem: a retarget keeps the head, so a fingerprint alone matched an identical verdict
  of another base. Example: the review of base A and head H was posted; the pull request was
  retargeted onto B, and B..H's review found the same findings; publishing B..H matched A..H's
  fingerprint, posted nothing, and returned A's review as B's. Solution: the revision is part of the
  match, so a retarget always gets a review of its own, planned against the head's open findings. A
  record an older Melian wrote names no revision; it counts as this revision's only while no other
  revision reviewed at the head has a verdict with the same fingerprint or legacy fingerprint, so an
  ambiguous one posts again rather than skip a review.
- Melian's markers on the pull request. Before posting anything the document lacks, the task asks the provider for the markers it finds for this head, and records what it finds instead of posting. A crash between a post and its record is the case this covers.

Every marker is signed with the changeset's publisher secret, and the provider counts only a marker whose signature verifies, as [the GitHub guideline](github.md#markers) describes. The secret is 32 random bytes, kept as hex in `PublisherDocument` on the root conversation. The commit that creates the first publish task generates it, and nothing replaces it afterwards: a new secret would orphan every marker already posted, and the next crash would post again. It lives exactly as long as the changeset's storage and is disposed with it, as a closed pull request's state is. Never print it, put it in a task's input, or pass it anywhere but the provider's calls. Anyone who can read the storage can sign a marker, so a host whose storage others can read, such as a state branch in a public repository, must keep the secret elsewhere before it publishes.

One phase posts the status, then the review. It edits each addressed finding's original comment and resolves its thread, or replies with the dismissal's reason. It then finds and writes the ledger and sets the status's ledger link. Before setting an unrecorded link, it reads the provider's latest review status. A matching state and target URL records the link without another write. A ledger refusal leaves the review posted and changes the status to an error naming recovery. `Publication.dismissed` counts those apart from `resolved`. A posted finding whose ID the verdict now holds only as a report merged into a dismissed finding is answered with that finding's dismissal, through `PublicationPlan.dismissals`, and counts as dismissed. Problem: only a dismissed finding's own ID mapped to its dismissal. Example: contracts' report was posted alone; at the next head correctness reported the same line and spoke for both, and the maintainer dismissed the defect; the contracts thread was told the revision no longer reported it. Solution: every ID a dismissal took maps to it. A merged report dismissed on its own maps to its own dismissal instead, which core carries on its `alsoReportedAs` entry. Problem: every merged ID mapped to the speaker's dismissal. Example: contracts' report was posted and dismissed with one reason; at the next head correctness reported the same line and was dismissed with another; adjudication merged the two dismissed reports, and publish told the contracts thread correctness's reason. Solution: each report keeps its own, and only one without a dismissal takes the speaker's. The status comes first, derived from the verdict, so a head carries one even when its review cannot be posted. Problem: the status was set only after the review posted, so a round GitHub kept refusing left the head with no `melian/review` status at all, and abandoning the round after three refusals did not change that. Solution: status first, and when a round is abandoned the status becomes `error`, `review could not be posted: <reason>`, the not-reviewed state, until a later round posts and the next publish sets the verdict's status again. The status also comes before the replies, so a thread that cannot take one never holds back the check: a reviewer who deleted Melian's comment leaves a thread the provider reports as gone, which is recorded as `null` and never retried. `verdict.publication` decides what the review posts against the open findings of the revision published before, and only a head with a recorded post has open findings. Problem: the commit that plans a head's first round creates its record with an empty `open` as a placeholder, and planning read that placeholder as the truth. Example: the first head posted, the second head's round failed, and the third head was planned against the second's empty set, so it reposted both open findings in new threads and never replied to the one the second head fixed. Solution: a round is planned against its own head's open findings only once a review of that head was posted, and otherwise against the latest head that has one, skipping heads whose rounds failed or were abandoned. The plan's resolved findings are stored with the review, so a rerun replies to the same ones. A second publish of the same head with the same verdict posts nothing. A second review of a published head can change its verdict: a lens that hit a rate limit made it `not-reviewed`, and the rerun found three findings. Publishing then posts a second review for that head, planned against the head's own open findings, so the findings reach the pull request and none is posted twice. A resolution an earlier head decided but never replied to, because its replies failed and a push followed, is carried into the next head's replies until one answers it. The carry holds the dismissal the finding has now, and the resolution counts as answered once a reply as it would read now is recorded. A dismissal note owed for a finding the next head no longer reports at all is carried as it was owed. Problem: the carry kept a dismissal note only while the finding stayed dismissed. Example: a finding was dismissed at one head and its reply failed; the next push removed the code, and the thread was never answered, neither with the dismissal nor with a resolution. Solution: while no finding with the ID is held, the owed reply goes out as stored. The verdict's fingerprint, core's `verdict.fingerprint()`, leaves out each finding's `dismissal` and `pastDismissals`, so dismissing a finding again with another reason plans no round. Problem: replies were keyed by finding ID alone, so the thread kept the first reason, and the changed verdict posted a review saying nothing new. Solution: after its rounds, the task resolves at the head every dismissed finding whose newest thread last heard another dismissal, with the dismissal it has now, and replies under a key with that dismissal's version. A finding posted in a review's body has no thread, so its new reason is not posted. Keying replies by thread too means a finding answered in one thread, reopened, posted in a new thread at the same head after a retarget, and dismissed again, gets a reply in the new thread. Version 3 of the published document rekeys each reply an older Melian recorded by finding ID. A provider failure ends the task `failed` with everything posted so far recorded, so publishing again resumes. A refused review counts against its round, and the third refusal abandons it: the round is dropped and recorded with its error, `Publication.abandoned` lists it from then on, and the next publish of the head plans a new round. Without that, a round GitHub always refuses, such as one with a comment it rejects with a 422, would block every later publish of the head, even after a fresh review. `publishReview` waits for any publish task a crashed run left before creating its own, so two tasks never post for one head at once.

A task a crash left behind may be for a target that is gone. Problem: the waiting resumed every
unfinished task as it was. Example: a publish crashed before posting; the parent landed and the pull
request was retargeted onto `main`, keeping its head; a fresh review found less; the next publish
resumed the old task, which posted the review of the old diff, and the pending round it left was
posted by the new task too. Solution: each task records its target in its input: the repository, the
number, the base branch and its tip as the provider reported them, the merge base, the head, and the
`revisionKey` it publishes. Before resuming anything, `publishReview` commits the target it
validated to `PublisherDocument`, and a task whose target differs ends `completed` with `superseded`
and the field that changed, writing nothing; `Publication.superseded` lists them. A pending round
records its `revisionKey` as well, and one planned for another revision of the head is dropped
unless the provider's markers show it posted, in which case it is recorded as usual. Immediately
before each review post, status post, and reply, the task asks the provider for the pull request
again; when the head, base branch, base tip, or repository differ from its target, it stops with
`staleTarget`, and `publishReview` throws `PublishError` `staleTarget`. A refusal of that kind does
not count against the round. `test/publish-crash.test.ts` in `packages/github` kills a publish
before its post, retargets, reviews again, and publishes.

## Comparing with external reviewers

`ComparisonDocument` in `src/compare.ts`, kind `melian.comparisons` at version 1, holds a changeset's comparisons with other reviewers on its root conversation, keyed by the `revisionKey` of the stored review each compares against; [the core guideline](core.md#comparison) gives the shape and the matching rules. It keeps its latest value, as the review index does: the hand matches are the maintainer's record, and a fork that forgot them would lose it.

Open the harness with `CompareHarness.open(storage, models)`, which installs no task, so a review or publication a crash interrupted does not resume in it, and asks no model. `reviewed(revision)` says whether Melian has a review to compare against, so a host can refuse before it imports anything. `importFindings(revision, sources, at)`, `match`, and `unmatch` each read the stored verdict and the comparison in one commit, apply the change, and match against the verdict again, its shown and dismissed findings but not its silent ones. A revision with no current, decided verdict is `CompareError` `notReviewed`, and the commit writes nothing. Both the preflight and the write commit check the indexed adjudication task, its recorded decision and the current findings version. A pending, missing or unsuccessful task cannot supply a verdict. A verdict predating decision records uses the indexed input’s findings version; one with neither an index nor a decision remains readable. An import replaces what its source last imported, so a replay or a second run writes the same state.

Problem: a commit hands the document's value as a view of its own, and `structuredClone` refuses it with a `DataCloneError`. Solution: copy a stored verdict or comparison read inside a commit through JSON, as `Comparison.from` does.

`FileImporter.open(path, { cwd, repoRoot })` reads a reviewer's JSON file, at most 4 MiB, through core's `ExternalFinding.fromFile`, and names it `file:` and its path relative to the repository when it lies inside, so the same file imported from another directory keeps its findings' IDs. It resolves both paths through `realpath`, since git reports the repository's real path and macOS's temporary directory is a symlink. A symlink regression checks the source and finding IDs through real and symlinked repository roots; bypassing either resolution fails it. A file it cannot read, or that is not JSON, is `CompareError` `unreadable`. Problem: V8's parse error can quote the bytes around the fault, and an unknown key's name is the file author's text, so either could carry an escape sequence to the terminal. Solution: the message names the file and the position only, and core names the object that holds an unknown key, never the key. The importer of a pull request's review threads lives in `packages/github`.

Codex's companion script wraps the review in an envelope when asked for JSON, with the review output under `result`. The importer reads the review output only, so the agent that ran Codex saves that `result` field as the file. Teaching the importer the envelope would mean following a plugin's private shape, which differs between its commands; one sentence in the skills is smaller.

## Contracts that read like mistakes

- A task phase reruns from its start after a crash. Work before the phase's checkpoint commit must be safe to repeat, or guarded by a durable record.
- A tool's own commit and its result land in separate durable commits, so a crash between them reruns a replay-safe tool and has the model retry an unsafe one. A tool with a durable side effect is therefore an idempotent upsert keyed by a stable ID, such as a finding's, and marked `replay: "safe"`. Otherwise it is not replay-safe, and a durable record guards its side effect. Never guard it with a memo.
- A phase must commit a new checkpoint or a terminal outcome. Returning without one faults the task.
- `memo()` belongs to one task, a tool call included, and is deleted when that task ends. Use it for intent within a task, never as a record that outlives the run.
- A conversation created by a task starts as a copy of its owner's agent. Set a lens's `tools` explicitly, or it inherits the orchestrator's.
- Lenses run as conversations owned by the lens task, which decides which lenses run. A model never chooses the topology through a subagent tool.
- Conversation IDs are numbers minted by storage. A `requestId` deduplicates within one conversation only.
- The tool task coerces arguments towards the schema before validating: `42` becomes `"42"` for a string field. Constrain a schema with formats, patterns, or lengths when coercion would let a bad value through.
- A fork taken before a document's first write has no document. Treat an absent document as its initial value.
- In a commit, an object assigned into a document is copied in. `const spend = (document.spend ??= { calls: [] })` hands back the plain object, and a later `spend.calls.push(id)` is lost; assign, then read the field back through the document.
- `waitForTask()` resolves at the task's terminal commit, before the phase function returns. Code after that commit in the phase may not have run yet; `close()` waits for it.

## Tests

- Use the fake model from `createFakeModels()` in `src/testing.ts`. Never a real provider, key, or paid token.
- Script parallel conversations, such as lenses, with `scriptConversations()`, which answers each request from the script whose `match` appears in its system prompt. A plain response queue would hand the replies out in whatever order the harness calls the model.
- Open review harnesses with `settings: { retry: { enabled: false } }` in tests, so a scripted error reply fails the lens at once instead of retrying with backoff.
- Use memory storage unless the test is about surviving a reopen or a crash. Then use SQLite in a temporary directory and delete it afterwards.
- Close every harness in `afterEach`, before deleting its directory, so a failed assertion does not leave a live SQLite handle. `close()` is idempotent.
- Test a crash with a real process kill. Run the first half in `test/fixtures/crash.ts`, have it append events to a log synchronously, SIGKILL it at a known event, and resume in the test process against the same file. Count reruns from the log.
- The parent polls that log while the child writes it, so ignore text after the last newline: it is an event still being written. Detect an early death through `signalCode` as well as `exitCode`, which stays null when a signal kills the child, and kill the child in a `finally`.
- A fake reply carrying tool calls needs `stopReason: "toolUse"`; the default `"stop"` ends the run without running them.
- Assert on what the model was shown, not only on what the harness returned. `captured()` in `test/fixtures/spike.ts` keeps each request's messages.


## Verifying a changeset

After lenses finish, read their producers and group findings through core's `Merge` and the shared per-path configuration lookup. Candidates are live defects with a verifying lens claim or an escalation-kept quick claim. Judge every lens claim on each, including quick sightings. Static and guardrail reports carry no claim. One `melian.verification` task owns one conversation per candidate and runs at most eight at once. Each candidate has fixed limits of 300,000 tokens and 60 tool calls. GPT-6.1 Sol exhausted the earlier 20-call limit after 45,902 tokens on one candidate. The larger constants allow the reading it needs; this step adds no configuration key.

A stored lens run without a verify field resolves it from that lens's definition at its recorded level. An explicit quick-level request still verifies after resume.

The optional root index entry records the task and input beside lenses and adjudication. The input includes the root, ReviewState and nonce, verifier version, claims, finder model, route and budget. The attachment key excludes the nonce and stored verdicts. A repeat review resumes live work or reuses a completed task only when every candidate outcome is done and its model is accepted. A completed attempt with recorded candidate failures or a refused model stays not reviewed until rerun. An aborted, faulted, orphaned or failed task, or a completed task missing candidate outcomes, starts fresh without rerun. The commit that repoints the index clears the revision’s previous judgements and removes its adjudication owner. The sweep aborts that adjudication before waiting for verification; its commit also refuses an unnamed owner. A replaced task asks no model and writes nothing. The open sweep aborts live lens, decision, adjudication and verification tasks the index no longer names. Pending replacement triage detaches verification even when the lens task finished.

Spawn commits every owned conversation together. Each has only lensExtension, read tools and report_verdict, with LensDocument's optional verifier role. The role refuses report_finding and renders the verifier's injection policy. Each labelled claim's text, paths and code enter a findings boundary; trusted labels stay outside. The instructions attack the guard, caller, type and base failure. A claim that needs execution stays plausible, with the required run named in its reason.

Each request ID contains the candidate and attempt. Failover commits the attempt and model together. Outcomes are done, unanswered, exhausted or ended by budget. report_verdict requires the three answers, verdict and reason. A refutation also needs evidence locations that Melian reads back. Malformed calls get a field-specific message before schema validation. Verifier read-tool and report execution errors quote diagnostics as findings data with visible text, since errors may name author-controlled paths. Reports use the same round meter as read tools. Every report commit checks task ownership and budget, including replay; beforeTool alone cannot protect a replayed write.

The findings document is version 6. Optional maps hold verdicts by revision, producer and verifier version beside each sighting. Reports run sequentially. Within one verification task, confirmed outranks plausible, which outranks refuted for the same claim; weaker replacements leave the record and findings version unchanged. A replay of one report upserts the same record without another version bump. Reads project the latest version onto each claim and the strongest onto its speaker. Clearing or replacing a sighting removes its verdicts. Version 5 reads unchanged; earlier evidence migrations still apply.
