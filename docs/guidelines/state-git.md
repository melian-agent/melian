# State branch guidelines

`packages/state-git` is the git adapter of core's `RecordStore`, `GitRecordStore`. It keeps the shared record on the repository's `melian/state` branch, by rule 12 of [the shared record decision](../decisions/2026-11-13-shared-record-behind-a-store-port.md) and [the decision that amends it](../decisions/2026-11-14-git-record-store-refuses-by-location.md). Read both before changing it.

## How it works

- `RecordRepository` is a bare repository of Melian's own, `records.git` in the clone's state directory. It is never the clone: a fetch writes nothing into the clone's refs, and the clone is never made shallow.
- Every call fetches the branch's tip alone, `--depth=1`, into a ref of its own, and deletes the ref. Two processes can share one `records.git`; a lock another fetch holds is retried.
- Each fetch then points `refs/melian/last` at the tip, in `records.git` alone. A fetch with `--depth` always asks the remote, and a repository with no ref to name what it holds is sent the whole tip again. With the ref, an unchanged branch sends nothing and a grown one sends what is new. The ref is a hint: no call reads it to answer, it is never pushed, and two calls updating it at once lose only the hint. An update that fails twenty times is given up, and the call goes on. Nothing deletes old objects, so `records.git` grows with the branch's history; [issue #451](https://github.com/melian-agent/melian/issues/451) tracks collecting them.
- `StateTree` judges every entry of the fetched tree before a call answers or builds a commit. An entry is known when it is a mode `100644` file at `changesets/<changeset>/cell.json` holding a cell Melian writes, or at the path a record's own bytes give. A stray in one changeset's folder refuses that changeset; a stray anywhere else refuses every changeset. A handle remembers what it judged by mode, type, object ID and path, so it reads each blob once, and an entry whose mode changes is judged again. A refusal or `melian doctor` names a path that is not UTF-8 in git's quoted form, as `git ls-tree` prints it, so two such names never read alike.
- A write builds one commit with `read-tree`, `hash-object`, `update-index` and `commit-tree` on a temporary index, and pushes it with `--force-with-lease` on the tip it read. A lost race waits a random time below a bound that doubles from 50 ms to 8 s, and reads again, until the deadline.
- A push stopped at its deadline counts as landed only when its commit is the tip or an ancestor of it. The check deepens its fetch until the history holds the commit, holds the tip the commit was built on without it, or ends. A tip that has not moved since the push proves nothing, because the lease still holds and a transport that outlived git can land the push later, so the call fails as `unreachable`, saying it may have landed.
- `deadlineMs` sets one deadline for the whole call, a `Deadline`, and `RecordRepository.run` takes it as a required argument. Each git command gets only the time left, and none starts once none is left. A backoff waits the smaller of its own time and what is left. A push ends by three quarters of what is left, inside the call's deadline, so a push that stalls still leaves the landed check a quarter to learn whether it landed. Core's `git` returns the moment its timer fires, without waiting for git to exit, so a call whose every command is slow ends a few milliseconds past its deadline; `test/deadline.test.ts` allows 250 ms.

## Rules

- Run git only through `RecordRepository.run`. It checks the repository's configuration bytes and passes `overrides`, the settings that would run a program or start background work. A new setting with that power goes on that list with a one-line reason, and a test proves it holds with the configuration check mocked out, as `test/overrides.test.ts` does.
- Never read a stray entry's bytes into a record, and never rewrite or remove one. A commit carries it along by its object ID.
- A failure to reach or answer from the remote is `RecordError` `unreachable`; never answer from a tree read in part.
- The location rule protects what a call reads, not whether the store stays available. Every call fetches every blob of the tip before it judges any, so a writer who pushes a very large file to the branch can make every call slow or fail, as a writer who deletes the branch can. A fetch that runs out of time or disk fails as `unreachable`, naming the branch. Git writes each object whole, under its own hash, and writes the fetch's ref last, so a later call reads only what a whole fetch named. `test/fetch.test.ts` cuts a pack part-way; a full disk stops the fetch at the same point, before the ref, so it needs no test of its own.
- A call holds every record and cell of the tip in memory, so a tip whose records and cells total more than 256 MiB, `tipLimit`, fails the call as `unreachable`, naming the branch, the total and the limit, before it reads a blob. A blob counts at every path it sits at, since each path's record or cell is held apart: one cell's bytes copied into many changesets' folders count once per folder. Disposing changesets brings it under. The read itself stops at the bytes the sizes git reported. The limit is provisional: [issue #455](https://github.com/melian-agent/melian/issues/455) designs a read that does not hold the whole tip, with [issue #361](https://github.com/melian-agent/melian/issues/361).
- A call holds every entry of the tip too, so a tip of more than 65,536 entries, `entryLimit`, fails the call as `unreachable`, naming the branch, the count and the limit, before it reads a size. The listing is bounded first: git is stopped once it prints 64 MiB, `listingLimit`, a KiB a line on average, and the call fails the same way. A new resource a call takes goes in [the decision's table](../decisions/2026-11-14-git-record-store-refuses-by-location.md#what-one-call-uses-and-what-bounds-it), with what bounds it or who accepted it unbounded.

## Testing

- `test/fixtures/remote.ts` makes a bare remote in a temporary directory and opens handles with state directories of their own, as hosts are. `Remote.plant` commits entries by hand, as a writer outside Melian would.
- A local `file://` remote inherits the client's `-c` settings through `GIT_CONFIG_PARAMETERS`, so a hook in the test remote never runs. Stand in for a slow or refused push with a spy on `RecordRepository.prototype.push` that calls the real push, or plants a commit, before it answers.
