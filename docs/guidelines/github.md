# GitHub guidelines

The github package implements core's `ReviewProvider` port for GitHub through Octokit, renders what a review posts, and reads Melian's markers back. The port is the class `GitHubProvider`, one per repository, which `createGitHubProvider` constructs. It holds the Octokit client and the token's user once it learns it; the publisher secret is not its state, and travels with each call, since it belongs to the changeset. The pipeline's publish task decides when to post and records each post; this package decides how a post looks and where GitHub puts it. [design.md](../design.md#cli) says why the CLI sets a commit status rather than a check run.

## Posting

- One review per revision, with the event `COMMENT`. Never `APPROVE` or `REQUEST_CHANGES`: Melian never approves, and the status, not the review, says whether a change may merge.
- Inline comments go on the right-hand side by `line`, with `start_line` for a span, never by the deprecated diff `position`. Core's `finding.place(lines)` only ever names an added line, because GitHub refuses the whole review with a 422 when one comment names a line outside the diff.
- A finding outside the diff in a changed file is anchored to the nearest added line, and its comment links to the finding's lines at the revision with `blobUrl`. `blobUrl` percent-encodes every character of a path segment outside the unreserved set, `(` and `)` included, which `encodeURIComponent` leaves alone: a path such as `src/a)b.ts` otherwise ended the markdown link early. A finding in a file the change does not touch goes in the review body under a marker of its own.
- A `ReviewComment`, `ReviewComment.from(finding, placement)`, renders each finding, inline at its placement or as a section of the review body; `renderReviewBody` takes each body section from it. A finding's comment shows its failure scenario through `renderProse`, then lists each evidence location as its role and a link to its lines, rather than quoting the code. A head location links at the head reviewed; a base location links at `ReviewDraft.base`, the base commit the review diffed from. A base location says "deleted by this change" only when it carries `deleted`, which `report_finding` sets when its lines overlap a hunk's old lines or its file is one the change renamed without editing and the change did not only move the finding's own file; any other base location says "at the base". Problem: every base location said "deleted by this change", so a lens citing unchanged base lines as context made the comment tell the author the change deleted code it never touched. Solution: Melian decides the claim when it reads the location, and the renderer repeats only what Melian found.
- When GitHub refuses a review with a 422 and it carries inline comments, `postReview` posts it once more with every finding in the body, under a line saying GitHub refused the comments. A comment GitHub cannot place, such as on a line an outdated diff no longer has, would otherwise fail the round until the pipeline abandons it, and the findings would never reach the pull request.
- The review body lists the checks that did not run, a lens its budget ended among them, with core's `describeBudgetEnd` saying which budget ran out and what the lens had used. A lens whose level counts a budget's end as a run, `budget.ended: count`, is listed apart, so an author sees that its findings are what it reported before it stopped. A lens that ran with a `reason`, such as the hand-offs its instructions left out for size, is listed under "Lenses that ran with a note", the reason rendered as prose.
- GitHub refuses a body over 65,536 characters (`maxBodyLength`). `renderReviewBody` drops findings in the body from the last until it fits, and says how many were cut and that `melian findings "#N"` lists them all; if the summary alone is too long, it cuts the text at a line and says so. The marker on the first line is never cut.
- `createReview` does not return its comments' IDs, so `postReview` lists the review's comments afterwards and reads each one's finding from its marker.
- A resolved finding's reply says the revision no longer reports it, or, for a dismissed finding, `Dismissed at <head>:` and the reason through `renderProse`. A dismissed finding posted in a review's body has no thread, so the next review's body lists it under "Dismissed since the last review" with its reason. Neither names the dismisser. Melian records the git author, whose email does not belong on a pull request, and GitHub already shows whose token posted the reply.
- The commit status context is `melian/review`. GitHub refuses a description over 140 characters, so `setStatus` truncates.

## Markers

Every post opens with a hidden marker on a line of its own: `<!-- melian:revision=<sha> <kind>=<id> sig=<signature> -->`. The kind is `finding` on a finding's comment and on each finding in a review's body, `verdict` on a review's body, and `resolved` on a reply that resolves or dismisses a finding. A reply that gives a dismissal also carries the dismissal's version, `resolved=<id> dismissal=<version>`, core's `dismissalVersion`, so a second reason for one finding is a reply of its own, and `findPublished` returns each reply under core's `replyKey` of its finding, the thread GitHub reports as `in_reply_to_id`, and that version. The ID is the finding's, or for `verdict` the fingerprint of the verdict the review posts, because a second review of one head can change its verdict, and the publication of the new verdict is a review of its own. A review's marker also carries its round at the head, `verdict=<fingerprint> round=<n>`, and `findPublished` matches a review by both. Problem: a verdict can recur. Example: a head's verdict went A, then B when a check failed, then A again once it passed; the third publish found the first A review by its marker, recorded it instead of posting, and set A's status while the newest review on the pull request said B. Solution: each round has a number that only grows, and a review counts only for its own round. The signature is the first 32 hex digits of HMAC-SHA256, keyed with the changeset's publisher secret, over `<sha>|` and everything between the revision and `sig=`, such as `<kind>=<id>`; [the pipeline guideline](pipeline.md#publishing) says where the secret lives.

`findPublished` lists the pull request's reviews and review comments and counts a marker only when its signature verifies against the secret, whoever posted it. Problem: markers were trusted by author alone, and the author came from `/user`, which an installation token cannot read. Example: a run posted a review, crashed before recording it, and the rerun, with a fresh provider that had never seen a post, could not tell who it was, read no markers, and posted the review a second time. Solution: the signature is the proof, and the author is a filter. When the provider knows the token's user, from `/user` or from a review it posted, a marker on anyone else's post does not count either; when it does not, the signature alone decides. It asks `/user` once per provider and remembers a refusal too, since an installation token is always refused and asking for every marker cost a request each. A marker without a valid signature never counts, so a pull request's author cannot forge one to hide Melian's review. Anyone can copy a signed marker from a post, but the copy names only what Melian already posted, and the signature covers the kind, so a thread's marker pasted into a reply does not read as a resolution. The first post carrying a marker wins, since a copy can only follow Melian's own. The publish task reads markers before posting, so a run that crashed after GitHub accepted a post and before the task recorded it finds that post instead of repeating it. GitHub takes no idempotency key, so the markers are the only record GitHub itself keeps.

Untrusted text must never forge a marker, even though a forged one now fails its signature. Problem: a lens writes finding text after reading a change its author controls, and the author also chooses file paths. Example: an explanation holding a copied `<!-- melian:revision=<next head> verdict=<fingerprint> sig=<signature> -->` on a line of its own would make the next revision's publication think its review was already posted, and post nothing. Solution: `renderProse` escapes `<`, `>`, and `&` in every piece of finding text, so no HTML survives; `code` shows control characters in paths and rule IDs as `\uXXXX`, so a path cannot start a line; and only a marker standing alone on a line counts.

Finding text is never live markdown either. Problem: Melian posts from the maintainer's account, and a lens's text is steered by the change it read. Example: an explanation holding `[log in again](https://evil.example)`, a `# Approved` heading, a fence, `@octocat`, or `Fixes #123` rendered as a link, a heading, and code in the maintainer's voice, notified a stranger, and cross-referenced an issue. Solution: `renderProse` backslash-escapes every markdown control character, `` *_[]()#>!|~` `` and backslash itself, after collapsing runs of three or more backticks or tildes to one, and puts a word joiner (U+2060) after `@` and before the digits of `#123` and `owner/repo#123`, so nobody is notified and nothing is cross-referenced. Paths and rule IDs go in code spans through `code`, whose fence is longer than any run of backticks inside, so they cannot close it. Only Melian's own template text carries markdown. Any new rendering of finding text goes through `renderProse` or `code`.

## Importing review threads

`ReviewThreadImporter.open({ owner, repo, pullRequest, login, token })` imports another reviewer's findings from a pull request for `melian compare`, as [design.md](../design.md#comparison-with-external-reviewers) sets out. It reads through GitHub's GraphQL API, because REST's comment list carries no thread state, and a resolved thread is how CodeRabbit marks a finding fixed. Two paged queries, `MelianReviewThreads` and `MelianReviews`, ask for at most 100 nodes a page. Past 50 pages a query fails with `GitHubError` `failed` rather than stop, since a comparison missing threads past the cap would count them as misses no reviewer made.

- A thread is a finding when its first comment's author is the login, `coderabbitai[bot]` by default. Replies are conversation, never findings, and a thread a human opened stays the human's even when CodeRabbit answers in it. Each finding's reviewer comes from its author: CodeRabbit's bot is `coderabbit`, Copilot's, `copilot-pull-request-reviewer[bot]`, is `copilot`, and anyone else is `human`, kept by its login as REST spells it. The reviewer records `kind`, `bot` or `user`, from the author's GraphQL `__typename`.
- GraphQL names a bot by its bare login, `coderabbitai`, where REST and the web say `coderabbitai[bot]`. Problem: a filter that compared logins as GraphQL spells them never matched CodeRabbit. Solution: the query asks for the author's `__typename`, and a `Bot`'s comment counts for its login with or without `[bot]`, ignoring case, as GitHub does. So `github:coderabbitai` imports CodeRabbit's threads as `github` does. A `User`'s comment counts only for its own login, so a person who registered a bot's bare name is never taken for the bot.
- A thread's lines are `startLine` to `line`, GitHub's placement at the pull request's head. When GitHub no longer places it, `line` is null, and the finding takes `originalStartLine` to `originalLine` and is marked `outdated`. A file-level thread has no lines, and one on the diff's left side is marked `revision: "base"`. None of the three matches by site. A span whose `startDiffSide` differs from its `diffSide` starts in one file and ends in the other, so only its end line is kept. A thread whose first comment has no author, as for a deleted account, is skipped. The source reference is the thread's node ID and its first comment's URL, which carries the comment's ID, so the query asks for no `databaseId`.
- A finding's title is its first comment's first line that is not blank. CodeRabbit's comments open with a line naming the category and severity, such as `_⚠️ Potential issue_ | _🟠 Major_`, then the headline. So for CodeRabbit the first such line is the reviewer's `severity`, cut at 100 characters, and the next is the title. The importer selects lines and parses no markdown, as [the anatomy of CodeRabbit's output](../research/2026-10-04-review-output-anatomy.md) warns, so both keep their markup as written.
- Review bodies have no thread. CodeRabbit puts nitpicks and comments outside the diff there. The importer counts the login's non-empty review bodies as `skippedBodies` and reads nothing from them.
- Each finding records the commit its thread's first comment was written on, `originalCommit { oid }`, as `commit`, so core matches by site only a thread read at the compared head.
- `import()` returns the head GitHub placed the threads at, `headRefOid`, so the host can refuse a pull request that moved since Melian's review.

## Tokens

`resolveGitHubToken` reads `GITHUB_TOKEN`, then `GH_TOKEN`, then `gh auth token`. Report where a token came from, never the token. `GitHubError` messages carry GitHub's status and message only; Octokit redacts the token from the request it attaches to its own error, and that error is never printed.

## Tests

- Answer Octokit with the fake in `test/fixtures/fake-github.ts`, passed as `fetch`. It records every call, applies writes to a plain state object, and refuses an inline comment outside the diff as GitHub does. Never call the network.
- Answer the importer's GraphQL with `recordedGitHub` from `@melian-agent/github/testing`, over a recording such as `test/fixtures/review-threads.json`: the pages of each operation by name, written by hand from GitHub's documented shape. A request gets the page after the one whose end cursor it names. The CLI's scripted mode reads GitHub through the same helper, so its end-to-end tests never reach the network.
- `test/fixtures/scenario.ts` builds a pull request in two revisions and reviews it on the fake model, so publication tests run against a real verdict and findings document.
- The crash test, `test/publish-crash.test.ts`, runs `test/fixtures/publish-crash.ts` in a child process that parks once the fake has accepted the review, kills it, and publishes again in the test process. The child writes the fake's state to a file after every write, so the post outlives the process. It runs once with `/user` answering and once with it refusing, as for an installation token, so recovery never leans on knowing the author.
