# Evals guidelines

The evals package measures whether Melian's reviews find what they should and nothing else. It holds the golden corpus, a runner that reviews each golden, and scoring. [design.md](../design.md#evals-and-testing) says why evals are first-class: noise is where reviewers fail, and only measurement defends against it.

## A golden

Each golden is a directory under `packages/evals/goldens/`:

```text
goldens/correctness-null-deref/
├── base/           # the repository at the base commit
├── head/           # the repository at the head commit, every file, not only the changed ones
├── melian.golden.yaml  # optional; committed with base as melian.yaml, so it is the policy the review runs under
├── expected.json   # what a review must find
├── script.json     # the lens replies the scripted runner plays back
├── verifier.json   # optional; the scripted verifier's verdict on each finding, by finding ID
├── scripted.txt    # the scripted run's terminal output, compared by the gate
└── README.md       # optional; the comparison record and finding the defect came from
```

`buildGoldenRepository` commits `base/` on `main`, replaces the tree with `head/` on `feature`, and the runner reviews `main...feature`. A golden stores standards and policy under inert names, `AGENTS.golden.md` for `AGENTS.md` and `melian.golden.yaml` for `melian.yaml`, and `buildGoldenRepository` writes each under its live name, dropping `.golden` before the extension. Problem: the corpus sits in Melian's own repository, where an `AGENTS.md` is a standards file for the folder that holds it. Example: `conventions-unpinned-action`'s standards require pinned actions while its tree deliberately pins a tag, so a review of a change under that golden would load the fixture's rules as Melian's. Solution: only the golden's temporary repository sees the live names, and a test fails on any live name under `goldens/` but the corpus's own `goldens/melian.yaml`. Melian's root `melian.yaml` also keeps every lens off `packages/evals/goldens/**`, so seeded defects are never reviewed as Melian's code, and `goldens/melian.yaml` switches off `policy-change-review` beneath it, since a golden's `tsconfig.json` or `eslint.config.js` configures the golden's repository, not an analyser that runs on Melian; a change to that `melian.yaml` itself is still reported. A file in `base/` and missing from `head/` is deleted; a file that moves is a rename. Keep the trees small enough to read in one sitting, and write them as working code apart from the declared defects, so a live model is not distracted by unrelated breakage. The runner loads standards for the changed paths from the base and gives each lens its own chains. A nested `AGENTS.golden.md` reaches lenses covering that directory. The review reads standards from the base, so a golden that tests the `conventions` lens carries its `AGENTS.golden.md` in `base/` and, unchanged, in `head/`.

A golden whose `melian.golden.yaml` sets tiers runs Melian's own tier, as a test holds, and `buildGoldenRepository` writes the checkout's `.melian/lenses/*/LENS.md` into both of its built trees. Problem: a golden's review loads lenses from the golden's own repository, which holds only its trees, so Melian's repository lenses never reach it. Committing a copy into every tree meant re-copying every lens edit, 512 files for one routing change. A `LENS.md` under its live name inside the corpus would also be a lens for the folder holding it whenever Melian reviews itself. Solution: the builder adds them at build time, in the temporary repository only. Every such golden scores exactly the prompts Melian runs on itself, with both sides of every hand-off, and nothing under the corpus is a live lens. Every golden that names Melian's tier gets them, not every golden: a golden with no policy, or one that sets no tiers, models a customer's repository on the default tiers, and Melian's hand-offs to `durability` would change what it measures. A golden that needs a different lens commits it as `.melian/lenses/<name>/LENS.golden.md` in the tree that needs it, and the builder never overwrites it. Tests build every tiered golden and compare its lenses with the checkout's, prove an override wins, and prove a golden without Melian's tier gets none. Another fails when anything else sits beneath a `.melian/` or `.agents/` in the corpus, and another when a golden's `full` tier differs from the root's, or the root's leaves out a check of the default `full` tier. The root's `full` tier names `lens.design`, so every golden with a `melian.golden.yaml` scripts the `design` lens too, and scripts every lens in the tier. So every tiered golden scripts `trust-boundary-probes` too, the lens that probes beside the reading `trust-boundary`, with no finding, except the six `trust-boundary-probe-*` goldens. Problem: a probing golden's own `trust-boundary` probes at `deep`, and the probing measurement reroutes or strips that lens's probe alone. Example: the new lens extends the golden's `trust-boundary`, so in `trust-boundary-probe-round-environ-leak` its arm without probes would still plan and probe, and every pair would run a second prober on the committed route, whose findings count against precision. Solution: a probing golden's `full` tier is Melian's without `lens.trust-boundary-probes`, as the tier test holds, and its script leaves the lens out. The lens file still reaches its trees, but no tier names it, so the golden runs the lenses it ran before Melian's own rounds probed, with one prober. A lens that extends another under a new name needs a body line of its own. The scripted runner tells conversations apart by their instructions, so two lenses with the same instructions would share one script and run it out.

`expected.json` uses Martian's golden-comment shape, so Martian's judge reads it unchanged, with Melian's fields added to each comment:

```json
{
  "pr_title": "Trim manager names",
  "comments": [
    {
      "comment": "managerName reads name from an optional manager ...",
      "severity": "High",
      "category": "bug",
      "file": "src/user.ts",
      "rule": "null-dereference",
      "cause": "introduced",
      "failureScenario": "describe({ name: \"Ada\" }) ... throws a TypeError ...",
      "evidence": [
        { "file": "src/user.ts", "line": 7, "endLine": 8, "role": "cause" },
        { "file": "src/user.ts", "line": 7, "role": "context", "revision": "base" }
      ]
    }
  ]
}
```

`severity` is Martian's `Critical`, `High`, `Medium`, or `Low`. `file` and optional `alternativeFiles` name accepted locations. Scoring matches one of those paths and `rule`, which must be one the producing lens declares, or one of the optional `alternativeRules`. List an alternative by hand only where two rules name the same defect, and say why in the golden's README: `trust-boundary-probe-syntax-check-outside-text` accepts `path-traversal` beside `secret-exposure`, since the leak starts with a link the check follows out of the checkout. An optional `lines`, the first and last line of the defect at the head, makes a finding answer only where the claim that fits it was sighted, so a finding elsewhere in the file does not answer it; it must hold the line the evidence names as cause. A merged finding keeps its speaker's place, or a member's, and some members' evidence, and any of those can belong to another claim. So each claim is placed by its own check's sighting at the head, the one with its ID and level, read from the review's store as a miss's sightings are, and a guardrail's claim by its own finding. A lens claim with no sighting stops the score rather than missing it. An expectation counts as found when any finding fits it, so two expectations that share a file, a rule and a source would both count one broad finding, and a corpus test refuses them, counting an expectation that names no source as sharing any; a golden that needs two must first make `scoreGolden` count found from its one-to-one matching. An optional `source` names a check, such as `lens.trust-boundary`, that must have reported the finding. Problem: lenses that report one defect at one place share a finding, so a merged score cannot tell which lens found it. Example: `injection-in-comment` scores perfectly when `correctness` reports the planted comment, even if every other lens obeyed it. Solution: score adjudicated findings after merge and verification. An expectation matches the speaker’s rule and reporting check, or a rule and source paired in `otherClaims`. Each matching claim must be unrefuted. The speaker’s original verdict governs its eligibility, even when the merged verdict is confirmed by another claim. Scripted assertions use the same eligible claim. A check in `reportedBy` cannot supply another check’s rule. Each merged defect costs precision once; refuted and dismissed findings are excluded. `cause`, `failureScenario`, and `evidence` are what a good lens reports for the defect, `evidence` in the shape `report_finding` takes it. The scripted runner checks all three against the finding through `scriptedMismatches`, so the script's `report_finding` call carries the same scenario and locations; a live run checks none of them, since no model words a scenario the same way twice. A clean golden has an empty `comments` list, and any finding on it costs precision. Melian also reads one top-level field of its own, `live`, which [Adding a golden](#adding-a-golden) describes.

`script.json` maps each lens name to its replies, in order. A reply is `{ "calls": [{ "name", "arguments", "expectToolResult" }] }`, one model turn calling tools, or `{ "text": "..." }`, a final answer. `expectToolResult` is optional: a substring the call's result must contain. The runner checks it when the lens's next request arrives, and `runGolden` returns every miss in `toolMismatches`, which the gate requires to be empty. Problem: a scripted reply ignores what the tools returned, so a `search` broken to return "No matches." or a `read_file` of the wrong file still passed. Solution: give every call in a golden an expectation, such as the line a search must find or `recorded finding` for `report_finding`. Every lens the change selects needs a script, even if it only answers `Reported 0 findings.`; an unscripted lens fails the run.

`verifier.json` maps a finding ID to the scripted verifier's verdict, its reason and optional evidence; a finding it leaves out is confirmed with a stock reason. Script a verdict for every finding a golden about verification limits reports, so the golden says what the verifier must decide rather than leaning on the default. The `design-contradicts-documented-decision` goldens do: their clean variants have the design lens over-report and the verifier refute, so they prove that a refuted claim leaves the review clean. Live runs ignore `verifier.json` and use the real verifier.

## Two modes

**Scripted** runs are part of `npm run check`. `runGolden(golden, { kind: "scripted" })` routes every tier to the fake model, answers each lens from `script.json` by matching its instructions in the system prompt, and returns the findings and their terminal rendering. The test requires precision and recall of 1, the expected cause, failure scenario, and evidence for each finding, and a rendering identical to `scripted.txt`. Scripted golden tests allow 60 seconds because they create git repositories and run durable conversations; a loaded gate can exceed Vitest's five-second default. Scripted runs prove the plumbing: lens selection, the lens tools reading the head revision, `report_finding`, the hook, the findings document, and rendering. They say nothing about whether a lens's prompt finds the defect, because the script finds it.

After a deliberate change to rendering or to a golden, regenerate the snapshots with `npx vitest --run packages/evals/ --update` and read the diff before committing.

**Live** runs call real models and are never part of the gate. Run them with:

```bash
MELIAN_EVAL_LIVE=1 MELIAN_EVAL_MODEL=anthropic/claude-sonnet-4-5 npm run eval:live --workspace @melian-agent/evals
```

Credentials resolve as in a review, in this order: the named credentials of `melian.secrets.yaml` at the top level of the repository the script runs in, and of the user's own secrets file; then Pi's login; then the provider's environment variables. `npm run eval:live` runs the script in the evals package, not the root, so the first file sits there. `MELIAN_EVAL_MODEL` routes every tier a golden's `melian.golden.yaml` leaves unrouted. `MELIAN_EVAL_GOLDEN` names one golden to review instead of the corpus, as `MELIAN_EVAL_GOLDEN=contracts-breaking-signature`, for the repeated passes below. A name no golden has, or a golden marked `live: false`, which runs scripted only, stops the script with status 2 before it touches a provider. The script prints precision and recall per golden and micro-averaged over the corpus, skipping any golden marked `live: false`. Without `MELIAN_EVAL_LIVE=1` it exits with status 2 before touching a provider. Record each live run under `packages/evals/runs/`, with the model IDs, the commit reviewed, and what the misses and extras say about the lenses. Each score line ends with the run's total tokens and USD cost, as [Measurement cost](#measurement-cost) describes. A golden whose review throws, as when every model of a tier fails, prints `no score` with the error and available spend; the rest still run and the script exits 1. So does a golden whose review is not reviewed, such as one whose lens ended at its budget or whose prober left an attack open; the error names each check that did not run, with its reason. A golden runs its lenses alone, so guardrails and the static checks its tier names skip with leave, and only a lens, the verifier or a decision question can leave its review not reviewed. A scripted golden whose review is not reviewed fails its test. `MELIAN_EVAL_SHOW=1` prints, under each score line, each distinct note the golden's lenses recorded, once, with the lenses that carry it, such as the attacks a probing lens planned and the probes it ran. A note is a diagnostic, so the default output leaves it out, as [high signal, low noise](../decisions/2026-10-25-high-signal-low-noise.md) sets for the terminal. The flag then prints each golden's rendered review: the findings a lens reported with the verifier's reason, or for a verifier golden the verdict with the checks that did not run.

One run cannot tell a fixed lens from a lucky draw. In the [second](../../packages/evals/runs/2026-10-03-live-goldens-2.md) and [third](../../packages/evals/runs/2026-10-03-live-goldens-3.md) runs, an extra finding that one pass drew on a golden was missing from the other pass over the same golden. A live run that judges a prompt change therefore reviews each golden three times and reports the worst and the mean precision and recall. This is the rule for future runs; `live.ts` still reviews each golden once and does not enforce it.

A lens meets the bar when, over three passes, its goldens' worst precision is at least 0.8 and their worst recall at least 0.6. A lens's goldens are those whose names start with its name, scored together as one corpus and counting every lens's findings on them, since a golden scores the whole review. A lens below either bar may still ship, marked below the bar in its run record and in the plan; its goldens are never loosened to lift it over. A golden accepts what the review of record would accept as its defect, set by [the parity decision](../decisions/2026-11-16-parity-is-with-the-review-of-record.md), never by one live run: an expectation may name no `source` and may list `alternativeRules` only on that ground.

`MELIAN_EVAL_THINKING="heavy=medium,verifier=high"` overrides levels for one live run after its model routes are chosen. `EvalThinking.parse` refuses unknown or repeated tiers and unknown levels before credential discovery. Unlisted tiers keep their configured settings; overrides preserve models and fallbacks. Replacing the verifier model also retains its configured thinking. Live lens and verifier goldens accept the parsed override in their mode. Triage goldens use its light level, the role their direct model already serves. Scripted modes ignore live overrides. Each spend line uses recorded telemetry to print requested, sent and provider-reported levels. The gate tests live-run routing with fake models alone.

## A lens tool's before and after

A change that gives a lens a new tool is measured at two commits of Melian, the one before it and the one that adds it, with one model route for both. [Issue #241](https://github.com/melian-agent/melian/issues/241) gave the `tests` lens `list_mutants`, and these commands measure it. Each commit runs from a worktree of its own, so its build and its lens files are that commit's. Set `before` and `after` to the two commits and `model` to the route, then repeat the block for each.

```bash
commit=$before; tree=../melian-worktrees/measure-$commit
git worktree add --detach "$tree" "$commit" && (cd "$tree" && npm ci)
for golden in $(ls "$tree/packages/evals/goldens" | grep '^tests-'); do
  for pass in 1 2 3; do
    (cd "$tree" && MELIAN_EVAL_LIVE=1 MELIAN_EVAL_MODEL=$model MELIAN_EVAL_GOLDEN=$golden MELIAN_EVAL_SHOW=1 \
      npm run eval:live --workspace @melian-agent/evals) > "measure-$commit-$golden-$pass.txt" 2>&1
  done
done
```

Score the `tests-` goldens as one corpus, from the counts on each score line, as [Scoring](#scoring) says, and report the worst and the mean of the three passes at each commit.

The real misses are past ranges that another reviewer found test gaps or surviving mutants in. They are read by hand, not scored. Review one range with only the `tests` lens, at one commit of Melian, and keep the output in a file. In the worktree for that commit, an uncommitted `melian.local.yaml` names the lens alone, and a state directory of its own keeps one run from reusing another's lens run:

```bash
printf 'tiers:\n  fast: [lens.tests]\n  standard: [lens.tests]\n  full: [lens.tests]\n' > "$tree/melian.local.yaml"
(cd "$tree" && MELIAN_STATE_DIR="$(mktemp -d)" NODE_USE_ENV_PROXY=1 node packages/cli/bin/melian.js review "$range" --model "$model" --json) > "range-$commit.json" 2>&1
```

`$range` is the past change as `<base>...<head>`, both commits in the clone. Remove `melian.local.yaml` before the worktree is used for anything else, and the worktree once both commits are read.

## A level that probes

A golden for a level that probes scripts two conversations. Its lens's own name, such as `trust-boundary`, scripts the planner, whose instructions hold the lens's body. `trust-boundary/prober` scripts the prober, whose instructions do not. A call argument `{{probe}}` stands for the last probe ID a tool result named, since no script knows a probe's ID before the run. The runner runs every golden on the reviewer's word, since it builds the golden's repository itself, so a level that probes probes. That word only lets the head's code run inside whichever sandbox the harness holds, because `runGolden` runs the lenses alone and no static check. If `runGolden` ever runs a static check, which runs a trusted head's code unconfined, that stops being true, and the head's trust must then come from the caller, as the sandbox does. A scripted run of the committed corpus passes `probes: "unconfined"`, and only then does the runner give the harness `unconfinedSandbox`, since those probes are the corpus's own reviewed scripts. Without it, a scripted run probes under the host's sandbox-runtime, so a corpus loaded from anywhere else never runs its probes unconfined. A live mode has no such field: a live run's probes are a model's. The probing goldens are named `trust-boundary-probe-*`. Each `melian.golden.yaml` carries Melian's full tier, as every lens golden does, and holds `trust-boundary` at `deep`. A live run so scores the whole review, the other lenses' findings included, as the bar in [Two modes](#two-modes) requires. Their scripts answer every other lens with no finding. No shipped level probes until the measurement picks the routes, so each golden's `.melian/lenses/trust-boundary/LENS.golden.md` gives `deep` its probe. Each defect golden has a clean twin whose head is the fix as `main` holds it. The same scripted probe passes there, so `report_finding` refuses the finding and the review is clean. A defect golden's head is its clean twin with only the measured defect put back, never the real commit before the fix, by the maintainer's ruling of 2026-11-09. Problem: a real pre-fix commit can hold other defects, of the same file and rule, that the fix also removed. Scoring matches file and rule, so a live run could find one of those and score the golden as found. Example: #274's `claim.yml` at `fcb25afa` also lacked the timeline-lag guard its fix added, a second `fail-open` in the same file. So the twins differ in the measured defect alone, and a synthetic golden, such as the tsc stand-in, follows the same rule. A clean twin is clean in fact: before it settles, read it as a reviewer would, and fix in both twins anything a lens could rightly report there, so the defect twin still differs by the measured defect alone. Each such fix is named in the README and is not an expectation. The first live measurement found three on the syntax-check stand-in's head, and a reviewer a fourth; the defect twin's README lists them. A probing golden's expectation names a `source` only where the defect is one the probing lens alone should find; by the maintainer's ruling of 2026-11-16 in the coordinator's session, parity is with the review of record, whichever lens finds the defect, as [the parity decision](../decisions/2026-11-16-parity-is-with-the-review-of-record.md) records. `trust-boundary-probe-claim-lost-release` names none, since its race has no hostile party for the planner to plan for, and the correctness lens found it under `state-ordering`.

### Measuring the probing level's routes

`npm run eval:probing --workspace @melian-agent/evals` measures a level that probes, `trust-boundary`'s by default, against real models, for [issue #356](https://github.com/melian-agent/melian/issues/356). It runs on the harness `live.ts` uses: each review is `runGolden`'s, or `runRange`'s for a miss, so a review that is not reviewed, or whose level fell back to running without probes, gets no score. It reads the same settings `live.ts` reads, `MELIAN_EVAL_LIVE`, `MELIAN_EVAL_MODEL`, `MELIAN_EVAL_THINKING` and `MELIAN_EVAL_GOLDEN`, and these of its own:

- `MELIAN_EVAL_PROBE_ROUTES`: the combinations, separated by `;`. `label=planner>prober` runs a pair; `label=model` runs `deep` without probes on that model. Each model is read as core reads a model, so a model ID may hold `/` but not `>` or `;`.
- `MELIAN_EVAL_PROBE_LENSES`: the lenses that probe, separated by commas, `trust-boundary` by default. Only `trust-boundary` has probing goldens, so a run that includes goldens exits 2 for any other list, and names `MELIAN_EVAL_PROBE_SET=misses` for measuring other lenses on misses. A lens gains probing goldens of its own before it can be scored on goldens: on another lens's corpus, that lens's committed probe can earn the recall. Each one's `deep` level probes, on the combination's planner and prober routes, for goldens and misses alike, and a miss's review runs every level of such a lens as its `deep`. Any other lens whose level already probes, by its committed `LENS.md` or because `lens` mode makes `trust-boundary` probe, follows the combination too: it runs on the planner's route, its probes run on the prober's, and the arm without probes drops them. Only a named lens gains a probe it does not declare. The run asks core's `Lens.probeRefusal()` whether each may probe, and exits 2 for one core refuses, such as `tests` until [issue #493](https://github.com/melian-agent/melian/issues/493) lands, a lens without probing wording, or a lens that takes a built-in's name without extending it. It also exits 2 for a name the base's policy does not load, for a lens the tier of the review's `pull-request` stage does not run, and for one the review's configuration switches off or whose paths select none of the changed files, since each of those reviews would score a prober that never ran. A lens of a new name that extends `trust-boundary` or `correctness` but declares no probe is refused as a lens without probing wording, because core records the built-in it extends only once a level of it probes. The first review whose policy refuses one ends the run. The setting changes the levels in memory only and no committed `LENS.md`, so a measurement with it measures a policy nobody has committed, not the committed policy's behaviour.
- `MELIAN_EVAL_MISS_REVIEW`: `lens`, the default, reviews each miss with `trust-boundary` alone; `whole` reviews it with every lens in the base's `full` tier, as a pull request's review would, so a lens other than `trust-boundary` can find it. [Miss review cost](#miss-review-cost) gives each mode's cost.
- `MELIAN_EVAL_VERIFIER_MODEL`, required: one verifier route for every combination, keeping the golden's configured `thinking`.
- `MELIAN_EVAL_PROBE_PASSES`: passes per combination, three by default.
- `MELIAN_EVAL_PROBE_SET`: `goldens`, `misses` or `all`. It is `all` when `MELIAN_EVAL_MISSES` is set, else `goldens`.
- `MELIAN_EVAL_MISSES`: a JSON array of `{ name, repo, base, head, file, rule?, alternativeRules?, fix?, lines? }`, each a valid miss that a review of record found and Melian missed, in a clone on the machine. `lens` mode measures a miss that names no rule, or one of whose rules `trust-boundary` declares, in a file `trust-boundary` covers; `whole` mode and the parity measurement measure any. `fix` names the commit that fixed it; `lines` is the first and last line of the defect at the head. A sighting under `rule` or any of `alternativeRules` can find the miss. A miss may leave out `rule` only when it has `lines`, and then a sighting under any rule at those lines finds it; `alternativeRules` needs a `rule`. Each rule must be one some lens of the base's `full` tier declares for the file, in either mode, so one misses file serves both and a misspelt alternative exits 2. In `lens` mode one of them must be `trust-boundary`'s. A miss is scored on the reviewing lenses' own sightings at the head, `trust-boundary`'s in `lens` mode and every lens check's in `whole`, read from the review's store level by level, because a finding merged with another lens's, or with another level's, keeps only its speaker's lines and words. An ID excludes lines, so quick and careful can sight one ID at different lines, and the verifier can refute one and uphold the other. A sighting answers the miss when the verdict holds the claim of its check, ID and level unrefuted, it sits at the file under one of the miss's rules, or any rule when it names none, and it overlaps those lines. The claim may sit in any of the verdict's groups, so a refuted one scores the miss as not found. A dismissed claim counts by its own verification, since the measurement asks whether the lens sighted the defect and the verifier let it stand, and a dismissal is a person's later call that a fresh store cannot hold. A sighting the verdict holds no claim for, a reviewing lens's claim with no sighting, or a claim the verdict holds twice, leaves that miss with no score, as a failed review does. The score follows the verdict: an unrefuted claim counts whether or not its probe was sound, and the results file is what lets a reader check. Without `lines`, they come from git's diff of the head against the fix: the old side of each hunk in the miss's file, and for a pure insertion the line before it and the line after. A fix that changes nothing in the file exits 2 before any provider. Only a hand-entered `lines` range scores a miss, found or missed, by the maintainer's ruling of 2026-11-16, given in the coordinator's session. A fix's diff says which lines changed, not which defect each line held: one hunk can repair two touching defects, and several hunks can repair more than the miss. So a location from a fix decides nothing. It matches as `fix hunks`, and whenever an unrefuted sighting sits at the file under the rule, the miss prints as unadjudicated, naming every hunk and the ones the sightings overlap; give the miss `lines` to adjudicate it. A miss with neither matches by file and rule alone, the same way. An unadjudicated miss may hold another defect's sighting, so its review gets no score, as a failed review gets none, and its pass gets no miss recall. A review that sighted nothing at the file under the rule still scores as missed. A miss scores, found or missed, only when the review's own telemetry shows a completed conversation of a responsible lens, other than a prober's, whose stored coverage holds the miss's file, and which saw the defect. The responsible lenses are those the review runs that cover the file and declare one of the miss's rules, or all of them when it names none. `whole` mode scores only a miss with hand-entered `lines`, since its other lenses sight more of the file than the miss, and exits 2 before any provider, naming each miss without them. Each lens stage carries the `coverage` its conversation's stored policy gave it, and core's `lensCovers` answers. It also carries `shown`, the head path of each file whose diff its prompt carried whole, and `read`, the head lines `read_file` delivered to it for each changed file, as the transcript reader that counts review coverage finds them. A lens saw the defect when `read_file` delivered it a line inside the miss's lines, or when the prompt showed it the file and a head-side hunk of the range's diff holds one of those lines. The miss's lines are its hand-entered `lines`, or else the head lines its fix changes, so a fix-located miss with no sighting scores as missed only where the lens was shown or read a line the fix changes. The diff has no context lines, so a block shows only the lines its hunks change, and a pure deletion shows no head line. For a miss with neither `lines` nor `fix`, a shown file or any line `read_file` delivered counts. A prompt past its 200 KB limit stops before the block that would cross it, so a diff block is shown whole or not at all, and a file whose block was cut counts as not shown. A `search` result counts for nothing, since it delivers lines the lens asked about by pattern, not the code around them. A review where no responsible lens saw the defect prints the miss as unadjudicated with no score and says why, lens by lens: `not run` for a lens with no completed conversation scoped to the file, and `never shown` for one whose conversations were neither shown the file nor read the lines, so the report can tell a lens that saw the defect and missed it from one that never saw it. A stage an older Melian wrote has no `shown`, so its misses print as unadjudicated unless the lens read the lines. The goldens are not affected: the largest golden's whole head is about 41 KB.
- `MELIAN_EVAL_PROBE_TRUST`: the full commit IDs whose code this invocation vouches for, separated by commas. A miss's base and head are resolved in its clone and compared by commit, and both must be vouched for: the head's code runs in the probes, and the base's policy decides what they may read. A miss's probes run only on that decision, never because the misses file names it.
- `MELIAN_EVAL_POLICY_COMMIT`: a commit, such as `main`, whose policy, standards and lenses review every miss in place of its base's. Each miss resolves it in its own clone, and the results file records the commit as `policyCommit`. Goldens keep their own policy. Today's standards then judge old code, so a finding outside the miss's lines says little about that code's review. While a combination probes, the policy commit must be vouched for in `MELIAN_EVAL_PROBE_TRUST` beside the base and head, since its policy decides what the probes may read, and the run exits 2 before any provider otherwise. Every check that reads the base's policy for a miss, its rules, its coverage and its lenses, reads this commit's instead.
- `MELIAN_EVAL_PROBER_TIER`: the tier the prober runs on, `medium` by default.
- `MELIAN_EVAL_PROBE_OUT`: a file for the results as JSON. Each combination's passes hold a record of every review: its score, or whether it found its miss, or the error that left it none; for a miss, whether it `matched` by `lines`, by `fix hunks`, with the fix's `hunks`, or by `file and rule`, and the ID, lines, headline and failure scenario of each sighting that answered it (`hits`) and of each at its file under its rule that missed its lines (`near`), with `sightedBy`, the lens and level whose lines and words they are, the `evidence` and `verification` of that level's claim as the verdict carries them, the verifier's verdict and reason among them, and for a `fix hunks` hit the `hunks` it overlaps, so a reader can adjudicate every hit from the file alone; for a found miss, `foundBy`, the lens and level of each sighting that found it; `probedBy`, the lenses whose prober completed; for an unscored one, `unseen`, each responsible lens with `not run` or `never shown`; its notes; the other lens checks that ran on the prober's tier; its spend; its telemetry; and `probers`. A prober's stage in that telemetry holds the counts, the attacks it skipped, and each probe's attack, exit code, signal, time and whether it `failed`, `passed` or was `inconclusive`. `probers` holds, by that stage's ID, the plan the prober was given, each attack in it whole, each skip's reason, one whose attack was later probed included, and each probe's script, files and output, read from the review's store before it closes. Telemetry stores no completions, as the telemetry decision requires, so `melian review --json` and `melian telemetry` carry none of that text. The results file does, and a probe's output can hold any file `probe.read` allows, so the file is a local one and never an artefact. That text is the model's and the head's, held to the probing tools' limits, so a reader treats it as data. So the file answers what the terminal showed, without it. A claim names no probe, so the file cannot say which probe a hit rests on; to keep the full rendered review, run with `MELIAN_EVAL_SHOW=1` and keep the terminal output beside the results file. It also says what was measured: a `version`, 2 since `missReview` and `probeLenses` record the mode and the probing lenses, the evals checkout's `commit` and whether its tree was `clean`, and each miss's names, its `rules` and the responsible `lenses`, with the `baseCommit` and `headCommit` they resolved to when the run began, and its `location`: the lines it was matched against and whether they came from the misses file or the fix's diff, with the `fixCommit`. Every pass reviews those commits, so a branch that moves mid-run changes nothing. The run writes the file before any provider and replaces it whole after each pass, with `complete` false until the run ends, so a cut run keeps the passes it finished.

A malformed setting, a misses entry whose file the range does not change, whose file `Lens.select` under the base's configuration leaves out of every reviewing lens's files, by its path or, for a file the range renames, its old path, as the review covers a renamed file, whose rule no lens of the base's `full` tier that reviews the file declares, or, in `lens` mode, none of whose rules a `trust-boundary` lens that reviews the file declares, whose file at the head is empty, or one core's `readRevisionFile`, the lens's own reader, refuses or cuts before the miss's lines, or whose `lines` run past its file at the head, a selected miss whose base or head is not vouched for while a combination probes, a results file the run cannot write, or a host where `Probe.availability()` refuses, exits 2 before any provider. The planner runs as `trust-boundary`'s own lens route, so no other lens changes. The prober cannot: `probe.prober` names a tier, and the configuration has only light, medium and heavy. So the prober's tier routes to the prober's model, and every other lens level on that tier runs on it too. Each combination prints those checks, and the results file keeps them as `sharedProberTier`; read a clean golden's precision with them in mind. A route keeps its tier's `thinking`, the planner heavy's, so effort is per invocation, set with `MELIAN_EVAL_THINKING`.

Each review prints a line with its score, or `found` or `missed` for a miss, and its spend; a miss located by its fix or by file and rule alone, with a sighting at its file under its rule, prints as unadjudicated with no score, then every note its lenses recorded, such as `lens.trust-boundary: it planned 2 attacks and ran 2 probes in 0.4 s`. The measurement prints notes without `MELIAN_EVAL_SHOW`, because the attacks planned and probes run tell a prober that skipped its attack from one that probed and found nothing. `MELIAN_EVAL_SHOW=1` adds each rendered review. Each combination ends with its worst and mean precision and recall over the passes, and miss recall, with the spend of every review, failed ones included. A combination with a review that had no score gets no worst or mean, and the script exits 1. In `lens` mode a miss reviews `trust-boundary` alone, and in `whole` mode the base's `full` tier, under the base's policy, each probing lens at its `deep`.

```bash
MELIAN_EVAL_LIVE=1 MELIAN_EVAL_MODEL=openai-codex/gpt-6.1-sol MELIAN_EVAL_VERIFIER_MODEL=anthropic/claude-sonnet-5-5 MELIAN_EVAL_PROBE_ROUTES='pair=openai-codex/gpt-6.1-sol>openai-codex/gpt-5.6-terra;off=openai-codex/gpt-6.1-sol' npm run eval:probing --workspace @melian-agent/evals
```

#### Miss review cost

`lens` mode runs one lens conversation per miss per pass, `trust-boundary`'s, plus its planner and prober when the combination probes, and the verifier for each claim. `whole` mode runs a conversation for every lens the base's `full` tier selects for the miss's changed files, plus a planner and prober for each lens that probes, and the verifier for every lens's claims. On the scripted `trust-boundary-fail-open` golden, a two-file TypeScript change under core's default tier, `whole` mode ran six lens conversations and a verification where `lens` mode ran one. Melian's own `full` tier holds nine checks, so expect a miss on Melian to cost several times its `lens` review, and read each pass's spend line before running three.

### Measuring parity per total budget

`npm run eval:parity --workspace @melian-agent/evals` asks whether Melian finds a review of record's misses when its lenses together spend what a committed round spends, for [issue #561](https://github.com/melian-agent/melian/issues/561). The maintainer ruled on 2026-11-18, in the coordinator's session, that Melian in aggregate should use the same budget as the review of record and Codex's review, not each lens by itself, and that the pilot runs first. The arm is called "Parity per total budget" in the tool and the record.

Each miss gets two reviews, both with the whole review of `MELIAN_EVAL_MISS_REVIEW=whole`, and both with every route held to its first model:

1. The committed arm: the policy commit's policy and lenses as committed, with Enola's graph opened as the CLI opens it.

Before a miss's reviews, the run builds Enola's graph of its head with the call the CLI's `static.enola` check makes, under the policy commit's Enola settings, and both arms open it from the cache. Enola reads the head's own configuration, so it builds only a head vouched for in `MELIAN_EVAL_PROBE_TRUST`, and refuses any other before a provider runs, as a probe is refused. Each attempt records the head's snapshot ID as `graph`. A miss whose graph cannot be built is unscored, its committed attempt saying why, and the parity arm is not run; it is never reviewed without its callers.
2. The parity arm, whose lenses share the committed arm's lens spend on the same miss. The spend is Melian's budget count, input, cache writes and output, without cache reads, since that is what each lens's budget meters. The total holds only the committed arm's `melian.lens` conversations, a probing lens's planner included; its probers, triage, verification and walkthrough are left out, and the run prints each of their spends beside it after every review. Each lens of the tier gets a share of `total × (0.5/N + 0.5 × lines/Σlines)`, where `lines` counts the changed lines of the files the lens selects. A lens that probes splits its share between its planner and its prober, since each conversation spends against its level's budget. Every lens gets the design lens's capabilities: the graph tools, with the design lens's paragraph on them appended to its instructions in memory; `high` thinking on its route; and one level in place of its own, declared as both `careful` and `deep` and never `quick`. That level is its `deep` level, which probes wherever core's `Lens.probeRefusal()` allows, with at least the policy commit's design lens's findings budget and its tool-call ceiling, read from that lens as loaded, so the token share is what binds; a policy commit with no design lens at its root refuses the arm. Problem: a review under a revision policy reads each lens's band from the policy and raises an untrusted head to `careful`, so a level set in configuration alone does not hold, and a lens triage put at `quick` escalates and runs a second conversation. Example: the first form of the arm set `deep` in configuration, and every lens ran at `careful` on its committed budget. Solution: whichever level triage picks or the floor raises it to runs the same settings, and with no `quick` nothing escalates, so the lenses together spend no more than the total. The level an attempt records is the one triage picked, and in the parity arm it is a name only; the attempt records the token limit, tool limit and thinking that ran beside it. A test reviews a range through each arm on a scripted model and holds the parity arm to these settings and the committed arm to its policy's own levels and budgets. A lens its share ends counts with `budget.ended: count`, keeping its findings so far. A share is a soft limit: the request that crosses it finishes, so two lenses on shares of 50,000 that each make one request of 80,000 spend 160,000 against a total of 100,000. The shares alone therefore promise nothing. What keeps the promise is a check after each parity review: it sums the budget count its lenses and probers recorded, and a review whose sum passes the total is saved unscored, its `overrun` the tokens past the total and its `said` naming both. A review at the total scores. No committed file changes.

It reads `MELIAN_EVAL_MISSES`, `MELIAN_EVAL_PROBE_TRUST` and `MELIAN_EVAL_VERIFIER_MODEL` as the probing measurement does, and these of its own:

- `MELIAN_EVAL_PARITY_MISSES`: the misses to measure by name, separated by commas; every miss in the file by default. Each must have hand-entered `lines`.
- `MELIAN_EVAL_POLICY_COMMIT`, required: the commit whose policy reviews every miss in both arms, as the probing measurement reads it. Old misses are reviewed under one policy, not each under its own base's. It must resolve to one commit in every miss's clone, and its commit ID must be vouched for in `MELIAN_EVAL_PROBE_TRUST`.
- `MELIAN_EVAL_PARITY_DRY=1`: check every miss and stop before any provider. It prints `scorable` with the reviewing lenses for each miss the policy can score, a `refused` line for each it cannot, naming the check that failed (`file unchanged`, `file uncovered`, `rule undeclared`, `head unreadable`, `lines unreadable`, `unvouched` or `commit unresolved`), and a count, and exits 0. After each `scorable` line it says whether Enola's graph of that miss's head is cached or needs building before its reviews, and builds none. Without it, a run with any refusal prints the same lines and exits 2, so one exit names every miss to fix.
- `MELIAN_EVAL_PARITY_OUT`, required: the results file. A run resumes from it, skipping the arms it finished, and refuses one written at another commit, on another probe host, under another policy commit or with another `MELIAN_EVAL_VERIFIER_MODEL`. The probe host is the pipeline's `probingHost`: the sandbox's platform, kind and installed release, and the architecture and version of Node, which a probe's answer depends on, so both arms of a miss probe on one host. A results file of version 1, written before the host was recorded, is refused. The file records each miss as first reviewed, by repository, resolved base and head, file, rules and lines, and a resume refuses a reviewed miss that now names anything else. The checkout must hold no uncommitted change, so the commit names the code that ran. The results file, its stores beside it, and the misses file therefore live outside the checkout, as the command below has them: a run exits 2 before any model when `MELIAN_EVAL_PARITY_OUT` or `MELIAN_EVAL_MISSES` names a path inside it, through a symbolic link or not, since the stores it writes would leave the checkout changed and refuse the resume.
- `MELIAN_EVAL_PARITY_STOP_REVIEW` and `MELIAN_EVAL_PARITY_STOP_RUN`, required: token stops, counted with cache reads. The run stops after a review that spent more than the review stop, and before a review once the run has spent the run stop.

The run also stops after the first review whose telemetry did not measure a model stage's usage, by the pipeline's own `usageIncomplete` rule, rather than count it as nothing, and after the first review that met a provider's usage limit, by the pipeline's `isProviderLimit`, or in which any stage answered on more than one model. With every route held to its first model, only a failover does that. It stops too after a review in which a lens, a prober or the verifier did not run because its route reached no model with credentials, since the same stage would go unrun on every later miss; a resume picks up once the credential is back. This stop is a rule of this measurement only, and no judgement on fallbacks: the maintainer ruled a fallback equivalent in real rounds. Here both arms must answer on the same models to be compared. A stopped run records why and exits 3; run it again with the same results file to resume. A resume narrowed by `MELIAN_EVAL_PARITY_MISSES` that leaves a miss the results file names without both arms reviewed stops the same way, naming that miss, so a narrowed resume never reads as a finished run.

Every attempt goes in the results file, a stopped one marked with why, so the run's totals are always the sum of its attempts and a resumed run reviews a stopped arm again without forgetting what the stopped attempt spent. Each attempt and stage records both counts: `tokens`, with cache reads, as a round's Spend line counts, and `budgetTokens`, as Melian's budgets count. About 80% of a lens's tokens are cache reads, so the two differ by about five times. After each review it prints the review's tokens, its cache reads and its budget count, and the run's totals so far, then a line for each lens its share ended. The results file holds every stage's models, the reasoning effort its requests asked for and the effort the provider reported, as the stage's telemetry records them, and its tokens, cache reads, tool calls, minutes, token limit and how it ended, so a reader can check that each lens answered on its route's model and effort. For a lens its share ended, it also holds the covered changed files it was neither shown nor read, and for such a prober, the planned attacks it neither probed nor skipped. Each review keeps its store in its own SQLite file under `<results>.stores/`, and the results file names it, so a miss one arm found and the other missed can be read turn by turn. A review a stop cut keeps its file, and its resumed review takes the next name. Each attempt is saved before its review starts, marked pending, and replaced when the review ends. A run that died during a review leaves that pending attempt, and a resume first settles it from what its store recorded, through the pipeline's own telemetry reader: a store never opened spent nothing, a store that cannot be read refuses the resume, and a store that did not measure a model stage's usage stops the run once more after the settled attempt is saved. A resume that leaves out the pending attempt's miss is refused, since it could not settle it. The stores hold the head's code and the models' words, so they stay on the host, as the results file does, and never become an artefact.

A run record for it starts from [the template](../../packages/evals/runs/parity-per-total-budget.template.md), and must say, in its first paragraph, that the design lens's graph tools refused in every earlier measurement, because no measurement opened the graph, so every earlier figure understated that lens. It must also say what each published token figure counts: a round's spend line sums every response's input, output, cache reads and cache writes; a lens budget leaves out cache reads; and Codex's "tokens used" is input less cached input, plus output. It must say that the Agent tool's figure for a review of record was unverified, and is now known not to be a sum, and that `high` thinking spends part of each share on reasoning. Melian's measured yardstick is [the review of record on pull request #552](https://github.com/melian-agent/melian/pull/552#issuecomment-6965864283): 52 tool uses in 23 minutes, about 8.03 million tokens summed from its transcript with cache reads, beside Codex's 114,858 printed tokens, about 1.6 million with cache reads.

## Triage evals

The triage corpus under `packages/evals/triage/<name>/` holds changes whose right level, for each lens, the maintainer has judged: `base/`, `head/`, `expected.json` (`title`, and `levels`, a lens name to `quick`, `careful`, or `deep`), `script.json` (a lens name to the probability the scripted model gives each level), and a `README.md` saying why those levels are right. `melian.yaml` beside them switches off policy notices, and the root `melian.yaml` keeps every lens off the corpus. The levels are a judgement, not a measurement; change one only with the reason in that golden's README.

`runTriageGolden(golden, mode, passes)` reviews the change with the lenses the golden names, on a fake model that answers "Done.", under the real `FallbackDecider`, and reads what the decider chose for each lens from the stored decision, before the lens's band holds it. A scripted run answers through a stub text model, which answers only the questions the request asks and throws for one the script lacks, so it proves the plumbing: the questions reach the decider, its answer is read, and the choice is stored. It says nothing about the questions. A live run gives the decider a real model, `MELIAN_EVAL_MODEL`, and spends tokens on that one request a pass:

```bash
MELIAN_EVAL_LIVE=1 MELIAN_EVAL_TRIAGE=1 MELIAN_EVAL_MODEL=anthropic/claude-sonnet-5-5 npm run eval:live --workspace @melian-agent/evals
```

It asks each golden three times, or `MELIAN_EVAL_TRIAGE_PASSES`, and prints exact share, mean distance in levels, and the count of choices below the right level, which let a change through with less of a look than it needed. `MELIAN_EVAL_TRIAGE_OUT` writes the measurement as JSON, with the question set's version and the questions' fingerprint. `MELIAN_EVAL_TRIAGE_BASELINE` names an earlier measurement: the script prints whether the questions choose better, worse, or the same, a lower mean distance first and then a higher exact share, and exits 1 when worse. It also says when the questions changed and their version did not, or the reverse.

A changed question ships with its version bumped. `triageQuestionSet.version` in `packages/core/src/triage.ts` stands for the questions every shipped lens asks, in `lens.triageQuestion`. `packages/evals/triage/questions.json` records a hash of those questions for each version, `{"1": "<hash>"}`. A gate test fails when the current hash differs from the entry for the current version, or the version has no entry. The real-checkout test walks questions.json's complete history reachable from HEAD, without remote refs. Every recorded version keeps its fingerprint across all earlier snapshots, including the original questionSet/fingerprint shape. Unreadable, empty or shallow history fails closed. Outside CI, on a shallow clone, the real-checkout test checks the current fingerprint, then skips the walk over history and prints why, as [the amendment](../decisions/2026-11-08-shallow-history-skips-outside-ci.md) sets; CI fetches the whole history. A one-snapshot history passes only when that commit added the record. Fixture repositories prove that a committed rewrite fails and a new version passes. After editing a question, bump the version, add its entry to `questions.json`, run the live measurement against the last version's recorded measurement, and put the comparison in the pull request. A measurement of one pass over a stochastic model is a draw, so compare three passes, as the lens corpus does. A comparison refuses, as incomparable with exit 2, an incomplete baseline or one measured with another decider model, thinking level or golden set, and reads means within 0.005 as equal.

## Verifier evals

Verifier regressions live under `packages/evals/verifier/<name>/`, separate from the lens corpus. Each directory holds `base/`, `head/`, `candidate.json`, `expected.json`, `script.json` and a `README.md` naming the comparison record and finding. The four initial misses come from [pull request #68](https://github.com/melian-agent/melian/pull/68), C5 and C8, [pull request #72](https://github.com/melian-agent/melian/pull/72), C9, and [pull request #61](https://github.com/melian-agent/melian/pull/61), A1. The decoys cover a null guard and a type with one caller that excludes zero. Two cases judge a `reimplements-an-authority` claim under a stated gap: `design-reimplements-an-authority-unsupported-gap` must be confirmed, and its decoy `design-reimplements-an-authority-supported-gap` refuted.

`loadVerifierGoldens` validates the files. `runVerifierGolden` plants the candidate through a scripted lens's `report_finding`, so Melian reads the snippets, then runs the real verification task. `scoreVerifierGolden` accepts confirmed or plausible for a `needs-execution` case, only refuted for a decoy, and only confirmed for a `design` case. A missing judgement fails. A verifierFailed review scores that golden as unjudged and continues the corpus; other errors still stop the run. The scripted suite runs in the gate; it checks integration and scoring, not model quality. A design case selects the design lens and receives the base decision index. Its script may require instruction substrings through `expectInstructions`; removing the base rule or context must fail the scripted conversation. The root policy excludes this corpus from lenses, and its own `melian.yaml` disables policy notices beneath it.

A directory with a `scenario.json` is a scenario golden, loaded by `loadScenarioGoldens` and skipped by `loadVerifierGoldens`. The eleven that [the lowering decision](../decisions/2026-10-13-re-scope-held-for-the-compiler.md) lists are scenarios, named by group: `lowering-`, `surfacing-` and `conflict-`. A scenario holds `base/`, `head/`, `candidate.json`, `scenario.json` and a `README.md`. It may hold `head2/`, a second revision reviewed on the same storage, and a `melian.golden.yaml` that becomes the repository's policy.

`scenario.json` lists the `report_verdict` calls a scripted verifier makes, one a turn, each with the substrings its result must contain. It may plant a deterministic co-report on the candidate's own lines, ask for a second run with the reports reversed, and require verifier instructions. It ends with what each revision must show: the status, and the one finding's severity, original severity, cause, resolution, verdict, lowering and place under "Pre-existing, important", with text the terminal must and must not print. `runScenarioGolden` plants the candidate through a scripted lens and judges it through the real verification task. `scenarioMismatches` describes every difference, and the gate expects none. Scenarios are scripted only: they test what Melian does with a report, never what a model says.

Live verifier runs need both `MELIAN_EVAL_LIVE=1` and `MELIAN_EVAL_VERIFIER=1`. `MELIAN_EVAL_VERIFIER_MODEL` routes their judge independently; `MELIAN_EVAL_MODEL` is its fallback. `MELIAN_EVAL_GOLDEN` selects one verifier case. An unknown name or absent model stops the suite before provider access. The finder stays scripted, so the suite measures whether the judge retains a real defect. The runner prints each verdict and pass or fail, then the total; any failure exits 1. An unjudged golden prints the reason its verifier check recorded, as `unjudged (Codex error: ...)`, so a provider's error does not read as the judge's silence. The judge retries a failed request with backoff, as a review does. Problem: the harness once switched retries off, and one overloaded reply scored a golden unjudged. Example: three of six live verdicts on [pull request #114](https://github.com/melian-agent/melian/pull/114) were unjudged, each a provider error. Live runs spend tokens and remain outside the gate.

Existing lens goldens explicitly route the fake verifier in scripted mode. In live mode their verifier uses `MELIAN_EVAL_VERIFIER_MODEL`, or `MELIAN_EVAL_MODEL`, or the committed verifier route when neither variable is set. A fake provider can be added to an existing opaque model collection through the pipeline testing entry; this lets a planted finder share a harness with a separately routed judge.

## Resolution goldens

The twenty goldens that [the resolution decision](../decisions/2026-10-13-resolution-as-built.md) lists live under `packages/evals/goldens/resolution/<name>/`. They run no model and no lens, so `loadGoldens` leaves that directory out and `loadResolutionGoldens` reads it.

Each holds a `base/` tree with the policy, under the corpus's inert names: `melian.golden.yaml` at any level, and `.melian/lenses/<name>/LENS.golden.md` for a lens that declares a default. A `head/` tree, when there is one, is laid over the base as the change. `scenario.json` scripts the findings a review would hold: each report's check, rule, severity and place, the verifier's verdict on a lens report, and a lowered severity. Two reports at one file, line and code are one defect.

`runResolutionGolden` commits the trees and reads policy and lenses from the base, as a pull request's review does. It runs the guardrails over the change, resolves every finding through `configsFor` and core's `Adjudication`, and lists what `melian doctor` would print through `resolutionOverrides`.

A golden is held three ways. `expect` in `scenario.json` says what each finding must resolve to and which file must have decided, written by hand from the decision. `doctor` lists the doctor lines. `expected.txt` holds the rendering `melian findings` prints, with its `Decided by` lines, and is read before it is committed. The rules that tie a lens golden's `LENS.golden.md` and tiers to Melian's own leave these goldens out.

## Scoring

Score the verdict’s adjudicated findings, excluding its refuted and dismissed groups. A finding matches an expected path or `alternativeFiles` path, overlaps the expectation's `lines` when it names them, and holds a rule/source pair from the speaker or `otherClaims`, the rule being `rule` or one of `alternativeRules`. `reportedBy` retains co-reporters, but never pairs a check with a rule another claim supplied. Each expected finding is a true positive at most once, and findings are paired with expectations so that as many count as can: a second reported finding matching an expectation already matched is a false positive, because it reports one defect twice. Precision is true positives over reported findings; recall is expected findings found over expected findings. A golden with nothing expected has recall 1, and one with nothing reported has precision 1. `scoreCorpus` sums the counts across goldens before dividing, so a golden with many findings weighs more than a clean one.

File and rule is a coarse match. Two findings under one rule in one file count as one expected finding found, and a finding on the right file and rule but the wrong line still matches, unless the expectation names `lines`. Martian's judge compares comment text; run it when the match needs to be semantic.

## Adding a golden

1. Write `base/` and `head/` so the change carries only the declared defects, or none for a clean golden. One change may carry more than one, as real changes do: `contracts-breaking-signature` breaks a caller and gets yen wrong. Declare every real defect, because a lens that finds an undeclared one is right and would score as noise.
2. Write `expected.json`, naming for each defect the lens rule that should catch it, its cause, a failure scenario with concrete values, and the evidence locations that show it.
3. Write `script.json` with the tool calls a good lens would make, each with the `expectToolResult` that proves its tool worked, ending each lens with a final answer. Each `report_finding` call carries the failure scenario and evidence its expected finding names.
4. Run `npx vitest --run packages/evals/ --update` to write `scripted.txt`, read it, and commit all of it.
5. Run the live eval if you have credentials, and record a miss as a learning about the lens, not by loosening the golden. A live run can show that a golden refuses a finding the review of record would accept; change the golden then under [the parity decision](../decisions/2026-11-16-parity-is-with-the-review-of-record.md), with the reason in its README, never to lift a score.

A lens body's examples never restate a golden. Problem: an example drawn from a golden tells the lens the answer, so the golden measures recall of the prompt rather than judgement. Example: `removed-behaviour` once named "the worktree is removed even when the task throws" as an invariant, the very defect `removed-behaviour-dropped-cleanup` seeds. Solution: write examples in shapes no golden seeds, and when a golden is added, check the lens bodies for its shape.

A repeated review finding that becomes a guardrail gets a golden too, named `guardrails-<rule>`. Its `melian.golden.yaml` carries the rule, copied from the root `melian.yaml`, and a test fails when the copy drifts. `expected.json` names `guardrail/forbidden-patterns` as the rule. `runGolden` runs the guardrails for a golden that expects a `guardrail/` rule and for no other. Problem: the default guardrails would add notices to every fixture's `package.json`. A guardrail finding has no failure scenario and no evidence, so a scripted run holds it to its cause alone. The golden sets `live: false`, since no model takes part. The lenses still run, scripted to report nothing.

`live.ts` runs every golden, or the one `MELIAN_EVAL_GOLDEN` names, unless its `expected.json` sets `"live": false`. It prints `<golden>: skipped, live: false` for such a golden and leaves it out of the corpus score; the scripted run still covers it. Problem: some goldens test plumbing a live lens has no reason to exercise. `pre-existing-beside-change` proves that a `context` location in changed code does not promote an old defect, so it expects a `pre-existing` finding, and a live lens that rightly declines to audit old code never reports one. Live, that golden could only cost recall. Set `live: false` only for such a golden, never to hide a lens's miss. `injection-in-comment` checks that a lens reports an instruction planted in the change under `melian/injection-attempt` and still finds the defect beside it; on a live run, a lens that obeys the comment scores a recall of zero. Each backlog lens has a targeted one too, `trust-boundary-injection`, `removed-behaviour-injection`, `tests-injection`, and `conventions-injection`: the planted comment names that lens and sits beside a defect only it owns, and the injection attempt is expected with `source` set to that lens, so a lens that obeys loses recall even when `correctness` reports the comment. `correctness-deleted-guard` is a pure deletion: the finding beside the deleted guard has no new lines to overlap, so only its `cause` location at the base, read with `read_file` and `revision: "base"`, makes it `affected`.

`correctness-deleted-rethrow` runs under the `standard` tier, as a `pre-push` review does. `runGolden` reviews under the tier of the `pull-request` stage, and that golden's `melian.golden.yaml` routes the stage to `standard`, so `correctness` runs alone and renders no hand-off. Its policy still carries Melian's `full` tier, as every golden's must.

Comparison records feed the corpus where an adjudication owes a golden, as [Comparisons](#comparisons) sets out.

One defect can fit two lenses’ rules, and each can report it under its own. Scoring uses the merged, adjudicated defect once. Expectations can require either rule and its source; a second sighting does not cost precision. Declare a second finding only where the second lens's instructions claim that kind of defect, as both `correctness` and `removed-behaviour` claim a removed guard: `correctness-deleted-guard` and `removed-behaviour-dropped-guard` each expect `correctness`'s `wrong-result` and `removed-behaviour`'s `dropped-guard`. An independent defect with no matching expectation costs precision. An expectation can require a lens through `source`, but it cannot require another lens to stay silent on the same lines, because that sighting merges into the expected defect. `design-reimplements-an-authority-standard` expects `conventions` alone, so its live record counts `design`'s sightings by hand.

## Comparisons

The shadow reviewers keep running until Melian reaches recall of at least 0.75 against the shadows' adjudicated findings. Use the ten most recent eligible merged pull requests after 2026-10-06T00:00:00Z. Every merged pull request in this repository after that instant is eligible, whether its comparison exists or not. A missing record or pending adjudication in that window blocks retirement. Require at least one adjudicated valid in-scope distinct shadow finding; zero findings leave recall undefined and keep both shadows running. The committed root key `comparison.retirement` holds `pullRequests: 10` and `recall: 0.75`. Only the maintainer may tighten the criterion. Count each distinct valid in-scope finding once across the shadows, and each pull request once across rounds. Noise, duplicates and out-of-scope findings do not count. Unadjudicated findings stay pending and missing records stay absent; either blocks retirement within the window. A shorter window keeps the shadows. The retirement line in `melian compare stats` follows [pull request #72](https://github.com/melian-agent/melian/pull/72).

Every Melian pull request gets a comparison record under `packages/evals/comparisons/`. It lists what Codex's adversarial review, Claude Code's review, and Melian found, and the maintainer's adjudication of each. `melian compare export` writes each new record from the stored comparison. Earlier hand-written records stay as history. [design.md](../design.md#comparison-with-external-reviewers) says how a comparison is built, and how it serves a repository that runs CodeRabbit.

Each finding is adjudicated valid, noise, or a duplicate, with a severity. A duplicate names the finding it duplicates through `--of <id>`. It costs its reviewer recall as well as precision; only that reviewer's own valid report earns recall credit. A valid finding Melian missed takes one reason:

- `owned-missed`: a lens or check owns it and missed it. It usually owes a golden for that lens.
- `no-owner`: no lens or check owns it. It points at a new rule, guardrail, or lens, and a repeat on a second pull request is a candidate check.
- `needs-execution`: it was found by running code, not by reading it. It joins [verifier evals](#verifier-evals) and the tool manifest's list, not the lens golden corpus.
- `out-of-scope`: Melian does not review this kind of change. It owes nothing, and does not count against Melian's recall.

A Melian finding judged noise owes a clean golden for the lens that raised it. A golden is owed only where the adjudication says so, naming its lens; a difference alone owes nothing. A golden drawn from a record names its finding in a `README.md` beside `expected.json`, since the expected file's schema is Martian's and has no field for it.

[goldens/BACKLOG.md](../../packages/evals/goldens/BACKLOG.md) lists, by lens, the owed goldens not yet written. Its present entries are kept by hand until goldens drain them. `melian compare backlog --markdown` prints the later generated section; replace the generated section after the frozen entries.

A historical hand-written record has no field for the reason. Its Adjudication column carries the words above. New records use the stored reason.

For each adjudicated `needs-execution` miss, add `{ record, finding, tool }` to Melian's root `tools.yaml`. The record is its repository-relative path; the finding is its ID. Name the run that would catch it: `enola`, `opengrep`, `gitleaks`, `tests`, `repro-run`, or `none`. The manifest parser refuses a record outside `packages/evals/comparisons/`, a finding ID that is not letters then digits, a duplicate record and finding, and an unknown tool name; it does not read the record. Execution discoveries without that adjudication do not qualify. The original list holds thirteen misses from the [pull request #89](https://github.com/melian-agent/melian/pull/89) record: twelve map to `tests` and one to `repro-run`. Five local misses from the [pull request #250 record](../../packages/evals/comparisons/2026-10-27-pr-250.md), `LA3`, `LB1`, `LD2`, `LD3` and `LE2`, follow them and map to `repro-run`. ### The drain rule

Problem: records mark goldens faster than anyone writes them, and nothing forces the list down. BACKLOG.md still holds owed goldens from the record for [pull request #10](https://github.com/melian-agent/melian/pull/10).

Solution: every third comparison record is followed by a backlog pull request. It ships at least two owed goldens, or every owed golden when fewer remain. It re-measures each new golden's lens with a live run of three passes, as [Two modes](#two-modes) requires, and records the run under `packages/evals/runs/`. Records count from [pull request #65](https://github.com/melian-agent/melian/pull/65) on, and an empty backlog owes no drain. `melian compare stats` sees only this clone's stored changesets and self-declared discharge through `--golden none`. It counts changesets once, preserving all rounds for metrics. Its clone-wide notice remains due after the first threshold while debt remains, even with filtered metrics. It cannot see which drain pull requests shipped or which live runs passed, so it cannot verify the periodic drain. Hand-written historical records are not imported.

Comparison adjudications name an owed lens through `--golden <lens>`, or owe none through `--golden none`. A later judgement changes debt only when it includes `--golden`; omitting the option carries the debt forward. Every replacement keeps the prior judgement in history. A noise judgement on Melian is a comparison label; use dismissal separately to change the review.


## Measurement cost

Lens and verifier runners return detached StageTelemetry with each run, read before the in-memory store closes. Score lines print its total tokens and USD cost. A failed run carries the same record in GoldenRunError, so no-score output retains available spend. Triage's runner supplies each pass's telemetry to its caller; TriageResults stores each pass's full detached telemetry and prints per-golden totals with the score. If a triage pass fails, print every attempted pass’s available spend, including completed goldens and the failed pass once. Write those records to MELIAN_EVAL_TRIAGE_OUT before propagating the failure; print no score for the incomplete golden. Version-3 measurements also store the light tier’s effective thinking level and render it beside the model. Comparison refuses different levels, keeping older absent levels distinct from off. Version-2 measurement JSON introduced the completion field and records `complete: false` on failure and `complete: true` on success. Comparison refuses an incomplete baseline before computing score differences. Older files without a completion field retain their complete-baseline behaviour. Older measurement files have no telemetry field and leave usage unavailable. Partial usage must not read as a complete total.

Use the pipeline's records, never catalogue prices, prompt sizes or reconstructed token counts. Models remain keyed by their actual provider/model, including planted fake finders and fake lenses. Escape golden names, model text and errors in terminal output. Measurement remains opt-in through MELIAN_EVAL_LIVE=1; the gate uses fake models alone.

Each golden's spend line also prints the recorded per-model reasoning settings, including requested and provider-reported levels and the capture source. Reuse StageTelemetry.spend; never resolve a new setting or alter the measured request.
