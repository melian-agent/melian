# CLI guidelines

The cli package is the `melian` command. It is the primary host and the only thing the skills call, so every Melian capability must be reachable from it. It chooses what the domain leaves to a host: which revision policy comes from, where storage lives, which models run, and how the outcome reaches a shell. Review logic stays in core and the pipeline.

## Commands

| Command | Does | Exits |
|---|---|---|
| `melian review <range\|#pr> [--rerun]` | Reviews a range of the checkout, or fetches a pull request and reviews it, then prints the verdict's terminal rendering. `--rerun` runs again the checks and lenses that failed in the last review of the same base and head, and asks triage again when its decision did not complete, never when it did | `0` passed, `1` findings with one blocking, `2` not reviewed, `3` findings with none blocking |
| `melian publish <#pr>` | Posts the stored review of the pull request's current head to GitHub | `0` published, `1` refused or failed |
| `melian findings <range\|#pr> [--open\|--all] [--json]` | Prints the warnings of the plan the review stored with its verdict to standard error, as `review` did, read through `ReviewPlan.from` rather than resolved again, then the stored verdict, or with `--open` the findings that still need attention, as text or JSON. The text counts silent and dismissed findings; `--all` prints them, each dismissed one with who dismissed it, when, and why. `--json` prints the whole verdict, or with `--open` a SARIF log of the findings that need attention | `0`, or `1` when nothing is stored |
| `melian dismiss <range\|#pr> <id> --reason <text> [--only]` | Dismisses a finding of the stored review, recording the reason, the git author, and the time, and decides the verdict again, so `findings` and `publish` count the finding out. Dismissing a dismissed finding replaces its reason and keeps the old one in its history. A finding adjudication merged from several reports is dismissed whole, and the output names each report dismissed with it by rule, check, and ID; `--only` dismisses the report the ID names alone and leaves the others live. Reads only local refs and storage, as `findings` does | `0` recorded, `1` when nothing is stored or the verdict has no finding with the ID, or when the dismissal was recorded but the verdict could not be decided again, which the message says, `64` for a missing, blank, or overlong reason or an ID that is not 16 hex digits |
| `melian doctor` | Checks Node, git and `--attr-source`, and Pi's login; which providers have credentials, the GitHub token's source, gh, and the repository; which `melian` ran and whether it lies inside the checkout, warning when it does; the state directory and whether it is writable. It also checks the named credentials of the secrets files, failing when git tracks `melian.local.yaml` or `melian.secrets.yaml` or a secrets file cannot be read, and warning for one others can read. It checks whether each lens's levels cost more from `quick` to `deep`, warning for a level on a lighter tier or with a smaller token or tool budget than the level below it. It checks whether Biome and tsc come from the checkout or Melian's own copy. It also prints the review plan it would resolve now, as `plan` lines. Each routed tier shows its models, the credential each comes from, and the file that routed it, or that it was derived. Each lens's levels show the tier and model of each. Every warning appears too, such as a tier a stage's lenses run on that has no route, naming the lenses and the ways to fix it, a tier with no model with credentials, a tier policy fails, or a route off the committed one. It fails with its own `decisions` line when `melian.yaml` sets `decisions.provider` | `0`, or `1` when Node or git cannot run a review, `melian.yaml` sets `decisions.provider`, git tracks a file only a maintainer may hold, a secrets file cannot be read, or a named credential's provider is one the catalogue does not know |

A command line Melian cannot read exits `64`. A `ReviewOutcome` holds the verdict `review` prints and the exit code it ends with, from `reviewExitCodes`; `findings` and `dismiss` name the stored review they read with a `StoredReview`, which says how to make one when there is none. `doctor` asks each lens for its `inversions()`. `review` and `findings` end each finding's first line with its ID, which `dismiss` takes. Under that line they list each report merged into the finding, with its severity, rule, check, and ID, so a maintainer sees what a dismissal would take with it before running one. A review that fails before it has a verdict, such as on a `melian.yaml` that does not parse, exits `2`: nothing was reviewed. `--model provider/id` routes every lens tier to that model alone, over any route or fallbacks that `melian.yaml` or a preference file sets. Problem: it used to fill only unrouted tiers, so in a repository whose `melian.yaml` routed every tier to one provider, a contributor holding another provider's credentials had no way to run a review. Solution: the flag wins, and it is the one-off counterpart of `melian.local.yaml`. The flag goes through the review plan like any route: a check it moves off a committed route records that lineage, and a tier whose policy says `acceptOverridden: false` refuses it.

`review` resolves the review plan before it runs anything: `reviewModels` in `src/models.ts` builds the models, with the secrets files' named credentials, and resolves the plan from `loadConfig`'s routes, pi-ai's catalogue, and the credentials present. It prints the plan's warnings to standard error, each line starting `melian: Plan:`. It runs the command of each named credential the review's lenses may need, so a failing command stops the review before it starts, with a message naming the credential and its file. It then passes the plan to `reviewChangeset`. The deterministic checks take the configuration as loaded, so a different route never changes their run's identity.

`review` triages each lens through the LLM fallback, `FallbackDecider` from `@melian-agent/decisions`. It runs on a model from the review plan's lens tier routes, as `--model` leaves them. That is the first model with credentials, trying `light`, then `medium`, then `heavy`. `review` unlocks the providers of those tiers with the lenses' before it starts, so a command credential the fallback needs runs then. `doctor` resolves the plan but asks for no decider, so it runs no command. A tier whose route cannot be read, such as a model without a provider, is passed over. A broken route no lens uses never stops a review. With no such tier there is no decider, and every lens's record says why; in scripted mode there is none either, silently. Either way every lens runs at its default level, `careful`, within its band. A `melian.yaml` that sets `decisions.provider` is refused before anything runs, exit `2`, with the reason and the fix. No decision-model adapter exists until milestone 4. A provider Melian cannot open would leave `decisions.fast` unasked and every review not reviewed, as [issue #24](https://github.com/melian-agent/melian/issues/24) found.

A pull request is `#` and its number. Quote it, `melian review "#12"`: an unquoted `#` starts a comment in bash and in zsh scripts, which leaves `review` with no argument. A bare number is not accepted, because `1234` is also an abbreviated commit hash. Every message that suggests a command quotes it the same way, `melian review "#12"`, and quotes an argument it echoes unless it holds only characters no shell treats specially, so the suggestion can be pasted as it stands.

## Where policy comes from

- A pull request reads `melian.yaml`, standards, and lenses from the base commit GitHub reports, so the head cannot rewrite its own review.
- A range whose head is the checked-out commit reads them from the working tree: its author is the one running Melian, and an uncommitted `melian.yaml` edit should apply.
- Any other range reads them from its base.

The lenses always read the head commit, never the working tree.

The preference files, `melian.local.yaml` beside the root `melian.yaml` and ignored by git, and `config.yaml` in the user's configuration directory, are where a maintainer keeps personal model routes and provider choices; [the core guideline](core.md#layering-precedence) says how they layer. The user's configuration directory is `$XDG_CONFIG_HOME/melian/`, or `~/.config/melian/` when the variable is unset; Core's `userFiles` names both files there, for the CLI and for live evals. Core reads the preference files only from the working tree, so they apply to a range on the checked-out commit and never to a pull request, which reads its base and its base's routes. The secrets files, `melian.secrets.yaml` beside the root `melian.yaml` and `secrets.yaml` in the user's configuration directory, are credentials, not policy, so every review reads them, a pull request's included. A credential's `command` source runs only from the user-level file: `melian.secrets.yaml` sits in the working tree, where a pull request's head could have written it, so it holds `key` and `env` sources only, and the loader refuses a command there with a message naming the user-level file. Review a pull request in a repository that routes no tier with `--model`.

## Pull requests

`review '#12'` reads the pull request through the provider, fetches `refs/pull/12/head` and the base branch from `origin` into `refs/melian/pull/12/head` and `refs/melian/pull/12/base`, points both at the commits the provider reported, and reviews `refs/melian/pull/12/base...refs/melian/pull/12/head`. The changeset's ID is core's `pullRequestChangesetId`, a hash of the kind `pull-request`, the provider, the `origin` repository, and the number, so every push to the pull request is a new revision of one changeset with one storage file, and the findings document can tell new from still open from resolved. A range hashes the kind `range` with its ref names, so `melian review refs/melian/pull/12/base...refs/melian/pull/12/head`, or the same refs spelled `melian/pull/12/...`, is a range with storage of its own. Problem: both used to hash the ref names alone, so a range review of those refs, with the head checked out and policy read from the working tree, wrote its verdict into the pull request's storage under the same base and head, and `publish` posted it. Solution: separate identities, and a verdict that records where it came from.

Every verdict records its provenance beside it: its kind, `range` or `pull-request`; for a pull request, the repository, number, and the base and head commits the provider reported when `review` fetched it; the policy source, `worktree` or `revision:<sha>`; the tier's checks; and the lenses that ran. `publish` refuses with exit `1`, naming the mismatch, unless the verdict is a `pull-request` review of the same repository and number, its head is the pull request's head now, and its policy came from `revision:` of the base commit the provider reported.

A review is keyed by its base and head, the merge base and the head commit, so `findings` and `publish` read the verdict stored under both. `publish '#12'` reads the pull request again, fetches its base branch, and computes the merge base it diffs from now. It refuses when the head or that base differs from the stored review's, naming which, with a message to run `review` again: a pull request retargeted to `main` after its parent merged keeps its head, but GitHub now shows another diff. It opens storage with only the publish task installed, so a review a crash interrupted does not resume and spend tokens during a publish. A publication a crash interrupted for another target, such as before a retarget, is dropped without posting, and `publish` says so; if the pull request moves while `publish` runs, it stops before the next post and exits `1`. It never posts a review of a range or a working tree: storage for a range is a different changeset, `publishReview` refuses a base and head with no stored verdict, and it refuses a verdict whose provenance is not a pull-request review under the base's policy. `findings '#12'` reads the local refs and storage only, with no network.

`origin` must name the GitHub repository. The token comes from `GITHUB_TOKEN`, then `GH_TOKEN`, then `gh auth token`; Melian prints where it came from, never the token.

## Checks, then lenses

`review` drives the deterministic checks and the lenses, in that order. The tier `melian.yaml` maps the `pull-request` stage to is the review's manifest, and every check in it needs a record, as [the pipeline guideline](pipeline.md#the-manifest) describes. `reviewChangeset` runs only the lenses, so the CLI first calls `runChecks` for that tier, which runs guardrails, Biome, and tsc on the base and head, and passes its records to `reviewChangeset` as `options.checks`. Without them every review of a default tier reads not reviewed, each deterministic check under "no record".

- The harness opens with `checksExtension` and a Node execution environment in the checkout, through `openReviewHarness`'s `checkout` option. The static tools run the checkout's own Biome and tsc when its `node_modules` has them and git does not track it, and Melian's copies otherwise; `doctor` reports which.
- `runChecks` takes the configuration as loaded, before `--model` replaces its routes, so a different `--model` does not change the run's identity and run the tools again.
- A repeat `review` of the same base and head attaches to the last review's finished check and lens tasks and prints what they stored, so it spends no tokens and runs no tools unasked. `--rerun` runs the failed checks and the failed lenses again, after a timeout, a rate limit, or an outage, and asks triage again when its decision failed or a crash left it undecided. It never asks again after a decision that completed, since that would change the levels and rerun every lens.

## Dismissals

`dismiss` records who dismissed a finding as the git author, `git var GIT_AUTHOR_IDENT` without its timestamp: `GIT_AUTHOR_NAME` and `GIT_AUTHOR_EMAIL`, then `user.name` and `user.email`. Not the GitHub login the token resolves to: a range has no GitHub at all, `dismiss` works offline as `findings` does, and the record sits in local storage that trusts whoever can write it, so a login the token proves would add a network call and no trust. A reply on the pull request never names the dismisser; GitHub shows whose token posted it. [The decision](../decisions/2026-10-04-dismissal.md) says more.

A dismissal lives in the changeset's SQLite file under the git common directory, so every worktree of the clone sees it, and nothing outside the clone does. A second maintainer never sees it until the state branch lands in milestone 3, and losing the clone loses it. It reaches a pull request only when `melian publish` posts the verdict it changed: the thread of a finding posted earlier gets a reply with the reason, and the status counts the finding out.

A range's changeset ID hashes the names its refs resolve to, so `melian review main` on a branch and `melian dismiss main` in a worktree with a detached HEAD name different changesets: `HEAD` resolves to the branch in one and to nothing in the other. Name the branch, `main...feature`, to reach the same storage from every worktree. A pull request's ID does not depend on the checkout.

## Storage

Each changeset has one SQLite file, `melian/<changeset-id>.sqlite` in the clone's common git directory, which is `.git/` in an ordinary clone and is shared by every worktree. Pi Durable allows one process per storage, so two `melian` commands on one changeset at once is unsupported.

`MELIAN_STATE_DIR` moves storage to `<MELIAN_STATE_DIR>/<clone>/`, where `<clone>` is the first 16 hex digits of a SHA-256 of the common git directory's real path. Problem: Codex's default sandbox keeps `.git` read-only, so `melian review` exited 2 with SQLite's "unable to open database file", and the skill forbade the rerun that asking for access needs. Solution: the directory is configurable, and the clone's own subdirectory keeps two repositories apart, since a range's changeset ID hashes only its ref names. A failure to create the directory or open the file is a `CliError` that names the path and both remedies. `melian doctor` reports the directory and whether a file can be written there; a sandbox can pass a permission check and still refuse the write. Rerunning after the fix is safe: the review's durable tasks resume.

## Scripted mode

`MELIAN_TEST_SCRIPT=<script.json>` runs every lens tier on the fake model, answering each lens from a script in a golden's `script.json` shape, through `scriptLenses` from `@melian-agent/pipeline/testing`. It triages nothing, so every lens runs at `careful`, the level the scripts were written for. It routes them as `--model` would, through the plan, so a test can show a check's lineage and a tier policy refuses without a provider. `test/cli.test.ts` points `XDG_CONFIG_HOME` at an empty directory, so no test reads the developer's own files, and puts a literal key in a secrets file of its own where a plan must not depend on the machine's credentials. It exists so the gate can run the `melian` command end to end, through the shim and a real process, without a provider. Storage moves under `melian/scripted/`, and `publish` refuses to run, so nothing a script produced can reach a pull request.

## The binary

`bin/melian.js` is committed and executable. npm links a package's bin only when the target exists at install time, and `npm ci` runs before any build; a bin pointing into `dist/` was never linked, and `npx melian` then asked the registry for a package named `melian` instead. In a checkout the shim runs `src/bin.ts`: Node strips the types, and a resolve hook adds the `@melian-agent/source` condition, so every workspace package resolves to its source as it does under Vitest and tsc. The published tarball ships no `src/`, so there the shim imports `dist/bin.js`. No test reaches that branch; CI's publish step packs every package with `npm run pack`, installs the tarballs into an empty project, and runs the installed `melian --help`, which must write nothing to stderr, so the built output still drops the SQLite warning. Nothing in development reads `dist/`: run `npx melian` from the repository straight after `npm ci`, with no build. [The decision](../decisions/2026-10-05-dist-only-at-publish.md) says why.

Node 22 prints `ExperimentalWarning: SQLite is an experimental feature` on every run that opens storage, and a test that expects an empty stderr fails on Node 22 alone. `src/warnings.ts`, imported first by `src/bin.ts`, drops that one warning and passes every other to Node's own printer. Keep it the first import: ES modules evaluate in import order, and the warning fires as `node:sqlite` loads. The shim registers its hook with `module.registerHooks`, which runs on the main thread. `module.register` runs hooks on a worker, so loading the module graph yields to the event loop, and the warning prints before `src/warnings.ts` has run.

## Skills

The skills under `skills/` are how a coding agent calls Melian: `skills/claude-code/`, `skills/codex/`, and `skills/pi/`, each an Agent Skills directory whose `SKILL.md` runs `melian` and relays what it prints. They never review with the host's own model, reimplement a check, or read storage. `melian doctor` is the only command a skill runs without a trigger, `melian publish` runs only when the user says to, and `melian dismiss` only when the user tells the agent to dismiss that finding, with the user's reason. The three files differ only where their hosts do: Claude Code's pre-approves `melian doctor`, and nothing else, and runs a review in the background, since one can outlast the Bash tool's ten-minute limit; Codex's and Pi's set no bound. All three say that a review killed before it exits resumes from its checkpoints when run again, so running it again is correct.

A skill runs only the `melian` on the user's `PATH`. It never builds, installs, or runs Melian from the checkout, not even Melian's own, and never through npx. Problem: the checkout is what Melian reviews. Example: an earlier skill, finding no `melian`, ran `npm run build` and `npx --no melian` in any checkout holding `packages/cli/bin/melian.js`, pre-approved, so a repository could ship that file and have the agent run it. Solution: without `melian` on `PATH` the skill tells the user how to install it from a source they trust and stops. `melian doctor` prints the path that ran and its real path, and warns when either lies inside the checkout, since a change could then alter its own reviewer; the skill reviews only after the user confirms they put it there.

`test/skills.test.ts` enforces the boundary. It parses every line of every fenced block and every inline code span that reads as a command, splits each at `&&`, `|`, and `;`, and fails on any executable but `melian`, and on any command substitution. A span that starts with an option, or holds one path, number, quoted argument, or word from `melian doctor`'s output, is data; any other span of several words is a command. It checks `allowed-tools` apart from the body, against the exact allowlist `Bash(melian doctor)`, and fails on any entry naming `publish`, `review`, `findings`, or `dismiss`. It also checks that every `melian` command and option is one `usage` lists, that the exit-code table matches `review`'s, that the rules making publication and dismissal wait for the user are present, and that the Codex and Pi skills are identical. A list of edits, from pre-approving `Bash(melian publish:*)` or `Bash(*)` to building the checkout's `melian` or renaming `--model`, runs against the Claude Code skill, and each must fail. Write prose that is not a command, such as a message Melian prints, in quotes rather than a code span.

To install a skill, first put `melian` on `PATH`: in a clone of Melian, `npm ci --ignore-scripts`, then `npm link` in `packages/cli`. The linked command runs the clone's source as it stands, with no build, so whatever branch that clone has checked out is the reviewer; link a clone kept on `main`, not the one you change.

- Claude Code: symlink `skills/claude-code` to `~/.claude/skills/melian`, or copy `skills/claude-code/SKILL.md` to `.claude/skills/melian/SKILL.md` in a project. This repository does the latter, so a Claude Code session here can ask Melian to review its own work. It copies rather than links because git writes a symlink as a text file where symlinks are off, and the skill would not load; `test/skills.test.ts` fails when the copy drifts from the source, and copying the source over fixes it. That works because the maintainer has linked the CLI onto `PATH` once. The root `melian.yaml` routes heavy to Claude Opus 5.5, with GPT-5.5 behind it, and medium to Claude Sonnet 5.5; a maintainer without those credentials gets a route derived from the ones they hold, which `melian doctor` prints, or routes the tiers in a preference file, or passes `--model`.
- Codex: symlink `skills/codex` to `~/.agents/skills/melian`, or to `.agents/skills/melian` in a repository.
- Pi: `pi install ./skills/pi` from the clone. `skills/pi/package.json` declares the skill under `pi.skills`.

## Tests

`test/cli.test.ts` runs `bin/melian.js` with plain Node, as a user of a clone would, with no build, against golden repositories from `@melian-agent/evals` in scripted mode. It checks exit codes, and that `review` prints exactly `verdict.render()` of the verdict `findings --json` reads back. The goldens have no `tsconfig.json`, so their tests keep the deterministic checks to guardrails with an uncommitted `melian.yaml`; a TypeScript repository the test builds runs the default tiers, Biome and tsc included, clean and with a Biome finding. Publication is tested in `packages/github` against a fake GitHub; nothing here calls the network.

The plan derives a model family from the catalogue name: remove the vendor prefix and parenthesised qualifier, then take the first word. A verifier route tries another family first. With no verifier route, it falls back to lens routes, heavy then medium then light, and records that lineage. Refused verifier tiers never fall back. Doctor prints the route with families. Warnings name fallback routing and a review judged entirely within the finders' families.

Verification runs after lenses and before adjudication. Its unfinished or refused check exits 2 through the stored not-reviewed verdict. Finding headers show confirmed, plausible, refuted or unverified. Verified names the model and reason; Correction follows when present. The verifier check shows counts by verdict. Refuted findings print with `--all` and remain in `--json`, including each otherClaims entry's judgement. Scripted mode accepts a reserved verifier key mapping finding IDs to verdicts, confirmed by default. Doctor prints model families and warns about fallback and same-family verification.
