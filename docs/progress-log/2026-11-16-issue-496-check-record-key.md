# A check record is keyed by its run's whole request

For [issue #496](https://github.com/melian-agent/melian/issues/496), a check's shared record now takes its key from the check run's full request key, the base, the head and the check's name. Before, the key hashed the run's identity: base, head, tier, the first 16 hex digits of the request key, and the task number the host's storage minted. Two hosts that ran the same request numbered their tasks differently, so their records never shared a key, and the key held 16 of the request's 64 digits.

`runChecks` already computed the full key to build the identity's prefix. `CheckRun` now carries it as `request`, the CLI passes it to `reviewChangeset` as `checkRequest`, and the export keys each record on it. The key travels in memory: the export is its only reader, and it runs in the process that ran the checks, or that found their stored run and computed the key again from the same facts. The checks document and the rounds document keep the identity they had, since they decide reuse on one host, so neither changes version. A test on SQLite runs the checks, closes the store, reopens it in a new harness, and finds the stored run with the same full key and the same record keys an uninterrupted run gives.

A review given checks with no request keys their records on `request: null`, which no request's key equals. Only a caller of `reviewChangeset` that passes records without `checkRequest` reaches it; the CLI always passes the run's request. The identity guideline's row now says what the key holds and what it leaves out.

The [mutant inventory](2026-11-16-issue-496-mutants.json) lists the 14 mutants of commit 35e440e1. Each of the 12 generated mutants was run by hand against its named test alone, after that test passed unmutated, and all 12 were killed; the other 2 are ignored string literals. The `LogicalOperator` mutant at `review.ts:3649` was applied with parentheses, since `a && b ?? null` does not parse. The CLI's `checkRequest: checks.request` yields no mutant, so the CLI's records export test now asserts that no check record carries the key of no request; it fails with that line removed and passes with it.
