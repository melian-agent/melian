[Pull request #314](https://github.com/melian-agent/melian/pull/314), the first of the two high findings in Codex's adversarial review of b231987.

- Every command that opened a pull request's storage pushed its copy when it closed, even when it wrote nothing: a `melian dismiss` with no review to dismiss, or a command that failed before writing. A copy with no files put an empty tree on `melian/state`, so the branch said it held the pull request, and a clone that kept its SQLite storage from before the branch could no longer reserve it to publish. A push now stores a tree only when the copy changed since the branch's. An unchanged or never-written copy moves only the lease, released or kept, and records no write. A copy emptied since the branch stored it is refused rather than pushed. `stores no tree for a copy nothing wrote, and releases the lease`, `records no write for a copy unchanged since the branch's, and keeps the stored tree` and `keeps the lease for a copy nothing wrote yet, without storing a tree` failed first on 6ef02551, then passed. Seven older tests pushed an empty copy and expected the branch to hold it; each now writes a note first, and its outcome is unchanged.
- A failed command that wrote part of a review still stores what it wrote, by design: the next run resumes from it, on any clone.
- The merge 6ef02551 carried the lease's incarnation over from [pull request #310](https://github.com/melian-agent/melian/pull/310): reservations, keep-lease pushes and the restore-failure expiry fence on the lease the run took, by incarnation and generation.
- Two test files failed on this branch from 26338cc on, unseen until this pass: `pull-request-export-guards.test.ts` faked every git call with the remote's URL, which the restore before a scan then used as a directory, and `pull-request-export-scope.test.ts` faked `readdir` for the store directory alone, though the scan now reads `state/` beside it. The export-guard tests now open the comparison as `melian compare export` does, offline, and both fakes answer only the request they expect.
- The second high finding: a legacy reservation took no copy lock. Two publications of one pull request's SQLite storage in the same clone share a holder, so the second read the first's live lease as one a crashed run left, took it over, and both published. A reservation now takes the copy lock a checkout takes, in the clone's copies directory, holds it until it is released, and releases it when the reservation is refused or the SQLite storage cannot be opened. `refuses a second reservation in the same clone while the first holds the changeset`, `refuses a checkout in the same clone while a reservation holds the changeset` and the CLI's `refuses a second publication of legacy SQLite storage in the same clone while the first holds it` failed first, then passed. Removing the lock's release on refusal, or on release, fails `refuses a second reservation in the same clone while the first holds the changeset` or `releases the lock when the reservation is refused`; removing the release when SQLite cannot be opened fails `releases the reservation when legacy SQLite storage cannot be opened`. Moving the lock from `.git` to the copies directory is equivalent for these tests, since a pull request with legacy storage is never checked out in the same clone; it keeps every copy lock in one place.
