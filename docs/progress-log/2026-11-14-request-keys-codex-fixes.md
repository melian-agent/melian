Codex's adversarial review of [pull request #436](https://github.com/melian-agent/melian/pull/436) found three gaps in the request keys of [issue #394](https://github.com/melian-agent/melian/issues/394). Two are fixed and one is documented, as the coordinator advised on the issue. The advice is not a ruling.

- Host paths reached two keys (fix `56e65d8c`). The verification request held the root conversation's ID and the checkout's path, and the check request held the preference file's path and Stryker's install path. So the same review from another checkout, or another storage, missed its own earlier work, which breaks the identity guideline's rule 6. Each producer now leaves those fields out beside its hash, with a comment, and its coverage test names them as exclusions. New tests key a review from another checkout the same.
- A check run was not keyed by Melian's own check code (fix `f2448ae8`). A build that changed what a check finds attached to a run an earlier build made. The check request now carries `checkVersions`, one hand-raised number per deterministic check, and a test fails when a check has none. Nothing checks that a contributor raised the number when they changed a check. [Issue #437](https://github.com/melian-agent/melian/issues/437) asks for that guard, and [the request keys decision](../decisions/2026-11-14-request-keys-as-built.md) records the limit.
- Host facts describe the Melian process, not wherever a tool runs. Every tool runs on this host today, so the facts are right. The decision now says an environment that runs tools elsewhere must supply its own host facts, and a comment says so where `checks.ts` reads them.

Each fix started with a failing test. Before `56e65d8c`, four tests failed for the reported reason: the two coverage tests found the host fields keyed, and the two checkout tests saw another key (`expected '1f86…' to be '26c0…'` and `expected '8575…' to be '15a8…'`). Before `f2448ae8`, the new version test failed because the request held no `checks`. After each fix, the same tests passed.

[The fix pass's inventory](2026-11-14-issue-394-fix-pass-1-mutants.json) comes from `melian mutants list` over `5f50053b...f2448ae8`, with `--claims-in` for `check-request.ts`. `checks.ts` gains a comment and `verification.ts` only destructured exclusions, so neither holds a mutant. Each of the 14 generated rows was run at `f2448ae8` against its named test alone, after that test passed unmutated: 11 are killed by an existing test, 2 by a test this pass added, and 1 is equivalent. A worktree source alone reaches `{ kind: source.kind }`, so `{}` names it as uniquely. The one ignored row is a configuration note. `node scripts/enumerate-mutants.mjs --sample` accepts the inventory.
