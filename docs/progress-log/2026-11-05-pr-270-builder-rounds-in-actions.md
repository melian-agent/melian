A builder can now start its own Melian round on GitHub Actions, for [issue #270](https://github.com/melian-agent/melian/issues/270). Rounds ran only on the coordinator's machine, where the provider credentials are, so every fix pass waited there. `.github/workflows/melian-round.yml` runs on `workflow_dispatch` with a pull request number. A gate job refuses a starter without write, maintain or admin permission and a head outside this repository, so a fork's head never runs with secrets. The round job checks out the head with full history, runs `npm ci --ignore-scripts`, raises the lens budgets with `scripts/round-budgets.mjs` as [AGENTS.md](../../AGENTS.md#three-reviews-before-ready) sets them, and runs `melian review origin/<base>...HEAD` with the head's own build; the provider secrets reach only that step. The whole output is the job summary and the `melian-round` artefact. A report job with no secrets comments, through `scripts/round-comment.mjs`, the run's link, the `Verdict:` line, the checks that did not run, and every block and acknowledge finding, all inside one code fence no backtick run in the head's text can close. It never publishes or dismisses, and its store is thrown away. The routes are the committed ones on API-key secrets, which every tier's `accept` already covers with a Claude model; the credentials and cost questions are open on the issue. GitHub dispatches a workflow only from the default branch's copy, so the first recorded run follows the merge and gets its own entry.
