A probe's copy of its `probe.read` entries is now bounded, for [issue #398](https://github.com/melian-agent/melian/issues/398). Before, an entry that grew to a build's output or a dataset was copied whole into every probe's scratch. `copyReads` in `packages/pipeline/src/probe.ts` counts each entry through `cp`'s filter before it is written, and refuses the probe with `invalidProbe` once the copies together pass 50,000 entries, 512 MiB or 60 seconds, the bounds `probeLimits.read` holds; `Probe.open` then removes the partial copy with its scratch, unless a read-only directory in it blocks the removal, which [issue #447](https://github.com/melian-agent/melian/issues/447) takes up. [The decision](../decisions/2026-11-14-probe-read-copy-is-bounded.md) says why those numbers and what the bound misses: a file that grows while it is copied. The tests in `packages/pipeline/test/probe.test.ts` copy at each bound and refuse one past it, count the bounds across entries, and refuse a probe whose deadline passes part-way through its copy, leaving no scratch behind. That last test failed on `ef750c6b`, the head before the change, because the probe opened.

The mutation inventory, `2026-11-14-issue-398-mutants.json`, lists the 33 mutants of `origin/main...b906d82c`, all in `probe.ts`: 28 killed, each by its named test run alone at that head after the test passed unmutated, and 5 string literals Stryker ignores under the repository's configuration.

Codex's adversarial review of `8fb39ce0` found that the deadline was read only between entries, so a slow last file let the copy succeed past 60 seconds. `2cdfeb9c` reads it after each entry's copy too, on a monotonic clock. Its test, a clock that passes the deadline only once the last file is written, failed on `8fb39ce0` with `promise resolved "undefined" instead of rejecting` and passes after. A copy that stalls inside one file is still not interrupted; the decision says so.
