[Pull request #492](https://github.com/melian-agent/melian/pull/492) gives the `tests` lens the mutants on a change's lines, for [issue #241](https://github.com/melian-agent/melian/issues/241). The lens had to think of each untested change itself, though `melian mutants list` already enumerates what a mutation tool would try. The new read-only lens tool `list_mutants` asks that enumerator for one file's changed lines in one line range, and runs no test and no head code. It reads Stryker's exclusions from the review's base, so a head cannot switch its own mutants off. It lists the mutants a disable comment in the head ignores, marked. It shows at most 200 a call, cut at a line boundary, with what is left and where to ask from next. It enumerates each file once per lens run, in memory, keyed by the review's resolved commits. Step 4 of the lens's instructions tells it to read rather than run, to group mutants by the test that would catch them, and to call the tool only on changed source it has read. The tool's description carries its cap, so the lens request key changes with it. [The evals guideline](../guidelines/evals.md#a-lens-tools-before-and-after) gives the commands for the live before-and-after measurement, which is still owed.

Codex's adversarial review at bc954a22 raised two high findings. The first: a call that joined the queue got its 120 seconds only once its turn came, so a long queue could stall `list_mutants` for every review in the process. Two tests failed at bc954a22: a queued call's deadline was not set when it joined, and `list` ignored a caller's deadline of 1000 ms at 1000 ms on a faked clock. They pass at 8793e91f, which starts the deadline when the call joins the queue and lets `list` take a caller's deadline, keeping its own 120 seconds as the ceiling; the same test at 999 ms starts work. 8793e91f also makes the failed-listing test fail its first enumeration whichever file joins the queue first, since the two calls raced to join. [That commit's inventory](2026-11-16-pr-492-deadline-mutants.json), `melian mutants list bc954a22...8793e91f --claims-in packages/pipeline/src/lens-tools.ts --claims-in packages/pipeline/src/mutation-enumeration.ts --json --all`, holds 9 rows, each killed by a named test run alone at 8793e91f after passing unmutated: 9 runs, 9 kills.

The second: the review resolves the instrumenter to build the key, and the tool resolves it again when it runs, so an instrumenter that changes during one review, across a crash and replay, can leave that run stored under the key that names the old one. It is the second instance, after the missing key, of the class "the key and what runs can disagree", so the builder stopped fixing instances and asked the coordinator. Pinning the tool to the keyed instrumenter needs the identity stored with the lens task's run, since the task stores only the request's hash, and a new field on that shape takes a version that issue #493 and issue #489 already claim. The decision file names the case as a limit awaiting the maintainer's read; the code is unchanged for it. The full gate passed on the commit that adds this paragraph.
