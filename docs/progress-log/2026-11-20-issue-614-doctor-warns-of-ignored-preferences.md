# Doctor warns of preferences a pull request's review ignores

[Issue #614](https://github.com/melian-agent/melian/issues/614) came from [pull request #532](https://github.com/melian-agent/melian/pull/532). There a lens route in an uncommitted `melian.local.yaml` printed in `melian doctor`'s plan as applying, and two pull request rounds ran on the committed model before anyone knew. A pull request's review reads its policy and lenses from its base and no preference file.

The first form of this pull request gave doctor a target, `melian doctor "#12"`, and printed that review's plan. Codex's adversarial review found its no-target wording called the plan a range review's, which it is not: it covers every stage's checks and the root's lenses. The own-build round then blocked on a P1 design finding: two active decisions, [restore-doctor-clauses](../decisions/2026-11-08-restore-doctor-clauses.md) and [doctor-github-read-deadline](../decisions/2026-10-06-doctor-github-read-deadline.md), say doctor has no pull request argument and never fetches, so it stays a bounded readiness check. The coordinator withdrew the target, since the failure needs neither a pull request nor a fetch.

Doctor now warns, beside the plan, of each preference file it read and every key the file sets: `melian.local.yaml sets lenses.correctness.route.model, which a pull request's review ignores`. The list comes from the loader, `LoadedConfig.preferences`, which names the preference layers it merged, nearest first, and which a revision source leaves empty. It leaves out `output`, which every review, a pull request's included, reads from the preference files to render; the next round found the first wording warned of `output.emoji` too, and a test of that failed first at 81d376bf. `packages/cli/test/doctor-preferences.test.ts` failed first at `origin/main` c2e68c4e: doctor named no ignored preference. It covers `melian.local.yaml`, the user's file by its path, and a tree with neither. `packages/core/test/config.test.ts` pins the loader's list and that a revision reads none. The [cli guideline](../guidelines/cli.md), the [design](../design.md), the three skills and the AGENTS.md learning on routing a lens past Codex's content filter say so. No changed file guards trust or durability: doctor decides nothing, and no review reads the loader's new field.

The review of record found that `output: {}` gave the bare key `output`, which the filter's `output.` prefix missed, so doctor warned of a setting every review reads. The test "leaves out an empty output too" failed on 2e82e69d with `melian.local.yaml sets output, models.heavy.model`, and passes once the filter compares the first segment of each key.
