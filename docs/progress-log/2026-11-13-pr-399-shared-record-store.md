Step 46's build 1, for [issue #392](https://github.com/melian-agent/melian/issues/392), landed in [pull request #399](https://github.com/melian-agent/melian/pull/399). It gives core the shared record of [the shared record decision](../decisions/2026-11-13-shared-record-behind-a-store-port.md). `SharedRecord` validates an envelope by rules 2 to 4 and names it by the SHA-256 of its RFC 8785 bytes. `RecordSet` computes from the set alone what `supersedes` does and which rounds stand. `RecordStore` is the port, with `MemoryRecordStore` and `DirectoryRecordStore` as its adapters. The conformance suite in `@melian-agent/core/testing` has one case per promise of rule 3, and `test/record-store.test.ts` runs each case against an adapter built to break that promise. A round carries its revision and its whole manifest, by rule 4, and a dismissal's envelope carries no revision. Every other kind's payload is refused until the build that defines it registers a check, so nothing parses on trust. Codex's adversarial review found that a dying `add` could leave a record listed after disposal, and that any caller could write the disposal mark. Round 1 found a leading byte order mark dropped on read. The host round from the branch's own build found three more defects: writes followed a symlinked directory out of the store, `list` answered empty when the store vanished mid-walk, and a record's payload could be mutated under its ID. A later host round found that a dismissal with an empty payload, or a round naming no manifest, parsed and counted; the payload checks above close both. The review of record found four P3 defects. A payload check could change a payload after its ID was fixed. A cell write threw a raw error when the store vanished. A cell named 2^53 made `dispose` loop forever. And two equivalence claims were wrong. The last host round found that `RecordSet.of` trusted every record when its caller named no trust, and that a cell took any string where the decision says JSON. A trust predicate is now required, with `everyRecordCounts` for a store whose every writer is trusted, and a cell must hold JSON. [Issue #396](https://github.com/melian-agent/melian/issues/396) owns the cell's size bound. The same round found that a directory cell's version numbers restart if someone deletes the cell's files by hand. The maintainer read and accepted that on 2026-11-14, in the coordinator's session, and the guideline says so. The final host round found that no test signed a record carrying a revision and `supersedes`, and that `DirectoryRecordStore.open` let a raw filesystem error escape. A test now covers the first, and `open` fails `unreachable`. The last Actions round found that the conformance suite demanded that a batch holding an invalid record land nothing, while rule 3 lets a batch land in part. The case now asks only what rule 3 says, and a test holds that it passes a store that writes a batch record by record. A later host round found that `RecordSet.of` checked every payload before asking whether a record counts, so an untrusted writer's record with a bad payload could stop the set from building. The set now checks the envelope, then trust, then the payload of the records it keeps, and a store's `list` checks envelopes only. Its 19 changed-line mutants were proved by hand and reported on the pull request, outside the inventory, by the maintainer's ruling of 2026-11-14 in the coordinator's session. The pull request's report comments name the fix commit and the failing-test run for each. The mutation inventory is `2026-11-13-pr-399-mutants.json`: 341 mutants ignored by configuration, 889 killed and 10 equivalent. Its 18 remaining conformance-suite mutants stay unclaimed. The maintainer ruled on 2026-11-14, in the coordinator's session, that they are listed with a reason under the label "suite assertion, proved per case", and `2026-11-13-pr-399-suite-mutants.json` lists them. The inventory fails `--sample` until [issue #406](https://github.com/melian-agent/melian/issues/406) adds a claim for them.
