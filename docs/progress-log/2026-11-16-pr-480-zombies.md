On [pull request #480](https://github.com/melian-agent/melian/issues/480)'s branch, `518fc85d` made the deadline's result wait for the stop of git's tree, about a second at most. In a cloud container, state-git's deadline test then failed alone. Its git stand-in had exited while the stop ran, and the container's pid 1 never reaps an orphan, so the stand-in stayed a zombie. `terminateRecorded` read the zombie as live, signalled it, and waited its whole second, since a zombie ignores SIGKILL. [Issue #333](https://github.com/melian-agent/melian/issues/333) had reported the same for the mutation check.

- `ProcessTable` and the mutation supervisor's embedded read now ask `ps` for `stat=` after `lstart=`. `parseProcesses` reads lstart as its five fields, then an optional state, then an optional command. `terminateRecorded` neither signals nor waits for a recorded process whose state starts with `Z`. A row with no state counts as live, as before.
- The tests came first. In `packages/pipeline/test/mutation-process.test.ts`, "neither signals nor waits for a recorded process that ps shows as a zombie" failed with "expected [ [ 10, 'SIGTERM' ], …(3) ] to deeply equal []". The parser's Linux, macOS and command fixtures failed on the missing state, and the `ps` request test on the missing `stat=`. The supervisor's zombie test failed with a second SIGTERM, to the zombie, pid 22. After the fix they pass, and the deadline test passes five runs of five alone.
- The Linux fixture's rows were captured from procps-ng 4.0.4 in this container, a real orphan zombie among them. The macOS rows are written from macOS's format; a new test in `packages/core/test/process-tree.test.ts` reads the real table, so CI's macOS job checks the real format there.
- Two existing tests changed with their outcomes unchanged. The supervisor's stderr test fed rows with one-word starts, such as "10 1 controller", and reading the state after the start needs lstart's five fields, which real `ps` always prints. Core's flood test with a recording table had a stand-in git that exited after the flood, so it was a zombie when the stop read the table; it now keeps running, as a live git would.
- CI would likely not have caught the lost second: GitHub's runners and macOS reap orphans at once. The fake-`kill` zombie test catches it everywhere.
