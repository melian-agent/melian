Codex's adversarial review of [issue #480](https://github.com/melian-agent/melian/issues/480)'s branch at `4c354be5` found that core's `git` counted a stop as complete once its first read of the process table worked. `terminateRecorded` reads the table again before each signal, and a later read can fail. Then no program below git was signalled, yet a timed-out result carried no `childrenLeft`, and the `gitOutputTooLarge` message had no clause saying so.

- The tests "says the programs git started were not stopped when the process table fails after its first read" and "says the programs git started were not stopped on a flood, when the process table fails after its first read", in `packages/core/test/git.test.ts`, use a table whose first read works and whose later reads fail. On `4c354be5` both failed: the timed-out result had no `childrenLeft`, and the error ended at "so Melian stopped it".
- `stop()` now returns a promise of whether every read worked. The deadline's result and the overflow error wait for it, about a second at most. Once git is stopped, its `close` no longer settles the call, so the deadline's result cannot be replaced by a plain exit. With the fix, all 49 tests in core's three git and process-tree test files pass.
- The coordinator agreed on 2026-11-16 to this shape before the fix. Codex's other finding, that `ps`'s one-second start time lets a recycled pid match, is with the maintainer.

Mutants: Stryker's instrumenter lists 33 on the changed lines of `git.ts` at `518fc85d`. Each ran alone against its named test, which passed unmutated first, in a cloud container, with `ProcessTable.kill` sending no signal.

- 31 were killed. Two on the rewritten `close` line, `code ?? -1` made `code && -1` and `-1` made `+1`, needed a test of their own. `1f5e2cae` adds it: "stops git once its output reaches maxBytes, and gives the cut result an exit code of -1".
- Mutant 110 forces `options.deadlineMs === undefined` to false. That sets a timer of `undefined`, which Node fires at once. It survived the test it was first paired with, and "gives git an ended input when it is given none, so a command that reads it cannot wait forever" kills it. To find that test, I ran core's whole git test file against the mutant once without the runner's no-op kill. So the mutated `git.ts` sent real signals, through the unmutated `stopTree`, to the git stand-ins the tests had spawned. No process outlived the run. The proof is the runner's later run, with the no-op kill.
- 2 are equivalent. Forcing `stopped !== undefined` to false changes nothing, since `stop` runs once: it clears the deadline and destroys standard error, the sources of its only two calls. Making `() => false` return `undefined` changes nothing, since both callers read the value only as true or false.
