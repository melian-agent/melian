# Shared records carry no static tool's text

[Issue #516](https://github.com/melian-agent/melian/issues/516) keeps Enola's and the mutation check's own text out of the records a review exports. It builds on [issue #496](https://github.com/melian-agent/melian/issues/496)'s work, which withheld outside text from every other field of a record and named this gap.

`ReviewRecords` now rewrites each static finding in a record's sightings, and a dismissal's sighting, to a fixed sentence naming its check and rule. It keeps the rule, place, snippet, trigger and ID. Enola's receipt keeps only the three fields Melian checks. In core, an Enola or mutation result with no code to go by takes a hash of its message as its discriminator, in place of the message itself, so the stored ID input holds no tool text. Such an Enola finding gets a new ID once, so its dismissal reopens once. [The decision](../decisions/2026-11-16-shared-static-findings-carry-no-tool-text.md) records why.

`packages/pipeline/test/review-records-static-text.test.ts` was written first and failed on every case at 44db99f9, the merge of [issue #496](https://github.com/melian-agent/melian/issues/496)'s branch into `main`, for the reason the issue gives: the made-up token reached the record's bytes, and the discriminator. It passes after the fix.

Codex's adversarial review found that Enola's rule ID is tool text too: the shared sentence and the record's `ruleId` both carried it. Commit b34106bb added a test that feeds a made-up token in as Enola's rule ID, and it failed at that head because the token reached the exported record. The fix keeps a rule ID only when the base's policy declares it as a rule's `id`, which the pinned Enola 0.4.40 was run to confirm is how it names a result, and hashes any other. The test passes after it.

The rule-ID fix's mutants are in `2026-11-16-issue-516-rule-id-mutants.json`, from `melian mutants list b34106bb...8f99c01e --claims-in packages/core/src/enola.ts --claims-in packages/pipeline/src/enola-static.ts --json --all`. Of its 37 generated mutants, 36 were run by hand at 99955754 and killed by their named test alone. One is equivalent: emptying the `catch` in `declaredRules` leaves its value unset, so the next line returns no rules, as the `catch` does. Four inputs were added first to kill the rest: an empty policy file, a null rule entry, an unresolved YAML alias, which is what makes the parser throw, and a result with no message.

Codex's second adversarial review found two more gaps. First, Enola names a built-in check's result by the check's name, such as `exported-surface` or `god-class`. No policy declares those names, so the rule-ID fix hashed them all. Core's edited-symbol rule matches `enola/god-class` by name, so it stopped working. Second, the check request key still held `static.enola` and `static.mutation` at version 1, so a run an earlier build stored, whose findings held the tools' text, was reused. Commit 39bf795b added tests for both, and all seven failed at that head for those reasons. The fix keeps the built-in names `enola help check` lists for the pinned 0.4.40, and raises both check versions to 2. The tests pass after it. One existing test used `hotspot`, which Enola never emits, as its other rule; it now uses the real `hotspots`.

The built-in names fix's mutants are in `2026-11-16-issue-516-builtin-rule-mutants.json`, from `melian mutants list 39bf795b...30aec440 --claims-in packages/core/src/enola.ts --json --all`. Its four generated mutants were run by hand at 94d15f6c, and each was killed by its named test alone. The 23 string literals of the name list are ignored rows; the test that lists every name still fails if one is emptied. Stryker does not mutate the version numbers in `check-request.ts`, so that file has no mutant; `check-request.test.ts` fails if either version drops back to 1.

Melian's round two, on 69e4743d, found that the export left Biome and tsc findings alone by their check's name. A build from before [issue #281](https://github.com/melian-agent/melian/issues/281) stored those tools' text, so the name did not prove the text was Melian's fixed sentence. Commit ca863417 added a test that labels a sighting holding a made-up token as Biome's, then tsc's, and it failed at that head because the token reached the record. The fix rewrites every static finding, and the test passes. The round's other findings above advisory were the two that Codex's second review raised, which 30aec440 had fixed.

That fix's mutants are in `2026-11-16-issue-516-label-mutants.json`, from `melian mutants list ca863417...7a8efcc7 --claims-in packages/pipeline/src/review-records.ts --json --all`. Its four generated mutants were run by hand at 7a8efcc7, and each was killed by its named test alone.

Codex's fifth adversarial review found that an earlier build's sightings still left the host. A review given bare check records, or a run of a build from before issue #281 or this one, exported the sightings that build stored, and their rule and discriminator, which the export must keep for the ID, hold the tool's text. Two consecutive reviews had found a new instance of one class, so the class went to the coordinator as a design question. The coordinator chose to export a static check's sightings only when the run that wrote them proves, by its own request, check code that stores no tool text, and to mark the check otherwise with a code a reader reads as not reviewed. `packages/pipeline/test/review-records-unproven-run.test.ts` was written first and five of its six cases failed at e436db90 for that reason: the token reached the exported bytes, and the reader read the round as `findings`. The sixth, a proving run, passed, as it should. After the fix all six pass. `review-records-static-text.test.ts` adds four cases of a dismissal refused for want of a proving request, and its two earlier dismissal cases now carry one.
