Codex's adversarial review of [pull request #433](https://github.com/melian-agent/melian/pull/433) at 8511bc31, after the entry limit and the merge of `main`, found two defects. Each is now fixed.

- A remote spelled as an option, such as `--upload-pack=<program>`, made `git fetch` run that program on the host, because the remote followed the options unmarked. `melian doctor` passes the checkout's `origin` through: it makes a remote with no colon absolute, but an `origin` with a colon and no slash before it, such as `--upload-pack=touch x;:`, reached git as written. Since 33fb486a, fetch and push pass `--end-of-options` before the remote, so git refuses it as a strange pathname and the call fails as `unreachable`. The fetch test failed on 8511bc31 with the marker program's file present, and passes now. The push test passes on both heads: the argument after the remote is `<commit>:<ref>`, which git reads as an ssh host, so `--receive-pack` names a program for the far end and nothing runs here. The push keeps `--end-of-options` as the fetch has it, and its test guards the property without having reproduced it.
- One cell's bytes copied into many changesets' folders counted once toward the 256 MiB tip limit, by object ID, yet each path's cell was parsed and held apart. A tip within the limit could hold thousands of copies of a 4 MiB cell and exhaust the heap. Since 4087021c, each readable path charges its blob's size. The test with one cell at 65 paths, each reported at 4 MiB, read the tip on 8511bc31 instead of failing, and fails as `unreachable` now; 64 paths, exactly the limit, still read.

[Their inventory](2026-11-15-pr-433-codex-five-mutants.json) lists the 13 mutants of `8511bc31...4087021c` and one by hand, the fetch's `--end-of-options` removed, which Stryker does not generate. Every generated row and the hand row fail their named test at 4087021c, each checked passing unmutated first. The configuration ignores eight rows, string literals of the push's arguments and the fetch's new one. They were run too, and each fails its test: `a closed handle` for the push's, whose writes must land, and `retries deleting its ref` for the fetch's, whose fetch must succeed. The push's `--end-of-options` removed survives its test, for the reason above, and is not claimed. The hand row makes the inventory's row count exceed its `total`, as the entry limit's did, so the legacy sampler refuses both.

Codex's review of 36e3279b raised one finding: a deleted branch reads as empty, and the next write recreates it holding that write alone, so earlier records and disposal marks are lost while the call reports success. The coordinator answered on 2026-11-15, from rule 6 of the shared record decision, that this stands: write access to the store is the trust, and a writer who can rewind the store can drop its later records. A guard in the handle would protect only the rest of one process's calls, since a fresh host cannot tell a deleted branch from a store never made. The decision's table now lists the limit, and the guideline no longer says a deleted branch makes calls fail. [Issue #463](https://github.com/melian-agent/melian/issues/463), which the maintainer agreed on 2026-11-15, protects the branch with a ruleset once it holds real records. The test that asserts the behaviour stays.

Before round 3, every value this package hands git was checked for the option-injection class. The remote and the refspecs, which carry the caller's branch, follow `--end-of-options`. Every other value is one Melian built, such as the fetch ref, the hint and the index, or one git printed, such as a commit or object ID, or is passed on standard input, as object IDs, blob bytes and the index's lines are. `git init` gets a path made absolute, and `--git-dir` takes its path as a separate argument.
