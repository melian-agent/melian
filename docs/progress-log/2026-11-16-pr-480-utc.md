On [issue #480](https://github.com/melian-agent/melian/issues/480)'s branch, both reads of the process table now run `ps` with `TZ=UTC` beside `LC_ALL=C`. `ps` prints a start in the caller's time zone, so one pid gave three start strings under UTC, New York and Sydney. Codex's review of [issue #460](https://github.com/melian-agent/melian/issues/460) found it, and the coordinator chose the fix on 2026-11-16, as a choice of approach. Within one stopped git call the zone is constant. The mutation check, though, compares a start the supervisor wrote with the controller's own read, and the two need not share a zone.

- The tests came first. Through a fake `ps` whose start's hour follows `TZ`, "records the same start whatever the caller's time zone" read `Mon Nov 16 12:00:00 2026` under Sydney. The supervisor's zombie test, now "in any locale or time zone", has a controller that recorded in UTC and a supervisor whose environment names Sydney; its `ready.json` held Sydney starts. In core, "reads the same start for this process whatever the caller's time zone" read three starts from the real table. The `ps` request test failed on the missing variable. All four pass with the fix.
- A probe with a real `sleep` child and the real `ProcessTable`, its `kill` replaced, confirmed what a record stored before this change in another zone does. The pid recorded in Sydney time drew no signal, and the same pid recorded in UTC drew SIGTERM and SIGKILL. Such a record reads as another process, which fails toward leaving a process running.
