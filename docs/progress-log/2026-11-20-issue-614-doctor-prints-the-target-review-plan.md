# Doctor prints the plan of the review it is asked about

[Issue #614](https://github.com/melian-agent/melian/issues/614) makes `melian doctor` answer for one review. Before this, doctor printed the plan from the working tree and the preference files. A pull request's review reads its policy and lenses from its base, so on [pull request #532](https://github.com/melian-agent/melian/pull/532) a lens route in an uncommitted `melian.local.yaml` printed as applying while the round ran the committed model, and two reruns went by before anyone knew. `melian doctor <target>` now takes a target as `review` does, `"#12"` or a range. It prints that review's plan from `ReviewTarget`, which `review` now resolves its changeset, policy source, lenses, policy and tier checks through too, so the two cannot drift. A first `plan` line names the review and where it reads its policy. When the review reads a revision, a warning names each preference file it ignores, `melian.local.yaml` or the user's own. With no target, doctor keeps its plan and says it is a range review's on the checked-out commit. A target doctor cannot resolve fails the `plan` line. `packages/cli/test/doctor-target.test.ts` failed first at `origin/main` c2e68c4e: doctor printed the local route for `"#7"` and named no review. It now covers a pull request, the user's preference file, a range with its head checked out and one without, and a target that cannot be resolved. The [cli guideline](../guidelines/cli.md), the [design](../design.md), the three skills and the AGENTS.md learning on routing a lens past Codex's content filter now say which plan doctor prints for which target. The change guards no trust or durability property: doctor decides nothing, so no mutation inventory is owed.
