Every read-ahead credential unlock now acts only on what its read found, for [issue #474](https://github.com/melian-agent/melian/issues/474). [Pull request #466](https://github.com/melian-agent/melian/pull/466) gave `runLenses` that rule and left the other sites to this issue. Three broke it: triage, the final verification and the walkthrough each read that they would attach to a task, or do nothing, and so unlocked nothing, and another review in the same process could commit between the read and the commit. Each commit then attached to, or created, a task whose model's credentials were still locked. [The decision](../decisions/2026-11-15-every-read-ahead-unlock-acts-on-its-read.md) states the rule for every site, lists each, and says why `startWave` and `ReviewHarness.resumedProviders` need no change.

Each fix began with a test that runs a second review between the first's read and its commit, by wrapping the harness read the step makes. Each failed on ab09fd50, the base, with no credential command run:

- Triage, 81130979: `test/read-ahead-unlock.test.ts`, "unlocks the decider's providers when it read a finished decision and a rerun meanwhile replaced it", failed with `expected undefined to deeply equal [ 'decider' ]`.
- The final verification, 60232f96: `test/verification.test.ts`, "unlocks the candidates' routes when it read a task to attach to and another verification meanwhile replaced it", failed with `expected [] to deeply equal [ [ [ 'faux' ] ] ]`.
- The walkthrough, 07098ca6: `test/summarize.test.ts`, the two tests that read the attempt cap while a `--rerun` starts a task or leaves an attempt free, each failed with `expected [] to deeply equal [ [ [ 'faux' ] ] ]`.

Each passed after its fix. 9c123c00 moves each commit's body into a named callback at its old indentation, so the diff holds only the new lines. 646aff58 makes the walkthrough refuse by throwing a private error after it counts an attempt, since Pi Durable stores none of a commit whose callback throws; an earlier pre-check copied the counting rule and let its mutants survive.

[The mutation inventory](2026-11-15-issue-474-mutants.json), over ab09fd50...f3e11807, claims all 58 mutants of `review.ts`, `verification.ts` and `summarize.ts`: 53 killed by existing tests and 5 by tests f3e11807 added, none equivalent. Each kill ran its named test alone, by an anchored name with exactly one test collected, after that test passed unmutated. The runs of `review.ts` and `verification.ts` were at 9c123c00, and those of `summarize.ts` at 646aff58; each file's source is unchanged from there to f3e11807, where the five new-test mutants ran. Those five had survived. One was the walkthrough's catch that stores the failure note when a commit fails for another reason. Four were guards in `startVerification`: the first verification of a revision, a failed task replaced by a live one, an index that lost its verification, and a live task that ended aborted.

Melian's own-build round at efc36131 found nothing blocking. Its design lens raised one acknowledge finding at P2: after a refused commit, the step unlocks every provider even when it then attaches to a task that has since finished. The concrete-route decision said a finished task needs no unlock, and `ReviewOptions.unlockModels` promised that finished attachments call nothing. The behaviour is the rule [pull request #466](https://github.com/melian-agent/melian/pull/466) chose, so no test reproduces a defect. The decision now amends that sentence, says why reading again before the second commit would not bound the loop, and the TSDoc and the pipeline guideline name the exception. The round's two advisories, overlong sentences in the guideline and this entry, are split.
