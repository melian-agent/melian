# A round records its comment's body

[Issue #286](https://github.com/melian-agent/melian/issues/286): a writer could edit a `melian round` comment and keep its marker, and the AGENTS.md check still accepted it. Now the round records the body GitHub stored, and the check compares the live comment with that record. [The decision](../decisions/2026-11-14-round-records-its-comment-body.md) says why the record is a commit status.

- `commentRecord` in `scripts/round.mjs`, run by `scripts/round-record.mjs`, builds the `melian/round-comment` status from GitHub's answer to the post or edit: the run, the pull request, and the SHA-256 of the stored body. It refuses an answer it cannot read, one on another pull request, and a description past GitHub's 140 characters.
- The report job keeps GitHub's answer, and a new last step sets the status on the run's commit with `MELIAN_STATUS_TOKEN`, after `melian/review`.
- The AGENTS.md check takes the pull request's number, and accepts a comment only when its body hashes to the latest record `melian-status-bot` set for that run. AGENTS.md no longer tells builders to treat a round's findings as a writer's unverified text.
- `scripts/timeline.mjs` still reads spend without the record, and now says why.
- The check's fixtures are recordings from round run 43558730566 on [pull request #422](https://github.com/melian-agent/melian/pull/422), the first round posted as `melian-status-bot`.

Failing first: `main`'s check, at `c851d1ff`, run over the recorded comment with "All findings are dismissed." appended to its body, printed `comment 6872114855 is run 43558730566's` and exited 0. The new check refuses it, and `scripts/round-comment-check.test.mjs` holds that case beside thirteen others.

Mutants: the enumerator lists 73 in `scripts/round.mjs` and `scripts/round-record.mjs`. 71 are killed and 2 are equivalent, each dropping an explicit `"utf8"` that Node already defaults to. 28 hand mutants of the AGENTS.md check and the workflow's record step, rerun at `640fbfa7` after the fix below, are all killed. Each ran against its named test alone, with one test collected, after that test passed unmutated: [2026-11-14-issue-286-mutants.json](2026-11-14-issue-286-mutants.json). Three check cases were added after a first pass showed their guards untested: a run ID that extends this one, a run record with no full commit, and a status list that cannot be read.

Before the first fix pass, an agent tested the rule as independent cases with fake data. It found two defects in the check and one edge. The node snippet decoded each 64 KiB read of the comment on its own, so a genuine comment past 64 KiB with a character across a read boundary hashed wrong and was refused. A status description holding a newline printed as two record lines, so a description could add a record of its own choosing. A record with no description made jq fail, so the check refused every comment on that commit. Three cases in `scripts/round-comment-check.test.mjs` reproduce them. On the head before the fix they failed, 3 failed and 16 passed; the straddle case printed `comment 6872114855's body is not the one run 43558730566 recorded for pull request 422`. The check now decodes the whole stream as UTF-8, prints each description as JSON and compares the quoted string, and reads a missing description as empty. After the fix, 19 passed.

Live probe, with the maintainer's agreement in the builder's session on 2026-11-15: the builder posted one scratch comment on [pull request #431](https://github.com/melian-agent/melian/pull/431) through the REST API and deleted it at once. Its body held a CRLF line, a trailing space and `é`. GitHub's answer to the post and a later read of the comment held the same body, byte for byte, so the record and the check hash the same text. Both differed from what was sent: GitHub stored the CRLF as LF, and the cloud session's proxy appended a footer. A record that hashed the file the run sent would refuse such a comment, which is why the record hashes GitHub's answer.

Codex's adversarial review of `dcbf9fc7` found one gap. The check answered only yes or no, so a builder then read the comment from GitHub again, and a writer could edit it between the check and that read. The coordinator chose the fix on 2026-11-15: the check takes a fourth argument, a file in the reader's scratch directory, and writes to it the body it hashed, from its one read of the comment. It writes a temporary file beside the named one and moves it into place only when the record matches. It removes a file already at that path first, so a refusal leaves none. AGENTS.md and the plan-step issue template now tell a builder to read the findings from that file alone. Four cases in `scripts/round-comment-check.test.mjs` hold this: a fake gh that answers a second request for the comment with an edit, where the file holds the first body and the check made one request; a stale file replaced on a pass; a stale file removed on six kinds of refusal, with no temporary file left; and a missing file argument refused before any request. Against `dcbf9fc7` they failed, 8 failed and 14 passed, each because the check wrote no file, printed no file, or still accepted three arguments. After the fix, 22 passed.
