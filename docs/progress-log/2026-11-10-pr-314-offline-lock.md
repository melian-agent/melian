[Pull request #314](https://github.com/melian-agent/melian/pull/314), after merging [pull request #310](https://github.com/melian-agent/melian/pull/310)'s head 403d1099.

- The merge left `reserve` without the clone's identity: it never minted or read the copies directory's ID, so the lease's holder had no clone and `Lease.take` refused it, and it compared a live lease's clone with the bare label. Four existing reservation tests failed on the merge for that reason. `reserve` now identifies the copies directory first, as `checkout` does, and compares the full identity. `names its clone by the label and the copies directory's ID, as a checkout does` fails with the identity call removed; `refuses a live lease of another copies directory, though its label is the same` covers the comparison.
- Three of #310's deadline tests expected a checkout to reject when a transfer passed its deadline. On this branch ruling 3 makes that an unreached checkout, so they assert `unreached` with the same message.
- The CLI no longer mints a holder ID of its own. It passes the label `melian`, and the branch names the clone by that label and the ID it mints. `index.json` is not sealed, so the label names no host.
- The host round on #310's 403d1099 raised that ruling 3's offline fallback could open a copy another process in the clone holds (64189d1c9e6591c7). The maintainer ruled on 2026-11-10 to settle it here, where the offline path lives. On this branch a checkout takes the copy lock before it fetches and keeps it when it returns unreached, so the finding does not reproduce at 27b29ce7. `lets no second process in the clone reach a copy another holds, when …` runs the holder in a child process, and the three cases pass at that head; with the offline path releasing its lock, the two where the holder's fetch fails do not. Ruling 3 now says offline work holds the copy lock.
