[Issue #342](https://github.com/melian-agent/melian/issues/342), the display half of [issue #315](https://github.com/melian-agent/melian/issues/315): an inherited dismissal now reads as inherited from its root wherever a dismissal shows, as [the decision](../decisions/2026-11-08-dismissal-carries-to-restatement.md)'s Attribution section requires. Core's `describeInheritance` gives the words, ", inherited from `<root>`", from the dismissal's `inheritedFrom`, so no stored shape changes. The terminal reads `Dismissed, inherited from <root>, at <time>: <reason>` and never `by melian`; the status reads `0 findings, N dismissed, M inherited`; the GitHub reply, the body's dismissal fold, its "Dismissed since the last review" list, the ledger's dismissals and closed findings, and the CLI's attested dismissals each name the root. The ledger reads a closed finding's root from the round's verdict, since the closed record keeps only the reason. A trust-floor restatement's proposal shows through `Finding.likelyDismissalNotes()` in the terminal, the inline comment and the ledger line, naming the root and the `melian dismiss` command that accepts it. `packages/github/test/inherited-dismissal.test.ts` renders one verdict holding an inherited dismissal and a person's, and asserts each surface whole; the person's dismisser appears only in the terminal, which named them before, and nowhere for the inherited one. `packages/pipeline/test/restatement.test.ts` checks the terminal and the status of a real review's inheritance, and that an injection attempt restating a dismissed one shows neither form. The published document's entry type now names the `inheritedFrom` its dismissal already carried at runtime since part one; its version stays 10. The fingerprint is left to [issue #334](https://github.com/melian-agent/melian/issues/334).
