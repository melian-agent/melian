[Pull request #98](https://github.com/melian-agent/melian/pull/98), the mutation check, is rebuilt on `main` with no sandbox, after the maintainer's decision of 2026-10-14 that static checks run unconfined and only agents are sandboxed. [Pull request #112](https://github.com/melian-agent/melian/pull/112) is closed unmerged, with its work at the tag `archive/sandbox-boundary-r5`; the form of #98 that stood on it is the branch `mutation-on-sandbox` (d8dcbce7), and the first form the tag `archive/mutation-check-r12`. The port, a9c6070f, is main plus what that branch changed on top of the boundary, with every sandbox dependency taken out: no profile, no loopback flag, no confined housekeeping or teardown, no confinement field, no scratch home, and no repository of its own for the worktree, which existed only because the sandbox hid the checkout's. Stryker runs as an ordinary child of the supervisor with the environment every static tool gets, plus one marker, `MELIAN_MUTATION`, so a test that starts Stryker itself skips inside a run. Kept: the Stryker integration, selection through Vitest with the whole-suite repeat, the incremental cache with its installation identity, authority across runs, the line budget with one advisory, set-aside files raising `mutation/unmutated`, the supervisor and its recorded-pid termination, the lost-scratch error, CI's full-history fetch, the guardrail and the doctor line. A mutation run now locks its worktree with the one reason every build reads, under the ordinary `melian-static-` prefix: with no confined cleanup there is nothing only this build may remove, so main's cleanup code is untouched but for one guard, that its liveness probe never asks about pid 0 or 1. Main's cleanup, copied verbatim, runs against a parked mutation run in a test.

The guard and the rule, recorded in [the unconfined decision](../decisions/2026-10-14-static-checks-run-unconfined.md), which supersedes the sandbox decision of 2026-10-08. The check runs the head's tests only where the host allows the head: the reviewer's own checked-out commit, a head a writer pushed to the base repository, or any head on a host that declared itself an isolated runner with `melian review --isolated-runner` or `MELIAN_ISOLATED_RUNNER=1`. The decision is typed, `WriterTrust` with `by: "checkout" | "writer" | "isolatedRunner"`, made by the CLI from what the host knows, part of the run's identity, and the incremental cache keeps a head that ran only on an isolated runner apart from a trusted one. A configured static check that did not run leaves the review not reviewed: a refused head and a run past its timeout lost their leave, and only a change with no production lines keeps it. The verdict line, the `melian/review` status, which is `error`, and the review body each name the check and the reason, and the reason leads with the particular cause so a status cut at 140 characters still says it. Tests confirm the same rule for Biome, tsc and Enola, skipped or failed; no gap was found there. A repository can still name a check in `checks.allowSkip`.

Twenty-eight mutations were run by hand and each failed a test. The host gate passed at a9c6070f with 126 files and 4,042 tests.

The check on its own branch. One real run of the backend over `origin/main...a9c6070f`, with no model, on the macOS host: `static.mutation.timeout` 3,600 seconds, `maxLines` 1,250, Stryker's concurrency 4. Stryker instrumented 22 files with 1,049 mutants. Vitest related 112 test files of 126, and that initial run hit Stryker's own twenty-minute limit for it, `dryRunTimeoutMinutes`. The runner repeated with the whole suite, whose initial run passed, 4,041 tests in 18 minutes 48 seconds. Nineteen minutes were left for the mutants, and the check ended at its timeout after 3,603 seconds: a skip with the cause `timeout`, which now leaves a review not reviewed. The timeout and the budget were not raised. The machine was not idle: the one-minute load average ran from 4.9 to 26.9, with a mean of 9.4, against the 4 asked for, and another review of the clone ran in 9 of the 61 minutes sampled. The run left no scratch, no registration and no process. So the check does not finish this branch within its hour here, and removing the sandbox did not change that: the initial run is serial and takes about nineteen minutes for this suite whichever tests are selected, because the related selection keeps 112 of 126 files. What would let it finish is for the maintainer to choose: a longer timeout, about two hours at this size; a smaller budget, since 1,049 mutants at four at a time need more than the forty minutes an hour leaves; more concurrency on a machine that has the cores; or a suite whose initial run is shorter.
