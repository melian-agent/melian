# 2026-10-22: `melian/review` on merge-group commits, designed

Step 10, required status on `main`, needs `melian/review` on the commit the merge queue tests, or every queued pull request times out after 30 minutes. [The merge-group decision](../decisions/2026-10-22-melian-review-on-merge-groups.md) chooses a `merge_group` workflow that runs `melian status merge-group` from the base's build and copies each head's status onto the group commit. It rules out a pull-request-only requirement, which GitHub does not offer, and a pinned required workflow, which needs GitHub Team.

The design reads the ruleset, the rehearsal's statuses on [pull request #164](https://github.com/melian-agent/melian/pull/164) and the `MergeQueueEntry` schema, all read-only. The workflow and the command are not built yet; the decision lists nineteen tests the build must have and the ruleset change the maintainer will make.

An attacking review of [pull request #166](https://github.com/melian-agent/melian/pull/166) found that no workflow edit drew the policy notice the trust argument relied on. The root `melian.yaml` now adds `.github/**` to `policy-change-review.files`, and `packages/core/test/guardrails.test.ts` proves an edited, added or renamed workflow and an edited action each draw a P1 notice, and none without the glob. The revision also binds the status to its reviewed base and makes a failure eject only the group's own pull request. It records what an admin bypass skips.

A second attack found that a landed earlier link had no pull request number for status validation, and that a bypass merge races `main`. A landed link is now part of the trusted base and skips head-status validation, with a test of the whole result. The bypass section states the race, narrows it with a base check immediately before the merge, and records the split ruleset as the preferred option pending the maintainer's live probe at step 10.
