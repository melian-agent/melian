[Pull request #472](https://github.com/melian-agent/melian/pull/472) bounds git's standard error at `stderrLimit`, 4 MiB, so that a remote cannot exhaust memory through it. The design lens found that the bound counted bytes while keeping one `Buffer` for each chunk. A remote that writes one byte at a time sends one chunk per byte, and each kept `Buffer` costs far more than its byte, so 4 MiB of standard error could hold hundreds of megabytes. [Pull request #448](https://github.com/melian-agent/melian/pull/448) fixed the same defect in the tool download by copying chunks into fixed slabs. Core's `git` now does the same: it copies standard error into slabs of 64 KiB, allocated only when a byte needs one.

- The test, `packages/core/test/git-stderr-memory.test.ts`, fakes `spawn` so that git writes 1 MiB of standard error one byte at a time. It measures the heap and array buffers after a forced collection, and asserts they grew by less than 4 MiB. On `329f2a29` it failed with "expected 228537020 to be less than 4194304". With the fix it passes, at about 1.07 MB of growth in each of five runs.
- The tests at the limit and one byte past it, in `packages/core/test/git.test.ts`, pass unchanged.
- Standard output, under a caller's `maxBytes`, still keeps a `Buffer` for each chunk. Only callers that read local objects pass `maxBytes`, so no remote writes there, and this pass leaves it alone.
