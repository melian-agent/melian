[Issue #488](https://github.com/melian-agent/melian/issues/488) found why a lens that failed over did almost no work. When a lens's model failed, the lens task told the next model on its route to continue where the last had stopped, with findings already recorded, even when the last had failed before it did anything. During a Codex outage on the round for [pull request #471](https://github.com/melian-agent/melian/pull/471), six lenses moved to Claude that way, and each answered at once with no finding and no tool call. Now `holdsWork` in `packages/pipeline/src/harness.ts` looks for a reply that ended by stopping, at its length limit, or calling a tool. A conversation that holds one gets `handoverWording.continue`, the old text. One that holds only inputs gets `handoverWording.fresh`, which says nothing was done or recorded and asks for the work from the beginning. A planner's and a prober's conversation fail over through the same code. Both wordings enter the lens request's key, so the first review after this change asks every lens again rather than attach to or copy from a task asked under the old wording. A request names its base and head, so only a review of a revision already reviewed pays for that: one round's lens spend, $3.57 to $9.85 on recent rounds, once per such revision, and nothing on an Actions round, whose store is thrown away. The split test "moves a lens whose model failed before it started to the next model, which starts the review afresh" in `packages/pipeline/test/review.test.ts` failed before the fix, given the continue text, and passes after; its sibling for a model that failed after a tool call passed both times.

The verifier's failover sent "Continue judging the labelled claims. Already recorded verdicts remain" to its next model on every attempt after the first. A verifier that judges nothing still leaves its claims unjudged and its outcome unanswered, so the text could not pass a review, but it claimed work that had not been done. It now chooses between the same two kinds of wording through `holdsWork`. Both wordings enter `verifierText`, so the wave version and the verification request change, and every stored wave and verification task is judged again once, inside the round that re-asks its lenses. Two other places ask a next model, and neither hands over a conversation. Triage asks one request of the first model on its route that has a credential, through `RouteTextModel`, with the whole question set in it. A walkthrough runs on one model, and a failed one leaves a note and spends an attempt, so the next try is a new task with the whole prompt. Neither says anything about earlier work, so neither changed. No decision named the wording. Two later ones promised that a verification resting on no probe keeps its key, and main pinned those keys in `verification-request.test.ts` and `verification-request-cut.test.ts` after this branch was cut. Merging main failed both. With the single continue wording put back in `verifierText`, all four pinned keys equalled main's at `959a2a69`, so the fresh wording alone moved them. On the coordinator's answer of 2026-11-18, the tests pin the new keys, and [the decision of 2026-11-18](../decisions/2026-11-18-failover-wording-in-the-verification-key.md) amends both promises and says the cost; the pipeline guideline says failover changes only the model, which still holds, since the wording is an input and not the agent's configuration.

The choice decides whether a fallback reviews at all, so it is trust code, and its mutants were run by hand at `f8e84c6a`. `melian mutants list` gave 16 mutants over the range, 5 of them ignored string literals. Each of the 11 generated ones failed its named test, run alone after that test passed unmutated. Stryker makes no mutant of the two conditions on `holdsWork`, so four more were made by hand, each fixing the lens's or the verifier's choice to one wording, and each failed its test.

Codex's adversarial review, and then the review of record, found that a compaction hid the work. Pi Durable writes a compaction's summary as a user message, and can cut the context after the last reply, so a conversation whose model had recorded findings showed only inputs, and its next model was told to start afresh. The test "finds the work a model did after compaction has summarised it away" in `packages/pipeline/test/holds-work.test.ts` failed at `e01caef0`, with three more of that file's tests, and passes after the fix. `holdsWork` now reads the context Pi Durable shows the next model, through the task's `context`, and follows each compaction's `head` back to the context it summarised. A reset links to nothing before it, so work before one counts as none. This followed the coordinator's answer of 2026-11-18, which is not a ruling.

The first form of that fix read raw entries and copied Pi's unexported list of the stop reasons it leaves out of a context, and counted `pending` and any unknown reason as no work. Melian's own round on `5ad2ed86` raised it as `reimplements-an-authority`: Pi keeps a `pending` reply in the context, so its next model would see a reply and be told nothing was done. The coordinator agreed on 2026-11-18, in an answer that is not a ruling. Each view `holdsWork` reads now answers through its `messages`, Pi's own filtered context, so the copy and its type are gone. The test for each stop reason pi-ai names, and one it does not, now asks that `holdsWork` agree with Pi's context; `pending` and the unknown reason failed at `5ad2ed86` and pass after the fix.
