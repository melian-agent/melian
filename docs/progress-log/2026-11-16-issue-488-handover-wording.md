[Issue #488](https://github.com/melian-agent/melian/issues/488) found why a lens that failed over did almost no work. When a lens's model failed, the lens task told the next model on its route to continue where the last had stopped, with findings already recorded, even when the last had failed before it did anything. During a Codex outage on the round for [pull request #471](https://github.com/melian-agent/melian/pull/471), six lenses moved to Claude that way, and each answered at once with no finding and no tool call. Now `holdsWork` in `packages/pipeline/src/harness.ts` reads the conversation's model context through Pi Durable's `context`, which leaves out a reply that failed or was aborted. A conversation that holds a reply gets `handoverWording.continue`, the old text. One that holds only inputs gets `handoverWording.fresh`, which says nothing was done or recorded and asks for the work from the beginning. A planner's and a prober's conversation fail over through the same code. Both wordings enter the lens request's key, so the first review after this change asks every lens again rather than attach to or copy from a task asked under the old wording. A request names its base and head, so only a review of a revision already reviewed pays for that: one round's lens spend, $3.57 to $9.85 on recent rounds, once per such revision, and nothing on an Actions round, whose store is thrown away. The split test "moves a lens whose model failed before it started to the next model, which starts the review afresh" in `packages/pipeline/test/review.test.ts` failed before the fix, given the continue text, and passes after; its sibling for a model that failed after a tool call passed both times.
