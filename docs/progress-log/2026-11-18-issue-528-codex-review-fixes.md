# Issue #528: two fixes from Codex's adversarial review

Codex's adversarial review of [pull request #557](https://github.com/melian-agent/melian/pull/557) at cc30edc0d found two ways an unchanged revision stays unproven after an upgrade. Both fail closed: the sightings or the dismissal stay unshared.

A run an earlier build completed is reused. The request key had not changed, so the review found the old build's completed check task and reused it, and that task's terminal commit wrote no stamp. Commit d6ef085b2 raises each static check's version in `checkVersions`: Biome 3, tsc 4, Enola 3, mutation 3. The key changes once, so the review asks again. The new case in `packages/pipeline/test/check-requests.test.ts` moves a run to the key the old versions give and deletes its stamp. It failed at cc30edc0d with `expected 'b7ee6513…' not to be 'b7ee6513…'`, since both builds asked under one key, and passes after the bump. `melian mutants list` generates no mutant for that commit: Stryker leaves number literals alone.

A repeated dismissal cannot take a stamp. A dismissal made before stamps carries no `run`. Repeating it with the same reason after a stamped run returned early, so the run was never stored. Commit a6948cc66 counts a different run as a change, for a dismissal that records a sighting. The new case in `packages/pipeline/test/findings-check-stamp.test.ts` failed at d6ef085b2 with `expected undefined to be '2222…'` and passes after the fix.

Files that guard trust or durability: `packages/pipeline/src/findings.ts`. The inventory, [2026-11-18-issue-528-repeated-dismissal-mutants.json](2026-11-18-issue-528-repeated-dismissal-mutants.json), lists the 9 mutants `melian mutants list a6948cc66~1...a6948cc66 --claims-in packages/pipeline/src/findings.ts` generates. The survivor replaced `severity === undefined` with `false`; a second new test, a repeat that names no severity after a later run, kills it, run the same way.

## An empty result needs its run's proof

Codex's second review, at 89449306c, found that a stale run can hide a blocker. Run B finds a blocker; a stale run A of another request then finds nothing, replaces B's sightings with none, and stamps A's key. The export shared a check with no sightings without proof, so B's record called the revision clean. The coordinator answered on 2026-11-18 that every ran or provisional static check needs the proof; the maintainer has not ruled. Commit 80ed5f65a drops the exemption. The older race, where a stale run's commit replaces a newer run's sightings at all, is [issue #562](https://github.com/melian-agent/melian/issues/562); until it lands the host's own verdict can still pass, and the decision names it as a third limit.

The new case in `packages/pipeline/test/review-records-unproven-run.test.ts`, tsc's empty result stamped by another run, failed at 89449306c with `expected { Object (result, sightings, ...) } to deeply equal { v: 1, result: { …(4) }, …(1) }`, since tsc exported as ran, and passes after the fix. Every end of a static check, ran, provisional, skipped or failed, goes through the check task's one terminal commit, which stamps the run's key, so an honest clean run is proven.

Nineteen tests broke. Fifteen in `recorded-round.test.ts` and one in `review-records-export.test.ts` handed in bare check records, which prove nothing, so their clean static checks were withheld. They compare a reader with its host, and a host's round holds a run, so `test/fixtures/proven-run.ts` writes what a run's terminal commits leave and hands that run in; their assertions are unchanged. Three cases in `review-records-unproven-run.test.ts` asserted that tsc's empty record was shared from an unproven run. Each case now names tsc's record: withheld where the run is unproven, ran where only Biome's stamp fails or the older build asked for today's tsc code.

Files that guard trust or durability: `packages/pipeline/src/review.ts`. The inventory, [2026-11-18-issue-528-empty-result-mutants.json](2026-11-18-issue-528-empty-result-mutants.json), lists the 8 mutants of `80ed5f65a~1...80ed5f65a` in it: 7 generated and 1 ignored by configuration. The scratch runner applied each at 80ed5f65a and confirmed each failing test alone, as above: all 7 were killed, 5 by `recorded-round.test.ts` through the proven run, and 2 by `review-records-planted-sighting.test.ts`.

## A request that did not key its run shares no static result

Codex's third review, at b597683d4, found that two runs can share one request key. A request `checkReusable` refuses, one whose install Melian could not identify or whose working tree's `melian.yaml` it could not read whole, starts a new run each time it is asked. Run A finds a tsc blocker; run B under the same key finds nothing, replaces A's sightings and stamps the same key; A's review, exported then, called tsc clean. The coordinator answered on 2026-11-18, not a ruling, that such a run proves nothing for the export. Commit d87c7a532 adds `StaticProof.keyedFully`, which asks `checkReusable` of the stored request, and the export writes each static check of such a run as `failed`, `unkeyed`. The same-key case is added to [issue #562](https://github.com/melian-agent/melian/issues/562), since the host's own verdict has the same gap.

The new case in `packages/pipeline/test/review-records-unproven-run.test.ts`, A's tsc blocker under an unidentified install with B's empty result stamped under the same key, failed at b597683d4 with `expected { result: { findings: 1, …(5) }, …(2) } to deeply equal { v: 1, result: { …(4) }, …(1) }`, since tsc exported as ran with one finding and no sightings, and passes after the fix. A new case in `static-proof.test.ts` gives `keyedFully` a request of each kind.

Twenty-one tests broke when the check landed. Every fixture's request was `{ checks }` alone, with no install facts, which the proof now reads as not keyed fully. A real run's request always keys the install, so `test/fixtures/proven-run.ts` and the unproven-run cases now key an identified one; their assertions are unchanged.

`melian doctor` prints nothing about whether the install is identified, so no line there names the cost; the decision and the pipeline guideline state it.

Files that guard trust or durability: `packages/pipeline/src/review.ts`, `packages/pipeline/src/static-proof.ts` and `packages/pipeline/src/review-records.ts`. The inventory, [2026-11-18-issue-528-unkeyed-mutants.json](2026-11-18-issue-528-unkeyed-mutants.json), lists the 29 mutants of `d87c7a532~1...d87c7a532`: 23 generated and 6 string literals ignored by configuration. The scratch runner applied each generated mutant at d87c7a532 and confirmed each failing test alone, as above: all 23 were killed. It ran the 6 ignored ones too. Five were killed, the two that empty `unkeyed` among them. The sixth, which fills the withheld record's empty `error`, is equivalent: `checkResult` writes `withheld` as the error of every failed record.

## A stamp names the check task that wrote the sightings

Codex's fourth review, at 7d236e705, found that a request key does not name one execution. Run R finds a blocker. Run S, of another request, takes the revision's mutation authority. R is asked again under its full key, starts a new task, finds nothing, and stamps the same key. R's first run, exported then, called the revision clean. The coordinator answered on 2026-11-18, not a ruling, that the stamp should name the check task that wrote the sightings, and the export should require the run's own task to have recorded that check task. Commit 3f5909e89 makes the stamp `{ request, task }` and has `StaticProof` read `CheckSources` for the run's task. The findings document stays at version 12, with no second bump. A stamp an earlier build of this branch wrote, a bare key, reads no task and fails closed.

The new case in `review-records-planted-sighting.test.ts`, R's first run exported after the restart, failed at 7d236e705 with `expected { result: { findings: 1, …(5) }, …(2) } to deeply equal { v: 1, result: { …(4) }, …(1) }`, since Biome exported as ran with no sightings, and passes after the fix. Two cases cover a rerun of failed checks: a kept check's record is still shared, since the rerun's task copies the kept checks' entries from the earlier task's `CheckSources`; and a kept check whose sightings a third task replaced under the same request is withheld. Neither needed more than `CheckSources` already holds.

## A static check's record is the one its run stored

The own-build round at 7d236e705 blocked, at P1, on a record handed in beside a genuine request. The Actions round there, [run 44224804956](https://github.com/melian-agent/melian/actions/runs/44224804956), raised the same case at P2. tsc finds a blocker under run R. A caller hands in R with tsc's record changed to `ran`, `findings: 0`. The stamp, the request and the task all prove R, so the export took the caller's record and said tsc found nothing. The coordinator answered on 2026-11-18, not a ruling, to fix it here and to prefer reading the stored record. Commit 194e34733 has `StaticProof` read the run's records from the checks document, and the export takes a static check's record from there. A static check that the caller says ran, and whose run stored no record of it, is withheld.

The new case failed at 3f5909e89 with `expected { findings: +0, …(5) } to match object { status: 'ran', findings: 1 }`, and passes after the fix. A second case deletes the stored tsc record and expects tsc withheld. One older case in `review-records-export.test.ts` handed in a Biome record with absent fields; Biome's record now comes from the store, so the case hands that record for guardrails, which still takes the host's.

A guardrail is stamped too, so repeating a guardrail's dismissal after a later run counted as a change, though nothing shares a guardrail's dismissal by its stamp. The new case in `findings-check-stamp.test.ts` failed at 194e34733 with `expected { by: 'maintainer', …(2) } to be undefined`, since the repeat replaced the dismissal, and passes after the fix.
