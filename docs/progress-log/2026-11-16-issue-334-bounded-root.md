The host round on [pull request #471](https://github.com/melian-agent/melian/pull/471) at `3b211536` raised one acknowledge finding from the design lens. The amendment said the ledger always names an inherited dismissal's new root. But the ledger is cut to GitHub's 65,536 characters, from its end.

Two tests built the scenario before anything changed. In the first, a merged report switched from root A to root B under a live acknowledgement, beside 90 dismissed findings with 1,000-character reasons at paths that sort first. No review or reply posted, and the status stayed as it was. The cut ledger named neither root and was not rewritten, since its text read the same with either. The second review's body, cut the same way, never named A. With the fillers at paths that sort after the report's, B survived, so survival depends on where a path sorts. In the second test, nothing was live and five inherited findings had distinct roots. The switched root sat among those the status counts as "and 3 more", so the status did not change either. In both, `melian publish`'s attestations named B.

The coordinator put the result to the maintainer. On 2026-11-16, in the coordinator's session, the maintainer chose to state the promise as it is, answering "agree". The coordinator opened [issue #482](https://github.com/melian-agent/melian/issues/482) for changing what gets cut. [The decision](../decisions/2026-11-15-inheritance-and-the-verdict-fingerprint.md) now says the ledger names the new root while its dismissals fit, and the status while the root fits its line. Past either bound only `melian publish`'s attestations and `melian findings --all` do. Its amendment narrows the restatement decision's "wherever the dismissal is" to the same bounds, since a cut review body can lose a root when an inheritance first appears. `docs/design.md`'s Publish step, the GitHub guideline's attested list and the pipeline guideline's restatement section say the same.

The two scenarios are now tests in `packages/pipeline/test/publish.test.ts`: "keeps the status as it was when the switched root is among the roots it counts, and names it in the ledger" and "names a merged report's switched root only in publish's attestations once the ledger's dismissals pass GitHub's limit". They pin behaviour the code already had. No code changed, so they owe no mutation proof. The same audit checked the decision's other "always", "every" and "never" claims against named tests, and each holds.
