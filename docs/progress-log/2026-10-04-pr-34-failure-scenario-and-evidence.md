Every lens finding now carries a failure scenario and evidence locations, in [pull request #34](https://github.com/melian-agent/melian/pull/34), so the verifier has a claim to attack. `report_finding` requires a scenario of at most 2,000 characters and one to ten locations, each a `cause` or `context`, at head or at the base for deleted lines; Melian reads and stores the code at each. Only a `cause` location overlapping the change, new lines at head or old lines at the base, makes a finding outside the diff `affected`, which [the evidence locations decision](../decisions/2026-10-04-evidence-locations.md) records, superseding the rule that a base location never promotes. The terminal, JSON, and GitHub renderings, the lens instructions, and the goldens carry both fields, and the scripted runner checks them. Findings, verdicts, and pending rounds stored before read tolerantly: a single old evidence location becomes one `cause` at head, and a head published before the upgrade is not posted again. The reviews of the pull request added four rules: a file the change renamed without editing counts as changed code; a merged finding keeps every member's claim whole, as [the merged finding claims decision](../decisions/2026-10-04-merged-finding-claims.md) records; every stored snippet is cut at 2 KiB for display, while a finding's ID and its trigger's comparison read the whole text; and a head counts as published only for the revision its last review was of, so a retarget with the same findings still takes a review. `report_finding` now quotes back what each location resolved to, and `read_file` reads the base.
