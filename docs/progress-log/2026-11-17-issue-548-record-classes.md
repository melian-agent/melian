# A shared record's classed fields refuse free text when it is read

For [issue #548](https://github.com/melian-agent/melian/issues/548), core's payload schema now checks each class the producer applies. Before, a check record whose Enola snapshot held `snapshotId: "ghp_token"` passed `SharedRecord.checked(reviewPayloads)`, so a reader such as the relay of [issue #397](https://github.com/melian-agent/melian/issues/397) would take a record Melian never built. [The decision](../decisions/2026-11-17-shared-record-classes-checked-on-read.md) lists each class, the fields that stay free text, and why.

Each pattern lives once, in `packages/core/src/record-payloads.ts`, and `ReviewRecords` imports it: the snapshot's object ID, snapshot ID, receipt and hashes, the record codes, the two caveats, and `isToolVersion`. The lens version and the verifier version take their lengths from `lensVersionDigits` and `verifierVersionDigits`, which the code that computes each version cuts its hash with. Two producer gaps closed with them. A decided check's version and coverage IDs went into a record unchecked; now a version that is not a tool's reads as Melian's sentence and a coverage ID that is not a hash reads `null`. A snapshot's commit was not checked against an object ID; now a check whose snapshot names something else is withheld. A refusal names the field and no longer repeats the value it refused.

The payload version stays 1. `packages/pipeline/test/review-records-main.test.ts` reads 105 records main's build wrote at e6ed960bd, one of each shape among the 768 its tests built, and every one passes the new schema. Twenty more came from tests that handed `ReviewRecords` lens versions such as `1` or `abc`, which no loaded lens has, and were left out.

`packages/core/test/record-payload-classes.test.ts` holds a test per classed field with only that field wrong: 53 of its first 75 tests failed on e6ed960bd, and all pass now. The four lens-source cases the mutant proof added came after. `packages/pipeline/test/review-records-classes.test.ts` tests the producer's new guards: three of its four failed on e6ed960bd, each for the reported reason (the decided version `ghp_token` kept, the coverage ID `ghp_token` kept, the snapshot commit `ghp_token` kept), and the fourth, that the verifier keeps its own version, passes on both. The relay's third schema test, from `claude/records-relay-397` at dd26e6a22, passes against this branch, 4 of 4; it stays on that branch.

The [mutant inventory](2026-11-17-issue-548-record-classes-mutants.json) lists the 182 mutants of `origin/main...5e2f4abff`: 140 generated and 42 ignored. Each generated mutant was run by hand against its named test alone, after that test passed unmutated. 138 were killed. The first pass named the new class tests; 27 survived them, and 19 of those fell to the older record tests. The six left in core, the lens branch of `sourceVersion` and a dismissal sighting's version, fell to four cases added to `record-payload-classes.test.ts`, each with one part of a lens source wrong. Two are equivalent. At `review-records.ts:114`, `id !== undefined` forced true reads `null` all the same, since `RegExp.test(undefined)` tests the string `undefined`. At `review-records.ts:149`, `status === "ran"` forced true changes nothing, since only a ran record carries snapshots.

## The fix pass after round 2

The round and the reviews found five gaps, each closed with a failing test first: 9 tests in core and 1 in pipeline failed at 77e4f2a52 for the reported reason, and all pass now.

- A refusal repeated text the record supplied: an unknown field's name, a map's key in a schema path, the verifier check's name and a sighting's key. A schema path now keeps only the segments the schema names and array indices, and shows any other as `*`. Only an unknown kind's refusal still names the kind, since the store conformance suite requires it.
- A claim's verification could name any version. It now names the verifier's.
- A telemetry stage's outcome was free text. It is now one of `telemetryOutcomes`, and `ReviewRecords` withholds any other.
- A record's key was any non-empty string. By the coordinator's answer, option A, not a ruling, a dismissal's key is now a finding's ID and every kind a writer's job relays is keyed by a request's key, in the envelope and wherever a round names a record. Tests make a key from a label with `recordKey` and `findingKey` in core's testing entry, which landed in its own commit before the check. The key check's 10 new tests failed on that commit, each because the wrong key was accepted, and pass with the check.
- A finding ID's pattern was written out beside the code that cuts the hash. Now both take `findingIdDigits`.

Two records of main's capture no longer match: one telemetry record whose stage ended `done`, and one verification record whose claim named a version no verifier computes. Both came from tests that handed `ReviewRecords` values no producer writes. They were dropped from the capture, and the payload version stays 1.

The [fix pass's inventory](2026-11-18-issue-548-fix-pass-mutants.json) lists the 92 mutants of `77e4f2a52...05a703488`: 60 generated and 32 ignored. Each generated mutant was run by hand against its named test alone, after that test passed unmutated; the [runs](2026-11-18-issue-548-fix-pass-mutant-runs.json) record each. 59 were killed. The first pass named one test file per source file and left 11 alive; 10 fell to other existing tests, and a finding ID's full hash, which broke `findings.test.ts` at load rather than in a test, fell to a new test of a dismissal keyed by `findingId`. Two helper branches with nothing to read them were removed rather than tested. One is equivalent: at `record-payloads.ts:430`, `error instanceof FindingError` forced true changes nothing, since `Finding.parse` throws only `FindingError`. The enumerator lists no mutant for the outcome check at `review-records.ts:593`, so it was forced true and false by hand, and a `ReviewRecords` test failed both ways.

## After Codex's review of 6f9af2b11

Codex raised two findings.

- A run's rows that ran or were reused exported as `withheld`, since `runDetails()` names them `ran` and `reused` and neither was in `telemetryOutcomes`. Main's capture held one telemetry record, built by hand with an outcome of `done`, so no real run's rows were ever read against the list. The repeat-review test in `packages/pipeline/test/lens-reuse-review.test.ts` now exports its run through `ReviewRecords.telemetry` and checks every row keeps its outcome. It failed at 6f9af2b11, eight rows with `ran` and `reused` withheld, and passes with both added. The enumerator lists no mutant for the two entries, so each was removed by hand, and the test failed both times.
- A dismissal's key is checked as a finding ID, but not bound to the ID of the finding in its sighting. By the coordinator's answer, not a ruling, that binding goes to [issue #481](https://github.com/melian-agent/melian/issues/481), the first code that reads dismissal records, and `PayloadChecks` is unchanged here.
