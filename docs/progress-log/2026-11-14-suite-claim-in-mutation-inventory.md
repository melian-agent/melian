The mutation inventory takes a fourth claim, `suite`, for [issue #406](https://github.com/melian-agent/melian/issues/406). It records the label "suite assertion, proved per case", which [the suite-assertions decision](../decisions/2026-11-14-suite-assertions-proved-per-case.md) sets for a shared test suite's duplicate assertions and fixture housekeeping. Before this, `node scripts/enumerate-mutants.mjs --sample` refused [pull request #399](https://github.com/melian-agent/melian/pull/399)'s inventory, whose 30 such rows had no claim it knew.

A `suite` row needs a one-line reason as its evidence, as an `equivalent` row does, and core's `MutationInventory.parse` checks that without reading any file. The sample lists every `suite` row under its own `suite` key, apart from the probes, because a reviewer reads its reason rather than runs it. Those rows also leave the probe groups, so a file or mutator covered only by suite rows draws no probe.

The decision covers only a suite kept under a source folder for other packages to import. An inventory row carries only its file's path, which cannot say that. So `SuiteExports`, in core, reads package manifests through core's revision source, at the head commit a version-2 inventory records. A `suite` claim stands only in the file that the nearest `package.json` above it maps `./testing` to. A legacy inventory records no head, so its suite claims are refused with a message to enumerate again. That refusal comes when the inventory parses: the Melian round on `0a7b40fc` found that the shared claim union had widened version 1's schema too, which the sampling decision keeps as it was, so version 1 now keeps its own three claims.

Node is the authority on what `./testing` resolves to, and it cannot run here without the revision's files on disk. Two consecutive Codex passes each found the hand-written resolution differing from Node's. The first normalised `src/record.ts`, `/src/record.ts` and `../core/src/record.ts` into an ordinary source file of the package. The second found that `import`, listed before the source condition, wins in Node. The same pass found the exports read from the working copy rather than the inventory's head. By the convergence rule the class went to the coordinator, whose answers on approach are recorded on the issue. The third pass found that Node reads a target as a URL, so `./src/testing.ts?case/production.ts` loads `src/testing.ts` while the check accepted a different git file. The coordinator then chose an allow-list over running Node, since running Node would write head-written files onto the reviewer's disk and spawn a process there. The sampler accepts only a shape with one possible reading: `@melian-agent/source` as the first condition, with a string value of `./` then one or more segments of `[A-Za-z0-9._-]` joined by single slashes, none of them `.`, `..` or `node_modules`, and `exports` holding only `.` and `./` subpaths with no pattern. Everything else, an unreadable manifest, or a commit the repository lacks, refuses the claim and says why. The coordinator chose this rule on 2026-11-14, as its answer on approach, recorded on the issue: the package's exports are the authority on what other packages import, where a path convention would be a hand-kept rule and an inventory's own list would let a builder excuse its own rows. Both `melian mutants sample` and the compatibility script read the exports at the inventory's head, from the repository they run in. Codex's fourth pass found the first form reading every package's manifest on every version-2 sample, so a head with thousands of packages could stall sampling. Its fifth found the narrowed form still reading a workspace list the head writes, where tens of thousands of repeated `packages/*` patterns each spawned git. That was a second instance of one class, and the coordinator's answer on approach replaced the workspace list altogether. The sampler now walks up from each suite row's file to the first directory holding a `package.json`, reads that one manifest, and never climbs past it, so the rows, not the head, bound the reading. It reads nothing for an inventory with no suite rows. The same pass found that a sample run from a subdirectory failed, since core's revision reader takes the repository's top level, and the sampler now resolves it first. The rule no longer checks that a package is a workspace member: a head could add a `package.json` beside a production file with a `./testing` export naming it, which shows in the diff, and the sample prints every suite row with its file.

The limit: a head that adds a `./testing` export widens the rule for its own rows, and a reviewer sees that change in the diff. On pull request #399's branch, `packages/core/package.json` maps `./testing` to `packages/core/src/testing.ts`, and the conformance suite is defined in that file, not re-exported into it.

Inventories written before the change still parse and sample, by a test over two committed inventories: one at version 2 and one legacy. A mutant's ID is unchanged.
