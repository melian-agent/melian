# [Issue #483](https://github.com/melian-agent/melian/issues/483): fixes from the first reviews

Eight review findings on [pull request #490](https://github.com/melian-agent/melian/pull/490) changed the per-lens probing wording or its load check, each with a test that failed first.

- Codex's first review found that the `correctness` wording counted any throw as a defect, though code that refuses an input it does not accept is right. Its plan, prober and judgement now count a throw only where a result is expected (bd8a4c97).
- The first Melian round found that no test held each lens's planner to its own words for earlier findings. `probing.test.ts` now does (253199ce).
- Codex's second review found that a `tests` probe exited 0, the passing outcome, when its test already failed on the unchanged copy, so a broken test read as one that covers the change, and could refute a carried finding. Such a probe now prints what the test printed, exits 125 and reports no finding. A fake-model test shows that its refutation is refused and the verdict holds no finding. Melian still counts the attack as answered, so no level may probe with the `tests` lens before [issue #493](https://github.com/melian-agent/melian/issues/493).
- The second Melian round found that no test held a planner's reminder to its own lens's words. A fake-model test now has a `tests` planner record no plan at first, and checks that its reminder is the `tests` lens's own `recordPlan`. With `recordPlanPrompt("trust-boundary")` at `review.ts:635`, the round's mutant, it fails.
- Codex's third review found that `Lens.load` let a repository turn on `tests` probing, which the earlier fix said no level may do. `Lens.load` now refuses `probe` on the `tests` lens at any level, naming [issue #493](https://github.com/melian-agent/melian/issues/493), which lifts it (9d543e60).
- The second Melian round found that the load check keyed on the lens's name alone, so a repository lens that took the name `correctness` for a purpose of its own probed under the built-in's words. `Lens.load` now refuses `probe` on a lens of such a name unless it, and every farther lens of the name, extends the built-in (9d543e60, 4ff5b12b). Each new test failed first: four tests, on `expected undefined to be an instance of LensError`. Of the 30 mutants `melian mutants list` generates over the two commits in `lens.ts`, 29 failed their named test, run alone after it passed unmutated, at head `4ff5b12b`. The other, `base.builtin` without `?.`, is equivalent: `layer()` refuses an `extends` that names no farther lens before `resolve` runs, so `base` is defined wherever it is read. One kill, of `base?.builtin === true` forced true, needed the fourth case, a lens extending a farther same-named lens that replaced the built-in.
- Codex's fourth review found that a review in flight across the upgrade, holding a probing run of a lens the table no longer names, throws when it resumes. Two fake-model tests take a `tests` lens's wording away mid-run, standing in for such a run. Both fail closed: once the planner finishes, the lens ends failed and the review reads not reviewed; once a claim rests on its probe, the review stops before it has a verdict. The coordinator chose to record this limit in the decision rather than migrate the lens task.
- Codex's fifth review found that a lens counted as the built-in when its file's path began with `builtin:`, which a repository folder named `builtin:x` gives it, so a lens there that replaced `correctness` could probe under the built-in's words. A definition now carries whether Melian shipped it (e0729495). A fourth case in the refusal test, run in a worktree and from a revision, failed first on `expected undefined to be an instance of LensError`. Of the 15 mutants generated over the commit, 14 failed their named test, run alone after it passed unmutated, at e0729495; the 15th is the same equivalent `base.builtin` without `?.`.
