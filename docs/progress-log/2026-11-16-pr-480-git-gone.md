On [issue #480](https://github.com/melian-agent/melian/issues/480)'s branch, [pull request #498](https://github.com/melian-agent/melian/pull/498), a stop that finds git gone from the process table now says the programs git started may still run. Before, `stopTree` found no root, recorded nothing, and resolved as though it had stopped the whole tree. Codex's adversarial review of `3a375395` found it.

The case is real, not only a race. A git that exits while a program it started holds its output open does not close, so the deadline fires after git has gone. Its child has been re-parented and no longer reads as below git. `stopTree` now returns `undefined`, having signalled nothing, when the table shows no live process with the root's pid, a zombie included, since a zombie's children have been re-parented too. `git` already reads `undefined` as a stop that left programs running, so the timed-out result carries `childrenLeft` and the overflow error ends with the warning, now worded "the process table could not be read or no longer showed git".

- The tests came first. On `3a375395`, "signals nothing, and says it could not stop the tree, when the root is no longer in the table" and its zombie twin got a promise, not `undefined`. "says the programs git started were not stopped when git has already exited and one holds its output open" got a timed-out result with no `childrenLeft`. All three pass with the fix.
- "stops git one byte past its limit" changed its input, its outcome unchanged: its stand-in exited as soon as it had written, so the stop could find it gone. It now keeps running, as a fetch does while its remote writes. Two assertions changed with the warning's new wording.
