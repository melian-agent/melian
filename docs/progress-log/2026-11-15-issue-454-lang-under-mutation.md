[Issue #454](https://github.com/melian-agent/melian/issues/454): a check run's key now holds the tools' `LANG` when `static.mutation` is on. Stryker runs the head's own tests with the host's `LANG`, and a test can read the locale, so two hosts with different locales shared one mutation answer. With mutation off the key holds no `LANG`, so hosts with different locales still share every other check's results. [The amendment](../decisions/2026-11-15-check-run-keys-lang-under-mutation.md) corrects the request-keys decision's sentence that `LANG` cannot change a finding, and says why `PATH`, `HOME` and `TMPDIR` stay out.

`16d178dc` adds `lang` beside Stryker's facts in `packages/pipeline/src/check-request.ts`, read in `runIdentity` through `toolLocale()` in `src/static.ts`, which reads the same list of variables the static runner passes to every tool. The test "keys the tools' locale only when mutation runs the head's tests", in `packages/pipeline/test/check-request.test.ts`, failed at `088aa41f`: `expected '5f55df0331b37168202ade366c07a5c2eedea…' not to be '5f55df0331b37168202ade366c07a5c2eedea…'`, two mutation-on requests that differ only in `LANG` keyed alike. The key-coverage test failed there too, `expected [ Array(1) ] to deeply equal []`, once the sample held `lang`. Both passed after the change. "reads the LANG a tool runs with, and null when the Melian process has none", in `test/static.test.ts`, covers `toolLocale`.

A mutation-on run stored before this change has a key without `LANG`, so the first review after it runs that check again once. A mutation-off run keys as before.

At `16d178dc` each was killed by the locale test alone, which passed unmutated first. `checks.ts` gained a call, which no mutator changes. `static.ts` is left unmutated by the enumerator because it sends process signals, so `toolLocale`'s `?? null` was not run as a mutant; its test asserts a set value, an empty one and an unset one.
