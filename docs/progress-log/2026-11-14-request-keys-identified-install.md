The Melian round at `7ea1e50b` on [pull request #436](https://github.com/melian-agent/melian/pull/436) blocked on the install key. Whether the install is identified depends on whether `node_modules` exists, and no keyed digest records that.

Problem: a run made beside a `node_modules` no manager recorded is stored, though never reused. Once the user removes `node_modules`, every digest still reads `unavailable`, the install now reads as identified, and the next review reused that earlier run, made under an install that is gone. Solution: `checkRequest` in `packages/pipeline/src/check-request.ts` keys the whole `InstallDigests`, whether it identifies the install included. [The decision](../decisions/2026-11-14-request-keys-as-built.md#what-a-check-runs-key-holds-and-leaves-out) and [the identity guideline](../guidelines/identity.md#the-keys-melian-has) now list it in the key.

The fix started with a failing test. At `7ea1e50b`, "never reuses a run made beside an unrecorded node_modules once it is removed" in `packages/pipeline/test/checks.test.ts` failed with `expected 8 not to be 8`. After `b888477b` it passes, with 141 tests across `checks.test.ts`, `check-request.test.ts`, `mutation-cache.test.ts` and `review-checks.test.ts`.

The changed line guards trust: it decides what a key matches. The enumerator finds no mutant in `7ea1e50b...b888477b`, so [the inventory](2026-11-14-issue-394-identified-mutants.json) is empty; it names no `claimsIn` file, since the sampler refuses a claimed file with nothing to prove. One hand mutant stands for the change: keying `install.digests` again, the code at `7ea1e50b`. [The run](2026-11-14-issue-394-identified-mutant-runs.json) at `b888477b` passed the new test unmutated and failed it with the mutant, so it is killed.
