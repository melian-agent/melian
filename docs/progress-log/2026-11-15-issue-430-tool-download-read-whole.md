# Issue 430: the tool cache reads a download whole before writing it

[Issue #430](https://github.com/melian-agent/melian/issues/430): every Melian round in a cloud session crashed within seconds, while the tool cache downloaded Enola through the session's proxy. The download awaited a file write per chunk, so Node's bundled undici paused its parser, and when the server closed the connection the parser's `assert(!this.paused)` ended the process ([nodejs/undici#5360](https://github.com/nodejs/undici/issues/5360), fixed in undici 8.4.1; Node 22.23.4 bundles 6.29.1 and Node 24.22.1 bundles 7.30.1). `ToolCache`'s download now gathers the body in memory under its 128 MiB bound, checks the SHA-256, and writes the archive once. A digest mismatch now writes nothing.

Two tests pin it: a body pulled in 64 chunks is read whole before any archive file exists, and a mismatched digest opens and writes no archive. Both failed on `d127d7bc` for the reported reason and pass after. The test that counts file handles after a binary stat refusal now counts two, since the download opens none.

A third test checks that the written archive keeps mode 0600. `tool-cache.ts` verifies what it downloads, so it is trust code. The enumerator lists 13 mutants on the changed lines. Three are string literals the configuration ignores, and the other ten each failed their named test, run alone at `13d32698` after it passed unmutated. [The inventory](2026-11-15-issue-430-mutants.json) records each run.

A Melian round from this build, started on 2026-11-15 with an empty state directory, fetched Enola through the session's proxy, ran `static.enola` in 26 seconds, and completed with one finding. The finding said the change contradicted the active clause "Stream the download to a temporary file while hashing it", and that joining the chunks held two copies of the archive at once. [A new decision](../decisions/2026-11-15-tool-download-read-whole.md) amends that clause, and the download now writes the chunks it read with no joined copy. Its test, "writes the chunks it read, with no joined copy of the archive", failed on `ed99748d` with `expected [ Array(1) ] to deeply equal [ [ …(2) ] ]` and passes after.

The fix's [inventory](2026-11-15-issue-430-mutants-fix.json) lists the 2 mutants of `ed99748d...a98ff61e`: the options object emptied, killed by the mode test run alone after it passed unmutated, and a string literal the configuration ignores. The empty-array mutant at line 268, whose kill had relied on the join, was run again at `a98ff61e` and still fails "reads a download whole".

Codex's second review, at `0a52c9a6`, found that keeping every chunk as it arrived left memory unbounded: the byte limit counts payload, not the objects that hold it. A probe against real undici on Node 22.23.4, with a local server that wrote one byte per chunked write, gave 1,154,162 chunks and 481 MiB of resident memory in ten seconds for a 1.1 MB body; the download's 120-second timeout allows several GiB. `main`'s streaming write had no such cost. The download now copies each chunk into 1 MiB slabs; the same probe on the slab copy used 34 MiB and kept two slabs. Three tests pin it: "keeps a download in slabs of 1 MiB, however finely it arrives", with one-byte and empty chunks, and "writes a download of 1048576 bytes as one slab" and "of 1048577 bytes as two slabs", at the slab's bound and one past it. All three failed on `0a52c9a6`, with the write given one piece per chunk received (`expected [ 1, +0, 1, +0, …(4372) ] to deeply equal [ 1048576, 457878 ]`, `expected [ Array(256) ] to deeply equal [ 1048576 ]` and `expected [ Array(257) ] to deeply equal [ 1048576, 1 ]`), and pass after. They replace "writes the chunks it read, with no joined copy of the archive", whose promise the slabs change.

The slab fix has its own inventory, [`2026-11-15-issue-430-mutants-slab.json`](2026-11-15-issue-430-mutants-slab.json), the enumerator's whole output for `0a52c9a6...22c6399c`: 20 mutants in `tool-cache.ts`, 19 claimed killed and 1 string literal Stryker ignores. A scratch script ran each against its named test alone, at `22c6399c`, after that test passed unmutated. Fifteen failed. Four turned the copy loop into one that never ends, `offset <= view.length`, an emptied loop body, and the two that never push a full slab, so their test hung; the script stopped each after 90 seconds, by the pids it recorded under the command it started, and found no worker left.
