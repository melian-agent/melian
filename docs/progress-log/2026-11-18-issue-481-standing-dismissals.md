# Issue #481: every standing dismissal counts, and a dismissal made again supersedes the old one

[Issue #481](https://github.com/melian-agent/melian/issues/481) shares a dismissal through the record store. [The first entry](2026-11-16-issue-481-dismissal-records.md) built the export, the verification key and the reader. This entry covers what followed it on the same pull request.

A dismissed static finding is no longer a restatement root. Its dismissal may have no record to name, since a static run that cannot prove it stored none of its tool's text leaves the dismissal unshared. Before, a lens claim under the static finding's rule made verification throw and the review failed. The test in `restatement.test.ts` failed at the head with that `DismissError` and passes after the fix.

`RecordedRound.contents(revision)` hands a reader the round's sightings, proving hunks and standing dismissal records, and refuses a revision the round did not review. Its tests in `recorded-round.test.ts` assert the whole value.

The reader counts every standing dismissal record, never only the latest. Two hosts that each dismiss a finding again leave one standing record each, and the finding stays dismissed while either still holds. This builds rule 7 of [issue #395](https://github.com/melian-agent/melian/issues/395) as the coordinator answered it on 2026-11-17, a coordinator's answer, not a ruling.

A writer now fills a dismissal record's `supersedes` with every other dismissal record of the same finding that its store held when the review began. A review lists its store once, and verification and export both read that listing. So the record ID the verification request names is the ID the round exports, and a record imported mid-review changes neither. The coordinator chose this design on 2026-11-18, a coordinator's answer, not a ruling. [The decision](../decisions/2026-11-16-a-dismissal-record-holds-what-melian-dismiss-stored.md) and the identity guideline's verification-request row state the cost and the limit. A round's `before` list reads the same listing.

Failing test first, for gap 3. At the committed head `e944fefa6`, the key tests in `review-records.test.ts` failed 2 of 3, the one passing being the negative case; the review test in `restatement.test.ts` that supersedes another host's record failed with `expected [] to deeply equal [ Array(1) ]`; and the re-dismissal test in `review-records-export.test.ts` failed the same way. All pass on the fix. The test of a record imported after the listing passes either way, since the old code superseded nothing; mutant 18 below, which lists the store a second time in the export, is its proof.

It now pins the key #525's code gives the same sample with no dismissed root, `5116db37…`, which this branch's code also gives.
