Codex's fourth adversarial review of [pull request #436](https://github.com/melian-agent/melian/pull/436) asked how a check run under a working tree's unread policy stays apart from a run that read it. The coordinator advised on [issue #394](https://github.com/melian-agent/melian/issues/394#issuecomment-6876031714) that an unreadable input fails closed through a flag, not a random key value, as the identity guideline's sixth rule says. The advice is not a ruling.

Problem: `runIdentity` keyed a run whose working-tree `melian.yaml` failed to parse with a random UUID, so the key changed on every call and no run reused it. That held, but by an accident of the key's value: a reader could not tell from the key that reuse was refused. Solution: `checkReusable` in `packages/pipeline/src/check-request.ts` says whether a request may attach to a stored run, false when the policy is `unread`. `runIdentity` returns it beside the identity, which stays a stored shape, and `runChecks`'s one lookup refuses a run that is not reusable.

The changed code guards trust: it decides what a key matches.
