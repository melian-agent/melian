On [issue #480](https://github.com/melian-agent/melian/issues/480)'s branch, [pull request #498](https://github.com/melian-agent/melian/pull/498), core's `git` no longer reads the process table once Node has reaped git. Codex's review of `86fa8374` found that a git which had exited, while a program it started held its output open, could leave its pid to another process before the deadline, and the stop would then signal that process and its children.

It was the third instance of one class in two consecutive reviews: the stop acted on git's pid without knowing git was still there. The builder raised the class with the coordinator, which chose the rule on 2026-11-16 as a choice of approach. Node sets `child.exitCode` or `child.signalCode` in the callback that reaps git, so until both are null git's pid can be no other process's. `git` checks them at the moment of the stop and calls `stopTree` in the same turn. After git has exited, the stop signals nothing below it and reports that the programs git started may still run.

- The test came first. On `86fa8374`, "signals nothing below git once git has exited, though another process now holds its pid" drove a fake table that showed git's pid as another program with a child. The timed-out result had no `childrenLeft`, since the stop recorded and signalled the stranger's tree. It passes with the fix, with no signal at all.
- "reads the table and records the tree before it returns, with nothing awaited between" shows that `stopTree`'s first signal follows its read in the same turn.
