Codex's fourth adversarial review of [pull request #436](https://github.com/melian-agent/melian/pull/436) found that the install key read npm's record alone. The coordinator advised on [issue #394](https://github.com/melian-agent/melian/issues/394#issuecomment-6876031714) to key every manager's record, established by its documentation or a real install, to refuse reuse when a lockfile has none of its manager's records, and to fail closed on an unreadable record through a flag. The advice is not a ruling.

Problem: a pnpm or Yarn install that changed `node_modules` under the same lockfile reused the earlier tsc run, and a checkout whose record was missing read as an unchanged install. Solution: `installDigests` in `packages/pipeline/src/mutation-static.ts` now digests each manager's lockfiles and records, and says whether they identify the install. A file it cannot read, or a lockfile none of whose manager's records is present, leaves the install unidentified, and `checkReusable` refuses the run. Real installs established each record: npm 11, pnpm 9.15.0, Yarn 1.22.22 and Yarn 4.5.3 with each linker. Bun 1.2.23 wrote none, so it is an exclusion, and [the decision](../decisions/2026-11-14-request-keys-as-built.md#what-a-check-runs-key-holds-and-leaves-out) now lists every input a check run's key holds and every one it leaves out.

The fix started with failing tests. At `12520c70`, nine of the eleven new tests under "the checkout's install" in `packages/pipeline/test/checks.test.ts` failed with `expected 8 not to be 8`: the run reused task 8 after a pnpm or Yarn record changed, beside a lockfile with no record, and beside an unreadable record. npm's row and Bun's passed, as before. After the fix all eleven pass, with 302 tests across `checks.test.ts`, `check-request.test.ts`, `mutation-cache.test.ts` and `mutation-enumeration.test.ts`.

Cost: a checkout with a lockfile and none of its manager's records never reuses a check run, and reruns Biome and tsc on every review. Every check run reruns once after the upgrade, and a mutation partition starts cold once.

The changed code guards trust: it decides what a key matches. The inventory over `12520c70...20d9478f` is [2026-11-14-issue-394-records-mutants.json](2026-11-14-issue-394-records-mutants.json), with `claimsIn` naming `mutation-static.ts` and `check-request.ts`. Stryker generated 35 mutants there, and eleven hand mutants stand for the list of managers, which it does not mutate, and for the request's install field. [The runs](2026-11-14-issue-394-records-mutant-runs.json) were made at `20d9478f`, each against its named test alone after that test passed unmutated. The first run killed 43 of 45. One survivor was a plan error that named the wrong test; against Bun's test it is killed. The other, an unreadable file read as missing, survived the unreadable test because its directory record also tripped the no-record rule. `038dda89` gave npm a full record in that test, so only the unreadable file decides, and the mutant is killed. One mutant is equivalent: `lockfiles.some` as `every`, since each manager with records has one lockfile.
