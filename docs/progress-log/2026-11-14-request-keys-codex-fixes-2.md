Codex's second adversarial review of [pull request #436](https://github.com/melian-agent/melian/pull/436) found that a check run of the working tree was not keyed by its nested `melian.yaml` files. The coordinator advised option A on [issue #394](https://github.com/melian-agent/melian/issues/394): key their text. The advice is not a ruling.

Problem: the check request keyed the root configuration, and the guardrails read every `melian.yaml` from each touched path up to the root. Example: a maintainer reviews the working tree, adds a forbidden-paths rule to `pay/melian.yaml`, and reviews again; the second review reused the first run and reported nothing. Solution: core's `configLookup` gains `policyText(paths, maxBytes)`, which reads each of those files through the guardrails' own reader, under `maxConfigBytes` per file and a total the caller sets. `runChecks` passes the touched paths and `maxKeyedPolicyBytes`, 1 MiB, and keys the text for a working-tree source. A file past either bound, or one that cannot be read, keys a random value, so that run is never reused and the guardrails still report the failure. A revision source's key is unchanged.

The fix started with a failing test. At `06583b07`, "runs again when a nested melian.yaml in the working tree changes" in `packages/pipeline/test/checks.test.ts` failed with `expected 8 not to be 8`: the second run took the first run's task. After the fix it passes. New tests hold each bound at the limit and one past it: two in `packages/core/test/config.test.ts`, one per bound, and one in `checks.test.ts` that reuses a run at the per-file limit and never one byte past it. `check-request.test.ts` adds the policy field to its coverage sample and checks that two unread values key apart.

Every check reads code from a commit, so no other working-tree edit changes what a check finds. The race between keying and running is named as a known limit in [the request keys decision](../decisions/2026-11-14-request-keys-as-built.md), with the root configuration as precedent.
