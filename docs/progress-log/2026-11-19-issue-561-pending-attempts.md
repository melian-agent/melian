# Issue 561: a parity review the run ended during still counts

Codex's third adversarial review of [pull request #582](https://github.com/melian-agent/melian/pull/582), at 1dd2d5f1, found the last gap in the parity run's spend. A process that died during a review, or after it and before its attempt was saved, left only the review's SQLite store. A resume took a new store name, reviewed the arm again, and never counted the first review, so the run could pass its token stop while reporting less. It was the third consecutive review with a new way spend went uncounted, so the builder raised the class.

The coordinator ruled on 2026-11-19 to build the proposed shape. Each attempt is now saved, pending and naming its store, before its review starts, and the finished attempt replaces it. A resume first settles every pending attempt from its store, read through the pipeline's `TelemetryReader` as a failed golden's telemetry is read, and keeps it as a stopped attempt so the arm is reviewed again. A store the review never opened spent nothing and is not created. A store that cannot be read refuses the resume with exit 2 and names the file. A settled store that did not measure a model stage's usage stops the run once more, after the attempt is saved. A resume that leaves out the pending attempt's miss is refused, since it could not settle it. The coordinator also ruled that after this pass a further way spend could go uncounted goes into the run record's limits, unless it would let the parity arm spend more than the committed arm's total; the template now names one.

Four tests in `packages/evals/test/parity.test.ts` reproduce the crash by a review that never returns. One runs a real live review on fake models into a SQLite store, and the resume counts what that store recorded. Against fa829d4d, all four failed: no attempt was saved before the review, and the resumes neither refused nor stopped. All pass now. Twenty-one hand mutants of the new code ran against their named tests; twenty fail. The survivor drops the `attempt.store === undefined` operand, which is equivalent: a pending attempt always names its store, and the operand only narrows the type. Closing the store after the read has no test, since a leaked handle changes nothing the run reports.
