# Request keys hold the installed packages each producer runs

For [issue #470](https://github.com/melian-agent/melian/issues/470), each producer's key now holds `packages`, a digest of every installed package beneath what its code imports. The lens run keys the packages beneath pi-ai and Pi Durable, in place of their two versions. A run offered `list_mutants` keys the instrumenter's packages, Babel included. The checks and adjudication key the packages their own modules import as they load. The coordinator chose the approach on 2026-11-20 and [recorded it on the issue](https://github.com/melian-agent/melian/issues/470#issuecomment-7028716067); [the decision](../decisions/2026-11-20-keys-hold-installed-packages.md) holds it, and the identity guideline's rows for the lens request, the adjudication key and the check request say what each leaves out and what a miss costs.

`scripts/code-hashes.mjs` records which packages each producer imports, from Node's resolver while the producer's entry loads in a child process, and the gate fails when the record drifts. At run time `installedPackages` walks from those imports with `findPackageJSON`. A package that does not resolve, or a manifest that cannot be read, fails the key and names the package.

The failing test came first. On main at 56f7fb059, a lens request and a check request kept their keys when a package beneath pi-ai, or `yaml`, moved; on the branch both keys change.

`adjudication-key-reopen.test.ts` reopens a version 8 task that main's own code left pending, captured by `capture-pending-8.mjs` from `git archive 56f7fb059`. It fails, and the next review decides again with no model call. In the other direction, main's code at 56f7fb059 resumed a pending task this build wrote with `packages`: it failed on its `code` check, made no model call and did not crash, since the task has no input schema. So `packages` takes no task version, and [issue #562](https://github.com/melian-agent/melian/issues/562) keeps version 9.

The mutation inventory, [2026-11-20-issue-470-mutants.json](2026-11-20-issue-470-mutants.json), lists 271 mutants of 56f7fb059...b6a84e29c, 177 generated. Each ran by hand against its named test alone, after that test passed unmutated: 161 died to existing tests, 11 to new ones, and 5 are equivalent, each with its reason.

Fix commits: `31bd013b4` keeps an assignment out of an expression for Biome; `7365b2e2b` gives the legacy fixtures and adapter fakes this build's packages; `cc0d7117b` adds the tests that kill the surviving mutants.

Codex's adversarial review found one medium finding: the first rule left out every platform build, so a root platform package, or one a parent named by a range, could move with no key change. `dfe3b4c73` leaves one out only when its parent's manifest names its exact version, since the parent's version then stands for it. Three tests failed on the old rule and pass on the fix. [2026-11-20-issue-470-platform-mutants.json](2026-11-20-issue-470-platform-mutants.json) lists the fix's 21 mutants. All 18 generated ones died to their named tests, two of them new; the three string literals are ignored by configuration.

Codex's second review found the digest held which releases were installed but not which copy each package resolved, so two installs that swapped a shared dependency's releases collided. Melian's own round at 82d44b8e4 found that the platform rule depended on the walk's order: a root that a parent also pinned exactly was dropped when the parent came first. `20060e123` adds a `parent > name@version` line for each resolution and decides each platform resolution on its own; the coordinator agreed the format on 2026-11-20 and asked for the mirror test, that the same resolutions installed in another order give one digest. The swap test and the four order tests failed before the fix and pass after it. The round's second finding, that no review test moved the instrumenter's packages alone, is closed by `e70dc6031`, whose test fails with a constant in place of `adapter.installedPackages()`. [2026-11-20-issue-470-resolution-mutants.json](2026-11-20-issue-470-resolution-mutants.json) lists the fix's six mutants: all four generated ones died to their named tests, and the configuration ignores two string literals.

Codex's third review found that the resolution lines still collided: two copies of one release of `tool`, at two places, could swap which `sdk` each resolved and give the same lines. The coordinator chose on 2026-11-20 to key the layout instead, since a copy's place fixes what Node resolves from it. `b1cbdf6d5` keys each reached copy as `place name@version`, its real directory relative to the install root, and drops the resolution lines. The test of that swap failed on `c6acaadb5` and passes on the fix; the two earlier collisions keep their named tests. New tests show one layout at two absolute paths giving one digest, a linked package keyed at its real place with its dependencies resolved from there, and a copy outside the install root failing. One lockfile installed with `npm ci` by npm 11.19.0 and by npm 10.9.2, in two directories, gave one digest over 42 copies. [2026-11-20-issue-470-layout-mutants.json](2026-11-20-issue-470-layout-mutants.json) lists the fix's mutants: all 11 generated ones died to their named tests, and the configuration ignores the string literals.

Melian's own round at `c6acaadb5` found that the digest holds no Melian package. Each workspace package named the others as `"*"`, so a published pipeline could run beside a newer core under the same recorded code version. The coordinator chose on 2026-11-20 to pin them, under the AGENTS.md rule for direct dependencies. `c6007e0bc` names each workspace package at the others' exact version, `0.0.0`, and makes `scripts/check-pinned-deps.mjs` fail any workspace dependency that is not that package's own version. The script had let `"*"` through for a workspace name on purpose. Its three new rejection cases failed on the old script and pass on the new, and a fourth test holds this repository's manifests to the rule. The lockfile diff moves only the workspace packages' own `dependencies` entries. [2026-11-20-issue-470-pin-mutants.json](2026-11-20-issue-470-pin-mutants.json) lists the commit's mutants: all 12 generated ones died to their named tests. The same round's P2 is closed by `c96e617fa`: a dismissal after an install change must carry the dismissing install's packages, and the round's mutant, `previous.packages ?? packagesVersion("adjudication")`, fails it with `adjudicationFailed`. `2c9bfabe9` takes TSDoc off the package-internal module, for two P3s, and `c6007e0bc` splits the identity row's two new long sentences, for the third. `097638b60` moves a package's release in place in the moved-package fixture: the fixture had put the moved manifest in a temporary directory, which the layout key now refuses as outside the install, and which would have moved its place as well as its release.

Codex's fourth review found that the first root alone set the install root. npm can nest one root beneath a workspace package and hoist the next to the checkout, which put the second outside the install. `1e918ae0a` took the install root from every root; its test failed on `c4d4b9b4d` and passes on the fix. A root npm nests, with one of its own dependencies hoisted, still failed the same way, so `a93396f9f` takes the install root from every copy the walk reaches, and `51def5721` adds a nested sibling so that only every folder, not any one, decides it. That test failed on `1e918ae0a` and passes on `a93396f9f`. Of the 27 mutants the two commits generate, 25 fail a named test by hand and 2 are equivalent; [the inventory](2026-11-20-issue-470-root-mutants.json) records each.
