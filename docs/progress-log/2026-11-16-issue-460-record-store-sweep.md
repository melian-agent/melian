# The record store sweeps what a killed call left

[Issue #460](https://github.com/melian-agent/melian/issues/460) closes the last open row of the git record store's resource table: a temporary index, a half-made repository or a fetch ref that a killed call, or a call cut off at its deadline, left behind. Each is now named after its owner, a hash of the host's name and the pid, in `packages/state-git/src/owner.ts`. Opening the store sweeps the state directory, in `RecordRepository.sweep`, and removes a leftover only once core's `ProcessTable`, which [issue #480](https://github.com/melian-agent/melian/issues/480) moved into core, lists no process with its pid on this host. It keeps what it cannot prove gone, a reused pid's leftover included, and `melian doctor`'s `records` line names it. [The sweep decision](../decisions/2026-11-16-record-store-sweeps-what-a-killed-call-left.md) records the method, the coordinator's choice of approach on 2026-11-16, and the host hash's limit.

`packages/state-git/test/sweep.test.ts` holds 17 tests, written first. Before the code, 16 failed for the missing sweep or the names' missing owner. The seventeenth passed then, as it must: it asserts that a name falls back to a plain UUID when this process is not in the table, which every name was before. A live owner is a real child process the test spawns, records by pid and stops by that pid; its leftovers survive a second handle's sweep. A fake table plants a leftover between the listing and the table read, and the leftover is kept. Five tests in `packages/cli/test/doctor-record-store.test.ts` assert the whole `records` line for a kept leftover, seven kept and a control character, an unreadable table, a failed removal, and a sweep that removed all it found; the first four failed before the change because the line said nothing of the sweep.

The first form compared the start time `ps` printed when a call named its leftover with the one it printed at sweep time. Codex's adversarial review found that `ps` prints that time in the caller's time zone and locale, so a sweep run under another `TZ` read a live call as gone and removed its index. A test written first, "keeps what a live process holds when the sweep reads the table under another time zone", names a leftover under `TZ=UTC` and sweeps under `Australia/Sydney`. On the start-time code it failed, with every leftover removed; on the fix it passes. The coordinator chose on 2026-11-16 to drop the start time and remove a leftover only when its pid is absent. The tests now also show a leftover whose pid another process holds kept and named, one whose pid the table does not list removed, and a plain UUID name when the table lists this pid with another parent, or this parent with another pid. `packages/state-git` passes 205 tests.

Codex's second review found two more gaps, each fixed test-first. Doctor dropped the sweep's notes when the branch read failed after the store opened; a test with an unreachable origin and a kept leftover failed with no sweep note on the line, and passes now. The sweep ignored the open's deadline while it removed leftovers. The coordinator chose on 2026-11-16 to stop removing once no time is left and count the rest as unswept. Two tests on a fake clock, one at the bound with 1 ms left and one past it with none, failed with every leftover removed; they pass now, and the second shows the next open finishing the sweep. Two doctor tests show the count. `packages/state-git` passes 207 tests, and `doctor-record-store.test.ts` 25.

The hand run of the sweep's mutants at 2742a1a9 found `owner?.name()` in `RecordRepository.#create` surviving as `owner.name()`: no test built a repository when the table does not list this process. A test in `packages/state-git/test/create.test.ts` now does, and asserts the half-made repository is named by a UUID alone. With the mutant it failed with `Cannot read properties of undefined (reading 'name')`; unmutated it passes.

The run then found the `.sort()` on the state directory's listing surviving: the filesystem here listed the test's two leftovers in name order anyway. A test now reverses `readdir`'s listing and asserts the sweep's whole `removed` list in name order. With either listing's sort removed it failed, all eight names present in another order; with both it passes.

Next, `if (found === undefined) continue;` survived as `if (false)` in both listings: only a test of many handles opening at once could reach it, and only when one call removed an entry the other had listed. A test now adds a listed name that does not exist, and asserts the sweep passes over it. With either guard forced false it failed with `Cannot read properties of undefined`; unmutated it passes.

Then `force: true` on each leftover's removal survived as `false`: no test had a leftover vanish between the sweep's listing and its removal, as another call's sweep can make it. A test now removes the planted leftovers when the sweep reads the table, which it does after the listing, and asserts they count as removed, not failed. With either `force` set false it failed, naming them under `failed`; unmutated it passes.

The `$` that anchors `.lock` to the end of an index's name survived: no name held `.lock` anywhere else. The unparsed-names test now holds `<host>-<pid>-.lock<uuid>`, which parses as an owner once a stray `.lock` is cut from its middle. With the anchor dropped the sweep removed it and the test failed; anchored it is kept and named.

The `.sort()` on the fetch refs survived too, and it had to: `git for-each-ref` already sorts by refname, so the sort re-derived what git answers. The listing now asks git with `--sort=refname` and sorts nothing itself.

Codex's review at ab3c3c98, after `main` merged in, found two more gaps. The coordinator chose on 2026-11-16 to fix both, as choices of approach that only narrow what the sweep does. First, a sweep that could not read the process table named none of the leftovers it found. The unreadable-table test now expects every one of them under `kept`; on the old code it failed with `kept` empty, and passes now. The doctor test for that case now plants a kept leftover and asserts both notes on one line. Second, the fetch-ref listing took the open's deadline, so an open whose time ran out during the sweep failed with "ran past its deadline". Three tests in "the sweep's listing" show the listing not started at the bound, started with 1 ms left, and a listing that git fails. The two fixes' mutants are in `2026-11-16-issue-460-fix-mutants.json`, enumerated over `ab3c3c98...16d1ebb5` with `--claims-in` naming `repository.ts`, the one file of the three the fixes change. All 30 generated mutants there are claimed as killed, each by one named test in `sweep.test.ts`, run alone at 16d1ebb5 after it passed unmutated. The first run applied every mutant one column early and voided all 30 results: 19 left a file that failed to load, and 11 failed for broken text. The rerun checked that each mutant replaced exactly the text it names.

Codex's review at 9f782aa9 found a third instance of one class: either of the sweep's two `readdir` listings could throw out of the open. Two reviews in a row had each found one, so the coordinator chose on 2026-11-16 to close the class with one rule: no failure inside the sweep fails the store's open. `RecordRepository.sweep` now catches any failure of the whole listing, removes nothing and reports `unlisted`; the ref listing's own catch went. Two tests make each `readdir` reject. Both failed first with the open throwing `EACCES`, and both pass now. The test of a failing ref listing no longer expects an `unswept` count, since a failed listing now drops what it had listed. The removal half already met the rule: a removal that throws is named under `failed` and the open succeeds, as "names a stale leftover it could not remove, and still opens" shows. The open still fails on what is not housekeeping: `records.git` unreadable, not a directory or not creatable, a configuration the check refuses, and a shallow history.
