# Core's git stops once its standard error passes 4 MiB

[Issue #469](https://github.com/melian-agent/melian/issues/469): core's `git` runner capped standard output with `maxBytes` but kept standard error whole. A fetch or a push carries there whatever the remote or a credential helper sends, so a remote that wrote without end could fill memory inside any deadline. [Pull request #472](https://github.com/melian-agent/melian/pull/472) keeps at most `stderrLimit`, 4 MiB. One byte past it, the runner kills git by the pid it spawned, closes its own end of the stream, and rejects with `ChangesetError` `gitOutputTooLarge`, naming the subcommand and the limit. It never resolves with a cut message, because callers match git's message to recognise a missing remote ref or a held lock. A survey of the whole test suite, 111,982 git calls, found none that wrote more than 250 bytes to standard error.

The one-past test failed on the unbounded code: the runner resolved, and no error came back. The two tests that write without end were not run against that code, since there they exhaust the test process's memory. `melian mutants list` sets `git.ts` aside because it sends signals, so the mutants came from `scripts/instrument-mutants.mjs`. Each of the 21 mutants on changed lines ran against its one named test. Twenty were killed. The survivor removed `clearTimeout` from `stop()`, a call that changed nothing, since every ending reaches `finish`, which clears the timer. `d3c16c12` deletes that call, and the rerun of `stop()`'s five mutants killed all of them.

The amendment that retires the decision row "Not bounded: core's `git` keeps a command's stderr whole" follows in this pull request once [pull request #433](https://github.com/melian-agent/melian/pull/433), which adds that decision, lands. So does the test that the record store's checks for an absent branch and for lock contention cannot misread a cut stream.
