## Maintainer decisions

Five decisions came from the review. The first two are recorded in the dismissal decision, the third in the dismissal publication decision, the fifth in the affected finding trigger decision, and all five in `design.md`.

- **Dismissing a site dismisses it whole, visibly.** The merge by site stays what a maintainer dismisses, because it is what they see, but nothing is silenced unseen: `review` and `findings` list each merged report, `dismiss` names every report it takes, and `--only` dismisses one alone. From A2 and C2.
- **A dismissed report is never a path to a live finding.** An ID names the finding with that exact ID first, and members come only from a live speaker's merged reports. From C1.
- **A dismissal is published by its version.** Replies are keyed by finding, thread, and dismissal version, a hash of reason, dismisser, and time. Dismissals stay out of the verdict's fingerprint, so a round may be replies alone with the status unchanged. From A4 and C4.
- **The ledger never carries the dismisser.** The hidden stamp and the run details leave out `dismissal.by`, as the replies do. From C11.
- **An affected finding reopens only when the code that proved it changes.** Its trigger carries a proof, every proving hunk as a file and a hash, and the findings document keeps the union across sightings since the finding last reopened. A dismissed affected finding reopens only when a hunk in that set no longer exists unchanged in its file at the new revision, so neither the order nor the number of locations a model cites reopens it. From A1, D6, and E7.
