### For the maintainer: mode 600 for a command source

2932128 went beyond its brief. The brief asked for one open with `O_NOFOLLOW`, checks on the handle, a refused shared directory, and `chown` advice for a file another user owns. The commit also requires mode 600 for any secrets file that holds a command, the user-level file as well as the per-clone one. Before, the rule was a file the user owns that neither group nor others can write.

The reason is a path B1 named and d72b387 does not close. #61's `.gitignore` lists `melian.secrets.yaml`, so a head's file that a patch writes there, through `gh pr diff N | git apply`, is untracked and ignored, and passes both of d72b387's checks. Only its mode tells it apart: git writes it as 644 under the default umask. Mode 600 refuses it.

The rule held only under the default umask. A maintainer whose umask is 077 gets a patched file of mode 600, and the `git apply` path was open again for them. Codex's second pass found the same (D1).

The maintainer took the flag and closed the path another way. eb1d324 honours a command source only in the user-level secrets file, never per clone: `melian.secrets.yaml` holds literal and environment sources, and the loader refuses a command there, naming the user-level file. The user-level file keeps the owner, mode 600, and directory checks. The ignore check, which served only commands, goes; the refusal of a tracked per-clone file stays. The umask case is closed, because no file in the working tree can hold a command at all.
