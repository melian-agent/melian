## How this record was made

The rounds ran from a worktree on the branch, with range `origin/main...HEAD`, so the store holds all seven as revisions of one branch changeset. After the merge the range cannot be addressed. Each of these refused with the same message, `melian: Melian has no review of ce98228c30d0; run melian review <range>`:

- `melian compare origin/main...design-lens-authority-rule`
- `melian compare origin/main...ce98228c`
- `melian findings origin/main...design-lens-authority-rule`

`origin/main` is now the merge commit, so the merge base of any range from it collapses to the head. A changeset's identity hashes the full names of its refs. The record for [pull request #111](https://github.com/melian-agent/melian/pull/111) describes the same refusal. Its method was a scratch clone with `origin/main` reset to the pre-merge commit and a copy of the store. Here that would reach only the latest revision of the branch changeset, which is round seven alone. No command compares an earlier revision of a branch changeset; the readiness questions list that gap. This record is therefore written by hand from the saved sources, and `melian compare adjudicate` was not run.

Every row traces to a line in one of these files: the saved round outputs `melian-review-114-r1.txt` to `-r7.txt` and `round-114-r1.out` to `-r7.out` (no `round-114-r5.out` exists), `codex-adversarial-114.md`, `record-114.md`, the coordinator's notes, the pull request's progress-log entry, and its live run record `packages/evals/runs/2026-10-13-live-goldens-authority-rule.md`. The adjudications and miss reasons are the record author's reading, for the maintainer to confirm.

The comparison record has no fix-commit column. The fix commits are in [the progress-log entry for this record](../../docs/progress-log/2026-10-14-pr-118-comparison-114.md).

## L. The live golden run

The coordinator's live run of the 27 `design` and `correctness` goldens is a reviewer of an unusual kind. It is not a review round and not a reviewer of the diff, and it ran after the lens text was written. It found a real defect that no review round and no external reviewer had.

At `a2793b71`, with Sol as finder and Terra as verifier, `design-reimplements-an-authority-clean` reported one finding in all three passes and in a fourth solo run. A fifth run with `MELIAN_EVAL_SHOW=1` showed it: `reimplements-an-authority`, P2, `scripts/node-range.mjs` lines 6 to 8, confirmed by the verifier. The golden was meant to hold a supported stated gap and a hand-written Node range check that refuses what it cannot judge. The check read `>=022` as 22 and allowed Node `v22.0.0`. `semver` refuses the range as invalid: in npm's bundled 7.8.1, `satisfies("v22.0.0", ">=022")` is false.

Who found it: Melian's `design` lens under the new rule, confirmed by the verifier, in a live eval run and not a review round. Who did not: Codex's adversarial review attacked this very golden and found a different flaw (A4, the prerelease case). The Sonnet review traced the same fixture and judged it "the fail-closed shape the rule demands". Seven Melian rounds ran the branch's `design` lens at `deep` over a diff that held the fixture and reported nothing on it. The reading of the lens text is that the cause is the rule's own edge: `612ba42f` states that tests and fixtures are out of scope for the rule, so a review round would not look. That is an inference from the text, not a finding of any lens run. After the fix, the clean golden was clean in five passes of five, and in three of three at `ace07815`. The lens text did not change. The run record also holds the verifier eval harness fault the same run exposed: unjudged verdicts were provider errors made fatal by a harness with retries off (`8eeed1b1`).

The lesson is a goldens one: a fixture meant to be clean under this rule has to be checked against the dependency itself. The run record says the same.
