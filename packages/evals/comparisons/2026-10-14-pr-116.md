## What happened to the re-scope route

The verifier could propose that a finding was pre-existing and move it out of the blocking set. Melian accepted the proposal only if a set of checks held: no caller added under another name, no guard deleted in a caller, the base lines the verifier cited were the base twin of the failing head lines. Each check matched names and lines as text.

Every review found a new way past that text matching:

| Review | Head | What got past the name matching |
|---|---|---|
| A, Codex | `ef617de0` | A guard deleted from an unchanged caller; a new caller through an alias the base already held |
| R1 | `5c0ce686` | A named `export default function`; a file git reads as binary |
| R2 | `56879fb8` | A name spelled through a Unicode escape; an alias past the 300-character cut of a search line |
| R3 | `6979db2a` | A comment between `export` and `default`; a base line that was never tied to the head line's origin |
| R4 | `9f40b037` | An alias on the same line as the failing function's declaration; a replay on a machine whose compiler cannot start |

Each fix added more text matching, and the next review found the next gap. Round four was the stop point in the lane rules ("after four rounds"), and the pattern was plain. The author recorded 262 mutations killed by then. The coordinator's note of 2026-10-13 23:40 says that lowering and surfacing "drew few findings" in the same rounds, and that the re-scope route drew all the blocks.

The maintainer ruled: "Ship lowering, hold re-scope." The author removed the route whole: about 3,600 lines and 174 files, against the branch's 139 files and +3,573 lines at the merge. A new decision, `2026-10-13-re-scope-held-for-the-compiler`, supersedes the earlier verifier decision in part with the surviving clauses restated. A new plan step, step 20, "The verifier re-scopes through the compiler's call graph", holds the work until a call graph can answer what text could not. The coordinator also ruled that a pre-existing member counts toward the verdict exactly as an advisory finding does, which reverted a status change the author had made in round three.

The pattern is hand-matching text for what the compiler knows. Whether a name still reaches a function, whether an export is a default, whether a line is a declaration: a TypeScript program answers these exactly, and each regex or line scan answered a case short of that. Codex found it twice and four Melian rounds found it again, every time in a new spelling, and none of them found the end of it.

For the adjudications below: a finding on the route is valid for the head it was raised on, and is marked "resolved by removal". Nobody fixed the defect; the code is gone. That is not the same as a miss: Codex's first review ran on a head no Melian round saw.

### C1: which lens owns a defect that only a live run or a prompt read reveals

C1 is visible in two places: the instruction asks for "the severity one step down", and the claim builder passes no severity. Nothing in the diff shows the two meeting, because the instruction is a string and the claim is an object built elsewhere. The review of record found it by capturing the verifier's first request on the fake model, but a reader holding both texts would see it without running anything. So it is not `needs-execution`.

Which lens could see it:

- `contracts` queries callers of changed symbols. An instruction string has no caller, and `memberClaimSchema` was not changed.
- `design` asks whether the change contradicts a decision. The decision said the verifier lowers one step; it did not say the verifier is shown the severity. The design lens has no rule for an instruction that depends on an input.
- `tests` flags untested behaviour on changed lines. Its remit is lines with no test; here the tests existed and were scripted, which cannot see what a model was shown.
- `correctness` reads code paths, not prompt text.

Nothing owns it. The class is "an instruction names an input the code that builds the request never supplies", and it is wider than this step: any verifier or lens prompt change can have it. It is `no-owner`. If a second pull request shows the same shape, it is a candidate rule for `contracts` (a prompt and its request builder are a contract between two parts of the diff), or a check that renders the verifier's first request on the fake model and asserts every input the instruction names is present.

What closed it in this pull request: the fix `30ce0de9` puts the lens's severity on the trusted label line, and the fix pass added a test and a mutation for it (the author's mutation list for round eleven includes "label line carries no severity" and "every claim labelled with the first claim's severity", both killed). The remaining gap, which the review of record names, is that the review of record called no live verifier, so no one has seen a model act on the new label line. That is for a live verifier run, not the lens corpus.
