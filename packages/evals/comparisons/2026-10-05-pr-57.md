## Maintainer decisions

- **A hand-off past its cap is left out, not cut.** A cut list would silently hand some files and not others; leaving the hand-off out keeps ownership exact and costs only duplicate reports. The lens's check record names the neighbour. From A1 and C6.
- **A deleted guard stays with `correctness`, as well as `removed-behaviour`.** A deleted rethrow or error branch is `removed-behaviour`'s alone. The fix had one measurement to prove itself: had it failed, the wording would have been reverted and the contradiction recorded in the plan, with no second tuning. From C2.
- **A superseded task's write is `durability`'s, even when it races a live caller.** From C3.
- **`durability` is not tuned in #57 and ships below the bar.** Run 9 measures it at a worst precision of 0.56 over seven goldens. The plan's step 13 unblocks a tuning round on the boundary wording that remains. From A2 and C1.
- **The findings-cap hazard is owed, not fixed.** From C10.

## Differences

Codex and the Opus review converged on the two defects that mattered: the unbounded file list (A1, C6) and the listed form that no measurement had exercised (A2, C1). Each reached them its own way. Codex read the rendering, found no bound between the 200 KB change prompt and the instructions, and read run 8's method closely enough to see that every request took the short form. The Opus review counted the renderings itself. Neither finding needed the other reviewer, and one commit pair closed each.

Melian's first round saw only the two policy notices and the long sentence. The listed form's evidence lived in goldens and run records. The root `melian.yaml` keeps every lens off `packages/evals/goldens/**`, and though the run records are in every built-in lens's paths, no lens's rules ask whether a measurement supports the claim built on it; `conventions` read the plan as prose and found a sentence. The unbounded list was different: it sat in `lens.ts` and `review.ts`, which all seven lenses reviewed. No lens's rules claim it. `trust-boundary`'s oversized-input rule covers input that makes a check pass or read clean, and a prompt too large for its context fails the lens and leaves the review not reviewed. What an author gains is cost, and no lens counts cost.

The Opus review's byte comparison of 666 renderings is what freed it to look elsewhere. It turned "a neighbour over every file renders as before" from a claim into a measurement, so the review spent its reading on what the comparison could not settle. Its reading of the lens history found C2. Run 8 had missed `correctness-deleted-guard`'s guard in every pass, with the overrides and without, and recorded it as a `correctness` miss for its next tuning round. The Opus review traced the miss to the hand-off line, the line to 917be2e, and the commit to #42's fix for E3, Melian's own finding in [#42's fourth round](2026-10-05-pr-42.md#melian-review-round-four). That fix changed `correctness`'s prompt after run 6 had measured it, and nothing re-measured it. A hand-off is part of the handing lens's prompt. Changing one is a prompt change for that lens's goldens, and #42 made it without a live run.

Leaving out C10, which predates #57, Melian's recall is seven in eighteen and its precision seven in seven. Against the twelve findings already in the branch at cb8d4d3, Melian found one, B3, a long sentence; Codex found three, A1 restating C6 and A2 covering C1 and C5; and the Opus review found eleven, all but B3. On [#51](2026-10-05-pr-51.md) its third round found that every fingerprint test compared the code under test with itself. A fix pass writes code no external reviewer reads, and Melian's later rounds are the only review it gets.

### For the maintainer: declaring defects after a live pass

After run 9's first passes, f12a9b1 declared two real defects the new goldens held but did not expect. `durability-partial-handoff`'s deleted `Math.max(0, ...)` bound became `removed-behaviour`'s `dropped-guard` beside `correctness`'s `wrong-result`. `durability-injection`'s instruction in a file name became an injection attempt expected from `lens.durability`. Run 9 scores the goldens as committed and records the score as first written: worst precision 0.50 and recall 1.00 in every pass, against 0.56 and 0.90 as committed. The change cut both ways. Declaring the bound turned two lenses' reports into matches; declaring the file name with a `source` turned `durability`'s pass-3 miss into a recall loss and six other lenses' reports of it into extras.

The evals guideline pulls two ways here. [Adding a golden](../../../docs/guidelines/evals.md#adding-a-golden) says "Declare every real defect, because a lens that finds an undeclared one is right and would score as noise". It also says to record a live miss "as a learning about the lens, not by loosening the golden", and that a lens's goldens "are never loosened to lift it over". A defect the author first saw in a live pass's findings falls between the two. The author's call, a separate commit with the first score kept beside the new one, is defensible, but the guideline should rule on it. It could allow the change on those terms, require a fresh set of passes against the amended golden, or forbid amending a golden in the pull request whose run first saw it.

One finding overlaps another: C6 is A1. A2 spans C1 and C5. B1–B2, D1–D3, and E1–E3 are one set of notices, which D2 widened to `durability`'s lens. No reviewer raised a finding the maintainer judged noise.
