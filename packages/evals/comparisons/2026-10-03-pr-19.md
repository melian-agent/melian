# Comparison review: pull request #19

Pull request: [melian-agent/melian#19](https://github.com/melian-agent/melian/pull/19), step 8, publishing from the CLI.

Reviewers: Codex adversarial review, then an Opus review of record. Each group was applied in turn, in that order.

## Codex adversarial review

Three findings, all adjudicated valid and high, all on a trust boundary of publication. Every one was reproduced with a failing test before it was fixed.

| # | Reviewer | File | Summary | Adjudication | Golden |
|---|---|---|---|---|---|
| A1 | Codex | `packages/github/src/provider.ts` | Marker recovery trusted a marker by its author, learnt from `/user`. An installation token cannot read `/user`, so a rerun after a crash between GitHub accepting a review and the task recording it read no markers and posted the review a second time | Valid, high; markers are signed with HMAC-SHA256 under a 32-byte secret each changeset's storage generates once, and a marker counts only when its signature verifies. The author is a filter when known, never the proof. The crash test runs with `/user` refusing | Yes |
| A2 | Codex | `packages/cli/src/target.ts`, `packages/pipeline/src/publish.ts` | A range review of `refs/melian/pull/N/base...refs/melian/pull/N/head` hashed to the pull request's changeset ID, so with the head checked out it wrote a verdict decided under working-tree policy into the pull request's storage, and `publish` posted it | Valid, high; pull requests have their own changeset identity, each verdict records its provenance, and `publish` refuses anything but a pull-request review of the same repository and number, at the provider's head, under `revision:` policy of the provider's base | Yes |
| A3 | Codex | `packages/pipeline/src/publish.ts` | `publishReview` resumed every publish task a crash left, so a publish interrupted before its post, followed by a retarget that kept the head, posted the review of the old diff | Valid, high; each task records its target and ends superseded without writing when the validated target differs, a pending round for another revision is dropped, and the provider is asked for the target again before every post | Yes |

Two choices went beyond the brief:

- A1 signs `<revision>|<kind>=<id>`, not `<revision>|<id>`, and gives a reply the kind `resolved`. Anyone can read a posted marker and copy it, so a signature over the ID alone would let a thread's marker, pasted into a reply, read as a resolution. The first post carrying a marker wins, since a copy can only follow Melian's own.
- A2 checks the base by merge base, as before, rather than requiring the base branch's tip to be the one the review fetched. A tip check would refuse every publish once anything merged into the base branch, though the pull request's diff had not changed. The provenance records the tip, and the policy source must be `revision:` of it.
