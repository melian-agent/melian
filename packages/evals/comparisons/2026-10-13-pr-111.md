## How this record was made

The four Melian rounds ran the branch as `origin/main...HEAD`, so the store holds them as four revisions of one changeset. After the merge, `origin/main` is the merge commit and the merge base of `origin/main...HEAD` collapses to the head, so `melian findings` and `melian compare` in the main checkout report `Melian has no review of 72ec6d41389d` for every spelling tried (`origin/main...HEAD`, `origin/main...design-research-decisions`, `22a821b2...72ec6d41`, and each against the earlier heads). A changeset's identity is built from the refs' full names, so a range with another base names another changeset.

The comparison was made in a scratch clone whose `refs/remotes/origin/main` was reset to `22a821b2` and whose branch `design-research-decisions` was moved to each reviewed head in turn, with a copy of the changeset's store file. `melian compare origin/main...HEAD` ran at `a67c54be` with the Codex and review-of-record-one findings as `--from file:` sources, at `0154ee8f` and `72ec6d41` with none, and at `65aca1f2` with review of record two. The files hold each source finding's text from the saved reviews; the agent wrote them, as the importer expects of a Claude review. Codex's output is prose in this pull request, not its JSON envelope, so it also went in as a file. Every finding was adjudicated with `melian compare adjudicate`.

The export groups by import time and shows the same Melian finding as pending in each earlier round, because adjudication records against the newest round holding an ID. It also cannot carry fix commits or the argument below. This record is therefore written by hand from the stored adjudications, and the fix column comes from the progress-log entries for the pull request.

## Why the rounds were clean

This is a reading of the sources, not a finding of any lens run.

The design lens names this class of work. Its text says a head decision that conflicts with an active base decision without a `Supersedes:` line is a `criterion-selection-bias` finding, and that for a new decision governing no behaviour an active decision covers it should judge whether the decision's own assumption holds. It has read tools and `paths: ["**"]`. It ran at `deep` four times and reported nothing. The sources hold no lens transcripts, so they do not say whether it read the new decisions.

The 19 findings fall into three kinds, and a lens can be expected to catch them unequally:

- A decision that contradicts an active one, or fits a rule the lens already has. A1 (the verifier's label replaces cause by location), A2 (one slot, overwritten by call order) and C3 (no `Supersedes:`) are these. The lens owes a golden for each, and the three are listed above.
- A decision that claims something about the code that the code does not do. B1, B4, B6 and B7 are these. A lens with read tools can check them, but its rules name no such shape, so the misses split between `design` (B1, B4, B7) and `no-owner` (B6, which names a check that exists only on an unmerged branch).
- A rule that is ambiguous or open to a worked counterexample. A3, A4, B3, B5, C1, C2, C4, C5 and C6 are these. The reviewers found them by working the specified algorithm by hand against examples, and the second review lists thirteen hand-worked cases. A lens reads and searches; it does not execute a specification. These are the findings least likely to come from a lens round.

Both Sonnet reviews had a brief with numbered questions (what contradicts, what is stored today, whether a new decision needs a `Supersedes:` line). Melian's lenses had none. The `design` lens is meant to ask those questions unprompted, and a docs-only pull request that adds decisions is the case its text describes, so the misses are `owned-missed`. Whether the lens can do it unprompted is a live-run question, not one this record answers.
